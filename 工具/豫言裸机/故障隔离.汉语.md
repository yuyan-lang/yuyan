# 用户任务故障后继续运行

此阶段把用户数据访问异常及生成代码的运行时陷阱接入任务退出路径。故障只终止当前任务；若另一个任务仍可运行，内核保存故障任务帧并调度另一个任务。不会返回出错指令，也不会把它修补成成功结果。

## 状态和接口

故障任务状态为 14：曾运行（2）、已完成（4）、故障（8），没有可运行位（1）。正常完成仍为 6。平台导入 `任务退出码：(i32) → i32` 返回已结束任务的退出码；无效编号或尚未结束返回 -1。当前正常完成为 0，用户数据访问异常为 139，生成代码陷阱为 132。这些数值是本项目的内部约定，不声明 POSIX 信号兼容。

两端分别在内核私有区域保存两个退出码：ARM64 为 `0x400b0050`、`0x400b0054`，AMD64 为 `0x103358`、`0x10335c`。退出信息暂时保留，尚未实现等待后回收任务槽。

ARM64 同步异常入口已经核对来源为零级用户态。数据访问异常进入故障退出；其他非系统调用的用户同步异常进入通用陷阱退出。AMD64 缺页入口先检查用户代码段及错误码的用户访问位，去除硬件错误码并保存统一整数帧，再进入故障退出。两端生成代码使用的服务号 7 进入通用陷阱退出。内核自身故障不走可恢复用户任务路径。

双任务模式下，故障后仍有可运行任务才切换；若没有可运行任务，当前自动验收客体以失败结束。单任务模式保留既有故障及隔离验证协议。这是当前测试启动器的结束策略，后续通用操作系统仍需空闲任务和完整退出管理。

## 验收要求

- 分别让第一任务、第二任务发生真实用户态非法访问。
- 分别让第一任务、第二任务执行标准 Wasm 的不可达陷阱。
- 故障任务不执行正常核验，幸存任务必须查到准确的故障状态和退出码。
- 幸存任务随后再执行百万次求和、检查自己的全局值，并成功调用用户态查询服务；它必须独立完成四次核验。
- 故意写错退出码、故意把故障状态当作正常完成、放开故障任务的受测内核页权限，都必须拒绝。
- 原有双任务成功用例拒绝带故障位的同伴，防止新增故障处理掩盖正常用例的失败。

缺页负载的模块主体为空，镜像生成器在其返回后插入已有的原生非法访问探针；这不是私有 Wasm 指令。陷阱负载直接包含标准不可达指令。原始模块随镜像一同保存。

实测证据见本篇后续记录及验证记录，不以用例设计代替实际执行结果。

## 边界

尚未实现完整处理器异常覆盖、故障地址与指令详细报告、动态进程创建／终止、阻塞等待、页和任务槽回收。退出码查询目前是非阻塞接口，测试中的等待是有界轮询。AMD64 的其他处理器异常仍没有此恢复路径。当前代码、栈和线性内存仍使用静态大页，未具备写入／执行互斥。

这些限制不改变默认用户态豫言 Shell、用户态 Wasm 执行器、IPC、持久化文件系统和完整 WasmGC 的后续目标。

## 实测记录

2026-09-22，ARM64、AMD64 共 138 项 QEMU 检查全部通过，其中新增故障退出正反例 14 项。正常用例退出码分别为 0、33，负对照分别为 1、35。全部类型检查通过。

构建时发现旧 `yy` 的增量产物仍运行旧 124 项用例；该次结果已排除。本轮复制已经过自举验证的 `yy3_bs`，以新缓存身份冷构建，确认 138 项实际执行。此处是构建绕行办法，没有修复旧编译器的缓存缺陷。

```sh
cp yy3_bs yy故障验证编译器
./yy故障验证编译器 工具/豫言裸机/验证。豫 -o yy裸机验证 -j 1
./yy裸机验证 --外部模块 yy外部C模块.wasm yy外部C错误.wasm
```

不提供外部模块时运行 134 项。受测镜像和串口日志位于 `/tmp/yy裸机验证.l9oTNS`；编译器及镜像哈希见 `验证记录.json` 的“故障任务退出扩展验证”。后续改动宜继续使用新编译器，并核对实际执行用例数，避免把旧产物结果用于新源码。

后续已实现阻塞等待及正常／故障退出唤醒，见[阻塞等待](阻塞等待.汉语.md)。本篇轮询描述及 138 项结果属于故障隔离阶段；动态进程管理与资源回收仍未完成。

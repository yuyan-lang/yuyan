# 设备持有者退出清理

2026-09-22：ARM64、AMD64 共 326 项 QEMU 验收通过，含十二项新退出用例。类型检查和十二个配套 Wasm 产物的格式验证通过；四个默认镜像已重新生成并与验收产物逐字节核对。

设备授权现在跟随持有任务的生存期。当前唯一设备属于初始用户任务；该任务自然返回、显式退出或发生用户陷阱/缺页时，都会经过共同退出路径执行内核清理。其他任务结束不会撤销初始任务仍在使用的设备。

## 清理顺序

1. 清除内核设备授权标志，后续寄存器访问立即拒绝。
2. 关闭 PCI 总线主控，保留复位所需的寄存器窗口，并读回核对。
3. 写入 Virtio 复位状态，等待设备状态归零。
4. 关闭寄存器窗口解码并读回核对。
5. 清除设备上下文入口及整页叶表，发布必要的 CPU 缓存更新。
6. 执行 IOMMU 配置/上下文和翻译缓存失效，等待完成并检查结果。
7. 核对相关入口已清零，输出清理完成标记，再继续唤醒与调度。

退出码和任务状态在清理之前保存；清理结束后重新读取调度所需的当前任务索引和元数据基址。清理不能靠用户程序自觉调用停用函数。正常 Shell 的主动停用仍保留，内核退出清理负责最终收回授权。

ARM64 清除 SMMUv3 流表入口与最低级页表，执行配置失效、全局翻译失效和同步。当前只有一次初始授权，命令队列必须停在已完成的前三条命令，再提交退出所需的三条命令；不覆盖未完成命令。

AMD64 清除 VT-d 根入口、设备上下文及最低级页表，完成全局上下文失效后，再执行带读写排空请求的全局 IOTLB 失效。能力、完成状态和实际失效范围均需符合要求。

所有等待均有上限。若无法确认复位或失效完成，内核进入失败路径，不继续调度或宣称资源已经可以复用。

## 验收

新用例故意省略用户态停用：

- 设备持有者初始化队列后自然返回。
- 持有者显式以四十二退出，子任务确认退出码后继续运行。
- 持有者陷阱退出，子任务确认一百三十二退出码后继续运行。
- 持有者触发真实 CPU 数据访问异常，子任务确认一百三十九退出码后继续运行。此诊断镜像在用户入口返回后追加原生保护页探测，探测不属于配套 `.wasm` 模块本身。
- 子任务正常退出后，父任务确认设备仍就绪，并将预先填充的缓冲通过真实磁盘读取覆盖为零。
- 子任务陷阱退出后，父任务完成同样的设备可用性检查。

所有持有设备的现有用例也必须恰好出现一次内核清理完成标记，包括文件 Shell 和文件系统错误恢复。硬件检查发生在该标记之前，不能用输出标记替代实际清理。

这一步覆盖当前固定设备、初始任务所有权和共同退出路径。尚未提供设备转授、一般设备池、持有者自动重启，也未对随机在途请求做故障压力验收。物理页分配器和通用资源复用仍需继续实现，不能把映射撤销等同于所有物理资源已回收。

复位语义依据 [Virtio 1.2 设备复位规范](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html)：设备报告复位完成后，在重新初始化前不得继续使用队列或发送通知。块请求构造仍在用户态，内核承担设备生存期与访问权限管理。

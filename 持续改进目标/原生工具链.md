# 原生工具链

目标：总体架构的 WP8。编译器与豫构经执行器 `客体二号` 预编二成原生程序（macOS、Linux、Windows），不要 Node 也能构建；原生要比 Node 快，然后把默认工具链切成原生。

主要基准：冷编打印探针。用预编二原生编译器与 Node 上的 `yy4_bs.wasm`，冷编 `豫言操作系统/裸机/普通探针/打印。豫` 连同标准库，比墙钟、用户态、退休指令与峰值内存。在 pit-mac（M2 Max）上安静时交替多轮测量。

## 现状（2026-10-02）

已做到：

- 不经 Node 自举：受限环境（`env -i`，`PATH=/bin`）里，原生豫构加原生编译器构建豫言编译器，产物与 Node 构建的逐字节相同；原生生成也能原生运行，造出第二代原生编译器后达到定点。
- 依赖：macOS 原生程序只链 libSystem（dyld 绑定 48 个函数，含 dlopen、dlsym、pthread_create、pthread_join）；Linux 原生程序是静态可执行文件。构建仍调用 `/bin/mkdir`（待办，见下一步 5）。
- 外部调用已从语言与降级器删除：原生函数都在接口文件里声明，降级器按「苹果原生表」生成调用。
- x86-64 有了局部寄存器分配的第一版（c83f16bf1）。
- 回收：分代（粘性标记加卡表）。macOS ARM64 上清扫分段，大部分交给后台线程（0d19b27e0）。

冷编打印探针，同机安静五轮取中位：

| 时间与版本 | 原生 | Node | 比 | 原生退休指令 |
|---|---|---|---|---|
| 10-01 晚（31f7737fd） | 5.67–5.75 秒 | 5.02–5.06 秒 | 约 1.13 | 1142 亿 |
| 10-02 凌晨，d10800ed9 | 5.56 秒 | 4.96 秒 | 1.12 | 1103 亿 |

Node 的退休指令约 959 亿（含它的辅助线程），峰值内存约 0.52 GB；原生峰值约 1.3–1.4 GB。

这一轮的三项转译与回收改动：

1. 分段清扫（0d19b27e0）：主线程当场清扫堆顶往下八分之一（至少 16 MiB）。其中 512 字节以上的空隙记进清扫游程表，供清扫期间分配；其余交给 pthread 线程。清扫期间主线程只用堆顶、当前游程与清扫游程表，大块从表尾 64 项里切。fork 前和下一次回收开始时，都要先等清扫结束。
2. 取变体标签窥孔（d14ace977）：编译器读变体构造子标签时生成固定形状（逐个 `ref.test` 各种变体结构，成功就取字段 0）。转译时认出整串，只读一次对象头，逐个比较类型号。
3. 类型号缓存与 i31 合并（约 −0.9%，指令 −2.8%）：取标签时把类型号存进块临时，并记为“局部 L 的类型号在 K”的事实。之后对 L 的具体类型转换只比较 K。`i31.get_s` 接 `i64.extend_i32_s` 合成一条 sbfx。

## 已测得的情况

1. **墙钟差在并行，不在指令效率**：Node 约有 1 秒 CPU 花在辅助线程上（并发标记、并行清道夫、后台编译）。原生的 CPU 总量早已比 Node 少，要在墙钟上赢，就得把工作挪到别的核，同时继续减少单线程工作。
2. **差距与缺页无关**：原生与 Node 的页回收次数几乎相同（约 8.3 万），系统态原生 0.28 秒、Node 0.38 秒。
3. **回收**：
   - 次要标记每次 0.2–6 毫秒，扫卡 0.4–6 毫秒。
   - 清扫原先全在主线程，现在后台线程合计约 168 毫秒；但主线程仍在 `pthread_join` 上等约 76 毫秒（采样所得），可能是清扫游程用完或大块找不到游程。
   - 只把整个堆交给线程几乎不快：回收后堆顶已近堆限，最近分配的存活对象又在堆顶附近，主线程马上就要等。
   - 回收下限调小（256 MiB、128 MiB）分别慢到 6.2、7.0 秒；调大到 2 GiB 快约 4%，但峰值内存到 2 GB，未采用。
4. **热点**（采样，客体函数名来自编译器 name 段）：
   - m923：在链表上走 n 步。每圈约 54 条指令：取标签，转换，取尾，经 `$box` 把布尔装成 i31 再拆回，搬移多。
   - f943、f1670：整数比较，含 i31 拆箱。
   - str_eq、chars、join：字符串运行时。
   - f900、f1220：变体分派。
   - 复制、填零助手各约 3%，`openat` 等系统调用约 3%（与 Node 相当）。
5. **间接调用**：闭包经 `call_indirect` 调用，每次约 19 条指令（查表描述、查界、取表项、判标记、查函数签名表），全程约 2.6 亿次。编译器模块的表零是静态的：11391 项，只有一个从下标 0 起的元素段，没有任何改表指令，也不导出。
6. **原生构建**：原生豫构每个编译任务另起进程，启动约 4400 万条指令；Node 宿主复用线程与已编译的模块。原生构建编译器 37–45 秒（`-j 8`），Node 约 36 秒。

## 下一步

### 1. `call_indirect` 静态分派（约 −2%）

- 转译时若表零是静态的（自定义、不导出、没有改表指令、元素段常量），就按表下标建一张分派表：每项是“类型号＋跳到函数 fn(i) 的跳转”。
- `call_indirect` 变成：下标与常数比界、读类型号比较、经分派表调用，约 7–10 条。签名不符时走慢路径（预编_验签）。
- 现有预编表只能按连续函数号区间生成，要新增“任意目标”的跳表（降级器的预编表片与合并模块的导出约定都要改）。
- 闭包改用 `call_ref` 是另一条路，要改编译器的闭包调用约定（ABI），待用户定。

### 2. 回收

- 剩余等待：主线程在 `pthread_join` 上约等 76–83 毫秒。采样的调用图确认等待在主线程上（`_pthread_join` → `__ulock_wait`）。每次冷编起 21 个清扫线程，各 1–18 个样本，合计约 170 个。已排除两条：
  - fork：冷编过程中不起子进程，用 PATH 前置的 mkdir 包装脚本数过，0 次；编译器建目录走 mkdirat，`mkdir -p` 子进程只在豫构构建时由包配置的语言服务调用。
  - 取空闲：清扫期间改为增长堆后仍等约 73 毫秒，可见多半不在“游程用完、大块找不到游程”这两条路径上。

  剩下的候选：回收开始时上一轮清扫还没完。分配失败而分配计已超过回收阈的四分之一时，尝试分配会提前回收，两次回收可能挨得很近。

  确认办法：清扫记录还剩 +40 到 +63 可用，可以
  1. 给回收、取空闲、fork 三处的 `等清扫` 各计“调用时线程未完”的次数；
  2. 让清扫线程在结束时写一个完成标志；
  3. 在 苹系统 的「苹_退出」里把计数写到标准错误。

  先确认，再对症改（例如分配失败时先等清扫再判断，或让提前回收改为增长堆）。“清扫期间先增长堆”已试过，更慢，见下方记录。
- 并发标记：标记与扫卡约占 2–3%。要用写屏障配合，且主线程与标记线程会写同一张标记位图，没有原子操作就不好做，排在后面。
- 新生代：用户曾问为何不用复制整理。保守根使得只能做半复制的新生代，还没排期，要先做缓存对照实验再请用户拍板。

### 3. 转译与降级

- 类型号缓存推广：`ref.test (ref i31)` 等其他重复测试；取标签后又取字段时，可省的转换。
- 装箱即拆：`i31.get_u (ref.cast i31 (call $box x))` 等形状。m923 循环里每圈约 14 条，但全编译器只有 5 处，宜让编译器少生成。
- 搬移：降级器生成的 `mov` 仍多（早先按样本加权约占三成指令）。合并与定向还有余地。
- `and w, w, #单一位` 接 `cbz`：可合成一条 tbz。tbz 只能跳 ±32 KB，大函数要退回两条指令，收益约 1%。

### 4. 默认工具链切换

- 条件：原生在冷编与 `全部`、构建上都比 Node 快。
- 要做的事：
  - Wasm 工具链包里带上各平台的原生程序（或由起步时原生生成）；
  - CI 增加原生工具链的自举与定点核对；
  - 豫构的原生子进程启动开销（下一步 5）。

### 5. 杂项

- 标准库还没有建目录的宿主函数，包配置与构建编排靠 `mkdir -p` 子进程（待办）。
- 原生豫构每任务一个进程的启动开销：可考虑常驻工作进程。
- x86-64：没有空闲的调用者保存寄存器放局部；ARM64 的融合内在尚未移植。
- Linux ARM64 容器里运行原生编译器报“包上下文要求规范的绝对包文件路径”，或无声退出 1，未查。
- 预编二的转换都假定本模块是主实例（实例号零），多实例时只走慢路径，属待办事项。

### 试验记录

- 清扫期间先增长堆、从堆顶分配，免等清扫线程：结果正确，但更慢（5.50 秒对 5.25 秒），峰值内存涨到 4.2 GB——每次只增 1 MiB，增出的堆顶很快用完又增，堆失控变大。已放弃。

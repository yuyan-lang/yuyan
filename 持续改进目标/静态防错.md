# 静态防错：哪些缺陷本可以在编译期报出来

立项：2026-10-25（用户定）。豫言首先是一门编程语言，看缺陷要从语言设计着眼：每个议题都问一句，语言或 API 要是有某种特性，这个毛病能不能在编译期就报出来。一个议题修好关掉以后，防住它的设计落实了，才算了结。本篇定下收集这些设计的做法。2026-10-28 用户定分两种：语言已有手段、改接口或库就能挡的，打标签「静态防错」，全部由代理自动处理、不经人工；语言本身缺手段的，打标签「语言设计建议」，记在 `静态防错/建议。数据。豫`，还没落实的排行发在发行页[「语言设计建议」](https://github.com/yuyan-lang/yuyan/releases/tag/language-feature-suggestions)，按每条建议防得住的议题多少排出先后，值得做的在议题里写明方案交用户议定（用户要提案时再写提案）。

2026-10-26 用户定主动防错，范围从议题扩到每个任务：修每个错、用户纠正代理的错、做任务时看出的易错处都要想，实现错与规格错都算，分布式系统与网络最要紧；长远目标是一组专门设计的领域专用语言，都做成豫言的子语言，彼此协同。见 AGENTS.md「主动防错」一条。

## 做法

1. 提议题时在正文末尾写一节「静态防错」：语言或 API 有什么特性，这个缺陷就不会发生，或者会在编译期报出来；确实防不住的写“只能运行时发现”，并说明缘由。修完关议题时，在关闭评论里写一句。见 AGENTS.md「静态防错」一条。
2. 分两种，判据看推荐的解法改不改语言（AGENTS.md「先分清语言的缺口与库的缺口」）：
   - 不改语言（语言已有手段，改接口或库就能挡在编译期）：打标签「静态防错」。这类与缺陷议题一样办，提了不关：只要合理，一律由代理自动实施、不经人工，改好接口或库再关；小的随修随做，大的提一个打同一标签的实施议题排期。不登建议表，不送用户审。
   - 要改语言（现有语言特性明显给不出足够的静态保证）：打标签「语言设计建议」，登进建议表。
3. 没有缺陷议题的语言设计案例（任务里顺手修掉的错、用户或审查人纠正的错、做任务时看出的易错处与规格漏洞）提防错议题：标题以「防错：」开头，打标签「语言设计建议」，正文写案例、建议的语言特性或子语言（附一小段写法草样），以及它还防得住哪些别的错。一案一议题：同一种建议有了新案例照样另提，正文引用先前的议题。登记进建议表后留着开，不派人去实现，等用户审议；值得做的由回顾在议题里写明方案，用户定了再做；用户审定以后（接受、暂缓或否决）就可以关，接受了的照议定的方案实施。
4. 建议表 `持续改进目标/静态防错/建议。数据。豫` 只收语言设计建议。一条「建议」有六个字段：名、类、说明、议题（它防得住的议题号列）、状态（待办；用户接受后为已接受；实施中、暂缓、已落实）、提案（没有就空着）。同一种建议并成一条，把新的议题号加进去。建议没落实之前，标签照留；缺陷本身已修好而关掉的议题，标签也照留。
5. 建议表推上 yybs 后，工作流「静态防错」用曲突（`应用/百工坊/曲突`，静态防错榜）读建议表，只把状态不是“已落实”的按议题数排出先后，重写发行页「语言设计建议」。曲突取名于《汉书·霍光传》“曲突徙薪”：客劝主人把烟囱改弯、把柴挪远，主人不听，后来失火；防患于未然，正是本篇的意思。同一工作流随后取稿府的开签与全议议题数据，让曲突以建议表为唯一来源核对三处：开着的、带「语言设计建议」标签的议题须被某条待审建议引用（状态待办或暂缓，所挂提案还没定）；待审建议引用的开着议题须带这个标签；提案已接受、已否决、已落实、实施中、暂缓实施或已取代的建议，其议题移出待审队列，由提案跟进；表里的议题号都要存在。对不上的列出议题号与缘由，先只报、不挡。#1272 定下这条核对，目的是一份声明（建议表）推出其余各处，标签、表与提案状态不再各记一份而漂开。
6. 议题号每过一百（以下文回顾记录里上次回顾到的议题号为准），或者按需，派一个代理回顾：逐个看上次回顾以后的新议题，补登语言设计建议（不改语言的不登，确认它带着「静态防错」标签、由代理跟进）；并掉同义的建议；按涉及的议题数与实现代价定先后；排在前头、代价合适的在议题里写明方案交用户议定（用户明说要提案时才写进 `提案/`，提案号记回建议的「提案」栏）；最后在回顾记录里记一笔。

## 分类

| 类 | 说的是什么 | 例 |
| --- | --- | --- |
| 类型区分 | 同为整数或文，含义不同（键与号、地址的区域、文件长度、退出原因、真实路径与链接路径），用新类型或枚举分开，混用即编译报错 | 键与号分类型、地址区域类型 |
| 依值类型 | 长度、下标、范围、移位量写进类型 | 移位量依值类型 |
| 穷尽检查 | 鉴的分支不全就编译报错 | 鉴不穷尽即报错 |
| 结果类型 | 可失败的操作返回结果类型，由调用方处理错误 | 可失败原语返回结果 |
| 类型状态 | 对象的状态（已实化、已打开、已释放）写进类型，次序不对就编不过 | 寄存器缓存类型状态 |
| 效应与资源 | 副作用、资源的开关与归属（锁、文件、内存、进程）写进类型，漏关、重复释放、越权在编译期报出 | — |
| 协议类型 | 程序间消息的格式与先后写成类型，收发两端出自同一份声明 | — |
| 由声明生成 | 表、号、偏移出自一份声明，由编译器生成或查重 | 状态格由声明分配、平台导入与降级表同源 |
| 子语言 | 一类工作（网络协议、分布式协调、构建与部署、界面布局、设备寄存器等）的规格写成专门的豫言子语言，各端实现、文档与测试由同一份声明生成，规格自身的矛盾与遗漏在编译期报出 | 协议子语言（收发两端与状态机出自一份声明） |
| 标签参数 | 同类型的几个参数或字段按名字给 | 系统调用号带标签 |
| 版本印记 | 产物与运行时带版本印记，装入、链接时核对，比运行到出错时早一步 | 单元与执行器同版印记 |
| 编译期检查 | 语言不变，编译器或豫构在编译时多查一项（常量越界、结果没用上、导入不认、接口没实现全） | — |
| 工具与流程 | 在 CI、格式检查、测试里防 | 状态格重叠检查 |
| 只能运行时 | 取决于外部环境、硬件或时序，只有跑起来才看得出 | — |

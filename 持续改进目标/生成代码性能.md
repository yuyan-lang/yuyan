# 生成代码性能

目标：豫言编出的程序在 Node（V8）与原生执行器上都更快。

主要基准有两类：
- 冷编译打印探针：用编译器 `yy4_bs.wasm` 冷编一个打印程序，连同标准库。
- `应用/性能研究/` 下的微基准。

## 下一步

### 1. 编译器少造闭包

- 数据：插桩后冷编整个编译器。
  - 动态闭包调用 74.5 亿次。
  - 通用组（闭包、环境、递归单元）构造 44.2 亿次、取项 233.4 亿次。
  - 用户元组构造 2.55 亿次、取项 34.7 亿次。
  - 一次闭包调用约 1.6 纳秒，直接调用约 1.5 纳秒，开销主要在分配闭包。
- 做法：
  1. 部分应用与柯里化的调用，按被调函数的元数直接满参调用，不造中间闭包。
  2. 把已知的 lambda 传给标准库高阶函数（态射、从左折叠等）时，内联或特化。
  3. 把顶层直接调用（工函数 `<路径>_直调_<名>_<序数>`）推广到局部函数。
- 不改闭包表示。结构体一律 final、没有子类型，改成结构体后每次调用约省三条指令，但有捕获的闭包要分配两个对象，取捕获也多一次间接，得不偿失。
- 验收：
  - 插桩计数前后对比。给动态闭包调用、通用组的构造与取项各加一个 i64 计数，插桩版自举后单进程冷编；插桩不入库。
  - Node 交替测速。
  - WP8 测原生指令数。

### 2. Wasm 清理优化遍（用豫言实现）

- 数据：WP8 用 binaryen 的 `wasm-opt -O3` 处理 `yy4_bs.wasm`，Node 冷编 −11.6%（5.78 → 5.11 秒），原生 −1.4%。
- 做法：
  1. 先拆解是哪几遍起作用：逐遍跑 wasm-opt，测 Node 冷编。binaryen 读我们的二进制要带特性参数。
  2. 把收益大的几遍在编译器里用豫言实现。编译器由结构化表示直接写出 Wasm 二进制，就在写出前的表示上做，例如局部化简与合并、死代码删除、冗余 `ref.cast` 删除、块合并、常量折叠。
  3. 不把 binaryen 接进构建。
- 验收：同上。

### 3. 小数字段特化（E1b 留的待办）

- 代码生成与边界转换都已支持构造器的小数字段存 f64，只是没打开。
- 小点基准上 f64 字段版：
  - 本机 M5 Pro 上慢约 46%，关掉 Wasm 内联后反而快约 17%；
  - pit-mac M2 Max 上快约 5%。
- 查清 V8 内联的差别后再定。

### 4. 原生侧

去装箱在原生上没有收益（指令 +0.5%）。原生与 Node 的差距还集中在字符串运行时函数和内联上。这部分由 WP8（会话“豫言操作系统接口定义”）跟进，转译时内联已经合入（bcd036792）。

## 规矩

- 编译器改动要完整自举（`全部 -j 24`，yy3 与 yy4 逐字节相同），合入前交 WP8 做原生全验。
- 测速时改前改后交替多跑几轮，取最小值，注明负载。指令数请 WP8 测，它不受负载影响。
- 语义取舍：去装箱信任声明的类型。用不安全转换或外调伪造的“整数”，穿过确知函数边界或存进整数字段时会陷入。两仓现在没有这样的代码。

# 构建系统

目标：让日常构建（自举、构建、类型检查、测试）尽量快。做法是先用构建日志量出时间花在哪里，再逐项改进，每项改完用日志复测。

## 现状（2026-09-30）

第一期已完成（提交 95d5174c6）：

- **构建日志**：豫构的构建类命令把每次运行写进仓库根的 `.yy构建日志/运行/<运行名>/`。每个 worktree 各有一份，不自动删除。
  - 文件：`运行.json` 记命令、提交、负载等；另外每个进程写一份 `<种类>-<纳秒>.jsonl`，记区间、目标、步骤、编译任务，每个任务带加入、就绪、开始、结束四个时刻。
  - 嵌套：豫构与编排经环境变量把运行目录传给子进程，嵌套的豫构与编译器写进同一次运行。
  - 格式：见 `应用/性能研究/构建性能/日志格式.汉语.md`。
- **分析工具**：`应用/开发工具/构建性能`，产物是 `yy构建性能.wasm`。命令有 `列出`、`摘要 [运行名|最近]`、`清理 保留条数`。
  - 摘要内容：进程树、编排目标用时，以及每次编译的墙钟、平均并行度、利用率、关键路径、等槽位、各阶段统计、最慢任务。
  - 判读框架与待验证的疑点：见 `应用/性能研究/构建性能/调查方案.汉语.md`。
- **CI**：自举、检查、三平台 Wasm 包起步、Windows 四类作业上传构件 `yy-build-logs-*`，保留 90 天。用 `gh run download <运行号> -n <构件名>` 取回。

看数据：

```sh
node 豫言操作系统/宿主/节点/宿主.cjs yy豫构.wasm 构建 构建性能 --输出 yy构建性能.wasm -j 24
node 豫言操作系统/宿主/节点/宿主.cjs yy构建性能.wasm 列出
node 豫言操作系统/宿主/节点/宿主.cjs yy构建性能.wasm 摘要 最近
```

## 已测得的情况

2026-09-30，Apple M5 Pro，18 个处理器，负载 50–150（常有并行会话同时构建）：

1. **`全部` 用时 251 秒，是一条串行链**：编译器二级 42 秒 → 三级 66 秒 → 四级 78 秒 → 豫构 40 秒 → 值桥 24 秒。值桥声明依赖豫构，两者又同在“豫构缓存”独占组。
2. **编译器构建受关键路径限制**：冷编整个编译器（1201 个任务）墙钟 65–76 秒，关键路径占 91–92%，加并发无用。
   - 类型检查占任务用时合计的约三分之一（322–363 秒）。
   - 关键路径上最长的一环是 `库/编译器核心/编译数据/抽象绑定树结构/抽象语法树/序列化/抽象语法树反序列化节点名称。豫` 的类型检查，10–13 秒。
   - 最慢的任务是 `库/编译器核心/编译步骤/代码生成/回收运行时。豫` 的类型检查，13–16 秒，但不在关键路径上。
   - 最终链接是 8–10 秒的单个任务，排在全部任务之后。
3. **编译器一换就从冷缓存编起**：缓存目录按“编译器路径 + 修改时间”命名。三级、四级都是新目录；自举后第一批用 yy4 的构建也是冷的，比如类型检查编译器要 98 秒，构建包配置的语言服务测试要 70 秒。`.yybuild` 里已积了 129 个这样的目录，共 242G。
4. **同一个库在不同包上下文里各编一次**：缓存目录下再按包上下文号分子目录（`包上下文/487.上下文.wasmgc-anf-v2/`、`488…`）。每个子目录里都有一份 `库/标准库/总集` 等共用库的中间产物，所以每构建一个不同的包，标准库、编译器核心这些共用库都要重编一遍。
5. **编排调度会漏收已完成的任务**：`执行任务图` 不限时地让出，子进程没有输入输出时不会醒。`自举#完成` 在第 186 秒完成，到第 227 秒豫构子进程结束才被收取，晚了 40 秒。
6. **豫构自身开销**：每次调用的包发现加包图 0.5–3.7 秒，负载高时变慢。全树测试会调用豫构上千次。
7. **冷编全树测试工具（50 个模块）**：墙钟 15.3 秒，关键路径占 96%，链上几乎全是标准库各模块的类型检查。

## 下一步（按预计收益排序）

每一项都先用日志量出改前数据，改后用同一命令、贴 `YY_BUILD_LOG_TAG` 复测，结果写成报告放在 `应用/性能研究/构建性能/`，汉语、文言各一份。

### 1. 共用库跨包上下文复用缓存

- **问题**：见上文情况 4。
- **做法**：
  - 先查清包上下文号为什么要分缓存：同一模块在不同上下文里编出的中间表示是否真的不同。线索在 `库/编译器核心/编译步骤/总体过程/编译过程工具。豫` 的「获取输出文件路径」与「包上下文缓存号」。
  - 若只取决于该模块所在包的依赖闭包，可以改按“包身份 + 其依赖闭包”建缓存路径，让不同上下文共享同一个库的缓存。
- **验收**：自举后依次构建几个不同的包，标准库模块的任务应命中缓存。命中与否要等第 4 项的第二期埋点，在那之前看各阶段的任务用时。

### 2. 编译器缓存按内容命名

- **问题**：见上文情况 3。
- **做法**：
  - 「当前编译器可执行文件标识」改用编译器 `.wasm` 内容的散列。
  - 标准库现有能力若算不了散列，要加宿主原语，属于 ABI，先问用户。
  - `库/构建基础/构建日志。豫` 的「构建日志缓存目录」复制了这个命名法，须一起改。
  - 另拟一个清理旧缓存目录的办法。
- **预计收益**：自举中 yy3 与 yy4 逐字节相同，自举后用 yy4 的构建可以沿用四级留下的缓存（同一包上下文时），编译器没变时重跑 `全部` 也能命中。
- **验收**：编译事件的“缓存目录已存在”为真；自举后 `目标 类型检查` 远低于 98 秒。

### 3. 修编排调度漏收（改动小）

- **问题**：见上文情况 5。
- **做法**：`库/构建基础/调度器。豫` 的「执行任务图」在 `限时` 为阴时调「让出」。可以改成总用「限时让出」（例如 200 毫秒），或在让出前若有已完成的在途任务就先收取。
- **验收**：各编排目标“完成”任务的结束减开始接近零。

### 4. 第二期埋点

- **工作进程内部**：让工作进程在 stderr 写一行计时，由调度器取出并删掉。内容包括缓存是否命中、读依赖、计算、写出各自的毫秒数与字节数。
- **宿主统计**：并入 `YY_NODE_STATS` 的每实例统计（模块准备毫秒、执行毫秒）。
- **分析工具**：`导出追踪`，生成 Perfetto 可读的甘特图；`比较 甲 乙`，对比两次运行各阶段与目标的差异。

### 5. 缩短类型检查关键路径

- **问题**：见上文情况 2。
- **做法**：
  - 查 `抽象语法树反序列化节点名称。豫`（在关键路径上）、`回收运行时。豫`、`着色译式。豫` 的类型检查为什么慢（模块规模、大型模式匹配或列表、类型检查器热点）。热点可以用 `YY_NODE_PROFILE=1` 看宿主调用分布。
  - 然后拆分模块，或给类型检查器提速。
- **验收**：编译器构建的关键路径与墙钟下降。

### 6. 第三期

- **构建基准**：做成仓库目标，每个场景自动贴标签、跑三次取中位数。场景有：冷缓存、无改动重跑、改叶子文件、改标准库底层文件、`全部`、`目标 类型检查`。
- **分析工具**：`趋势`，按命令看历次用时。
- **全树测试**：创建一次运行，把各测试的构建挂进去，避免每个测试各占一个运行目录。
- **调度优先级**：从“阶段越早越优先”改为按剩余关键路径长度排。目前关键路径上的任务等槽位合计只有约 5 秒，收益待测。

### 其他待查疑点

- 阶段缓存按修改时间判新旧，切分支、`touch` 会引起不必要的重编。
- 每个工作任务的固定开销（Wasm 实例化、读写中间表示），用“无改动重跑”场景量。
- 最终链接（整模块代码生成）8–10 秒，是全部任务之后的单线程长尾。
- 包发现每次都扫描全仓；可考虑缓存包索引，或让全树测试复用同一份索引。

## 注意事项

- 给构建基础、构建编排加减依赖时，要同步云仓 `应用/云仓构建/入口。豫` 的「构建程序上下文」，否则云仓构建程序编不过。
- 改日志格式时，同步 `应用/性能研究/构建性能/日志格式.*.md`（双语）和分析工具，字段只增不改，必要时升“格式”版本号。
- 往长串 `虑` 绑定里插日志代码会让排版器改动后文缩进。把逻辑写成顶层函数，内联处只写单行调用。
- 改编译器或调度器后，跑 `全部 -j 24`（核对定点），再跑 `目标 类型检查 豫构测试 --不连带 -j 24`。计时实验贴 `YY_BUILD_LOG_TAG`，并留意负载：负载明显高于处理器数时计时只作参考。
- 已知局限（待办事项）：
  - 进程被中途杀死时，未写盘的事件会丢；
  - Windows 上宿主按冒号拆 PATH，找不到 git，分支和提交为空；
  - 全树测试的每次构建各成一个运行，日志目录增长较快，定期用 `清理` 删掉旧运行。

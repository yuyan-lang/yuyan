# 文言命名整理

## 目标

整理豫言中偏生硬、偏直译、或不够达意的名称，使语法和标准库更像一套自洽的文言程序语言。

本计划只记录命名方向和取舍，不一次性改完所有名称。改名应小步进行，每次只动一类名称，并保留足够验证。

## 原则

命名优先级如下：

```text
明义 > 顺口 > 文雅 > 短
```

一个好名字应满足：

1. 读者能大致猜出语义。
2. 连续嵌套时仍通顺。
3. 不与已有核心语法词冲突。
4. 不为文雅而牺牲可读性。
5. 同一领域内成对或成组的词要互相照应。

## 保守不动

这些核心词目前可接受，暂不轻改：

```text
于: 函数应用
承: 隐式参数 / 泛型函数类型
化: 显式函数类型
之: 模块或结构投影
若 / 则 / 否则: 条件分支
鉴 / 有 / 或有: 模式匹配
虑: 局部绑定
```

其中 `化` 虽有“转换”之感，但 `化 A 而化 B 而 C` 的链式读法比 `由 A 至由 B 至 C` 更顺。

`虑` 目前还没有明显更好的替代词。`令` 太硬，`设` 偏现代，`寄` 和 `以...为...` 会改变语法气质或与既有用法牵扯。暂时保留。

## 第一批候选

### 列表构造子

当前：

```text
Cons -> 多
Nil  -> 空
```

建议：

```text
Cons -> 缀
Nil  -> 罄
```

理由：

```text
缀: 以一元素接续尾列。
罄: 至此已尽，无复余项。
```

保留：

```text
列
衔
【】
```

也就是说：

```yuyan
「列」立化「元类型」而「元类型」也。
「罄」立（承「元类型」者「甲」而「列」于「甲」）也。
「缀」立（承「元类型」者「甲」而化「甲」而化（「列」于「甲」）而「列」于「甲」）也。
```

### 文脉相关术语

当前若有类似译名：

```text
context window -> 背景信息窗口
```

建议：

```text
context window -> 文脉窗
context window size -> 文脉容量 / 文脉限度
```

`文脉` 比 `背景信息` 更贴近上下文的连续语义；`窗` 比 `窗口` 更短。

### 可选值

当前：

```text
或可有
可有
可无
```

暂不定案。可考虑另列一轮评审，因为这一组成组出现，改名会影响标准库、错误信息、文档和用户代码。

候选方向：

```text
存 / 阙
有 / 无
实 / 阙
```

需要先确认是否值得改，以及是否会与模式匹配的 `有` 冲突。

## 改名步骤

1. 先列出现有语法词、内建类型、标准库模块名、常用构造子和技术术语。
2. 按类别评审：核心语法词、数据构造子、标准库函数、错误信息、文档术语。
3. 每轮只确定少量名称，避免一次性重命名造成语义漂移。
4. 对确定改名的项目，先在标准库中提供兼容别名。
5. 更新语言规范、教程、示例和测试。
6. 等用户代码迁移后，再考虑移除旧名。

## 第一轮实施

第一轮只处理最确定的部分：

```text
「多」 -> 「缀」
「空」 -> 「罄」
```

注意不要误改非列表含义的 `空`：

```text
空节点
空结构
空签名
空串典
```

## 验证

先运行便宜验证：

```text
./yy_bs_stable 豫言编译器/入口。豫 --type-check-only
```

若改动影响编译器或标准库语义，再运行自举验证：

```text
./yy_bs_stable 豫言编译器/入口。豫 -o yy2_bs --parallel >/dev/null 2>/dev/null
./yy2_bs 豫言编译器/入口。豫 -o yy3_bs --parallel >/dev/null 2>/dev/null
```

生成 `yy3_bs` 即视为自举成功。

## 完成状态

完成后应有一份稳定的命名表，记录：

```text
旧名
新名
所属类别
是否已实施
是否保留兼容别名
迁移备注
```

命名整理不追求一次到位。每个名字都应经过实际代码片段检验，尤其要检查连续嵌套时是否仍然顺口。

# 函数应用隐式参数求解

实现位于 `编译步骤/类型检查/函数应用隐式参数合成。豫`。这一阶段只负责回答一个问题：一次函数调用中，哪些未写出的隐式类型实参可以由现有信息唯一确定？

## 顶层接口

`求解函数应用隐式参数` 接收命名环境、完整调用表达式、函数头类型、源参数脊和可选的期望结果类型，返回：

```text
列 表达式
```

返回列只包含需要自动插入的隐式类型实参，并保持它们在函数类型中的出现顺序。它不返回函数头、参数规划、合一上下文或结果类型。

- 合成模式传入 `可无`，因此不能从结果类型取得信息。
- 检查模式传入 `可有 T`，因此可以用 `T` 接地隐式参数。
- 用户已经写出的隐式类型实参不会出现在返回列中。

## 可用于求解的信息

每个隐式绑定都先实例化为本次调用独有的新鲜类型变量，并登记到 `var → optional expression` 的模式合一上下文中。用户显式写出的隐式参数立即记为该变量的 `Some expression` 解；缺省、需要推断的隐式参数起初记为 `None`，等待普通实参或结果类型接地。键不存在表示该名称不是本次待求变量。只有缺省变量会被记录到最终返回列中。求解器只读取下列信息：

- 用户写出的隐式类型实参。
- 普通实参为自由变量时，从命名环境直接读取的类型。
- 普通实参为文件定义引用时，从文件定义直接读取的类型。
- 检查模式中的期望结果类型。

lambda、函数调用等复杂普通实参不参与推断，留给后续常规类型检查。这避免了为了合成隐式参数而递归预检查实参。

每条可用信息都只做单向 matching unification：左侧类型可以含上下文登记的变量，右侧必须对这些变量是 ground。匹配成功才提交新的 `var → expression` 解；任一子结构不匹配时整次匹配回滚，不在求解阶段报告参数类型错误。真正的错误由重放检查报告。求解结束时再利用全部参数信息和可选结果类型检查所有待求变量是否已经接地。

模式合一直接复用原有的结构比较递归，并把同一个 `串典` 上下文随递归传下去。普通节点仍按原规则比较；只有比较遇到左侧自由变量时才查询上下文：未登记的变量仍要求两侧同名，登记但未解的变量写入 `Some 右式`，已有解则拿该解继续与右式比较。整个过程不预先“应用上下文”，也不执行表达式级局部替换；求解完成后直接从 `串典` 读取各隐式参数的类型表达式。

求解器不读取或应用这个上下文来改写当前函数类型。外层调用检查先沿函数头的原始类型骨架拆出当前参数组；当前组检查完后，常规依赖类型替换会给出真实结果类型，若源参数脊还有剩余参数，就把该结果当作新的函数头继续检查下一组。例如 `readRef : {A} -> Ref A -> A` 先只检查 `readRef ref`；若 `A` 被接地为 `X -> Y`，再以这个结果检查后续参数。这样无需“只读取顶层已解变量”这一特殊分支。

## 完全应用语义

函数名本身仍然可以作为函数值。只有语法树已经进入函数调用节点时，才要求这次调用完全饱和：

1. 遇到隐式派类型和源隐式实参时，消费该实参。
2. 遇到隐式派类型但下一个源实参不是隐式实参时，为该位置创建待求解的隐式参数，不消费源实参。
3. 遇到函数原始类型骨架中的箭头时，必须消费一个源显式实参；源参数已经用完就报告不允许部分应用。
4. 当前类型已经不是函数但源参数仍有剩余时，报告参数过多。
5. 遍历结束后，只要仍有隐式类型变量未确定，就报告无法完全确定隐式参数。

裸函数名在检查模式中可以用期望的箭头类型接地前置隐式参数，然后停在箭头类型上作为函数值。这不属于源码部分应用；但 `f [String]` 已经是调用节点，仍必须补齐后续显式参数。

完整调用的结果本身可以是函数值。例如 `readRef ref` 已经消费了 `readRef` 的全部参数；若引用中保存的是函数，它的结果类型仍是箭头，但这不是部分应用。外层检查器会把扁平源码参数脊重建为 `(readRef ref) arg`，而不是把 `arg` 错传给 `readRef`。

因此，若 `f : {A : Type} -> {B : Type} -> X -> R`：

- `f [String] x` 可以从 `x` 的直接可读类型或期望结果类型推断 `B` 时成立。
- `f [String] x` 无法确定 `B` 时报告错误，不会返回保留 `{B}` 的部分应用类型。
- `f [String]` 即使能确定 `B`，仍会因为缺少显式参数 `X` 而报告错误。

## 重放检查

求解结束后，表达式检查和模式检查分别重新沿函数类型与源参数脊前进：

- 在缺省位置依次取用求解器返回的类型表达式。
- 对显式写出的和自动补入的隐式实参执行类型的类型检查。
- 对普通表达式实参执行对象类型检查；对模式实参执行模式类型检查并更新环境。
- 每消费一个隐式参数，就把检查后的类型表达式代入依赖值域。
- 最终检查结果类型与期望类型一致，并重建完整的调用 AST。

求解与检查由此分开：前者只有一个小而稳定的返回值，后者负责所有真实的类型错误和语法树构造。

## 擦除后的调用约定

类型检查阶段要求源码调用完全应用；类型标注擦除阶段则统一使用内部柯里化表示。每个显式实参都会降成一个嵌套的 `Multi1` 调用，连续运行时拉姆达也保持为逐层 `Multi1`：

```text
f a b          => (f a) b
λa. λb. body   => λa. (λb. body)
```

这一区分很重要：箭头类型 `A -> B -> C` 本身无法说明实现是一次接收两个参数，还是先接收 `A` 再返回 `B -> C`。统一的一元运行时约定不需要从类型猜代码 arity，也自然覆盖“从引用读取函数后继续调用”等情况。源码层仍由类型检查拒绝参数不足；内部逐层调用不代表重新允许源码部分应用。

顶层定义与普通函数值走同一条闭包转换路径，文件定义引用读取相应的全局定义槽。旧的“顶层函数直接化”不再负责扫描优化结果、猜测 arity、eta 展开或把文件定义引用改写成函数符号。

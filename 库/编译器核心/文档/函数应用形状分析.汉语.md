# 函数应用隐式参数求解

实现位于 `编译步骤/类型检查/函数应用隐式参数合成。豫`。这一阶段只负责回答一个问题：一次函数调用中，哪些未写出的隐式类型实参可以由现有信息唯一确定？

## 顶层接口

`求解函数应用隐式参数` 接收命名环境、完整调用表达式、函数头类型、源参数脊和可选的期望结果类型，返回：

```text
列 表达式
```

返回列只包含需要自动插入的隐式类型实参，并保持它们在函数类型中的出现顺序。它不返回函数头、参数规划、合一上下文或结果类型。

- 合成模式传入 `可无`，因此不能从结果类型取得信息。
- 检查模式传入 `可有 T`，因此可以用 `T` 接地隐式参数。
- 用户已经写出的隐式类型实参不会出现在返回列中。

## 可用于求解的信息

每个隐式绑定都先实例化为本次调用独有的新鲜类型变量，并登记到 `var → optional expression` 的模式合一上下文中。用户显式写出的隐式参数立即记为该变量的 `Some expression` 解；缺省、需要推断的隐式参数起初记为 `None`，等待普通实参或结果类型接地。键不存在表示该名称不是本次待求变量。只有缺省变量会被记录到最终返回列中。求解器只读取下列信息：

- 用户写出的隐式类型实参。
- 普通实参为自由变量时，从命名环境直接读取的类型。
- 普通实参为文件定义引用时，从文件定义直接读取的类型。
- 检查模式中的期望结果类型。

lambda、函数调用等复杂普通实参不参与推断，留给后续常规类型检查。这避免了为了合成隐式参数而递归预检查实参。

每条可用信息都只做单向 matching unification：左侧类型可以含上下文登记的变量，右侧必须对这些变量是 ground。匹配成功才提交新的 `var → expression` 解；任一子结构不匹配时整次匹配回滚，不在求解阶段报告参数类型错误。真正的错误由重放检查报告。求解结束时再利用全部参数信息和可选结果类型检查所有待求变量是否已经接地。

模式合一直接复用原有的结构比较递归，并把同一个 `串典` 上下文随递归传下去。普通节点仍按原规则比较；只有比较遇到左侧自由变量时才查询上下文：未登记的变量仍要求两侧同名，登记但未解的变量写入 `Some 右式`，已有解则拿该解继续与右式比较。整个过程不预先“应用上下文”，也不执行表达式级局部替换；求解完成后直接从 `串典` 读取各隐式参数的类型表达式。

求解器不读取或应用这个上下文来改写当前函数类型。外层调用检查先沿函数头的原始类型骨架拆出当前参数组；当前组检查完后，常规依赖类型替换会给出真实结果类型，若源参数脊还有剩余参数，就把该结果当作新的函数头继续检查下一组。例如 `readRef : {A} -> Ref A -> A` 先只检查 `readRef ref`；若 `A` 被接地为 `X -> Y`，再以这个结果检查后续参数。这样无需“只读取顶层已解变量”这一特殊分支。

## 完全应用语义

函数名本身仍然可以作为函数值。只有语法树已经进入函数调用节点时，才要求这次调用完全饱和：

1. 遇到隐式派类型和源隐式实参时，消费该实参。
2. 遇到隐式派类型但下一个源实参不是隐式实参时，为该位置创建待求解的隐式参数，不消费源实参。
3. 遇到函数原始类型骨架中的箭头时，必须消费一个源显式实参；源参数已经用完就报告不允许部分应用。
4. 当前类型已经不是函数但源参数仍有剩余时，报告参数过多。
5. 遍历结束后，只要仍有隐式类型变量未确定，就报告无法完全确定隐式参数。

裸函数名在检查模式中可以用期望的箭头类型接地前置隐式参数，然后停在箭头类型上作为函数值。这不属于源码部分应用；但 `f [String]` 已经是调用节点，仍必须补齐后续显式参数。

完整调用的结果本身可以是函数值。例如 `readRef ref` 已经消费了 `readRef` 的全部参数；若引用中保存的是函数，它的结果类型仍是箭头，但这不是部分应用。外层检查器会把扁平源码参数脊重建为 `(readRef ref) arg`，而不是把 `arg` 错传给 `readRef`。

因此，若 `f : {A : Type} -> {B : Type} -> X -> R`：

- `f [String] x` 可以从 `x` 的直接可读类型或期望结果类型推断 `B` 时成立。
- `f [String] x` 无法确定 `B` 时报告错误，不会返回保留 `{B}` 的部分应用类型。
- `f [String]` 即使能确定 `B`，仍会因为缺少显式参数 `X` 而报告错误。

## 重放检查

求解结束后，表达式检查和模式检查分别重新沿函数类型与源参数脊前进：

- 在缺省位置依次取用求解器返回的类型表达式。
- 对显式写出的和自动补入的隐式实参执行类型的类型检查。
- 对普通表达式实参执行对象类型检查；对模式实参执行模式类型检查并更新环境。
- 每消费一个隐式参数，就把检查后的类型表达式代入依赖值域。
- 最终检查结果类型与期望类型一致，并重建完整的调用 AST。

求解与检查由此分开：前者只有一个小而稳定的返回值，后者负责所有真实的类型错误和语法树构造。

## 擦除后的调用约定

类型检查阶段要求源码调用完全应用；类型标注擦除阶段则统一使用内部柯里化表示。每个显式实参都会降成一个嵌套的 `Multi1` 调用，连续运行时拉姆达也保持为逐层 `Multi1`：

```text
f a b          => (f a) b
λa. λb. body   => λa. (λb. body)
```

箭头类型 `A -> B -> C` 本身不说明实现是一次接收两个参数，还是先接收 `A` 再返回 `B -> C`，所以一元约定是通用的运行时约定：函数值、闭包、从引用读出的函数都按逐层 `Multi1` 调用。源码层仍由类型检查拒绝参数不足；内部逐层调用不代表重新允许源码部分应用。

## 顶层直接调用

已知的顶层定义另有直接调用约定，实现位于 `编译步骤/优化/跨文件优化/顶层直接调用。豫`，在跨模块优化的末尾执行。

1. 元数取自类型检查过的签名。类型检查阶段按函数应用骨架为每个定义算出元数：去掉开头一组隐式参数，数展平后箭头类型的定义域个数；构造器取构造器类型。它就是上文“完全应用语义”中一次调用消费的显式参数个数。结果写进阶段产物 `签名元数`。
2. 签名元数 N ≥ 1，且优化后的定义（剥去顶层递归节点后）开头至少有 N 层一元拉姆达时，这个定义有工函数。工函数是 N 参数的全局函数，函数体是去掉前 N 层拉姆达后的定义体；顶层递归节点的自引用改为文件定义引用。定义本身变成“声明工函数，再给出柯里化包装”：包装有 N 层一元拉姆达，最内层一次把 N 个参数交给工函数。全局定义槽里存的是包装。
3. 工函数的名字、定义序数与元数写进阶段产物 `顶层元数`，先于优化后形式写出。他模块在自己的跨模块优化末尾读这份产物；并行调度保证依赖模块的跨模块优化先完成，依赖的优化后形式一旦更新，下游的优化后形式随之重建，所以分别编译与缓存下两边一致。
4. 调用脊的头是有工函数的文件定义引用、且实参不少于 N 时，前 N 个实参一次交给工函数（`函数调用 (函数引用 工) (多参数形 N)`），其余实参照一元约定逐个施于结果。实参少于 N、头不是已知顶层定义、或定义作为值使用（被返回、存进数据结构、作为高阶实参）时，照旧读全局定义槽里的包装。

```text
f a b c        （f 的签名元数为 2）   =>   (工f a b) c
```

改写不改变可观察的求值次序：原来逐层施用时，前 N−1 次施用只新建闭包，没有副作用；实参仍按源码次序求值，都先于工函数体。结果本身是函数的满参调用（如 `readRef ref` 再被调用）只把满参部分直接调用，其余照一元约定。尾位置上的直接调用由尾调用优化标成尾调用；自递归尾调用在后端变成循环。

签名元数小于拉姆达层数时（如返回类型写成函数类型别名），工函数返回闭包，余参照一元约定施用。拉姆达层数小于签名元数时（如 `会「格」而「读引用」于「格」`、别名 `「f」者「g」也`），不生成工函数，调用照旧经全局槽：这时先求出后面的实参可能改变中间函数体的执行次序。

去柯里化只再变换顶层定义内部的局部递归，顶层定义自身的递归由这里统一处理。异常、续延模块（`路径不应当优化`）、底层模式、`-O0` 与 `-fno-func-uncurry` 都不生成工函数，也不改写调用。模块初始化时直接调用前面已初始化的定义，不读全局槽；顶层没有前向引用，依赖模块先初始化，所以直接调用不会早于被调定义的初始化。

旧的“顶层函数直接化”（2026-08 删除）从优化结果猜测元数，并对别名和部分应用做 eta 展开；现行做法只用签名元数，不做 eta 展开。

## 去装箱

整数、小数平时装箱成 `(ref null eq)`：整数是 i31 或 `$big`，小数是 `$float`。编译器确知某个参数、返回值或局部变量是整数或小数时，就用 i64、f64 直接存与传，算术前后不再装拆箱。实现分两处：类别随签名带到代码生成，代码生成再在整程序范围推定表示。

1. **类别。** 类型检查写签名元数时，顺带算出每个显式参数与结果的类别。
   - 内建整数为整，内建小数为小。
   - 其余为通，包括类型变量、元组、列、函数、不透明类型、爻、字符串。

   签名元数与顶层元数两份产物都带类别。代码生成读全部模块的顶层元数，得到“工函数名 → 类别”的表。调用方的优化后形式只依赖元数，不依赖类别，所以分别编译与缓存不受影响。
2. **确知函数。** 工函数有类别签名，并且没有整组克隆、私形、虚组等变体时，就是确知函数。它的参数按用处择表示：

   | 参数 | 表示 |
   | --- | --- |
   | 签名为整，并在函数体里作整数用（整数运算、数组下标、确知调用的整数参数） | i64 |
   | 签名为小，并作小数用 | f64 |
   | 静态自递归函数里作数组读写对象 | `(ref $tuple)` |
   | 其余（只转手的） | eqref |

   结果类别取自签名，但必须尾调安全：函数在尾位置只调用自己（变成循环）或结果类别相同的确知函数时，才用 i64、f64 返回。尾调用闭包或非确知函数的，结果降为通。这一步反复做，直到不再变化。

   纯整函数也是确知函数，它的快体就是原来的 `$n`。纯整函数指：参数都在入口受整数运算检查，函数体只有整数运算。
3. **生成。** 确知函数生成两个函数：
   - 通用入口 `$f号`：参数与结果都是 eqref，留在函数表里，应用接口导出也调它。它拆箱后调用快体，结果非通时再装箱。
   - 快体 `$m号`。

   凡直接调用确知函数的地方，都按确知签名拆参，直接调用快体。这包括本模块、他模块、柯里化包装的最内层、闭包体。类别是确知的，不写守卫。尾位置上，结果类别相同就尾调用，不同就先调用、转换，再返回；尾调安全保证这种转换不会出现在尾调用环里。
4. **局部。** 代码生成在正则上前向推定局部的表示：
   - 得 i64 局部：整数运算、小数转整数、原语登记表里结果为整的原语（如取余、位运算）、结果为整的确知调用。
   - 得 f64 局部：小数四则、整数转小数、原语登记表里结果为小的原语（如开方、取整）、结果为小的确知调用、两支都产小数的若。

   整数运算之外的推定只在没有变体的函数里做。登记原语的结果局部是对应的 i64、f64 局部时，参数按登记的类别直接写，指令就地生成，不装箱。

   值存进元组、构造器、闭包、全局，或传给多态函数、闭包、宿主时，现场装箱。从多态代码出来的值，在作整数、小数的用处拆箱。
5. **循环。** 自尾调用仍然变成循环。回环时，确知的整数、小数参数直接写成 i64、f64，小数累加器不再每轮分配。

Wasm 层面的约定见《网页汇编接口》网四。

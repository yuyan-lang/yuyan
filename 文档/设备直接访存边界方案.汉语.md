# 设备直接访存的信任边界（已决定：直接实现 IOMMU）

当前已经验证的接口只允许初始任务读取固定 PCI 设备配置，尚未启用总线主控或 DMA。下一步将使设备写入内存，因此需要先确定驱动错误或恶意请求是否必须受到 DMA 隔离。这是安全承诺与微内核职责的选择，不是某条机器指令的实现细节。

CPU 页表限制 CPU 访问，不能自动限制设备 DMA。Virtio 规范规定，没有平台地址转换时，设备使用驱动提供的物理地址。不能把“驱动运行在用户态”当作 DMA 隔离的证明。[Virtio 1.2，保留特性位](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html#x1-1230006)

## 方案一：先由内核约束 DMA（未采用的过渡方案）

用户态块服务负责请求排队、磁盘块访问策略和错误报告，文件系统与 Shell 继续在用户态。内核暂时负责一小段 Virtio 传输：受限设备初始化、保护的队列描述符、固定 DMA 区域、提交与完成状态。用户态不能写设备队列地址、总线主控配置或内核使用的描述符。

第一版向用户态提供读扇区、写扇区、刷新、查询完成和复位等受限操作。请求以设备能力、操作、扇区号、用户缓冲区偏移和长度表示，不接受调用者提供的物理地址。权限、范围、溢出和操作类型检查通过后，由内核构造描述符。写请求先复制到受保护的 DMA 区域；读请求完成后再复制回经过检查的用户缓冲区。状态与容量由内核解析，设备返回的长度不直接成为不受限复制长度。

关键条件：不能只校验用户可写的描述符，再让设备读取同一份描述符；否则存在检查后篡改问题。请求在完成或成功复位前不能回收 DMA 内存。任务退出或超时不能直接释放仍可能被设备使用的页。先用一个队列、一个在途请求，后续再增加并发。

优点是当前无需先完成两种 IOMMU，仍能阻止用户任务伪造 DMA 地址。代价是内核包含一部分设备传输逻辑，并有数据复制开销；尚不能给出性能数值。此方案依赖设备遵守提交的描述符，不声称防御恶意物理设备。后续可以用 IOMMU 与受控页映射替换暂存路径，将更多传输代码移回用户态。

## 方案二：用户态驱动暂时可信，不实现 DMA 隔离

仅给专用驱动任务设备配置、寄存器和 DMA 区域访问权；普通程序与 Shell 不取得这些权限。驱动在用户态直接管理队列和物理地址。需要将设备权限从当前初始任务拆出，不能把能加载任意程序的任务直接视为可信驱动。

这更接近全部驱动逻辑留在用户态的最小特权内核，初期代码较少。但设备地址缺少硬件限制时，驱动错误仍可能破坏内核或其他进程；必须明确把该驱动列入可信计算基。普通程序的 CPU 内存隔离仍成立，驱动的 DMA 故障隔离不能宣称成立。驱动退出前也仍需等待完成或复位设备，不能省略生命周期管理。

## 方案三：先实现 IOMMU，再允许用户态直接驱动设备（已采用）

先在两种架构上实现 DMA 地址空间、设备绑定、页映射、权限、失效与撤销，再实现磁盘驱动。用户态驱动只能让设备访问获授权的页，内核管理映射和生命周期，驱动管理 Virtio 传输。

这是把驱动保留在用户态并获得硬件 DMA 限制的长期方案。代价是磁盘读写、文件持久化之前增加一整套硬件内存管理与故障处理。QEMU ARM virt 可提供 SMMUv3；其默认不创建 IOMMU。AMD64 的具体平台与对应 IOMMU 需要另行验证，不把某个模拟器开关当成已经完成的客体实现。[QEMU virt 文档](https://www.qemu.org/docs/master/system/arm/virt.html)

## 三种方案共同的验收

两架构均须实际读写临时磁盘，核对扇区边界、拒绝未授权任务、处理只读盘与 I/O 错误；写入、刷新、退出 QEMU 后再次启动并读回数据。退出、终止与复位期间不得过早复用 DMA 内存。方案一另验恶意请求无法设置任意物理地址；方案三另验设备访问未映射页被 IOMMU 拒绝。方案二必须明确保留其隔离限制，不得用普通页故障测试代替 DMA 隔离证明。

用户已选择直接实现 IOMMU：内核负责设备地址空间、映射权限和生命周期，驱动在用户态管理 Virtio 传输。不采用先将 DMA 传输下移内核的过渡方案，也不以可信驱动绕过 DMA 隔离。验证设备地址转换和拒绝未映射访问之前，不启用磁盘 DMA。浏览器平台另由宿主提供 I/O。原操作系统目标保持不变。

# 直接实现 IOMMU

用户已选择直接实现硬件 DMA 隔离。内核管理设备地址空间、授权、映射、撤销及故障；用户态驱动管理 Virtio 协议。浏览器平台使用宿主 I/O，不承担裸机 IOMMU 实现。本文件列出实施顺序，不代表所列能力已经完成。

## 两种验证平台

ARM64 使用 QEMU virt、SMMUv3，显式关闭默认 PCI 总线的 IOMMU 绕过。AMD64 使用 Q35、Intel VT-d，开启 DMA 翻译模型与缓存模式；初期不依赖中断重映射，仍须单独实现它才能承诺不受信任驱动的中断隔离。现代 Virtio 磁盘显式设置 `iommu_platform=on`、关闭 ATS。旧平台回归继续保留。

CPU 架构与 IOMMU 实现不能混为一谈：AMD64 是这里的指令集名称，QEMU 测试机器使用 Intel VT-d 模型。这不表示已经支持 AMD 硬件的 IOMMU，也不表示支持所有 ARM 平台。未来通过平台发现选择实现。

## 内核实现顺序

1. 从受信任的平台描述确认设备与 IOMMU 关联、寄存器范围和能力，再访问寄存器。不能在任意机器上试读固定 MMIO 地址并假定不会产生异常。
2. 分配仅内核可写的流表或根表、上下文、页表、命令与故障记录存储。没有授权条目的设备默认不获得 DMA 映射。
3. 完成初始状态设置和失效同步，确认硬件状态。只有读取到硬件确认，才能把设备隔离视为已启用；不能把 QEMU 参数或一次寄存器写入当成成功。
4. 为专用用户态驱动建立独立设备地址空间。返回设备虚拟地址与其拥有的 CPU 缓冲区之间的映射，不接受任意物理地址。支持显式读写权限、对齐与范围检查。
5. Virtio 驱动协商平台地址转换特性，提交设备虚拟地址。对能力与协商结果不符的平台拒绝运行，不能退回物理地址绕过隔离。
6. 实现撤销映射、地址转换缓存失效及完成确认。停止新请求、处理在途 DMA 后才能释放页；驱动退出、被终止或设备复位也必须执行同样的生命周期管理。
7. 记录并处理设备访问故障，使故障设备停止访问，其他任务保持可运行。IOMMU 自己使用的命令和故障队列必须由内核持有，不能交给普通驱动修改。

SMMUv3 与 VT-d 分别实现上述机制，上层设备能力与缓冲区接口共用。初期限制一个设备、一个设备地址空间和一个在途磁盘请求，是实现范围限制，不改变“未经授权不能 DMA”的安全要求；后续扩展并发与设备数量。

## 必须通过的验收

- 设备实际读取或写入获授权页，数据与预期一致。
- 故意向未映射地址、只读页及越界范围发起 DMA，硬件拒绝，保护区哨兵不变，并读到相应故障证据。
- 撤销授权后再次 DMA 失败，证明没有继续使用陈旧地址转换；回收页后不能被旧设备请求写坏。
- 对照测试故意放开目标页权限，保护区变化必须使验证失败，以防测试实际上未触发 DMA。
- 驱动或设备故障后，命令壳与其他任务继续可用。
- 通过上述隔离验证后，再接入真实磁盘读写、刷新和 QEMU 重启读回，继而实现持久化文件系统。

隔离平台发现首先验证了既有用户态程序与两种模拟平台兼容。随后加入的[内核初始配置](../工具/豫言裸机/设备隔离初置.汉语.md)设置空授权表并等待硬件开启确认。这两步均不替代上述实际 DMA 拒绝与映射撤销验收。

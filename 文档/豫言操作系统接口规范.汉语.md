# 豫言操作系统接口规范

状态：规范说明草案 0.1，2026-09-24。公开签名现放在仓库根目录的[豫言操作系统接口规范树](../豫言操作系统接口/总纲.汉语.md)；本文说明权威层、包身份、能力依赖、装载检查和图形能力边界。纯声明检查器及更多接口包仍待完成；现有宿主桥接代码不作为规范来源。

## 一、三层分离

1. **接口规范包**：`。包。豫` 给出所有者、名称、版本和依赖；包内 `。接口。豫` 用 `立` 声明名义类型与构造器，用 `乃` 声明函数签名，效果与资源寿命由双语语义注和包规范明确。应用依赖这些包。接口定义中不得出现宿主函数名、`C调用`、DOM/Worker/Node 私有对象、WAT 或驱动寄存器。
2. **宿主实现包**：分别为浏览器、CF Worker、V8/Node.js 及未来裸机实现接口包。它可以含豫言代码、JS 外壳或硬件驱动；这些文件不改变公开接口的类型与语义。实现包须声明其实现的接口包身份，并通过同一接口一致性样例。
3. **执行器与装载器**：验证并运行 Wasm、连接导入、执行资源授权和入口调用。豫言类型是源级规范；WasmGC 表示由编译器向下投影。执行器的内部调用协议不充当应用可见接口。

现有[浏览器宿主](../库/拓展库/浏览器宿主/说明.汉语.md)和[云工宿主](../库/拓展库/云工宿主/说明.汉语.md)已证明多项能力可用，但其 `核心。豫` 将类型声明和宿主调用实现写在一起；迁移时抽取公共契约，保留现有代码作为实现及行为样例，不以其私有原语命名规范公共接口。

## 二、接口包规则

- 包的身份为“所有者／名称／版本”；版本只在 `。包。豫` 中定义。`。接口。豫` 沿用豫言声明及类型语法，内容须可静态读取；不得依赖执行文件来求出函数签名。
- 应用包所依赖的接口包一律**必需**。构建器求传递依赖闭包；目标宿主缺少实现时停止构建或装载。增加功能可另定义接口包，并由需要该功能的应用发行包依赖。
- “宿主实现了接口”与“本次运行获授资源”分开检查。宿主可实现文件接口，却只授予某个目录；GPU 接口已实现，也不保证此时可取得 GPU 设备。缺少实现、未获授权、设备不可用和操作失败应报告不同原因。
- 首版按完整包版本匹配。任何改变公开类型、函数或承诺语义的版本都须重新发布包；更宽松的兼容规则留待一致性验证后制定。
- 每个接口函数需明确参数和结果类型、可能的系统效果、同步或异步、错误结果、资源来源与失效时点。字节、字符串及数值含义由豫言类型系统定义，目标宿主按同一语义适配。

## 三、首批接口面的范围

根目录现有基础、文件、出站网络、显示、启动与入站网页服务六个源级接口包；其中启动与网页服务的入口由应用导出，其余能力由宿主提供。具体程序形态、调用方向与生存期以[接口总纲](../豫言操作系统接口/总纲.汉语.md)和[执行契约](../豫言操作系统接口/执行契约.汉语.md)为准。基础包的[诊断接口](../豫言操作系统接口/基础/诊断。接口。豫)和[时钟接口](../豫言操作系统接口/基础/时钟。接口。豫)含下列纯声明；普通编译器尚不能把声明文件当成无实现的模块进行类型检查：

```text
「记录诊断」乃化「字符串」而「有」也。
「读取单调微秒」乃化「有」而「整数」也。
```

`记录诊断` 把一条完整字符串交给宿主的诊断通道；返回表示宿主已接收，不保证终端、开发者工具或平台日志立即显示，也不把日志当作应用持久存储。`读取单调微秒` 返回同一运行实例中不倒退的整数微秒值，起点没有日历意义；分辨率可低于一微秒，重复读数允许相等。实现该包的宿主须同时提供两项操作。三个首批宿主使用共同豫言样例验收；函数名和类型由根目录 `。接口。豫` 固定，不能由某个平台现有 API 反推。

## 四、图形与 GPU 能力

**GPU 访问属于豫言操作系统的可声明接口能力；GPU 驱动属于宿主实现。**图像的 CPU 绘制可由普通豫言库完成；系统接口至少区分以下能力包：

| 接口包 | 应用可依赖的语义 | 宿主实现示例 |
| --- | --- | --- |
| 显示与输入 | 将已绘制的画面提交到已授显示面，取得尺寸与键鼠事件 | 浏览器 canvas、桌面窗口、裸机帧缓冲与输入设备；CF Worker 无显示面时不实现 |
| 图形处理器 | 申请设备，建立缓冲区/纹理，提交计算或渲染命令，等待完成 | 浏览器 WebGPU；待实现的 Node 图形后端；未来裸机 GPU 驱动 |
| 窗口管理（待定） | 建立或排列多窗口等超出已授显示面的操作 | 浏览器 DOM、桌面窗口系统、未来裸机窗口层 |

图形处理器包的源级对象可包括适配器、设备、队列、缓冲区、纹理和命令；其具体操作与错误须单独规范，优先核对 [WebGPU 规范](https://www.w3.org/TR/webgpu/)及 [wasi:webgpu 提案](https://github.com/WebAssembly/wasi-webgpu)。WASI 提案同样把 GPU 使用与窗口显示分开。接口包可被实现而设备获取仍失败，例如机器无兼容 GPU、设备丢失或本次运行未获许可；程序必须收到豫言类型化结果。

裸机宿主可先用普通豫言库进行 CPU 软件绘制，再用帧缓冲实现显示包的画面提交，无需等待 GPU 驱动。以后若要硬件加速，由裸机实现包连接特定 GPU 驱动。浏览器与 Node 宿主则调用各自可用的图形后端；这些调用方式不进入公共 `。接口。豫`。CF Worker 可以用普通豫言库生成图像字节并通过 HTTP 输出，无须伪造窗口或显示面。

## 五、从规范到发行

`。接口。豫` 与 `。包。豫` → 豫言类型检查与接口清单 → 客体绑定／各宿主实现检查 → 目标 Wasm 投影与宿主装配 → 浏览器、CF Worker 或 Node 发行包。发行清单记录应用与接口包版本、实际导入、宿主实现、授权范围和目标特性。每个宿主对同一接口运行共同样例；接口包和实现包可独立迭代。

首批源级一致性样例现覆盖诊断、时钟、文件、出站请求、显示、启动和入站网页服务，详见[一致性样例](../豫言操作系统接口/一致性样例.汉语.md)。GPU 包待另行规范；其边界现在先定为“应用接口／宿主实现／驱动”三层。

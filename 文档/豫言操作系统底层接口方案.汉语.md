# 豫言操作系统底层接口方案

状态：设计提案，2026-09-26，尚未实现；文中的目录、包名、函数名与布局都是提案，不是当前功能。文言本见[文言版](豫言操作系统底层接口方案.文言.md)。本文不改动[豫言操作系统接口](../豫言操作系统接口/总纲.汉语.md)（下称 GC 接口）与[统一接口方案](豫言操作系统统一接口方案.汉语.md)，只增设一棵并列的非 GC 接口树。

## 术语

- **非 GC／底层**：编译模式为“底层”的代码。值只有 32 位整数，没有垃圾回收（[底层模式](底层模式.汉语.md)）。
- **shim（垫层）**：把一种接口翻译成另一种接口的一层代码。
- **后端**：在某个平台上实现底层接口的实现包（Linux 后端、裸机后端等）。
- **句柄**：平台发放的非负整数，指向一个打开的文件、目录、套接字、管道或进程。
- **出址**：调用者提供的内存地址，被调用者把结果写到那里。
- **HAL（硬件抽象层）**：内核里最贴近硬件的一层（中断、页表、设备寄存器、驱动），只有内核用，应用不碰。本方案不含 HAL。
- **裸机**：我们自己的、直接跑在硬件（或 QEMU）上的豫言操作系统。

## 一、目标与边界

**目标。** 在仓库根目录新增 `豫言操作系统底层接口/`：一套不含垃圾回收、数据形态只有整数与地址的操作系统接口，以**最少的代码**接到 Windows、macOS、Linux 和裸机，并且各平台不重复实现共同的部分。

**只有两个使用者，应用不直接调用它：**

1. **WASI shim**：把外来工具链（wasi-sdk 的 C／C++、Rust 等）编出的 WASI preview1 程序接到底层接口。
2. **GC shim**：把豫言 GC 程序经 `yuyan:gc-host/v1.call` 发出的系统原语（打印、读写文件、环境、时间……）接到底层接口。

非 GC 应用直接用 WASI，我们不另造应用面 ABI。

**不做：**

- **不做 HAL。** 中断、分页、设备寄存器、驱动、调度留在内核，属于裸机后端的内部（第九节）。底层接口只放“应用日常向系统要的东西”：时钟、随机数、读写文件、标准流、套接字、进程、等待。
- **不含 GC、浏览器、Worker、云能力。** 它们仍是 GC 接口树与各自宿主的事。
- **不含能在 shim 里用豫言算出来的东西：** HTTP、TLS、JSON、日期拆分、路径规范化、当前目录。底层只给原始能力。
- **不含线程。** 首版单线程。
- **不含显示与输入。** 第六节预留，v2 再做。

**三条硬约束（来自项目目标）：**

1. **豫言优先。** shim 与各平台后端都用豫言（底层模式）写，不新增 C 文件；非豫言的部分只允许是“进入操作系统的入口表”（第十一节）。
2. **无重复代码。** 凡能共用的都写在 shim 里一次；各平台后端只做“接口函数对应本平台调用”的薄映射。
3. **小。** v1 接口不超过 50 个函数。接口大小直接决定每个平台的移植量。

## 二、现状（依据当前仓库）

- **GC 侧。** [豫言操作系统接口](../豫言操作系统接口/总纲.汉语.md)是 52 个源级接口包、267 个函数声明，用豫言值类型（字符串、列、变体……）写成。浏览器和 CF Worker 上由豫言写的适配包（`豫言操作系统/适配/`）实现，落到宿主库声明的 `C调用` 名，全部经唯一的 Wasm 导入 `yuyan:gc-host/v1.call`（[规范](语言技术规范/网页汇编接口.汉语.md)）。`call` 是按需增长的外调通道：标准库声明 103 个名字，云工宿主库 336 个。它不冻结，也不要求与接口函数一一对应。
- **底层侧。** 执行器 `客体二号` 是底层模式的豫言程序，所有值是 32 位整数。它向平台导入 15 个内核服务（[平台。豫](../工具/豫言裸机/客体二号/平台。豫)：读写控制台字节、退出、两种时钟、中断查询、复制／等待／回收任务、邮箱），文件系统与 virtio 块设备驱动在执行器自己里面（[客体文件系统](../工具/豫言裸机/客体文件系统.汉语.md)）。它实现了 `call` 的 72 个原语（`主机*.豫`，约 1400 行）。内核调用约定目前最多传 2 个参数。
- **桌面侧。** 原生 LLVM 路线的运行时是 C（`运行时支持库/原生/`，`豫言_*` 入口，统一的 `豫言值` 类型）；另有 Node 夹具用来调试执行器。
- **WASI。** 已拆成单独的库 [WASI库](../工具/豫言裸机/WASI库/说明.汉语.md)（未接入，不保证可用），当年直接依赖执行器内部。
- **工具缺口。** 接口检查器只会定位自身、`标准库` 和以 `豫言操作系统` 开头的包，找不到 `底层库`。试验中，一个只有整数、含 6 参数函数和双语注释的底层接口包能被它解析，卡在依赖定位。

## 三、总体结构

```text
WASI 应用（wasm32）                GC 应用（豫言，经 call）
       │                                   │
   WASI shim                         GC shim（现 主机*.豫）      ← 豫言底层模式，写一次，在执行器里
       └────────────────┬──────────────────┘
                        ▼
       豫言操作系统底层接口（本文）           ← 源级接口包：整数签名；构建期绑定到某个后端实现包
                        ▼
       平台后端实现包（每平台一份，豫言写）
          ├ 裸机：内核服务 + 执行器内的用户态文件系统
          ├ Linux：系统调用入口表
          ├ macOS：libSystem 导入表
          └ Windows：kernel32／ntdll 导入表
                        ▼
       操作系统入口（非豫言的部分只到这一层：调用号或导入符号的表）
```

要点：

- **接口是源级的，形式与 GC 接口相同：** `名称。包。豫`、`名称。接口。豫`、`规范.汉语.md`、`规范.文言.md`。区别是包描述写 `「编译模式」者『底层』也。`、依赖 `底层库`，签名里只有 `整数`。既有规则“同一依赖闭包内编译模式必须一致，底层包不能依赖标准库”（[包依赖。豫:60](../库/包配置/包依赖。豫)）保证这些包不会混进 GC 类型。所以“哪些包属于非 GC 接口”由包描述的编译模式定义，可由机器检查。
- **构建期绑定。** GC 接口用 `yy豫言操作系统绑定` 把接口包绑到适配包；底层接口同理，在构建时把接口包绑到平台后端实现包。接口函数是源级函数，所以调用参数个数不受内核调用约定（≤2 个参数）限制，落到内核调用的是后端实现包。
- **shim 在执行器里。** shim 写在底层模式里，与执行器同一编译单元。GC 值与线性内存之间的搬运就在这里：GC 字节数组的内容本来就在执行器内存里，可直接以（地址，长度）交给底层接口，不必复制。
- **与已有代码的对应。** `主机*.豫` 成为 GC shim；`WASI库/` 成为 WASI shim；`平台。豫` 的内核服务导入成为裸机后端的内核调用层。

## 五、调用约定（v1 的核心）

1. **只有整数。** 底层模式的所有值是 32 位整数（爻 0／1，单元 0）。参数不超过 6 个，返回 1 个整数。
2. **返回状态码。** 返回 0 表示成功，否则是状态码（第七节）；结果一律写入调用者提供的出址。唯一例外：`退出` 不返回。
3. **地址是调用者线性内存里的偏移。** 缓冲区是（地址，长度）两个整数，UTF-8，不带结尾零，由调用者持有。被调用者不分配内存、不回调、不抛异常。
4. **64 位量**（纳秒、文件偏移、大小）：输入拆成（低 32 位，高 32 位）两个参数；输出写 8 字节小端到出址。
5. **需要长度的输出**（参数块、环境块、链接目标、初始句柄的名字）：缓冲太小返回状态 61（溢出），并把所需总长写到出址，调用者按此重试。`读目录` 按 WASI 的语义：已用字节数等于缓冲长表示可能还有余项，用游标续读。
6. **句柄** 是非负整数，由平台发放。0、1、2 恒为标准输入、输出、错误；-1 无效；关闭后不得再用（编号可能复用）。句柄同时是能力：目录句柄只能到达其子树。
7. **路径** 是 UTF-8，相对目录句柄（openat 式）。没有全局 `打开(路径)`，没有当前目录（当前目录与路径规范化由 shim 维护）。`..`、绝对路径、符号链接均不得越出目录句柄的子树，越界返回 76。授权以启动时的初始句柄表传入（预开目录），与 WASI 的 preopen、GC 文件包的“目录权”同构。工具链类程序要访问整个文件系统时，由启动方把根目录授予为预开目录；授权范围是启动方的决定，不是接口的默认。
8. **阻塞。** 函数阻塞到完成；等待多个事件用 `等待`；句柄可置为非阻塞，此时无数据返回 6。
9. **块。** 参数多于 6 个的函数改传一个块地址，块头 4 字节为块大小，便于扩展。v1 仅 `运行程序` 使用。
10. **布局小端**，记录布局沿用 WASI preview1（第八节）。
11. **不支持。** 平台没有的能力一律返回 58，不为此另设查询函数；shim 直接试用，据返回值降级。

## 九、平台后端

每个平台一个实现包，用豫言（底层模式）写。它做三件事：接口函数对应本平台的调用；把本平台的错误码换成第七节的状态码；把本平台的记录（stat、dirent）填成第八节的布局。路径逐段解析与越界防护也在后端里。

| 能力 | Linux（系统调用） | macOS（libSystem） | Windows | 裸机 |
| --- | --- | --- | --- | --- |
| 时钟 | clock_gettime | clock_gettime_nsec_np | QueryPerformanceCounter、GetSystemTimePreciseAsFileTime | 内核 时钟滴答（服务 5）、墙钟秒（服务 26） |
| 随机 | getrandom | getentropy | BCryptGenRandom | 熵源未定（候选 virtio-rng、CPU 随机指令） |
| 读写与位置 | read、write、pread64、pwrite64、lseek、close、fsync、ftruncate | 同 POSIX 名 | ReadFile、WriteFile、SetFilePointerEx、CloseHandle、FlushFileBuffers、SetEndOfFile | 控制台：服务 4／0；文件：执行器内文件系统的句柄层 |

| 网络 | socket 族系统调用 | BSD socket | ws2_32（WSA*） | 暂无（返回 58） |

说明：

- **路径编码。** 接口一律 UTF-8；Windows 的路径是 UTF-16，转换在后端里做。
- **越界防护是后端里最厚的一块。** Linux 有一步到位的 `RESOLVE_BENEATH`；macOS 的等价标志因系统版本而异，Windows 没有，后端要逐段解析路径并拒绝越界，并为回退路径做好准备。
- **裸机的文件能力要改造。** 现有文件系统是按整文件读写的日志结构，句柄接口首版可在后端内用整文件缓存实现（关闭或同步时写回），块级读写另案。
- **裸机的内核调用层：** 内核调用约定目前最多 2 个参数，超出的要打包（如服务 24／25 把静态偏移与长度合成一个参数），这是后端的事，接口不受影响。

## 十一、“非豫言代码最少”怎么做

- **入口表是数据，不是代码。** 后端与操作系统之间只有一张表：系统调用号（Linux）或导入符号（macOS 的 libSystem、Windows 的 kernel32 与 ntdll）。调用桩由工具据此生成。Linux 可以直接发系统调用；macOS 不保证系统调用稳定，Windows 的调用号随版本变，这两个平台必须走库导入，所以最少要有一张导入表。
- **落地路线（待定，三选一，建议 A）：**
  - **A. 豫言自有后端。** 把底层模式产出的 Wasm 模块经寄存器降级后端编成各平台本机码，接口入口降为系统调用或导入表。需要可执行文件写出器（ELF、Mach-O、PE）与 Apple 平台的代码签名。全程无非豫言代码。
  - **B. 译成 C 或 LLVM IR 再交系统工具链。** 有非豫言工具链参与，违背目标，仅作备选。
  - **C. 任一 Wasm 引擎加薄胶水。** 现有的 Node 夹具即此。只作差分对照验证，不作交付。
- **内存增长不进接口。** 底层模式的 `内存增长` 是语言指令，由各平台后端的代码生成负责（mmap、VirtualAlloc 或内核内存块服务），不是接口函数。
- **这条路径也是桌面路线摆脱 C 运行时与 V8 的办法：** 执行器成为各平台唯一的运行时，底层接口是它唯一要移植的一层。这不在本方案范围内，但本方案不与之冲突。

## 十二、验收

1. **接口一致性测试**：用豫言底层模式写，每个能力一组，在 Linux、macOS、Windows、QEMU（ARM64、AMD64）上输出逐字相同。
2. **GC shim**：现有的裸机验证与用户态验证在改接底层接口后全部通过；桌面上用同一批普通豫言程序对照。
3. **WASI shim**：`WASI库/示例/` 的 22 个 C 程序在裸机、Linux、macOS 上的输出与退出码，与 Node 自带 `node:wasi` 逐字一致（沿用 `对照.cjs`）。
4. **体量**：接口不超过 50 个函数；不新增 C 文件；平台后端之外，共用代码里没有任何平台分支。
5. **GC 适配**：对方的 GC 接口适配一致性用例（`适配/*/一致性验证`）能在裸机与桌面的适配包上通过。

## 十三、实施顺序

0. **前置**：检查器改用包定位器并接受底层包（与 GC 接口维护者协调）。
1. **写接口包与规范**：基础、句柄、文件（含一致性测试骨架）。
2. **裸机后端**：把现有内核服务与执行器文件系统按句柄模型包一层；`主机*.豫` 改调底层接口（GC shim），现有验证达到持平。
3. **WASI shim**：`WASI库/` 改调底层接口，接回执行器。
4. **Linux 后端与落地路线 A 的最小闭环**（可执行文件写出、系统调用入口），随后 macOS、Windows。
5. **可选能力**（网络、终端、进程），之后显示与输入（v2）。

## 十四、风险与待定

- **`等待`。** epoll、kqueue、IOCP 三套语义不同，v1 只保证文件、套接字、管道与进程、时钟四类订阅。
- **越界防护。** macOS 与 Windows 上要逐段解析，是后端里最厚的一块，且容易出安全问题，需专门测试。
- **系统调用稳定性。** 落地路线 A 必须实现 Mach-O 与 PE 的导入表与（Apple 平台的）代码签名，工作量不小。
- **裸机文件系统**现为整文件读写的日志结构，句柄接口首版用整文件缓存，性能有限。
- **裸机熵源与时钟精度**：没有随机数来源；墙钟只有秒精度，单调时钟 10 ms。
- **单线程。** 将来加线程需重审 `等待` 与句柄。
- **记录布局借用 WASI** 会绑定其快照版本；偏离处（权限位、订阅与事件）已在第八节列出。
- **命名。** 包名与目录名待与 GC 接口维护者对齐。
- **与包层级方案（另案）无依赖。** 将来可用它把这棵树归为一个父包，但不是前置条件。

## 十五、决策记录

以下是与项目负责人讨论后定下的前提：

1. 新增并列目录 `豫言操作系统底层接口/`，不并入 GC 接口树。
2. 底层接口只有两个使用者：WASI shim 与 GC shim；非 GC 应用用 WASI，不另造应用面 ABI。
3. “偏向硬件”指接口的形状（整数、地址加长度、状态码），内容仍是应用级平台服务，不做 HAL。
4. `gc-host/v1.call` 不冻结、不退役，继续按需增长；GC 接口在浏览器与 CF Worker 上继续由豫言写的适配包实现；不为 `call` 另定接口类型的 Wasm 表示。
5. 能用豫言的尽量用豫言，把非豫言代码降到最低；共同部分只写一次。
6. WASI 与 GC 接口对称地架在底层接口上，取代此前“WASI 走 `call`”的设想。

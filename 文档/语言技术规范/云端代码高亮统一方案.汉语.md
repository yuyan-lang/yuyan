# 云端代码高亮统一方案

## 一、目标与边界

让同一段豫言源码在 VS Code、云端只读代码浏览器、云工作台、包源码页、文档签名及静态源码树中得到相同的**词法类别**；在有可靠编译结果时，只对确实需要上下文的类别增加语义细分。颜色可以随主题改变，但类别、范围和优先级不得随页面改变。编辑中的未完成源码、缺少依赖的旧包和编译失败的文件仍须完整显示并保持基础高亮。

本方案以 `yuyan-vscode/yuyan.tmGrammar.json` 的 `source.yuyan` 为当前词法基线，以 `yuyan-vscode/test/grammar.test.js` 为现有行为样例。它是高亮契约，不是语言语法或类型检查的权威。若 grammar 与编译器词法发生冲突，应先核实语言规则，再修改 grammar、镜像及所有实现，不应为了统一而固化错误规则。

## 二、现状与可复现差异

| 入口 | 当前来源 | 已核实的差异或限制 |
| --- | --- | --- |
| VS Code | TextMate grammar，`source.yuyan` | 识别嵌套注释、字符串内转义、声明和类型上下文、内建类别、数字名称、引号内表达式、词界及标点；现有 grammar 测试覆盖这些行为。 |
| 云端只读代码浏览器 | `应用/豫言代码浏览/资源/豫言语法.json`，通过 Monaco 的 TextMate 服务加载 | 此文件与 VS Code grammar 的 SHA-1 相同，现状可作为云端对照组；仍需防止手工复制后分叉。 |
| 云工作台 | `应用/豫言云工作台/网页/词法高亮.mjs` | 只返回 `structure/type/keyword` 等粗类；依次按词表前缀匹配，未验证完整词界；没有声明/函数类型上下文、数值名称、字符串转义、内建细分和 `。` 专类。 |
| 包服务的浏览器侧 | `工具/包管理服务/源码/词法高亮.js` | 与工作台词法器现为逐字相同的副本；又被声明提取、限定名称链、文档链接、提示高亮使用，修改分词粒度时必须同时保护这些调用方。 |
| 包源码页、文档签名和静态源码树 | 豫言实现 `库/拓展库/网页客户端/源码高亮。豫` | 与 JS 词法器大体同形，但结构、类型、关键字词表不全等于 grammar；`递归虑`、`否则`、`者` 等可归错类，`。` 被归为普通标点；注释和字符串只能整体着色。 |
| 包发布的语义标记展示 | 编译器生成的 JSON；`工具/包管理服务/网页/市场.mjs` 可按范围渲染 | 有 13 个语义类别，包括绑定/引用与内建细分；历史包、失败或未完成源码可能没有标记。当前缺失或非法标记时，部分入口直接显示原文，无法保证词法保底。 |

典型错色应写入回归样例：`否则` 属条件控制而非结构；`递归虑` 属控制而非结构；`者` 在普通表达式与类型声明中可有不同类别；`化「甲」而化「乙」而「丙」` 的两个 `而` 属函数类型；`记者信息`、`包含若否则于也关键字` 是完整名称，不应把内部的字拆成关键词；`「一二点三」` 是数字名称；`。` 是结构终止符，`；` 是操作关键字；`《《内建类型：整数》》` 与 `《《内建函数：…》》` 不应同色。词法器当前把 `〇`、`两` 也视为数字，grammar 的数字规则没有这两个字；应先由编译器确认合法性，再统一两端规则。

## 三、统一契约

### 3.1 三层输出

1. **词法层**：读取原文，输出有序、互不重叠的半开区间及 TextMate scope。始终可用，不依赖包、导入或编译成功。
2. **语义层**：仅当编译器产出的标记对应同一份源码、范围合法且类别已知时，覆盖或细分词法层的相应区间。语义缺席不改变词法结果；语义错误只使语义层失效，不清空词法层。
3. **主题层**：把稳定类别映射为 CSS 变量或编辑器主题 token。主题只能改变颜色、字重等视觉属性，不得重新分词。

统一中间数据建议为 `{start,end,scope,kind}`，区间左闭右开；渲染前另做相邻同类合并。云端 JS 使用 UTF-16 偏移，豫言编译器语义 JSON 使用 Unicode 字符偏移：在语义叠加边界作一次显式映射，并同时校验源码版本或内容摘要。含补充平面汉字或 emoji 时不得直接混用两种偏移。源码恢复不变量是 `tokens.map(t => source.slice(t.start,t.end)).join('') === source`，空白和未着色区间也计入。

### 3.2 类别与优先级

| 优先级 | TextMate scope 或语义来源 | 统一类别 | 当前 CSS 类可迁移到 |
| --- | --- | --- | --- |
| 最高 | `comment.block.yuyan`，注释界符 | `comment` | `tok-comment` |
| 高 | `string.quoted.other.yuyan` | `string` | `tok-string` |
| 更高的字符串子区间 | `constant.character.escape.yuyan` | `escape` | `tok-escape` |
| 高 | `support.type.builtin.yuyan` | `builtin-type` | `tok-builtin-type` |
| 高 | `support.function.builtin.yuyan` | `builtin-function` | `tok-builtin-function` |
| 高 | `constant.language.builtin.yuyan` | `builtin-constant` | `tok-builtin-constant` |
| 高 | `constant.numeric.yuyan`，含数字名称 | `number` | `tok-number` |
| 中 | `entity.name.label.yuyan` | `label` | `tok-label` |
| 中 | `markup.bold.structure.terminator.yuyan` | `structure-terminator` | `tok-structure-terminator` |
| 中 | `markup.bold.structure.yuyan` | `structure` | `tok-structure` |
| 中 | `storage.type.function.yuyan` | `type` | `tok-type` |
| 中 | `keyword.control*` | `control` | `tok-control` |
| 中 | `keyword.operator*` | `operator` | `tok-operator` |
| 中 | `punctuation.*` | `punctuation` | `tok-punctuation` |
| 低 | `variable.other.yuyan` | `identifier` | `tok-identifier` |
| 低 | 无着色 scope | `plain` | `tok-plain` 或纯文本节点 |
| 语义细分 | `绑定标识符` / `引用标识符` | `binder` / `identifier` | `tok-binder` / `tok-identifier` |

`meta.declaration.*`、`meta.type.function.*` 是上下文，不直接指定颜色。`punctuation.definition.variable.*`、字符串与注释的界符默认继承容器颜色；如设计上需要界符弱化，应在所有入口一致实现。选取 scope 时用**最内层有效 scope**，但注释和字符串容器先封闭内部普通关键字；只有显式转义 scope 可以覆盖字符串色。

语义覆盖只允许在对应的词法区域内进行：绑定/引用覆盖标识符，语义操作符覆盖关键词/类型词，内建细分覆盖内建，数值、注释、字符串及句号核对一致即可。若语义标记跨过字符串、注释或区间边界、倒序、重叠、越界，整份语义层作废并记录诊断；词法层继续显示。不要把“没有语义标记”解释为“不应着色”。

### 3.3 TextMate 行为清单

- 按 grammar 的顺序处理：嵌套 `「：…：」` 注释；`『…』` 字符串与 `「：…：」` 转义；声明与类型上下文；内建；数字名称；标识符/引号内表达式；标签；普通数字；关键字连续段；句号；标点；裸名称。优先级重排须有对照测试。
- 注释可跨行且嵌套；字符串可跨行。未闭合区域延续到 EOF，在编辑器增量更新时保留行状态，不使后续关键字漏出。
- 关键词采用完整词界及最长合法匹配。相邻关键词连续书写时仍按 grammar 的组件拆分。不得用 `startsWith` 在 `记者信息` 中抓出 `者`，也不得把单词内部 `若`、`也` 涂色。
- `「…」` 的普通内容是标识符；`「一二点三」` 是数字名称；`「鉴「对象」…」` 是引号内表达式，可继续识别内部语法。`《标签》` 与 `《《内建…》》` 必须分别处理。
- 类型上下文与表达式上下文区别处理 `化`、`而`、`者`，尤其是递归函数签名、括号嵌套类型、缩进的构造器声明。不能只靠全局词表决定颜色。
- 中文、ASCII 数字的合法形式及 `〇`、`两` 边界先核实编译器；同一版本的高亮规则不得与自身 grammar 冲突。非法数字不强行扩张匹配区间。
- 保留原文的换行、CRLF、制表、组合字符及补充平面字符；HTML 输出只由文本节点或充分转义的内容构造。

## 四、实现路径

### 4.1 单一来源与产物

把 VS Code grammar 作为版本化输入，构建时**生成或校验**云端只读浏览器的 grammar 镜像；构建失败于内容摘要不一致。附带 `grammarVersion` 或摘要到静态资源，便于定位线上版本。不要维护两份可独立修改的 JSON。

云工作台和包浏览器侧共用同一词法模块。可在浏览器环境运行 TextMate/Oniguruma 时，直接消费 grammar 并保持逐行状态；若包大小、Worker 冷启动或现有内联脚本 CSP 不容许，则实现轻量状态机，但以 TextMate 输出作逐区间差分验证。状态机是生成物或受测兼容层，不得另有手写关键词真值表。包服务的内联 `豫言分词.toString()`、`限定名称链`、`提取源码声明`、类型链接与注释分段要随接口变化同步适配，尤其不要使原本依赖完整 `「名称」` token 的调用方失效。

豫言构建期高亮器需要同一分类表及上下文状态。可用生成的中文规则数据驱动，或逐项实现并用相同语料差分。保留当前无 parser、无导入依赖、可在损坏源码上工作的特性。它仍负责静态源码树、SSR 包源码和签名保底；生成器本身按仓库要求使用豫言实现。

### 4.2 语义叠加与缓存

编译器已有 `结构操作符、类型操作符、控制操作符、普通操作符、内建类型、内建函数、内建常量、绑定标识符、引用标识符、数值、字符串、注释、结构终止符` 13 类。保留这些作为语义层，建立明确的到统一类别的映射。包服务 JSON 的字符偏移转换、源码版本校验和范围校验集中在一个适配器，不散落在页面组件中。

缓存键至少包含源码摘要、grammar 摘要及语义标记版本。编辑后立即用本地词法层显示；异步语义标记只在版本仍匹配时合并。旧包或语义生成失败时使用同一词法层。云端只读 Monaco 可维持原生 TextMate；未来若接入语义 token，使用同一覆盖约束。

### 4.3 主题统一

先把类别映射统一，再做视觉统一。以 `代码浏览器.css` 中现有的 `--structure`、`--type`、`--control`、`--operator`、`--builtin`、`--string`、`--number`、`--comment` 为浅色主题基准，补 `--escape`、`--builtin-type`、`--builtin-constant`、`--label`、`--binder`、`--punctuation` 等明确变量；云工作台和包文档页引用同一主题表，避免局部选择器覆盖成另一个配色体系。Monaco 的暗色主题只要求同类别的视觉层级一致，颜色按暗背景单独定标。对正文、注释、字符串、关键词分别检查对比度；不能仅靠颜色区分绑定与引用，必要时用字重，但避免大量粗体干扰阅读。

## 五、测试与验收

1. **黄金语料**：复用 `yuyan-vscode/test/grammar.test.js` 的每个场景，另取真实标准库、编译器、旧包、未完成编辑、极长行及混合 Unicode 语料。记录原文、每段 `[start,end,kind]`、所在行及必要的 scope 栈。样例至少覆盖嵌套跨行注释、字符串转义、引号内表达式、声明中的 `者/也`、递归函数类型、全部内建细分、数字名称、标签、词界、`。/；`、CRLF 与补充平面字符。
2. **差分测试**：TextMate/Oniguruma 是词法对照；云 JS、豫言构建期与包 SSR 的同一输入必须得到相同的字符到类别映射。允许相邻同类 token 的切分不同，不允许任一字符类别不同。语义层另以合法标记验证覆盖，以过期、重叠、越界、未知类别标记验证词法回退。
3. **调用方回归**：限定名称链不得从注释和字符串取伪引用；声明提取仍能识别完整名称和结束符；文档链接不能误包住字符串；源码 HTML 的纯文本内容须逐字符等于输入，特殊字符不可变成 HTML。覆盖工作台、包静态页、包动态页、悬浮签名、静态源码树和 Monaco 页面。
4. **视觉验收**：同一短样本并排截取浅色各入口及 Monaco 暗色；逐类检查颜色和字重，检查选区、链接、行号、宽屏和窄屏。语义暂不可用时与词法完成态不能整页失色。
5. **性能门槛**：建立当前入口的 100 KiB、1 MiB 文件基线，再设回归阈值；词法总耗时随输入规模近似线性，增量编辑仅重算受影响行及后继状态直到稳定。超过页面上限时仍保持安全纯文本与可读行号，不冻结主线程。具体毫秒预算以基线和目标设备实测确定。

## 六、实施次序与完成定义

**第一批：先锁契约。** 整理 grammar 与编译器数字规则的差异，制定类别映射和黄金语料；给 grammar 镜像加摘要校验。此时不改配色。

**第二批：统一词法。** 抽出共用 JS 入口，替换工作台和包浏览器侧副本；升级豫言构建期高亮器；修复所有分词调用方；运行差分及页面回归。只有全字符类别一致才结束本批。

**第三批：叠加语义与主题。** 实现有版本约束的语义适配和安全回退；统一浅色 CSS token，校准 Monaco 暗色；做截图与可访问性验收。

完成标准：同一源码在所有入口的词法类别逐字符一致；合法语义标记只增加允许的细分；缺失、损坏或过期语义标记不会导致无色源码；输入原文可逐字符恢复；镜像 grammar 不会无声分叉；新增高亮规则必须附一条黄金语料及相应跨入口差分测试。

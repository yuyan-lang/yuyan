# 豫言操作系统统一接口方案

状态：架构与研究背景稿，2026-09-25。公开签名以仓库根目录的[豫言操作系统接口规范树](../豫言操作系统接口/总纲.汉语.md)为准，规则另见[接口规范说明](豫言操作系统接口规范.汉语.md)；本篇不作为宿主实现代码的规范来源。已确认：统一豫言接口以豫言类型系统为规范，WasmGC 是向下投影；接口复用现有豫言语法，版本与能力组由 `。包。豫` 声明；依赖的能力组一律必需。macOS、Linux 要并行提供 JS＋Node 宿主与基于现有 LLVM 原生编译路线和豫言原生运行时发展的宿主，两者都是正式目标，均须运行豫言 WasmGC 应用；原生宿主还须能装载符合其支持特性集的第三方标准模块。现有 Wasmtime C 宿主不列为第三条桌面产品路线。原生 WasmGC 执行能力、桌面能力和双路线发行尚未完成。实施时须与[系统编程语法方案](系统编程语法方案.汉语.md)及[网页汇编接口](语言技术规范/网页汇编接口.汉语.md)对齐。

## 一、目标与边界

豫言操作系统是一套版本化的程序装载、执行与系统能力契约。浏览器和 CF Worker 已承载豫言应用；macOS、Linux 各有两套应并行发展的宿主：JS＋Node/V8 宿主，以及由豫言原生运行时和 LLVM 原生后端发展出的宿主。两者分别装载同一豫言 WasmGC 程序，按各自实现提供相同版本的豫言能力接口，并各自形成可直接运行的发行包。LLVM 后端目前只把豫言程序编译为本机码；它尚不能装载标准 WasmGC。原生宿主必须另建通用 WasmGC 验证、实例化、执行或编译链，才能达到本目标。Windows 可在相同契约上后续接入；裸机/QEMU 是独立的硬件宿主路线。对于依赖豫言接口的程序，目标环境具备所需接口包、Wasm 特性和授权时，应取得相同的接口语义。第三方标准 WasmGC 模块不必依赖豫言接口；其所需导入由宿主明确提供或在装载时拒绝。

区分四层：

1. **豫言类型系统与高层统一 ANF**：豫言类型决定接口语义；ANF 表达程序及其效果，是编译器内部表示。
2. **`。接口。豫`**：复用豫言现有声明和类型语法，声明系统函数、类型、错误、资源与能力；所属包的 `。包。豫` 声明版本。
3. **中文 Wasm IR 与标准 `.wasm`**：接口声明降为经过验证的导入、导出及元数据，字节由豫言编码器直接生成。中文 IR 对应标准 Wasm 模块语义；WAT 不参与规范链路。
4. **两套桌面宿主与各自执行引擎**：macOS、Linux 的 JS＋Node 宿主使用 V8 运行 WasmGC；原生宿主须以项目自己的标准 WasmGC 执行链装载模块，可用 LLVM 把已验证的模块降为本机码，也可先用自研解释器。两套宿主分别连接豫言接口及桌面系统能力，并承担授权、调度与资源清理。原生宿主按真实导入处理标准模块，不以豫言编译器产物为唯一合法输入。

这里有两个需要分别检查的边界：应用依赖的豫言接口包属于豫言程序契约；Wasm 模块的标准指令语义及导入／导出类型属于通用执行契约。豫言操作系统服务层调用浏览器、Worker、Node.js、桌面系统或硬件的方式属于宿主适配边界。目标宿主的原始 API 不直接变成豫言接口的公开契约。此分层吸收 Inferno 的多宿主执行环境与 Drawbridge 的窄宿主接口经验，见第七节。

接口版本不能替代 Wasm 特性检查。能装载某个核心 Wasm 子集，也不能据此承诺能执行普通豫言 WasmGC 程序。

现有 `--target=llvm` 把豫言编为本机机器码，并连接[原生豫言运行时](../豫言操作系统/宿主/原生/运行时/入口.c)；这一链路不依赖 Wasmtime。该运行时的垃圾回收和系统操作可供新宿主复用，但 LLVM 编译豫言源码并不等于已能运行任意标准 WasmGC。现有裸机客体执行器已实现若干 WasmGC 子集；其验证与执行组件可在语义和平台依赖核对后复用，不能把子集验收视为桌面通用宿主已经完成。

仓库另有[Wasmtime 编译宿主工具](../工具/网页汇编宿主/说明.汉语.md)，通过 Wasmtime C API 运行编译器 Wasm、组装 WAT 并供部分测试使用。它与上述 LLVM 原生运行时是不同代码路径，不作为第三套桌面应用宿主。现有构建器仍调用其 `--组装`，所以源码删除须待组装与测试调用改接替代工具后进行；从产品方案移除它不等于现有构建依赖已消失。

## 二、接口源文件应描述什么

每个接口文件含：资源类型、函数签名、错误集合、能力需求、同步/异步性质及引用所有权规则。所属 `。包。豫` 提供稳定包名和版本；应用包再声明所需接口与入口导出。文件名可以是 `控制台。接口。豫`，其中中文名供豫言源码使用；二进制导入名称须由包身份与接口声明规范化生成。

接口先用豫言类型表达字节串、记录、变体、资源和结果。资源的取得、使用、关闭及授权由接口语义规定；这些语义不由 `eqref` 的具体布局决定。常规接口错误用类型化结果。异步调用需说明完成与取消，不能把浏览器/Worker 的异步能力伪装为通用阻塞调用。

下列仅是**候选源码形状**，展示意图；语法尚未进入解析器，也不是可直接编译的示例：

```text
「接口」者『豫言操作系统/输出流』也。
「能力」者『输出』也。
「输出流」立「不透明资源」也。
「写」乃化「输出流」而化「字节视图」而「结果」于「无符号三十二位」于「系统错误」也。
```

上例的包名与版本由同目录的 `。包。豫` 提供。实际落地时复用现有豫言解析器和类型检查器；接口文件只接受可静态确定的声明，不求值有副作用的定义。规范化后的类型与函数签名作为生成器、宿主与一致性测试的共同输入。

## 三、豫言接口与目标投影

`。接口。豫` 中的豫言类型与操作是豫言操作系统接口的源级规范。编译器按目标把它们投影为 WasmGC 的值、引用、导入和导出；现有 `yuyan:gc-host/v1.call` 是豫言程序可复用的桥接机制，属于可选的宿主导入，不是所有 WasmGC 模块必备的标准接口。第三方模块按其真实导入名称与 Wasm 函数类型链接，不能因缺少豫言元数据或该桥接导入而拒绝本可独立运行的标准模块。投影细节在编译器与执行器实现时验证和版本化，不成为当前接口语义设计的前置决策。

编译器从同一 `。接口。豫` 生成豫言调用封装、标准 Wasm 导入/导出、宿主实现签名和一致性样例。接口可附带 `yuyan.os` 自定义段，记录包版本、所需 Wasm 特性和能力请求；装载器仍须核对真实导入、导出及类型。自定义段不授予权限，也不替代标准 Wasm 验证。

## 四、能力、装载与应用入口

能力组由包定义：一个版本化的 `。包。豫` 组织若干 `。接口。豫`，如 `日志`、`时钟`、`文件目录`、`网络`、`窗口`、`画面`、`输入事件`、`字体`、`剪贴板` 等。**应用依赖的能力包一律必需。**例如仅桌面发行包依赖窗口包；另一发行包不依赖它，即可在无窗口的宿主上运行。构建器求出传递依赖闭包，装载器核对实际导入与获授资源；缺少接口、未获授权和暂时不可用应区别报错。某个平台独有且无法定义跨平台语义的能力留在平台命名空间。

WASI 社区用独立 WIT 接口及不同的 `world` 组合程序环境，且区分链接时提供的接口与运行时传递的资源能力。豫言采用按包组合能力组的思路，继续使用自己的接口语法；第一版不加入运行时可选组查询。

推荐装载顺序：读取字节并限额 → 验证标准 Wasm 与特性集 → 读取可选接口元数据 → 核对真实导入及类型，对豫言接口另核版本与签名 → 决定能力并建立资源表 → 实例化 → 调用约定的入口 → 回收句柄、内存及任务。装载错误分别指出缺少指令特性、导入提供者、接口版本、能力、入口或资源配额。豫言应用入口按 `命令行`、`图形应用`、`HTTP 处理器` 等程序形态声明；通用模块按其导出及启动约定调用，不强加豫言 `_start`。

原生桌面宿主须区分两种装载路径。通用路径接受任意来源、符合宿主已声明标准 Wasm／WasmGC 特性集的模块，验证标准字节码、导入导出和实例化语义；不要求 `yuyan.os` 自定义段、豫言包身份或 `yuyan:gc-host/v1.call`。模块请求的导入须有名称与类型匹配的提供者，未提供者明确装载失败，不自动获得文件、网络或窗口权限。豫言路径另核对接口包身份、版本、签名和授权，再连接豫言桥。两条路径共享标准执行引擎，不能因豫言私有表示而放宽或收紧标准验证规则。裸机执行器要装载普通豫言程序，还须覆盖编译器实际生成的 Wasm 特性；各目标验收分别记录。

## 五、宿主与发行

同一豫言程序由发行构建器选目标与宿主，收集所依赖的能力包及相应适配器，再生成可运行产物。macOS、Linux 均须提供下列两种桌面宿主产物：

| 目标 | 发行产物 |
| --- | --- |
| 浏览器 | 程序 `.wasm`、豫言操作系统浏览器适配器、启动脚本与网页资源 |
| CF Worker | 程序 `.wasm`、豫言操作系统云工适配器与 Worker 入口 |
| macOS、Linux 的 JS＋Node 宿主 | 程序 `.wasm`、豫言操作系统 JS 适配器、Node/V8 与启动器；作为正式桌面发行路线 |
| macOS、Linux 的原生宿主 | 由 LLVM 原生后端编译宿主，连接豫言原生运行时及自研 WasmGC 装载／执行链；连同程序 `.wasm` 发行，不携带 Node/V8 或 Wasmtime |
| Windows 桌面宿主（后续） | 分别接入 JS＋Node 与原生宿主，复用相同的豫言接口和装载契约 |

豫言应用发行包附清单，记录应用包版本、能力包闭包、Wasm 特性、宿主适配器版本、入口与产物摘要；启动时检查清单与实际 `.wasm` 导入。通用第三方模块只要求标准验证、明确的特性和导入提供者，不凭缺少豫言发行清单拒绝；宿主仍可为具体发行包记录产物摘要与资源授权。只收集所需能力包，不因宿主拥有更多 API 就把它们全部暴露给程序。这是从 MirageOS 的按依赖构成单用途映像和 Drawbridge 的窄宿主边界导出的工程规则。

两种桌面包的共同目标是用户解压后直接运行：JS＋Node 包随附所需 Node/V8，原生包随附自研宿主与执行链，无须用户预装。已有[双宿主构建器](../工具/双宿主构建/说明.汉语.md)可生成浏览器和云工产物；Node/V8 宿主已有自举用途，LLVM 原生程序与运行时也已可运行豫言代码。原生通用 WasmGC 装载、桌面图形能力、Linux 验收及双路线发行包仍待完成。现有 Wasmtime 工具可继续供构建和对照使用，但不进入原生桌面应用发行包。两套宿主的启动器和底层系统调用可以不同，豫言应用所依赖的接口语义应一致。

## 六、与现有工程的关系和实施次序

现有[中文网页汇编](../工具/中文网页汇编/说明.汉语.md)已提供豫言编写的模块结构、中文文本、标准二进制编解码与整数核心验证，但仍是 Wasm 子集；现有[裸机 Shell](../工具/豫言裸机/命令壳程序运行.汉语.md)能从磁盘运行受支持的标准 `.wasm` 子任务，且客体执行器正在逐项补充 WasmGC，尚不能完整运行普通豫言模块或任意第三方 WasmGC 模块。当前[统一 ANF](统一ANF架构审阅.汉语.md)服务原生与 WasmGC 后端；接口语义树应在它们的边界上被共同使用，而不把高层 ANF 的内部编号暴露给外部模块。

1. **确立桌面双宿主**：分别列出 macOS、Linux 的 JS＋Node 与 LLVM 原生宿主所需 Wasm 特性、豫言能力包、资源上限和应用生命周期，给同一豫言应用提供两种发行目标。明确现有 LLVM 原生编译只接受豫言源码，不能把原生运行时直接当作 WasmGC 执行器。
2. **建立原生通用执行链**：复用可移植的客体类型检查、指令验证与执行组件，补齐标准 WasmGC 所需语义；如以 LLVM 生成本机码，须先验证输入模块并实现 WasmGC 对象、根、回收、陷阱及资源寿命。按真实导入名称和类型连接宿主提供者，核对导出与入口，建立隔离的实例和资源表。先以不依赖豫言桥的第三方标准模块验收；未提供的导入与未获授权的资源分别报告。按需要另实现 WASI 或其他具名导入包，不能把它们暗称为 WasmGC 标准自带的系统接口。
3. **接通豫言接口投影**：用现有豫言语法定义 `。接口。豫` 的声明子集，生成客体封装、导入／导出与宿主桩；中文 Wasm IR 直接编码 `.wasm`，对实际二进制作反向核验。豫言桥作为通用执行器上的可选适配器。
4. **双宿主与第三方模块验收**：同一豫言 WasmGC 应用分别在 macOS、Linux 的 JS＋Node 和 LLVM 原生宿主运行，核对接口语义、授权及版本错误；原生宿主另用至少一种非豫言工具链产出的真实 WasmGC 模块验证通用装载，以独立标准引擎对照有效模块结果与无效模块的拒绝。单项指令通过不等于完整模块可运行。
5. **双路线发行与图形应用**：macOS、Linux 分别交付 JS＋Node 包和原生包，均可直接启动。为公共显示包在两套宿主上接窗口、RGBA 像素提交和键鼠输入，以同一豫言程序做可交互图形样例；再扩展字体、音频、GPU、流和多窗口等能力。Windows 与裸机/QEMU 分别接入相同契约，按各自宿主能力验收。
6. **执行链持续完善**：原生宿主以标准有效和无效模块做差分验收，逐步扩展声明支持的特性集、性能和资源管理；可把现有 Wasmtime 工具或 Node/V8 用作独立结果对照，但原生桌面包不依赖 Wasmtime。此工作不取代 JS＋Node 宿主。
7. **清退 Wasmtime 编译宿主工具**：先替换 `--组装` 的构建调用及依赖该工具的测试、自举命令，核对浏览器、云工和 Node 产物仍可构建；随后移除其专属源码、构建目标与外部库依赖。此项只涉及工具清退，不删 LLVM 原生运行时，也不改变两套正式桌面宿主的目标。本次仅修订方案，不执行清退。

接口层的首个桌面里程碑是由 `。接口。豫` 生成系统调用，令同一豫言 WasmGC 样例分别在 macOS、Linux 的 JS＋Node 和 LLVM 原生宿主运行，验证字节输出、单调时钟及错误分类。原生宿主另须独立装载一个不含豫言元数据和豫言桥、由非豫言工具链生成的 WasmGC 模块，验证执行、回收与导入类型检查；发行产物不链接 Wasmtime。浏览器与 CF Worker 继续参与接口一致性验收。

## 七、相关研究与对本方案的约束

下列是相近的原始论文及设计规范；没有一篇直接给出“豫言类型系统＋`。接口。豫`＋JS／原生双桌面宿主”的现成实现。表中最后一列是据论文作出的**本方案推论**，并非论文作者对豫言的评价。

| 工作 | 已证明或提出的结构 | 对豫言的推论 |
| --- | --- | --- |
| [Inferno 操作系统，Bell Labs Technical Journal 1997](https://www.inferno-os.org/inferno/papers/bltj.html) | Limbo 模块有明确接口；Dis 虚拟机随系统在裸机运行，也可在 Unix、Windows 宿主运行；资源经统一环境呈现 | 这是“同一语言系统既是原生 OS 又是宿主内运行环境”的最接近先例。豫言可沿用多宿主思路，以 Wasm 作为执行边界、以接口包组织能力 |
| [Drawbridge，ASPLOS 2011](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/asplos2011-drawbridge.pdf) | 应用随库操作系统运行，库操作系统通过窄 ABI 和平台适配层使用宿主服务 | 将豫言操作系统的公开接口与私有宿主适配明确分开；浏览器、Worker、Node.js 的原始 API 不直接进入应用契约 |

| [WebAssembly，PLDI 2017](https://pldi17.sigplan.org/details/pldi-2017-papers/48/Bringing-the-Web-up-to-Speed-with-WebAssembly) | 可验证、平台独立的低层二进制执行边界，与宿主环境交互 | 保持标准 `.wasm` 验证与特性检查；豫言接口语义在其上层，中文 Wasm IR 向标准字节投影 |
| [WARDuino，MPLR 2019](https://science.beardhatcode.be/papers/2019-WARDuino-MPLR.pdf) | 嵌入式 Wasm 虚拟机用导入模块暴露硬件能力，并在装载时核对导入类型 | 后续裸机宿主按接口包实现设备能力；装载阶段核对导入和宿主提供的签名 |
| [WIT 绑定生成器缺陷研究，ASE 2025](https://conf.researchr.org/details/ase-2025/ase-2025-papers/124/Finding-Bugs-in-WebAssembly-Interface-Type-Binding-Generators) | 生成的接口绑定可能出现运行时错误；论文用不同语言实现的差分测试发现缺陷 | `。接口。豫` 生成器的验收须覆盖值、错误和跨宿主行为，不能仅凭生成成功或类型检查通过 |

截至 2026 年 9 月，项目的后续发展也应影响取舍：[Inferno](https://inferno-os.org/inferno/downloads.html) 仍提供完整源码和宿主/原生发行材料，但官网所列可下载快照更新于 2015 年；[Drawbridge](https://www.microsoft.com/en-us/research/project/drawbridge/) 被微软明确标为已结束的研究原型；[MirageOS](https://github.com/mirage/mirage/blob/main/CHANGES.md) 仍维护，并在 2026 年发布 4.11 系列；[WARDuino](https://github.com/TOPLLab/WARDuino) 仍以未到 1.0 的研究项目自述；[WebAssembly](https://www.w3.org/2026/06/webassembly-wg.html) 则继续由 W3C 工作组标准化。由此推论：豫言应把可独立验证的标准执行边界和接口包优先做实；多宿主完整系统的长期维护、平台能力覆盖与发行，须用真实应用持续验收，不能仅凭研究原型的成功推定完成。

[WASI 能力设计](https://github.com/WebAssembly/WASI/blob/main/docs/Capabilities.md)与 [WIT 的接口和 world](https://github.com/WebAssembly/component-model/blob/main/design/mvp/WIT.md)是标准化工作的直接参照，性质不同于上表的研究论文。豫言继续使用自己的源级接口语言与包模型。

## 八、待定细节

- 缺少能力包、拒绝授权、暂时不可用三类结果及其报告位置。
- 已有标准库协作式异步、浏览器与 Worker 的 JSPI 宿主实现；仍需对齐接口层的完成、取消、重入及跨事件资源寿命，不重复设计异步任务。
- `。包。豫` 的版本兼容规则；程序入口沿用现有包和宿主入口机制，再统一装载时的识别与检查。
- 原生 WasmGC 执行链的标准特性分期、解释执行与 LLVM 提前编译的取舍、跨平台内存及回收实现；第三方模块导入提供者的注册、权限和版本边界。
- macOS、Linux 两套宿主各自的发行布局、窗口主循环与异步调度，以及相同豫言应用的双宿主一致性验收；Windows 后续适配。

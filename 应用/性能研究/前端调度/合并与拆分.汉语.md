# 前端任务合并与拆分实测

2026-09-09，Apple M5 Pro 本机，18 个工作进程。执行编译任务的是同一个 native 编译器 `yy调度对照编译器`，输入均为完整的豫言编译器源码及同一包上下文。以下比较输出后端的构建时间，不是 V8／Wasmtime 执行编译器的速度比较。

## 结果

| 输出后端 | 前端模式 | 墙钟秒 | 用户态 CPU 秒 | 系统态 CPU 秒 |
|---|---|---:|---:|---:|
| WasmGC／统一 ANF | 合并，第 1 次 | 23.17 | 81.31 | 9.97 |
| WasmGC／统一 ANF | 拆分，第 1 次 | 18.93 | 91.98 | 20.23 |
| WasmGC／统一 ANF | 拆分，第 2 次 | 18.16 | 86.24 | 20.93 |
| WasmGC／统一 ANF | 合并，第 2 次 | 22.35 | 73.38 | 11.33 |
| native／shadow | 合并 | 73.65 | 123.46 | 12.75 |
| native／shadow | 拆分 | 68.73 | 131.91 | 24.31 |

WasmGC 合并平均 **22.76 秒**，拆分平均 **18.55 秒**，拆分缩短约 **18.5%**。shadow 完整编译缩短约 **6.7%**，其中包含最终 clang 编译与链接；这组各只有一次测量。所有计时按表中顺序单独执行，本任务没有同时启动其他验证构建。

拆分确实增加 CPU 开销：WasmGC 合并平均累计 CPU 约 88.00 秒，拆分约 109.69 秒。但墙钟时间下降，说明在当前任务中增加并行机会的收益超过进程启动和阶段加载成本。不能据此保证其他并发数、项目或以 Wasm 实例执行各工作进程时也有同样结果。

两种模式都已经使用新的阶段优先级，所以这些百分比衡量的是**相同优先级策略下的任务粒度差异**，没有单独测量优先级修改本身的加速比。

## 管线与等待关系

前端实际使用相同的函数：解析、类型检查与擦除、跨模块优化、闭包转换。合并模式每模块一个进程，依赖模块必须完成整个前端，当前模块才能开始。拆分模式让当前模块的较早阶段在依赖完成对应阶段后便可推进，并与其他模块的后续工作交错执行。

此次有 182 个模块。合并模式为 `182 × 2 + 1 = 365` 个工作任务；拆分模式为 `182 × 5 + 1 = 911` 个工作任务，分别是依赖分析、解析、类型检查与擦除、跨模块优化、闭包转换，以及最后一次整模块生成。没有人为给新后端增加旧 ANF／CPS 或逐模块机器码生成。

依据这组结果，`wasmgc`、`wasmgc-anf`、`shadow` 的并行构建默认改为拆分，与旧 native 共用前端阶段图；保留 `--frontend-tasks=combined` 作显式对照。后端算法、阶段导出设置和最终依赖拓扑排序没有因此更换。

## 优先级实现

构建任务增加显式整数优先级，编译任务以阶段序号赋值。每次收取已完成任务、处理动态依赖后，对就绪任务按优先级稳定分组，再派发：

```text
依赖分析 → 解析 → 类型检查与擦除 → 跨模块优化
        → 闭包转换 → ANF → 代码生成
```

同优先级保持加入顺序。策略不抢占已经运行的任务，也不为尚未就绪的高优先级任务空留槽位。最终生成仍在所有模块成功之后执行。原 `新构建任务` 接口将优先级设为零，保留旧调用方同级按加入顺序执行的行为；需要优先级的调用方使用 `新优先构建任务`。

## 正确性与复现边界

- 同一模式两轮输出的 Wasm 分别逐字节一致。
- 跨模式有 264 条模式匹配诊断字符串编号不同，16 条相应字节数组初始化长度不同；其余 WAT 一致。这来自旧前端跨阶段临时名称计数的进程边界，属于可观察的诊断文字差异，尚未统一。
- 两种 Wasm 编译器各自串行完整编译当前编译器，生成的下一代 Wasm 字节一致，SHA-256 为 `5ff87ead0d8a80e85242c5224e817a20502faa5e797e94afa3453db98b6e98af`。这两次为验证并行运行，其耗时不计入性能表。
- shadow 两个产物的帮助输出相同，生成 C 去掉字符串与对应字符串长度编码后完全一致。
- 调度器专项测试实际执行单槽动态图，覆盖后加入的高优先级任务、同级顺序、被阻塞的高优先级任务，以及现有并发上限、失败停派、在途收拢和依赖循环检查。
- 最终默认值修改后，隔离缓存重跑的 `yy3_bs`、`yy4_bs` 字节一致，SHA-256 为 `d4407e6574d842a088228e6713def01ff6365acc2d60d43bd8107a656ac15228`，随后并行类型检查通过。
- 不传粒度选项的完整 WasmGC 编译通过，实际启动依赖、解析、类型检查与擦除、跨模块优化、闭包转换各 182 次，最终生成 1 次；确认默认走拆分管线。

性能表的源码指纹保存在 `计时源码指纹.json`，命令、二进制哈希与最终验证记录保存在 `验证摘要.json`。计时结束后，编译器源码只调整默认粒度及其注释；实测命令显式指定粒度。旧 stable 在当前 worktree 仍报“文件夹未找到”，诊断重跑同样失败，因此使用可信现有编译器通过豫构准备 yy2，再进行后续自举验证。修改默认值后的一次增量固定点比较失败，最终验证使用 touch 种子隔离旧缓存后重跑，不把失败的增量比较记为通过。

复测时使用支持新选项的同一编译器，逐条执行：

```sh
./yy豫构 构建 豫言编译器 --编译器 ./yy3_bs --输出 yy前端合并.wasm -j 18 -- --target=wasmgc-anf --frontend-tasks=combined --do-not-load-cache -c
./yy豫构 构建 豫言编译器 --编译器 ./yy3_bs --输出 yy前端拆分.wasm -j 18 -- --target=wasmgc-anf --frontend-tasks=split --do-not-load-cache -c
```

上述便捷命令包含豫构包准备；本表直接调用编译器并传入预先准备的包上下文，计时包含前端、默认阶段导出、后端及组装／链接。`--do-not-load-cache` 强制重算豫言阶段，不清空操作系统文件缓存，也不重建已经准备好的原生运行库。

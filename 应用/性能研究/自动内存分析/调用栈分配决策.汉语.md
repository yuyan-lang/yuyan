# 自动调用栈分配的决策点

本轮三个原型均未加入编译器：条件选择交换热轮 87.873 ms 对基线 44.648；增加数组长度守卫 46.556 对 45.089；显式内联四步 44.611，对同组基线 44.580、内联两步 44.889。均为五进程各六轮、校验和 6000002。没有收益依据，也不能由此证明 GC 路径已到极限。

下一条值得探索的路径是自动为生命周期受限、不会逃逸且只含原生数值的对象选择线性内存调用栈。公开函数签名、源码类型及默认 GC 后备保留，不缓存特定数组，不允许 GC 引用以裸地址混入线性内存。候选容量、指针算术、别名、边界与生命周期必须经过证明；证明不足走原 GC 路径。

需要用户决定的实际成本：调用结束只能恢复逻辑栈顶，已增长的线性内存容量会保留到实例结束，形成容量高水位。这与不缓存数组是不同维度，可能仍违背此前“不用私有缓冲”的要求。建议仅授权探索一个每实例最多 64 MiB 的通用调用栈，超过预算用 GC；这个预算可调整，尚未采用。

当前没有证明此方案能达到 C。异常、陷阱、递归、重入、容量失败后的清理以及公开 ABI 不变，都是实现前必须解决和验证的条件；不能因获得探索授权而跳过。未获决定前不实施该存储路径。仍可继续研究既有 GC 生成。

规范参考：https://webassembly.github.io/spec/core/bikeshed/ 。核心内存指令提供 size/grow 等操作，没有收缩内存指令；逻辑释放不能等同于归还实例内存容量。

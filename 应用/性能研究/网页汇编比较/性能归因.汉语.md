# Wasm 自举性能归因

完整自举实验已成功：内联检查加运行时 LTO 把 369.11 秒降至 **244.55 秒（减少 33.7%）**，仍为原生 62.72 秒参照的 **3.90 倍**。产物所有非 name 节均与原版一致，包括可执行代码、数据及导入；name 节不同来自输出文件名。完整原始日志与比较见《归因记录/完整自举结果.json》。

此处仅优化正在执行的实验编译器；它生成的后继仍使用源码中的原始检查生成规则与运行时构建参数，不会自动继承实验优化。全自举为单次比较，共享准备好的输入目录并使用 --do-not-load-cache 强制执行，不是清空操作系统缓存的测量。

2026-09-08。本次通过同一编译器的隔离副本做对照，生产编译器和运行时源码没有改变。当前不能承诺全面迁移后无性能损失；已找出能显著改善的实现问题，但修复这些问题后仍有差距。

## 已确认的主要开销

**栈检查被当成了通用、可能修改堆状态的外部调用。** 在本次编译器 LLVM IR 中有 39,152 处静态调用。每处除了边界判断，还保存当前栈／堆指针到全局变量，调用后再读取堆指针。Wasm ABI 又把 i128 参数拆成两个 i64，返回值通过返回缓冲区传递。检查函数还调用两个本来只是类型截断的值转换函数。这些操作发生在频繁的调用和续延路径上。

定位源码：`库/编译器核心/编译步骤/代码生成准备变换/代码生成准备变换。豫` 的“检查栈空间后”，以及 `库/编译器核心/编译步骤/代码生成/低级虚拟机/直接代码生成。豫` 的“解析后外部调用节点无类型”分支。栈检查不分配、不移动堆，其成功路径不需要通用外部调用的全部成本。

**Wasm 运行时没有使用原生已经启用的跨文件优化。** 本机原生运行时采用 `-O3 -flto`，Wasm 是 `-O2` 且无 LTO。隔离实验只给 Wasm 运行时加 `-flto`，保持 `-O2`，已经出现收益；这不是简单的优化等级对比。没有给全部编译器对象启用全程序 LTO。

## 独立 worker 实测

每项预热一次，正式三次，表中为墙钟中位数。各组按配置连续测量，没有随机交错；原始 CSV 和范围见《归因记录/》。

| 配置 | 字符串术类型检查 | 抽象语法树总集代码生成 |
| --- | ---: | ---: |
| 原生，256 MiB 初始堆 | 0.348 秒 | 1.398 秒 |
| 当前 Wasm，64 MiB 初始堆 | 2.842 秒 | 8.009 秒 |
| Wasm，256 MiB 初始堆 | 2.868 秒 | 未测 |
| Wasm，仅内联检查 | 1.501 秒 | 5.413 秒 |
| Wasm，仅运行时 LTO | 2.003 秒 | 未测 |
| Wasm，内联检查加运行时 LTO | **1.416 秒** | **4.699 秒** |
| 诊断副本，删除检查调用 | 1.309 秒 | 4.902 秒 |

保留检查的两项优化组合，分别降低约 50.2% 和 41.3% 耗时，但仍为原生约 4.06 倍、3.36 倍。删除检查只用于估计开销，不是迁移方案；组合优化甚至能在代码生成用例中超过“只删除检查但没有 LTO”的副本。

内联实验在每个 LLVM 模块添加 `alwaysinline` 检查：验证地址上下界、16 字节对齐及所需槽数，失败时仍调用原来的错误路径。实验副本尚不等于正式编译器补丁，不能跳过完整安全回归就用于发布。

## 已缩小的范围

- **不是 AOT 编译时间主导。** 原有自举使用预编译模块，单次 AOT 准备仅 0.40 秒，未计入 369.11 秒。
- **不是启动开销单独造成。** 帮助命令启动中位数原生 1.881 毫秒、Wasm 39.958 毫秒。上千个 worker 的启动值得优化，但单个字符串 worker 扣除启动后仍有数倍差距。不能直接把所有启动时间相加当成并行自举的墙钟占比。
- **不是简单增加初始堆就能解决。** 字符串术 GC 从 73 次降至 18 次，实际耗时没有改善。这只说明加堆无效，不能据此否认 GC 复制、分配器清零或线性内存的成本。
- **不是 LLVM 编译／链接独自造成。** 类型检查 worker 不执行最终 LLVM 代码生成，仍有明显差距。总集代码生成和完整自举则含本地 LLVM，不能全部当作 guest 执行时间。
- **不能归咎于 Component Model。** 本次运行的是 WASI P1 core module 加自定义构建宿主，还没有 WIT/Canonical ABI 组件边界。
- **不能默认每次 Wasm 内存访问都在软件做边界判断。** Wasmtime 默认利用虚拟内存保护减少显式边界检查；我们的豫言栈检查是另外一层。见 [Wasmtime 执行性能说明](https://docs.wasmtime.dev/examples-fast-execution.html) 与 [安全机制](https://docs.wasmtime.dev/security.html)。

## 剩余差距与优先级

剩余差距尚未获得完整 CPU 采样归因，不给虚构的百分比。源码上应继续重点查：16 字节通用值与 i128 调用约定、续延形式造成的频繁间接尾调用、反复反序列化和分配、GC 复制与清零、WASI 文件读取。i128 在 Wasm C ABI 中拆分传递确有规定，但“ABI 占剩余多少时间”尚未测出；参见 [WebAssembly C ABI](https://github.com/WebAssembly/tool-conventions/blob/main/BasicCABI.md)。原生也使用 16 字节值，不能把全部装箱成本算成 Wasm 独有。

建议顺序：先把栈检查做成专用生成规则并验证全部失败边界；随后对齐运行时 LTO 与优化配置；再对剩余热点做采样，决定是否需要改变 Wasm 的值表示和调用约定；最后评估常驻 worker／实例复用。当前只能保证自举语义已验证，不能保证性能无损。

全面切换应以同源码、同机器、同并发、明确缓存策略和相同安全要求的重复完整自举为门槛，统计区间不能显示退化，并单独检查峰值内存。不能用局部 worker 的加速幅度替代完整自举成绩，也不能为了达标删除必要检查。

# ANF 直接生成 Wasm GC 的原型

已实现可运行原型：**现有闭包 IR → 现有 ANF → Wasm GC 文本**。生成的模块没有 `memory` 和 `import`。WAT 的解析与引擎机器码编译仍是必要准备步骤。

结论是：这条架构能运行。**尚未支持完整编译器，因此没有直接 GC 后端的自举时间，不能据此批准全面迁移。**

## 已实现的直接路径

《应用/网页汇编/网页汇编直生/入口。豫》读取真实的 `.闭包形式.json`，调用 `处理闭包函数定义` 与 `求值正则变换`，然后直接生成 WAT。没有另造一份手写算法冒充 ANF 输出。

这里必须绕开现有 `求值正则变换/顶层。豫` 的最后一步：那个入口在 ANF 之后还会执行 CPS。普通调用现在映射为 Wasm 调用，尾调用为 `return_call_indirect`。特别处理 `let x = call in x`，否则 ANF 产生的身份绑定会让尾递归退化成普通递归；百万元素数组已验证不会因为该循环耗尽调用栈。

- 小整数使用 i31，大整数使用含 i64 的 GC struct，保留完整有符号 64 位结果。
- 元组、引用数组和闭包环境使用 GC array；函数引用目前是表索引，调用使用 `call_indirect`。
- 代数构造器使用带标签的 GC struct，字段保存在 GC array 中。
- GC 对象由引擎追踪；Wasm globals、locals、参数中的引用由引擎管理。
- 未实现的外部调用、跨模块链接明确拒绝；内部函数最多八个参数。任意异常、call/cc、字符串操作、通用 FFI 和完整标准库尚未支持。

使用的分配原语是标准 [`struct.new`、`array.new`、`array.new_fixed`](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP.md)。

## 开销来源

1. **当前输入是无类型 ANF。** 通用引用表示需要动态解箱、类型转换；超过 i31 的整数还会装箱分配。直接输出 Wasm 并不会自动恢复已经擦除的类型。
2. **构造器布局还很粗糙。** 原型分配“字段数组＋标签 struct”两层对象，树的分配数量、对象头和扫描负担因此增加。这是代码中已确认的实现差异，不是对整段耗时的百分比归因。
3. **闭包和调用仍然通用。** 普通函数指针仍从 GC 环境取出，经整数解箱后走表调用；还没有直接调用识别、闭包消除、类型化函数引用和针对 Wasm 的优化。

更合适的下一版是：保留类型及对象形状信息，让整数局部变量直接为 i64，让具体 ADT 对应直接含字段的 GC struct，让闭包含类型化函数引用；只有需要捕获的续延才显式堆分配。不能把普通 Wasm 调用栈当成完整 call/cc 的实现。

## 验证

24 项执行检查覆盖递归、构造器、零长度数组、超过 i31 的数组求和、负大整数及 i64 最小值，并验证负数和超过 wasm32 的数组长度拒绝。另有未知外部调用及跨模块链接拒绝测试。百万次尾循环成功。生成 WAT 无内存与导入，新版工具重复生成的 WAT 与计时版本逐字节一致。新后端工具单独构建并通过类型检查。

完整原始样本、配置、拒绝用例及摘要在《记录/》，实际生成模块在《生成/》。这些是架构原型测试，**不是编译器自举性能证明**。

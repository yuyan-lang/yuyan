# github 首页载入剖析（2026-10-29，pit-pc）

浏览器 1.0 第三条判据是「github 带脚本能载完，峰值内存两 GB 内」。**结论：载不完**——在 pit-pc（林纳 x86-64、回放、1280×800）上跑到二十五分钟被杀（退出码 124），卡在**布局**，不是脚本循环、也不是内存爆。峰值内存因此**没量到**。原始栈采样在 `豫言数据/网页数据/测速页/结果/github载入采样汇总-1029.txt`（主线程样本 896，采样间隔一秒）。

## 一、能不能载完

不能。两条命令各跑一次，都在限时内不返回：

```
远测.sh 钩深性能基准 --限时 1500 -- ./网页测速。林纳。豫行 量一 github 0     # 25 分钟被杀，退出码 124
远测.sh 钩深性能基准 --采样 1 --限时 900 -- ./网页测速。林纳。豫行 量一 github 0   # 同样不返，采到 896 个样本
```

段表自然也没印出来（段表是载完之后才印的）。所以要答「首屏各段耗时」，只能靠采样反推，见第三节。

## 二、卡的正是布局，且是弹性 + 界格 + 随行排除

栈采样（在栈百分比，前三十）：

| 在栈 | 函数 |
|---|---|
| 79.8% | `遍`（次第） |
| 78.6% | `布局网页块` |
| **77.0%** | `布局网页弹性单行` |
| **77.0%** | `布局网页弹性` |
| 69.6% | `网页界格排项` |
| **68.4%** | `布局网页界格` |
| 60.2% | `布局网页子流` |
| 28.1% | `布局网页随行排除`（浮动排除） |
| 27.9% | `布局网页随行排除一遍` |
| 19.4% | `网页弹性自动下限算` |
| 16.9% | `记弹性下限` |
| 12.5% | `样式取值` |

栈顶（自身）前几名：`str_eq` 6.8%、`index` 4.8%、`簿散自` 4.6%（映射查找）、`样式号值` 3.0%、`槽列抄` 2.7%、`择` 2.7%、`满参递归` 2.6%、`串整桶寻` 2.6%。

读法：整份时间几乎全在 `布局网页弹性` 里，而它的大头是**弹性单行**（77.0%）与**界格排项**（68.4%），随行排除只占 28%。栈顶那几支（字符串比较、按下标取、映射查找、样式取值）说明**布局在反复查样式、反复做列表下标访问**——不是一次性扫一遍，而是每项都重查。

## 三、页脚本：五处抛错，不致命但可能改了布局输入

载入过程中页脚本报五处错（已分别提 **#1443**、**#1444**、**#1445** 三张按根因归并的议题）：

- `environment-…js` 2:19697、`github-elements-…js` 103:8916 —— `TypeError: 类的父类的 prototype 须是对象或 null`
- `behaviors-…js` 2:710、`marketing-essentials-…js` 2:710 —— `TypeError: 对象操作需要有值的接收者`
- `landing-pages-…js` 2:64336 —— `TypeError: 需要构造函数`

这五支脚本没跑完，意味着**页面的类名、内联样式与 DOM 可能与真浏览器不同**（例如脚本本该加上的类没加上、本该删掉的节点还在）。这既可能让布局更难（更多盒、更多样式），也可能是「布局慢」的一部分原因。修归脚本那几路，本报告只记现象。

## 四、峰值内存：量到了，两点三六 GiB 起、三点一一 GiB 封顶

量具加了「载入中每三十秒印一行峰」的开关 `豫言测峰秒`（pit-pc、林纳 x86-64、回放、1280×800）：

```
远测.sh 钩深性能基准 --环境 豫言测峰秒=30 --环境 豫言测速限秒=1500 --限时 1800 -- \
  ./网页测速。林纳。豫行 量 github 1 0
```

跑满二十六分钟、五十二行样本（每行第一个数是距上次印的毫秒，约三十秒一行）。按序号折成时间，峰值曲线是：

| 时刻 | 峰值 | 时刻 | 峰值 |
|---|---|---|---|
| 30 秒 | 2.36 GiB | 480 秒 | 2.91 GiB |
| 60 秒 | 2.38 GiB | 510 秒 | 2.95 GiB |
| 120 秒 | 2.47 GiB | 600 秒 | 2.99 GiB |
| 180 秒 | 2.57 GiB | 690 秒 | 3.05 GiB |
| 240 秒 | 2.64 GiB | 780 秒 | 3.07 GiB |
| 300 秒 | 2.70 GiB | 870 秒 | 3.11 GiB |
| 360 秒 | 2.80 GiB | 900 秒起 | **3.11 GiB 不再涨**（余下十一分钟一条平线） |

要点：

- **判据的第二半直接不成立**：「峰值内存两 GB 内」——第一个样本（载入三十秒）就已经 **2.36 GiB**，全程最高 **3.11 GiB**，是判据上限的一点五倍。
- 曲线**先涨后平**：前十五分钟一路涨到 3.11 GiB，之后十一分钟纹丝不动。说明内存不是泄漏式增长，而是**布局吃到某个稳态规模就停**；卡住的是时间（布局一直算不完），不是内存把它撑爆。
- 与第三节的采样对得上：卡在布局（弹性单行 77%、界格 68%），内存稳态在 3.11 GiB——两件事同一处根因的两个面。
- **判据整体结论**：github 这一条现在是**两条都不满足**——载不完（二十六分钟仍在布局），峰值 3.11 GiB 超过 2 GB。要它转绿，得先把第三节那三条布局提速做掉，再看峰值能不能跟着降到 2 GB 内。

（开关的字段说明：`测速峰` 行第二个数是**距上次印的毫秒**，不是载入开始以来的毫秒；样本序号 × 三十秒才是时刻，上表已按此折算。）

## 四之二、附记：这一栏早前为什么是空的

本报告第一版写「峰值内存没量到」——因为量具原来只在子程交结果后才报峰，github 载不完就什么都没有。第四节的重测靠新加的开关 `豫言测峰秒` 补上了这条曲线，所以那句作废；这里留一条附记说明经过：量具改的是 `测工。豫`（新开关）与 `入口。豫`（`峰侍` 子命令，供 `量一` 用），开关读环境变量走 `豫章` 的「水土」之「问数俗」（严格解析，没设得零、写错报出名字与原值）。

## 五、给渲染测速/增量排版的三条

1. **弹性单行占 77%**：先看 `布局网页弹性单行` 是否对每个子项都重查一遍父容器的可用宽与样式（栈顶 `样式取值` 12.5%、`簿散自` 4.6% 支持这个猜测）。把可用宽、`flex-basis`、`min/max` 在进入单行前算一次，能砍掉大头。
2. **界格排项占 68.4%**：`网页界格排项` 与 `布局网页界格` 一起占了大半，若界格的轨道尺寸对每个项都重算一次，同样是把「轨道」提到循环外的问题。
3. **`index` 4.8% + `str_eq` 6.8%**：布局热路径上有按下标取（`第` 是 O(n)）与字符串比较，属于库层可改的常数因子——用列表前先转成数组、或把字符串比较换成语号比较。

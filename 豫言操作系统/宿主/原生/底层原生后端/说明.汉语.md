# 豫言操作系统底层原生后端

[豫言操作系统底层接口](../../../../豫言操作系统底层接口/总纲.汉语.md)在 macOS／Linux 上的后端。底层模式的 Yuyan 包，编译为标准整数 Wasm 模块（`yy底层原生后端.wasm`），设计上唯一的宿主导入是统一调度点 `底宿主:call(术码, 块址) → 状态码`；由 [底层原生宿主](../底层原生宿主/说明.汉语.md)（C，用 Wasmtime C API）加载并实现这个导入。

## 状态：已打通，端到端自检通过

**结论：这条路线（把底层模式编译成标准 Wasm、配一个用 Wasmtime 的原生宿主）现在跑通了。** 之前挡住它的编译器缺口——底层后端编译出的 Wasm 模块不导出线性内存，导致 Wasmtime 宿主拿不到 guest 内存——已经修好；自检用例端到端跑通，退出码 0，打印 `OK`。

### 修的是什么

- **编译器**：`库/编译器核心/网页汇编核心/存储二进制。豫` 的 `生成内存数据二进制`，在重新拼装导出段（第 7 段）时，如果模块声明了内存（`模` 中的内存列表非空），就在已有导出内容后面追加一条 `("memory", 种类=2, 索引=0)` 的内存导出项——只读旧导出段的 LEB128 计数、加一、原样保留其余字节、再拼上新条目，不解码每一条已有导出。故意不碰共享的 `网页导出` 类型（`模块结构。豫`）和共享的 `生成网页函数二进制`（`二进制生成。豫`）——这两处高级／WasmGC 路径也在用。已用 `库/癸象工具/癸象转义。测试。豫` 在 `--target=wasmgc` 下分别用修复前后的编译器编译，两边都干净通过，确认高级路径未受影响（WasmGC 代码从不声明底层模式的"声明内存"，这条新逻辑对它是纯粹的空操作）。改动后跑过完整自举（`yy_bs_stable`→`yy2_bs`→`yy3_bs`→`yy4_bs`），`yy3_bs` 与 `yy4_bs` 逐字节一致。
- **宿主**：[底层原生宿主](../底层原生宿主/底层原生宿主.c) 的 `术_取初始句柄` 原先直接把句柄硬编码成 3，并不对应任何真正打开的文件描述符；现在改成真的 `open(".", O_RDONLY)`，把拿到的真实 fd 报给 guest。
- **自检**：本包 `入口。豫` 的 `导出：启动` 原先直接把目录句柄硬编码成 `三`，从未调用 `取初始句柄`；现在先调用 `取初始句柄` 拿到真实句柄，后续 `打开`／`删文件` 都用这个句柄，不再假设某个数字恰好可用。

跑法（macOS，已验证；Linux 未在真机上跑过，代码通过 `#ifdef __APPLE__`／`__linux__` 覆盖两边，理论上同样成立）：

```sh

./yy底层原生宿主 yy底层原生后端.wasm   # 打印 hello from native backend 与 OK，退出码 0
```

### 已经做完、可用的部分

- **`术码。豫` + `入口。豫`**：45 个接口函数里，基础（11）、句柄（13）、文件（9）共 33 个已经写出真实的调用侧代码（把参数写进共享的 256 字节 `块`，调用 `底宿主_调用`，读回结果）；终端／网络／进程按裸机后端同样的思路占位，返回不支持。自检用例覆盖时钟／平台／处理器数／标准输出／取初始句柄／文件创建-写-关-开-读-比对-删，端到端跑通。
- **[底层原生宿主](../底层原生宿主/底层原生宿主.c)**：C 程序，Wasmtime 加载模块、`底宿主.call` 的调度实现（对应 33 个术码，真实调用 POSIX：`clock_gettime`、`open/read/write/close`、`openat` 一族等），状态码按 WASI errno 子集映射，`clang -Wall -Wextra` 零警告。

## 设计（供接手时参考）

- **术码**（`术码。豫`）逐个对应接口函数，宿主据此分派到真实的系统调用。
- **块**是 256 字节的共用暂存（地址 0），按接口函数原参数顺序，每参数 4 字节；有 `出` 参数的函数，结果由宿主直接写回 guest 内存对应地址，不经调用的返回值。
- 本包单线程、每次调用都同步完成才返回，共用一块暂存是安全的。
- `取平台` 也经宿主：宿主用 `#ifdef __APPLE__`／`__linux__` 报告自己是哪个平台（3／2），同一份 `.wasm` 两边都能用。

# 持久频道云工适配

`频道。豫` 完全用豫言写成，只用云工薄宿主的通用原语（`库/云工宿主` 的物宿主与物）取 `scheduler`、`AbortController`、`Date`、`crypto`。它实现[持久频道接口规范](../../../豫言操作系统接口/持久频道/规范.汉语.md) 0.1.0：订阅、保序发布、限时等待、取消、关闭与订阅数。

## 实现

- **频道表**：频道表与订阅柄表都是本实例的顶层可变格。薄宿主每个持久对象只有一个实例，同一对象的各个事件靠这两张表互相通信，它们本来就是跨请求共享的状态：作用域与持久对象一致，对象被驱逐即丢失。读写之间没有挂起点，交错的事件不会互相覆盖。频道表只放有活跃订阅的频道（按订阅先后排列），频道没有订阅时即删去。
- **限额**：每实例至多 64 个频道、每频道至多 256 个订阅，超限都抛可捕获的豫言异常（“持久频道数已达上限 64”“持久频道订阅数已达上限 256”）；消息文字至多 65536 字节，不得以字节 0xFF 起首；每个订阅积压（尚未取走的字节）至多 1 MiB。
- **发布**：消息文字原样排进各订阅的待取队列（前段按到达先后，后段新到的在前，取空前段时把后段翻过来），按订阅先后投递，返回送达数。积压加上本条超过 1 MiB 的订阅被断开：清空队列，状态 2，原因“订阅积压超过 1 MiB，已被断开”，不计入送达数。
- **等待与超时**：队列里有消息就取一条返回状态 0；否则新建一个 AbortController 登记在订阅上，`scheduler.wait(剩余毫秒, {signal})` 睡到期限或被唤醒；发布、关闭与取消都中止这个 AbortController 来唤醒等待者，醒后重新查队列，剩余时间按期限重算，所以读订阅数不会拉长或缩短等待。到期返回状态 1，零超时即立即轮询。
- **关闭**：频道立即从频道表删去（同名可重新订阅），各订阅先取完已排队的消息，再得状态 2 与关闭原因；返回被关闭的订阅数。
- **取消**：幂等；订阅终结（原因“订阅已取消”），离开频道，唤醒等待者；此后等待返回状态 2。
- **订阅柄**：取 `crypto.randomUUID()`，各订阅互不相同，也无从猜出。订阅柄表新的在前；终结的订阅仍留一阵，以便终结后再等待仍得状态 2，只保留最近 4096 条，更早的丢弃，之后用其柄得“订阅柄无效”。
- 用在持久对象里，不核对事件种类（提案 C0001）：在别的事件里调用时，频道属于这个程序实例。
- 所有内部辅助名都以 `持久频道内` 起首。

待办事项：薄宿主不知道事件何时结束，订阅柄不能随事件失效，同一实例里别的事件拿到柄也能用；事件结束时也不会自动取消遗留的订阅，遗留的订阅一直占着频道名额，直到对象被驱逐。应用须在所有出口取消订阅。

## 部署要求

1. 全局 `scheduler.wait`：Workers 自带；Node 宿主用 `node:timers/promises` 的 `scheduler` 垫片经 `创建云工宿主({全局})` 传入，见 `一致性验证/工具.mjs` 的 `造全局`。
2. 存活时间：薄宿主不另设每个事件的墙钟时限，由平台的 CPU 限额兜底；长时间的等待与转发循环应带周期超时与心跳。

## 本地 workerd 实测（Wrangler 4.129.0，兼容日期 2026-09-10，同一个持久对象实例上的多个并发 `durable-fetch`，真实 HTTP 与真实 D1）

薄宿主上的复验（`持久频道云端复验.test.mjs` 9 项、组合范例 `服务商连接云端复验.test.mjs` 1 项）全部通过：

- 跨请求订阅与发布、多订阅者按序各得一份、超时精度（探测订阅数不改变长短）、关闭先交后终、64 KiB 消息与零长消息、订阅上限 256 与积压断开的原因文字、一个订阅内收发 3000 条、先订阅再回放的窗口去重（真实 D1 上恰好各一次）均正确。
- 已有 64 个频道（前一事件遗留的订阅）时，再订阅新频道抛豫言异常，试验应用答 HTTP 500。
- **客户端断开之后持久对象里的事件继续运行**：订阅事件在客户端走后仍被频道消息唤醒，断开后又发布 3 条才发现断开，随后应用取消订阅。等待期间（无写入）客户端断开不会唤醒等待，只有消息或超时到来才会再次运行，所以长连接转发要靠心跳与周期超时。
- 云端（Cloudflare 边缘）行为留待验证。

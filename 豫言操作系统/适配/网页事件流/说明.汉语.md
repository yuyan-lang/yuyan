# 网页事件流云工适配

`流。豫` 用豫言写在云工薄宿主的通用原语（`库/云工宿主` 的物宿主、物、回调）之上，实现[网页事件流接口规范](../../../豫言操作系统接口/网页事件流/规范.汉语.md) 0.2.0：立即提交响应头、逐块写入（受背压）、断开检测、正常结束与异常终止。豫言用资源「云工物」直接持有 TransformStream、写器、AbortController 等 JS 对象；响应经宿主随入站请求传入的先交函数先行交付。

## 实现

- **响应与背压**：用 `Headers` 收齐标头，造 `TransformStream`，可读端交给 `Response` 作正文，再用「云工呼」调宿主随入站请求传入的先交函数（网页服务适配的 `入站请求先交` 取出）先行交付：宿主立即以这个 Response 作答，入口继续运行。返回给应用的出站响应由网页服务适配的 `物出站响应` 包同一个 Response，入口最后返回它，宿主已经交付，便不再理会入口的返回值。可写端的写器负责写入：`writer.write(字节)` 在读者拉取之前不会完成，这就是背压。
- **断开检测**：创建“断开等待”承诺——`scheduler.wait(24 小时, {signal: AbortSignal.any([请求信号, 我方信号])})` 再经 `Promise.allSettled` 包装（从不拒绝）。每次写入或关闭都让操作承诺与它 `Promise.race`，**断开等待排在前面**：请求信号一旦中止（客户端断开），无论写入本身能否完成都返回 1；操作被拒绝（响应体读端已取消）也返回 1。`入站事件流已断开` 读请求信号的 `aborted` 与写器的 `desiredSize`（出错为 `null`）。流结束、中止或收尾时中止“我方信号”，计时随之撤销，不留悬挂的计时。
- **收尾**：先交函数返回入口运行完毕的承诺（入口正常返回得 `true`，抛出得 `false`）。适配用 `登记云工回调` 在它上面挂一个收尾回调：入口运行完毕时，流若仍开放就结束它（入口抛出则以错误中止），撤销断开等待，移除登记，流柄随之失效；回调执行后自己注销。所以程序返回而忘了结束的流也会结束，客户端不会一直等待。
- **登记簿与流柄**：登记簿是顶层可变格，每项是（流柄，写器，状态，请求信号，断开等待，我方 AbortController，请求）。薄宿主每个程序只有一个实例，交错执行的各个请求共用这张登记簿，它本来就是跨请求共享的状态；读写之间没有挂起点，交错的请求不会互相覆盖。流柄取 `crypto.randomUUID()`，各流互不相同，也无从猜出。同一请求（`Object.is` 判同一个 Request）再开始抛异常。状态 0 开放、1 客户端已断开、2 已结束或中止、3 断开后又结束或中止。
- **校验**：状态、标头（token、值字节、禁用名、重复、数量）全部在提交响应头之前由豫言校验，违规抛豫言异常；写入大小先于状态判断；请求作参数传入，开始事件流只能发生在 HTTP 处理入口里。中止用 `writer.abort(new Error(原因))`，结束用 `writer.close()`。
- 所有内部辅助名都以 `流内` 起首，避免与应用或别的适配同名。

待办事项：四个流柄函数不带请求参数，同一实例里另一个仍在进行的请求拿到流柄也能写入；创建它的请求结束后流柄才失效。

## 部署要求

1. **兼容标志 `enable_request_signal`**：工作者配置的 `compatibility_flags` 必须包含它，请求的 AbortSignal 才会在客户端断开时中止（本地 workerd 已验），断开写入才会立即返回 1。云仓的 `wrangler.jsonc` 需要为使用本包的应用加上这一项。
2. **全局 `scheduler.wait` 与 `AbortSignal.any`**：Workers 自带；Node 宿主用 `node:timers/promises` 的 `scheduler` 垫片经 `创建云工宿主({全局})` 传入，见 `一致性验证/工具.mjs` 的 `造全局`。
3. **先交函数**：云工宿主（`豫言操作系统/宿主/云工/宿主.mjs`）在网页事件的入站请求里传入〔0, 请求, 上下文, 种类, 先交〕，网页服务适配的 `入站请求先交` 取出它。
4. **存活时间**：薄宿主不另设每个事件的墙钟时限，由平台的 CPU 限额兜底；长连接应按周期写心跳，并让客户端凭 `Last-Event-ID` 重连。

## 本地 workerd 实测（Wrangler 4.129.0，兼容日期 2026-09-10，`enable_request_signal`，持久对象内 `durable-fetch`，真实 HTTP）

薄宿主上的复验（`事件流云端复验.test.mjs`）9 项全部通过：

- 响应头先于程序结束到达；帧序、UTF-8、64 KiB 边界、大量块、并发流均正确；线路上出现附加标头，`Content-Type` 不可覆盖。
- 程序返回而未结束的流由收尾回调结束，客户端读到正常结束。
- 背压是宽的：读者停读 800 毫秒后写入方已写出 251 个 10 KB 帧（套接字与管道缓冲），随后才阻塞。
- 客户端中止 `fetch` 后应用继续运行：约 78 毫秒后应用记下“断开收尾”，写入返回 1，结束后写入返回 2。空闲连接的断开要在服务端再次写入之后才被发现，所以长期保持的流要按周期写心跳。
- `中止`：HTTP/1.1 客户端读到正常结束（分块结尾照发），宿主日志记一条未捕获异常；需要客户端可靠得知失败时，应在流里先写一帧错误事件。
- 云端（Cloudflare 边缘）行为——空闲流的超时、断开是否立即通知、异常终止在 HTTP/2 上的可见形态——留待云端验证。

# 基础接口首个纵向切片验证

日期：2026-09-24。公共签名来自[基础规范](../../../豫言操作系统接口/基础/规范.汉语.md)。过渡适配位于 `基础。豫`，复用标准库现有宿主调用；`验收。豫` 统一断言两次单调微秒读数不倒退，并返回“基础接口通过”。

| 环境 | 验证方式 | 已观察结果 |
| --- | --- | --- |
| 原生 | `./yy 豫言操作系统/适配/基础/基础。测试。豫 --type-check-only --do-not-load-cache` 后构建并运行 | 类型检查通过，程序输出“基础接口通过” |
| Node/V8 | `./yy3_bs` 将同一 `基础。测试。豫` 编成 WasmGC，Node 26.3.0 使用已有浏览器值桥 `创建豫言实例` 装载 | JSPI 调用完成，输出“基础接口通过” |
| 真实 Chrome | 同一 WasmGC 与现有浏览器 `入口.mjs`、`宿主.mjs`、值桥在本地临时页面运行 | 页面结果为“基础接口通过”；静态服务器记录程序和值桥 Wasm 请求均为 200 |
| 本地 CF Worker | [云工验收程序](../../../测试/豫言操作系统接口/基础云工/入口。豫)复用 `验收。豫`，以现有云工请求接口返回结果；Wrangler 4.129.0 本地 workerd | HTTP 200，正文为“基础接口通过” |

接口检查工具已对根目录九个 `。接口。豫` 文件完成解析，并能读取包的所有者／名称／完整版本及核对直接依赖；故意包含 `者` 函数体的样例被拒绝。普通编译器仍不能直接把纯接口包作为依赖。上述运行验证证明现有三端宿主可支撑这两项行为，并不证明完整接口绑定已完成。

后续检查已扩展到六个接口包的整包声明；函数方向现由 `。接口。豫` 与 `。应用接口。豫` 的后缀确定。基础适配的宿主角色、完整版本与两项函数签名均通过比对。把实现版本改为 `0.2.0`、把参数类型改为整数，或引用未定义的“伪类型”，都会被拒绝。[基础启动样例](../../../测试/豫言操作系统接口/基础启动/入口。豫)实现应用导出的 `启动程序`，方向及签名检查通过，其 WasmGC 在 Node/V8 输出“基础接口通过”。检查器可生成包含完整身份、依赖闭包、规范摘要和函数方向／签名的 JSON 清单；类型构造的完整语义仍待补齐。

2026-09-24 补验：`--核对清单` 对未改动的基础清单通过，对把“读取单调微秒”改名的过期清单返回失败。基础适配和启动应用的实际 `者` 定义通过；只保留两条同名 `乃` 声明的假适配返回“函数只有类型声明而无定义”。当前 WasmGC 产物实际通过 `yuyan:gc-host/v1.call` 导入通用宿主调用、以 `_start` 导出入口；豫言公共函数名仍属源级契约，须由后续绑定工具明确其到 Wasm 投影的对应关系。

清单格式现升为版本 2，增加公开构造与函数的源级声明，模块顺序按 UTF-8 字节固定。六个接口包均生成有效 JSON；基础包重新生成核对通过，将“资源配额已尽”只在临时副本中改名后，核对按预期拒绝。清单仍不含规范正文摘要，也未随编译产物进入三种宿主的装载阶段。

新增共享 `装载核对.mjs`，Node 26.3.0 对现有基础样例 Wasm 与两份一致的基础清单、启动清单返回通过；把宿主清单版本改为 `0.2.0` 或误传值桥 Wasm 时，均在调用入口前拒绝。单凭通用 Wasm 桥的形状仍不能反推出每个豫言函数的内部调用。

随后新增独立[基础构建包装](../../../工具/豫言操作系统基础构建/说明.汉语.md)，保留原宿主入口并让包装入口成为浏览器、Worker 成品的默认 `入口.mjs`。用启动样例生成浏览器成品：真实 Chrome 显示“基础接口通过”；把成品中的宿主清单版本改为 `0.2.0`，页面显示“装载失败：宿主提供的基础包清单与应用要求不符”，未运行样例。用云工样例生成 Worker 成品：Wrangler 4.129.0 本地 workerd 返回 HTTP 200 与“基础接口通过”；同样改坏版本后 workerd 在载入入口模块时拒绝启动。Node 26.3.0 用浏览器成品的相同 Wasm、清单与值桥，在创建实例前执行共享预检，输出“基础接口通过”。三端的默认启动接入范围目前限于该包装构建的首批基础成品；普通 `双宿主构建` 产物仍照旧运行。

浏览器成品现附 `节点入口.mjs`：直接执行 `node /tmp/yy基础成品浏览器/节点入口.mjs` 输出“基础接口通过”；把宿主清单版本改为 `0.2.0` 后，该入口在实例化前拒绝。构建包装还拒绝“检查的启动实现与编译源码不同”及“应用包缺少基础适配直接依赖”的两个反例。

清单格式继续升为版本 3，加入从当前包递归解析的完整依赖身份闭包。六包清单均可生成；启动包闭包含启动、标准库和基础包。临时让基础包反依赖启动包会被判为依赖环。Node、真实 Chrome、本地 workerd 用版本 3 成品复验均通过；只改成品中宿主清单的传递依赖版本，Node 在实例化前拒绝。

版本 4 清单再加入包描述、方向、接口源码、包内规范及根目录公共文档的 SHA-256 摘要。基础包记录 17 个逻辑文件摘要，其中诊断接口的摘要与独立 `shasum -a 256` 一致。只给临时副本的诊断接口追加注释，源级声明不变，清单核对仍拒绝；原包核对通过。六包格式 4 清单均生成成功；重新包装后 Node 输出“基础接口通过”、真实 Chrome 页面显示同文、本地 workerd 回 HTTP 200 且正文同文。

适配包新增独立[投影记录](投影.汉语.md)，列出两项公共函数经标准库到宿主原语的源级映射，以及成品实际的 `yuyan:gc-host/v1.call` 导入和 `_start` 导出。包装入口在三端核对投影文件；Node 改坏时钟原语名的负例于实例化前拒绝。Node 共同样例使用原语覆盖口计数，实际调用诊断原语 1 次、时钟原语 2 次；重新包装的真实 Chrome 和本地 workerd 仍分别显示、返回“基础接口通过”。这只证明共同样例走过这些调用，不能把任意应用内部的逐函数绑定视为已独立证实。

方向定义现随文件后缀：`。接口。豫` 的函数由宿主提供，`。应用接口。豫` 的函数由应用提供；不再使用 `方向。豫`。六包经接口检查与豫构检查通过，启动包为 0 个宿主函数、1 个应用函数；网页服务包为 6 个宿主函数、1 个应用函数。临时把启动应用接口改为普通接口后，应用实现检查拒绝；同名模块同时出现两种后缀亦拒绝。重建成品后，Node 和真实 Chrome 输出“基础接口通过”，本地 workerd 返回 HTTP 200 与同文。

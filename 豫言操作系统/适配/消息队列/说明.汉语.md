# 消息队列云工适配

生产者用云工 `QUEUE` 绑定的 `send` 与 `sendBatch`；消费者用 `queue` 事件的 `MessageBatch`：云工宿主以〔0, 批次, 上下文〕调用入口 `处理队列批次`，`队列批次` 的构造器 `云工队列批次` 包着 `MessageBatch` 与上下文（都是资源「云工物」），`ack`、`retry({delaySeconds})` 直接调用平台的 Message 对象。适配只用云工薄宿主的通用原语。适配的要点：

- **消息体经平台规范化**：豫言把消息体文字交给平台的 `JSON.parse`，再用 `JSON.stringify` 得到规范文字；规范文字核对大小与嵌套层数后再经 `JSON.parse` 得到交给 `send` 的值（`-0` 之类规范化掉的差别不带到平台）。规范文字里不许出现 `{"$句柄":`、`{"$未定义":`、`{"$大整数":`、`{"$数字":` 开头的对象（接口规范保留的宿主记号）；`1e999` 之类变成无穷大的数先用结森解析查出来拒绝。
- **批量数组由豫言拆分**：适配只在规范文字上做一遍带字符串与转义状态的括号扫描，拆出每项与其 `body` 文字，逐项验证形状与限额后重新拼成 `{"body":…,"contentType":"json","delaySeconds":…}`，全部合格才把数组文字经 `JSON.parse` 交给 `sendBatch`。`body` 始终是不透明的规范文字，不经豫言 JSON 库解析。
- **绑定**：用 `云工绑定`（许可类 QUEUE）取队列；未授权或当前部署没有配置的绑定名抛出可捕获的豫言异常，消息是宿主的原因（如 `未授权的QUEUE绑定：名`）。
- **消费侧读取**：读批次的 `queue` 与 `messages`，再读各条的 `id`、`attempts`、`timestamp`、`body`；`queue` 与 `id` 须是字符串，时间戳 `Date` 用 `getTime()` 取毫秒（测试替身也可直接给毫秒数）；`body` 须是 JSON 值（null、爻、有限数、字符串、数组、原型为 `Object.prototype` 的普通对象，逐层检查），`Date`、`Map`、二进制、`undefined`、BigInt、NaN、类实例等都使读取抛出豫言异常。合格后造出 `{queue, messages:[{id, attempts, timestamp, body}…]}` 对象，由平台 `JSON.stringify` 写出。
- **越界与延迟由适配先核对**：先用 `messages` 的条数核对序号，把越界变成可捕获的豫言异常；`retry({delaySeconds})` 只在延迟大于 0 时使用。
- 适配不使用 `ackAll`、`retryAll`，也不接触消息的内容类型。生产投递固定 `contentType: "json"`。适配没有顶层可变格（只有常量限额）。
- 真实本地 workerd（Wrangler 4.129.0）实测：`send`/`sendBatch` 以 `contentType: "json"` 投递，消费者读到 `attempts` 从 1 递增、`timestamp` 为 Date、`body` 为同一 JSON 值；`retry({delaySeconds})` 按延迟重投；单条消息体恰 128000 字节可投、128001 字节被拒（错误文字只是 `Unknown Internal Error (15000)`，所以适配自己按 128000 字节校验并给出中文原因）；`sendBatch` 里每条同样以 128000 字节为限（两条各 128000 字节共 256000 字节的批量可投）；不显式确认也不重试即视为成功；未捕获异常使**整批**重投，连已显式确认者一并重投（Miniflare 的 broker 在处理失败时不区分已确认消息），所以消费处理必须幂等。
- 薄宿主每个隔离体一个实例，多批消息可以在同一实例里交错处理；适配不保存任何状态。宿主对 `queue` 事件返回的 Promise 在入口返回时完成，入口抛出未捕获异常则被拒绝，平台据此重试整批。

后续版本的事项：没有指数记号、位数超过三百的整数也会被 `JSON.parse` 读成无穷大，现在不拦。

`一致性验证/` 里有试验应用、真实 Wasm 的 Node 测试（含批量拆分的随机结构对拍）和复跑说明。

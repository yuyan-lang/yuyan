# 豫言双架构裸机原型

## 当前系统总览（先看这里）

豫言操作系统现在是一个可以启动、可以交互、有持久文件系统的双架构多核系统，ARM64 与 AMD64 都在 QEMU 里通过自动验收，也已在实体电脑上启动：

**构建并运行**（在仓库根目录、已安装 QEMU 时）：

系统构建流程按底层执行器的模块类型选择读取路径，含 f32、f64 局部类型的执行器复用裸机后端的数值转译（与编译器直出原生产物所用的是同一份），再生成系统镜像。

```sh
./豫构。林檎。豫行 目标 造盘工具 -j 24
./豫言系统。林檎。豫行 运行 --架构 兼容六十四      # 造启动盘后由 QEMU 从 U 盘引导，交互；缺省带上示例程序；壳里输入“退出”结束，Ctrl-C 打断运行中的程序，卡死时按 Ctrl-A 再按 X 强制结束
./豫言系统。林檎。豫行 构建 --预置 某目录树       # 只造两种架构的启动盘（八核以上两个子进程同时造，各在输出目录下以架构名命名的子目录），不运行
```

「造盘工具」目标连带生成原生工具链，由原生豫构直出本机的造盘工具 `豫言系统。林檎。豫行`。造盘工具缺省取 `./豫构。林檎。豫行`（`--构`）与 `./编译器。林檎。豫行`（`--编译器`）。在 `git worktree` 工作树里造盘同样可用：`.git` 是文件时版本索引在主仓的 `.git/worktrees/<名>/` 下，造盘工具先把索引拷进 `.豫构缓存/版本索引.<随机数>` 再读，读完删掉。「启动光盘」目标（`./豫构。林檎。豫行 目标 启动光盘 -j 24`）连带造盘工具，造两架构的启动光盘（预置为空、带工具链）：`启动光盘/豫言系统-兼容六十四.iso` 与 `启动光盘/豫言系统-臂六十四.iso`，CI 拿它当发行物发布。Windows 的原生工具链留待后续版本，现在以 `node 豫言操作系统/宿主/节点/宿主.cjs` 运行 `.wasm` 版。

**制作双模式启动 U 盘（x86-64）**全程由豫言完成，引导程序与 ISO 结构都由豫言生成（见下文「自有引导」）：

```sh
./豫言系统。林檎。豫行 启动盘 --输出 启动介质 --预置 无
```

**开机与桌面**：两架构启动盘共用 `应用/豫构/开机。豫`，编译器以 `--目标 本机 --目标系统 豫言 --开机程序 --执行器 …` 从源码直出开机豫行文件，置于第三个模块 `boot/开机程序`。共用内核的 `开机装载。底层。豫` 读取段表，调用按段装载逻辑建立数据、代码与四兆字节栈，从文件入口运行。命令壳输入「图形」进入用户态桌面，文楷字体作第二个模块随盘（`boot/字体/文楷.ttf`，服务 34、35，见[帧服务](文档/帧服务.汉语.md)）。运行盘上的豫行程序时，执行器读文件段表，经服务 43 建立独立任务，工具栈为 128 MiB。地址布局见[豫行格式](文档/豫行格式.汉语.md)，任务装载见[动态任务](文档/动态任务.汉语.md)。

**多核（2026-10-07）**：AMD64 内核开机启动全部处理器核（xAPIC，至多 257 个），开机印“处理器核：N”；内核用一把大内核锁，任务分到各核上同时运行，没有可运行任务的核在内核里开中断停机。设计见[多核](文档/多核.汉语.md)。

```sh
./豫言系统。林檎。豫行 启动盘 --输出 启动介质 --预置 无
```

**系统内工具链**：启动盘缺省带工具链（2026-10-14 起；加 `--不带工具链` 才不带，那样的盘上壳里什么句子都运行不了），`/工具` 放编译器的本架构豫行文件 `豫构`、`编译器`、`豫言系统`、`格式化`，以及执行器汇编树码 `执行器。树码`。带工具链的盘上，除 `豫构` 以外的工具编成引用式清单（`--引用清单`）：`/工具` 里只有清单文件，单元按内容摘要放在 `/单元/`（同摘要只放一份，各工具共用）；`豫构` 自己保持静态，因为盘上的清单由它装入，`豫构` 运行清单工具时按摘要从 `/单元/` 取单元。豫构以这份树码把新程序与执行器一同降级为机器码，`构建` 与 `文件` 默认写出豫行文件。宿主上预编了前导的盘（2026-10-14 起），`/源` 只放壳要用的源码：标准库与壳命令两包的全部文件、仓库里每个包目录里的包描述与说明文档（包发现要核对包含关系），以及可执行包 `/源/你好`；阶段缓存只放前导模块的，前导与壳命令各部（见 `库/几席` 的 `部居`）的单元预编进盘，系统里只编用户输入的句子。加 `--全仓源码` 时 `/源` 包含整个受版本管理的仓库：宿主按 Git 索引取文件，并将相同次序的路径清单写进 `/源/源码清单`，系统内造盘沿用该清单，隐藏文件与文件次序保持相同；系统内造盘与远程开发要用这种盘。执行器在用户态读豫行段表，以服务 43「按段建任务」装载；编译器工作进程及其子进程的文件访问经初始任务代办。给 `--工具目录` 时复用目标架构相同的豫行工具，交叉目标从源码重新生成工具。见[客体二号](文档/客体二号.汉语.md)与[动态任务](文档/动态任务.汉语.md)。

```sh
./豫言系统。林檎。豫行 启动盘 --输出 启动介质 --盘容量 16777216
```

**预编前导（2026-10-13）**：宿主上带工具链造盘时，豫言系统照盘内的 `/源`、`/工具` 在仓库根的 `.豫构缓存/预编前导根/架构名` 下摆一棵树（`/源` 放与盘里相同的源码文件，`/工具` 放宿主豫构与盘上的执行器），以它为虚根（客体二号的环境变量 `豫言根目录`）运行宿主豫构的 `预编前导`，为盘的目标架构编好豫构交互的前导单元，再把 `/工具/.豫构缓存` 下本摘要的编译缓存与 `豫构上下文`、`/源/.豫构缓存` 下的 `交互外部包` 与 `单元运行` 放进盘（约多 16 MB）。开机壳见前导单元已编好就在读第一句之前装进来，新盘的第一句豫言句不再在系统里编前导（纯模拟约 25 分钟、HVF 约 4 分钟）。宿主豫构与盘上 `/工具/豫构。豫行` 须由同一份源码编成（客体摘要相同）；摘要不同或预编失败（前导或任一部没编出来）时造盘报错退出（2026-10-17 起），`--不预编前导` 关掉这一步。八核以上两种架构同时造盘时，父进程先编执行器、内核，并一次编完两种架构合编程序的前端、存下各程序的链接参数，两边子进程只链本架构的程序（`豫构 链接`），同时预编前导；链接并行数按物理内存定（2026-10-17）。系统内造盘不预编。

**QEMU 里用合成镜像要先扩大**：合成镜像只含数据区的非零前段，其后只多 1 MiB，盘上几乎没有空闲块；直接当 U 盘用时写文件很快就会失败（开机印“数据盘只有 N 个块，比文件系统小”，写失败时印“写文件失败：数据盘空间不足（路径）”）。先用 `truncate -s 8g 镜像` 之类把它扩大；写进真 U 盘时数据区用到 U 盘末尾。

**安装到内部盘**：ARM64 与 AMD64 启动盘都携带 `/工具/安装系统。豫行` 与桌面程序 `/工具/桌面程序。豫行`（桌面每个窗口独立成任务）。独立安装程序与开机程序共用六十四位地址执行器。在命令壳或桌面终端输入 `「安寓」`，程序列出内部 NVMe 与 AHCI 硬盘的盘号、控制器、型号及容量；每个 NVMe 控制器列出第一个可用的命名空间（VMware 把 `nvme0:N` 这块盘给作命名空间 N+1）；没有检测到可安装的内部盘时，程序报错并以退出码 1 结束。输入目标盘号，再输入数字确认两次：第一次 `1` 为否、`2` 为是，第二次 `1` 为是、`2` 为否；两次都选是，整块目标盘将被覆盖，其他输入取消安装。复制与读回核验时，每完成 10% 印一行进度。启动盘由引导程序传入的 MBR 签名识别，列盘时排除，整盘写服务也核对这一身份。USB 与光盘都可作安装源；只有 EHCI 的机器（如 ThinkPad E40）上 U 盘经增强主控（两架构共用的底层豫言驱动）逐扇区读写，同样能挂上数据区并作安装源。SATA 硬盘须在固件设置里选 AHCI 模式才会列出。

安装程序按一 MiB 分段复制启动介质的 ISO 部分与数据区，复制到最后一个已用块；同步后逐段读回核对沙256，再生成新的 MBR 盘签名，最后写入第零扇区并核验；随后把数据区就地扩到目标盘尾（2026-10-14，见[客体文件系统](文档/客体文件系统.汉语.md)的“扩容”；2 TiB 以上只用前 2 TiB）。完成后取出 U 盘或光盘，再重启。内部盘沿用相同的 BIOS MBR 与 UEFI ESP 引导，文件系统挂载该启动盘的整个数据区。两架构默认数据区都为八 GiB，安装介质容量须九 GB 以上，目标盘须容纳引导区与完整声明的数据区。早先装好的八 GiB 数据区用壳命令「扩数据盘」扩到整盘，「磁盘态」查看设备容量与用量。后续版本事项：为需要手动登记的固件添加 UEFI 启动项，以及列出同一 NVMe 控制器上的其余命名空间。

**远程更新（2026-10-14）**：从内部盘启动的系统可以就地换成新版，数据区原样保留。把 `豫言系统` 造出的新镜像（AMD64 的 `豫言启动.iso` 或 `豫言启动盘.img`，两者内容相同；ARM64 的 `豫言启动臂.iso`）放进一个目录（如 `/更新`），另要覆盖的工具可放进其下的 `工具/`，再在开机命令壳或远程登录里执行 `「葺寓」于「目录」曰『/更新』`。程序（`/工具/安装系统。豫行 更新 目录`）把镜像里数据区之前的系统部分按一 MiB 分段写进当前启动的内部盘，盘首最后写并保留本盘的 MBR 签名，同步后逐段读回核对沙256；再把镜像数据区（扩展文件系统四）里的 `/源`（壳编译句子用的源码树，连同 `/源/.豫构缓存` 里预编的前导与各部单元）与 `/工具`（连同 `/工具/.豫构缓存`）整棵暂存到 `/新版`，`工具/` 下的文件覆盖进暂存的 `/工具`，写齐后放标记 `/新版/齐备`（2026-10-17）。输入 `「更始」` 后生效：开机壳在读程序标识、进会话之前运行 `安装系统 换上`，这次开机是新系统的试启（单槽盘不看这条）就把现有的 `/源`、`/工具` 移到 `/旧版`、把暂存的两棵改名换上，再删去 `/新版` 与 `/旧版`；不是试启（新系统没起来、回到了原来的槽）就删去暂存。`/源` 与 `/工具` 在「葺寓」时不动，正在运行的会话照常编译执行（「更始」也要编译）；数据区里别的目录（`/系统`、`/软件`、用户文件）原样保留。从没有这项功能的旧版更新时，先用 sftp 把新版的 `安装系统。豫行`（造盘输出的 `豫行工具/` 里有）放进 `/工具/`，再「葺寓」。新系统部分须放得进本盘数据区之前（数据区在 ISO 之后第一个 64 MiB 整数倍处），放不下时用 U 盘重装；U 盘与光盘启动时用「安寓」。内核只许写内部启动盘数据区之前的扇区。造盘时加 `--预置 目录树`，在目录树里放 `系统/远程登录/授权公钥`（OpenSSH authorized_keys 格式，只认 ssh-ed25519），装好的系统开机就能用这把公钥远程登录；放 `系统/开机。数据。豫`（如 `「交互参数」者「列」【『--直读』】也。`）选开机壳的输入方式，`--直读` 时串口脚本整行原样读入、不经拼音（缺省 `--组字`，2026-10-16）。经 ssh 执行「更始」时机器直接复位，连接不会正常关闭，ssh 客户端加 `-o ServerAliveInterval=5 -o ServerAliveCountMax=3`，十几秒后自行退出。双槽盘的更新与自动回退见下段。

**系统双槽与更新失败自动回退（2026-10-14）**：「安寓」装出的内部盘有两个系统槽：盘首是安装源的系统部分（引导程序与原来的内核模块），其后是两个各 1 GiB 的槽区，数据区接在两个槽区之后，照旧扩到盘尾；目标盘放不下两个槽区（比单槽多要 2 GiB）时按单槽安装。字节 2048 与 2560 起是两个槽的引导表，第 6 扇区（字节 3072）是槽记录：主槽、试启槽、本次所启槽、本次试启、两个槽区与数据区的位置、两个槽的版本说明（来源加系统部分摘要的前八位：系统部分每 1 MiB 一段的沙256 相接后再取沙256，同一份镜像装上去与更新上去相同）。「葺寓」把新镜像的系统部分写进不在用的那一槽，引导表的盘上偏移加上槽区起点后写进那一槽的表位，再把试启槽记成它；镜像的引导表架构与本机不同、系统部分放不进槽区、或本次开机是还没确认的试启时拒绝。引导程序（BIOS 第二级、BOOTX64、BOOTAA64）看到试启槽就先清掉它、写回盘，再启那一槽；开机壳执行完开机自启的各句（远程登录已在后台启动）后自动执行「确认系统槽」，把新槽记成主槽。没确认就重启（含掉电），引导程序启原来的主槽；试启时内核走到致命错误的停机处（裸机核验失败、开机程序退出，以及多核时开机程序结束）就直接重启，坏的新系统不用人到场就回到原来的系统。试启时系统卡死要断电重启，重启后同样回到原来的系统。「系统槽状态」印出两槽各是哪一版、哪个是主槽、本次启的是哪一槽、有没有待试启；「回退系统」把主槽切到另一槽，下次开机生效。内核从槽记录取数据区起点。旧版装的单槽盘「葺寓」照旧改写系统部分，并提示一句；用新版 U 盘重装后有两个系统槽。「葺寓」在盘首部分只写槽区、槽的引导表与槽记录（槽记录在 `/新版` 暂存写齐之后才写），引导程序换新用 U 盘重装。后续版本事项：单槽盘写到一半断电后的回退；新版的 `/源` 与 `/工具` 换上之后新系统没能确认、回到原来的槽时，原来的系统仍用新版的这两棵；AMD64 引导表的盘上偏移是四字节，槽区要在盘的前 4 GiB 里。

带工具链时预置默认值为空，与系统内造盘相同；可以用 `--预置 目录` 明确加入示例文件。

**运行豫言脚本（2026-10-11，提案 00003 第 7 步）**：工具链盘上，命令壳与桌面终端的「行」「脚本」遇到 `。脚本。豫` 时起 `/工具/豫构。豫行 运行 绝对路径 参数…`：豫构在系统里把脚本连同它依赖的模块编成 AMD64 装载单元，装进自己的进程运行（单元目录在仓库根 `/源/.豫构缓存/单元运行/` 下，印记相同就不再编译），例如 `「行」于『/源/应用/豫构/脚本样例/系统/写读。脚本。豫』于「列」【】`；不属于任何包的脚本（如 `/数据/甲。脚本。豫`）也能运行。QEMU 纯模拟四核 8 GiB（`-cpu max`）第一次约 11–13 分钟（编译标准库并生成全部单元），之后同一脚本数秒、新脚本两到四分钟。盘上没有 `/工具/豫构。豫行` 时壳提示要造工具链盘。

在命令壳里用豫构构建并运行你好世界（先关掉构建日志，豫构就直接起编译器）：

**六十四位执行器**：开机程序与四个工具共用六十四位地址执行器（执行器只有这一种构建），盘内 `执行器。树码` 同样使用八字节引用。动态单元按这份树码生成，装载器按执行器引用宽度扩展零号表；单元文件中的函数引用仍以四字节传输，装载时零扩展为运行时表项。见[豫行格式](文档/豫行格式.汉语.md)。

**豫行文件（2026-10-08，提案 00005 第 3、4 步；2026-10-11 起由编译器直出）**：带执行器的普通程序由编译器直出[豫行文件](文档/豫行格式.汉语.md)（布局同工具）。宿主上用 `豫构 构建 包 --输出 名 -j 24 -- --目标 本机 --目标系统 豫言 --执行器 绝对路径/执行器。树码`；系统里编译器旁有 `/工具/执行器。树码`，豫构默认就出豫行文件，例如上面的 `构建 你好` 写出 `/源/你好`，`「行」于『/源/你好』于「列」【『豫言』】` 原生运行。底层程序（如林兼容）由编译器直接降级成豫行文件：`豫构 构建 林兼容 --输出 林兼容 -j 24 -- --目标 本机 --目标系统 豫言`，ARM64 再加 `--目标架构 臂六十四`，编译器的 `--符号表 文件` 另写函数符号表。

**系统里造启动盘（2026-10-07）**：豫言系统本身也是豫行工具，加 `--全仓源码` 造的盘 `/源` 是整个仓库，所以在系统里可以从源码造出启动盘：造盘全程只用豫言代码（仓库文件按 git 索引或逐层列目录得出，控制台字模由豫言的「字体」库生成，SHA-256 与合成镜像都用豫言算、拼）。在命令壳或桌面终端里输入一条命令（2026-10-10 起）：

```text
「营启盘」
```

它运行 `/工具/豫言系统。豫行 系统内造盘`：先设 `豫言构建日志=0`，把当前目录换到 `/源`，生成启动光盘与合成镜像。缺省选择当前处理器架构，`--架构 兼容六十四` 或 `--架构 臂六十四` 指定目标。开机程序由 `/工具/编译器。豫行` 直出豫行文件；同架构复用 `/工具` 的四个豫行工具，交叉架构从源码重建目标工具。`--并行` 缺省查询内核服务 45 的空闲 2 MiB 物理块数，预留 1 GiB，再按每个工作进程 2 GiB 预算，与核数取小，至少一个；空闲内存未知时取核数，核数未知时为四。显式参数覆盖缺省值。附加参数可用 `「行」于『构建启动盘』于「列」【『--架构』，『兼容六十四』】` 传入。宿主「启动盘」与系统内造盘的 ARM64、AMD64 数据区缺省容量均为八吉字节；`--盘容量` 指定扇区数。写入合成镜像的 U 盘容量需超过九 GB。

运行数据区需容纳全仓编译缓存与新产物，8 GiB 的 ext4 数据区可提供 262144 个节点。已有合成镜像扩容时，同时扩展块设备文件与其中的 ext4 文件系统。`--只出光盘` 可指定只写 ISO。QEMU 纯模拟的随机整数能力按处理器支持选择硬件随机指令或任务号、时钟、调用计数混合的散列，安全随机字节串使用硬件随机指令。

运行进度：开机逐步打印 USB 初置与 ext4 挂载结果；挂载读取超级块和组描述符表。造盘打印“【进度 已用 X 分 Y 秒】第 k 步”，共七步；最终链接中将开机程序与工具降级为机器码。进程回收后以服务 44 归还空出的二兆块，服务 45 提供空闲内存信息。命令壳用「设」于『时区』于『+8』设置时区，存入数据盘 `/.环境`，日期与构建日志按此显示；缺省为 UTC。

**豫行启动器（2026-10-13，[提案 00021](../../提案/00021-豫行跨平台运行.汉语.md) 第 4 步）**：在 macOS ARM64 与 Linux（ARM64、x86-64）上直接运行豫言操作系统的豫行文件（指令集与本机相同），同一个文件在豫言操作系统里与这些宿主上都能跑（Linux 版启动器：构建时加 `--目标系统 林纳 --目标架构 臂六十四` 或 `兼容六十四`）。启动器是带执行器的原生程序：把位置无关的豫行各段整体平移映射，换上服务门，服务调用由执行器代办（见 `客体二号/说明.汉语.md` 的 `豫行启动`）。现在能跑底层程序（如 `原生你好` 的豫行版）与带执行器的普通豫言程序（如 `豫行示例`、`豫构`）：程序的文件访问经文件代办转给宿主的文件系统，子进程由宿主进程再起一个启动器、在客体的当前目录里运行（客体切换当前目录后起的子进程跟着换），标准输出与标准错误分别写到宿主的两条流。`豫构` 的豫行在启动器下构建底层程序，产物与本机原生豫构的逐字节相同。`--合成 程序。豫行 输出 [启动器]` 把豫行合进启动器，写出单文件可执行文件（macOS 上豫行放在代码签名之前，严格签名校验通过；给出 Linux 版启动器时合成 Linux 单文件，豫行接在文件末尾）；单文件运行时命令行参数全部交给自带的豫行。macOS 上图形程序在原生窗口里显示（转授的显示面名是「主窗口」，1280×800 点；测试时在启动器后面先加宿主选项 `--显示面后台`，窗口不抢前台），客体的标准库网络经启动器落到宿主套接字。豫构交互也能在启动器里开（在仓库里运行 `启动器 豫构豫行 交互`；豫构豫行旁边放执行器 `执行器。树码`，两者可以放在仓库外，如豫言数据，以绝对路径调用）：客体读控制台（服务 4）时启动器阻塞读宿主的标准输入，读到文件尾就结束会话；豫构交互组字输入时（标准输入是终端），壳核心的编辑器经底层转送把宿主终端切到原始模式逐键读，回显、行编辑、输入法与历史都由壳做，与宿主原生、豫言操作系统里相同；直读时回显与行编辑由宿主终端负责；会话按豫言操作系统的系统会话办，壳的当前路径从启动目录起，「行」只运行豫行程序；豫构豫行旁边放源码树 `源` 时在任何目录都能起（2026-10-16）；装单元时的代码块映射与启缄（服务 60、76）也由启动器办理（macOS 用 mprotect 切换，Linux 与 Windows 的动态区映成可读写可执行）。macOS ARM64、Linux ARM64 与 Linux x86-64 上实测可用；x86-64 的 Linux 启动器自身占着低区，豫行只能平移装载，为本机生成的单元按相对址式取址，锚是运行中豫行的名义全局基址（执行器经单元现况报出）。启动器配六十四位地址执行器（执行器只有这一种构建），以 `-- --目标 本机 --执行器 执行器。树码` 构建。清单豫行（豫行版本二，提案 00038）读出文件头后交给启动器旁边的豫构的 `运行` 子命令（先找启动器旁的 `豫构。林檎。豫行` 等名字，没有就用 PATH 里的 `豫构`）；不加 `--合成` 的启动器直接运行清单豫行，输出与静态程序相同。

**关机与重启（2026-10-13，开放硬件驱动第 9 步）**：壳命令「息」「更始」经设备接口的「息」「更始」（执行器原语 241、242）请内核做硬件动作（服务 67、68，内核模块 `电源。底层。豫`）。AMD64 读 ACPI：在 EBDA 与 BIOS 高区找 RSDP，UEFI 启动再扫引导程序交来的 Multiboot 内存表里的 ACPI 可回收与 NVS 区段；经 XSDT 或 RSDT 找 FADT，关机写 PM1a／PM1b 控制寄存器（休眠类型取自 DSDT 或 SSDT 里的 `_S5_` 包），重启依次用 FADT 的重置寄存器、端口 0xCF9 与键盘控制器；没有 ACPI 表时关机试 QEMU 与 VirtualBox 的老端口。ARM64 经 PSCI 的 SYSTEM_OFF、SYSTEM_RESET（内核原语「超管调用」，hvc #0）。成功时机器断电或复位，命令不再返回，做不到才返回“错误：…”；动手前内核在控制台印一行诊断（如 `PWR OFF ACPI 0604 00`，格式见模块注释），实机上不成功时凭它看走了哪条路。用户数据由调用者先刷盘（文件系统写直通，事务提交处已刷新）。QEMU 验收（不加 `-no-reboot`）：两种架构启动光盘进命令壳，输入「息」后 QEMU 自己退出；输入「更始」后串口第二次出现“命令壳已就绪”，QEMU 仍在运行。AMD64 在 KVM 的 BIOS 与 UEFI（OVMF）下、ARM64 在 hvf 下通过。

**UTM 与键盘（2026-10-06）**：UTM 4.7.5（QEMU 10.0.2，UEFI，IDE 光驱）上实测进入桌面。UTM 默认关掉 i8042，把 usb-kbd、usb-tablet 接在 `-usb` 的 ICH9 EHCI/UHCI 上（另有一个 qemu-xhci 只给 USB 转发），内核驱动 PS/2、xHCI 上的 HID 键盘和增强主控（2026-10-13 起）管的 EHCI 高速设备，UHCI/OHCI 伴随控制器上的全速键盘尚无驱动（待办事项），所以要在「QEMU」页勾选「PS/2 控制器」，并在「输入」页把「USB 支持」设为「关」；只开 PS/2 不关 USB 时 QEMU 把按键送给 USB 键盘，仍然收不到。显示卡 virtio-vga 与 VGA 在 OVMF 下都有帧缓冲。QEMU 里在 xHCI 上挂 `usb-kbd` 也能进桌面。键盘与 USB 的启动诊断（`PS2 STAGE=`、`USB PCI=` 等）只写串口（主核的「串口裸字节」），不再画到屏幕上。开机不再等 30 秒的 USB 热插拔观察窗口（为林檎实机排查加的），开机到命令壳约 3.4 秒；PS/2 键盘输入环修正了写计数过 256 后把键全当“环满”丢掉的判满错误；退出桌面的清屏改由内核涂黑（提交帧像素地址给 0），不再在客体堆里新建 4 MB 数组。桌面支持 PS/2 鼠标、USB 鼠标与绝对坐标数位板（usb-tablet），滚轮可用；QEMU 默认机型自带 PS/2 鼠标，监视器 `mouse_move`、`mouse_button` 可测。

**高分屏与显示设置（2026-10-11）**：内核逐物理像素提交，执行器在宽超过1920或高超过1200时报告自动像素比2，其余为1。桌面按有效像素比直接绘制文字，系统设置提供八种缩放并保存。QEMU标准显卡、ARM64内存帧与威睿显卡可以通过共用底层豫言驱动切换1280×800、1920×1080、2560×1600；归还显示面时恢复开机尺寸。其他设备沿用固件尺寸。QEMU高分屏可用 `-vga none -device VGA,xres=2560,yres=1600`（BIOS引导按EDID选VBE，UEFI沿用固件GOP）。详见[帧服务](文档/帧服务.汉语.md)与[臂平台](文档/臂平台.汉语.md)。

**USB 鼠标（2026-10-06）**：内核的 xHCI 驱动认 HID 启动协议鼠标（类 3、子类 1、协议 2），开机前接好或开机后热插都可以；与键盘同在一个设备上的鼠标接口（例如林檎笔记本的内置键盘与触控板）也各配一个端点。报告换成 PS/2 三字节包写进与 PS/2 鼠标同一个鼠标环，执行器不用改。没有 PS/2 控制器时（状态口读到 0xFF）内核跳过 PS/2 鼠标的读取与初始化。QEMU 可用 `-device usb-mouse,bus=xhci.0` 接 USB 鼠标，加 `-machine i8042=off` 去掉 PS/2，模拟只有 USB 输入的机器。细节见 `文档/帧服务.汉语.md`。

**写屏与滚屏（2026-10-06）**：帧缓冲映射为写合并（PAT 第 4 项设为 WC），控制台到屏底时一次上移半屏、按 8 字节一次复制。实机上显存读写都要走总线，原先的强不可缓存映射加逐字节、逐行滚屏，在 2560×1600 的林檎笔记本上每滚一行约 10 秒。细节见 `文档/帧服务.汉语.md`。

命令生成 `启动介质/豫言启动.iso`。这是 x86-64 的可写入 U 盘的 BIOS/UEFI 混合 ISO（ARM64 另有 `豫言启动臂.iso`）：传统 BIOS/MBR 与 x86-64 UEFI 入口都由豫言生成的引导程序启动，按 Multiboot 1 装载现有无盘内核（见下文「自有引导」）。它可不依赖 Virtio 数据盘先进入壳，已接入 xHCI USB bulk-only 数据盘的持久文件操作（没有 xHCI 时由增强主控驱动 EHCI 上的数据盘，2026-10-13 起），未知盘不自动格式化；安装到内部盘见上文「安装到内部盘」。QEMU BIOS 测试把 ISO 作为 USB 大容量存储设备：

```sh
qemu-system-x86_64 -machine q35 -accel tcg -m 4G -smp 4 -display none -monitor none -serial stdio -no-reboot \
  -drive if=none,id=yy_iso,format=raw,file=启动介质/豫言启动.iso \
  -device qemu-xhci,id=xhci -device usb-storage,drive=yy_iso,bootindex=1 -boot order=c
```

**自有引导（2026-10-07）**：启动盘上的引导程序与 ISO 结构都由豫言生成（`豫言操作系统/裸机/库/冶铸/自有引导。豫`），造盘全程用豫言自己的代码。BIOS 启动时，MBR 读入第二级引导（光盘由 El Torito 直接装入），第二级在实模式下按盘上的引导表读入内核与模块，取 E820 内存表，按 EDID 首选分辨率设 VBE 帧缓冲，填好 Multiboot 1 信息，再切到保护模式跳进内核。UEFI 启动时，固件从 1 MiB 的 FAT12 分区映像里载入 `EFI/BOOT/BOOTX64.EFI`（PE32+；光盘经 El Torito、U 盘经 MBR 的 0xEF 分区找到它），它找到带引导表的整盘，读入内核与模块，取 GOP 帧缓冲与内存表，退出启动服务，然后回到 32 位保护模式，把内核拷到装载地址再跳进去。引导提示都是中文：BIOS 把提示用字的点阵装进显卡字库，UEFI 引导程序（x86-64 与 ARM64）先向固件的 HII 数据库登记中文字体（包「底层统一引导」），EDK2 一类固件在屏幕上显示中文。模块的物理地址：BIOS 下从内核的 bss 末址（16 MiB，内核模块区之后）起紧挨着放，碰到 124–128 MiB（USB 控制器的 DMA 区）就挪到 128 MiB 以上；UEFI 下放在固件分给的 4 GiB 以下的高址。第三方字体与拼音词库的许可证作 ISO 根目录的文件随盘（NOTO.TXT、SIYUAN.TXT、WENKAI.TXT、PINYIN.TXT）。

**ARM64 启动盘（2026-10-09）**：`启动盘 --架构 臂六十四` 造 ARM64 无盘内核与 ARM64 UEFI 启动光盘 `豫言启动臂.iso`（约 24 MB），引导程序 `EFI/BOOT/BOOTAA64.EFI` 与 ISO 结构都由豫言生成（`豫言操作系统/裸机/库/冶铸/臂引导。豫`）。光盘与 U 盘两种接法都能启动：固件载入 BOOTAA64.EFI，它按盘上的 ARM64 引导表把内核各段读进内存，退出启动服务，关 MMU 与缓存，再把各段拷到载址并跳进内核。在 Apple 芯片的 Mac 上用 QEMU 自带的 ARM64 UEFI 固件以硬件虚拟化运行，命令壳在串口上交互：

```sh
./豫言系统。林檎。豫行 启动盘 --架构 臂六十四 --输出 启动介质 --预置 无
qemu-system-aarch64 -machine virt,gic-version=3,virtualization=off,secure=off,highmem-ecam=off,iommu=smmuv3,default-bus-bypass-iommu=off \
  -cpu host -accel hvf -m 2G -bios /opt/homebrew/share/qemu/edk2-aarch64-code.fd -display none -serial stdio -no-reboot \
  -device virtio-scsi-pci -drive if=none,id=yy_cd,format=raw,media=cdrom,readonly=on,file=启动介质/豫言启动臂.iso -device scsi-cd,drive=yy_cd
```

U 盘接法把最后三项换成 `-device qemu-xhci -drive if=none,id=yy_usb,format=raw,file=启动介质/豫言启动臂.iso -device usb-storage,drive=yy_usb`；纯模拟把 `-cpu host -accel hvf` 换成 `-cpu cortex-a57 -accel tcg`。UTM 的 QEMU 虚拟机（ARM64、UEFI）也能启动这张光盘。同一张光盘也能在林檎芯片 Mac 上的 VMware Fusion ARM 虚拟机里启动（2026-10-09）：引导程序按内存起址算出物理偏移，内核按 ACPI 表找串口与 GIC，屏幕上显示命令壳的输出，VMware 的 USB 键盘、鼠标可用，「图形」桌面也能运行，做法与设置见[ARM64 平台](文档/臂平台.汉语.md)。两架构以豫构豫行程序开机，USB 合成镜像的数据区用于持久文件与系统内造盘。Fusion ARM64 自建探针已验证开机豫构与 USB 数据盘挂载。

**启动盘兼作数据盘（2026-10-07）**：启动盘命令同时生成 `启动介质/豫言启动盘.img`：在 ISO 之后第一个 64 MiB 整数倍处接上持久盘的非零前段（ext4 的全部元数据与已用块都在前段里），再加 1 MiB 零，共约 150 MiB。把这个镜像写进一个 U 盘，它既能启动，又是数据盘。内核的 USB 存储驱动按 ext4 超级块识别数据盘：开头（起点 0）找不到时，会在 64 MiB 的第 1 至 16 倍处再找；找到后把那里当作数据盘的开头，读写的扇区号都加上这个起点，ISO 所在的部分保持原样。数据盘的容量在造盘时由 `--盘容量` 定下（ext4 的块数写在超级块里，挂载不会按 U 盘容量放大；U 盘比它小时，分配不越过 U 盘末尾）；要用满大 U 盘，就把 `--盘容量` 给到数据区的容量。前段只写到最后一个已用块，镜像仍是约 150 MiB，U 盘上原有的内容不必清（见[客体文件系统](文档/客体文件系统.汉语.md)）。QEMU 把镜像文件的大小当作 U 盘容量，所以先复制一份，稀疏扩到想要的大小（下例 16 GiB），再只接这一个 USB 存储设备：

```sh
cp 启动介质/豫言启动盘.img 测.img
dd if=/dev/zero of=测.img bs=1048576 count=0 seek=16384
qemu-system-x86_64 -machine q35 -accel tcg -m 8G -smp 4 -serial stdio -no-reboot \
  -drive if=none,id=yy_boot,format=raw,file=测.img \
  -device qemu-xhci,id=xhci -device usb-storage,bus=xhci.0,drive=yy_boot,bootindex=1 -boot order=c
```

用这一个 U 盘可以在系统里构建你好（缺省带工具链，四核 `-j 4` 约 48 秒），BIOS 与 UEFI 启动都可以。内核把旧池第 30、31 块（物理 124–128 MiB）留作 USB 控制器的 DMA 区，开机分配最后才用这两块；xHCI 的寄存器区在 4 GiB 以上时（QEMU 的 OVMF 放在 0xC0_00000000），内核把它映到虚址 0xBFE00000 的 2 MiB 窗口。

UEFI USB 启动可用 QEMU 的 OVMF 固件验证。以下是 Homebrew QEMU 路径；先复制一份可写的变量模板，再以 pflash 挂载代码与变量文件：

```sh
cp /opt/homebrew/share/qemu/edk2-i386-vars.fd ovmf-vars.fd
qemu-system-x86_64 -machine q35 -accel tcg -m 4G -smp 4 -display none -monitor none -serial stdio -no-reboot \
  -drive if=pflash,format=raw,unit=0,readonly=on,file=/opt/homebrew/share/qemu/edk2-x86_64-code.fd \
  -drive if=pflash,format=raw,unit=1,file=ovmf-vars.fd \
  -drive if=none,id=yy_iso,format=raw,file=启动介质/豫言启动.iso \
  -device qemu-xhci,id=xhci -device usb-storage,drive=yy_iso,bootindex=1
```

Linux 等系统的 OVMF 固件文件路径依安装方式而异，替换上面两个固件路径即可。须关闭 Secure Boot：当前的引导器没有签名。

`--预置` 缺省就是 `豫言操作系统/裸机/示例`（写 `--预置 无` 得空盘），它指向的目录树整棵放进盘里（盘缺省 65536 个扇区即 32 MiB，`--盘容量` 可改）；树里以 `。豫` 结尾的文件先编成程序（`/程序/你好。豫` 成 `/程序/你好.wasm`，脚本 `/程序/回声。脚本。豫` 成 `/程序/回声.wasm`），数据文件（`。数据。豫`，如 `系统/开机。数据。豫`）原样放进盘，以 `.底层库` 结尾的标记文件构建同名底层包（`/库/库甲.底层库` 成 `/库/库甲.wasm`），壳里用 `运行 /程序/你好.wasm 参数…` 启动，普通豫言程序可用 `豫言_加载模块`／`豫言_调用导出` 装载并调用库。用法见 `豫言操作系统/裸机/豫言系统。豫`；可运行的示例程序（你好、回声、质数、斐波那契、统计、复制文件、行数、环境变量）见 [示例](文档/示例.汉语.md)。

用法与行为（2026-10-09）：各项由「并行模拟」（`豫言操作系统/裸机/并行模拟。豫`）同时运行，`-j` 是同时运行的 QEMU 数，缺省为在线处理器数的一半。编译探针仍在主线程逐个进行（同一编译缓存同一时刻只跑一个构建），同一个源只编一次（八项壳测试共用一次 壳。豫 的编译）。仓库根有原生工具链（`豫构。林檎。豫行`、`编译器。林檎。豫行`）时缺省用原生的，否则用 Wasm 的，`--豫构`、`--编译器` 可另指。每项的镜像、盘、串口与日志放在临时目录下以项名为名的子目录里；同一盘组各阶共用的盘放在临时目录本层，同组各阶按原次序依次运行。结果按原次序打印；失败不中止，前项失败的同组后项记为跳过；全部跑完后打印汇总与失败清单，登记的已知失败（见下）单列、不计入失败，有失败则退出码为一。每个交互等待步至多五分钟，交互完后等模拟器退出至多一小时。2026-10-09 在 M 系列 Mac（18 核，其他会话同时占用，负载约 20）实测：98 项约 4–6 分钟（`-j 9`），时间主要花在豫构编译（71 次，约 240 秒）；同机串行（`-j 1`、Wasm 工具）411 秒；改动前的旧验证器约 10 分钟，且跑到 AMD64 壳测试就中止。

**已知失败**（验证器「已知失败」的登记：照常运行，打印为“已知失败”，不计入失败；登记的项通过时汇总提醒移出登记）：

- AMD64 的壳测试（`普通-壳-*-兼容六十四`，8 项）：壳经「中书」依赖「小学」，把「字书」的全拼候选表（约 6.5 MB）与拼音转换表（约 9.1 MB）编进被动数据段，壳.wasm 约 20 MB，其中大段约 19 MB。AMD64 用 `-kernel` 启动的镜像把大段区放在用户基址后两 MiB（0x400000），到外置的根端口扫描代码（0x7D0000）为止共 3.8 MiB（裸机后端 存储镜像「裸机大段区容量」、兼容核心「生兼自定镜像」），生成镜像时报“裸机大段区超过上限”。ARM64 的大段区在 0x50000000 起，共 64 MiB，这 8 项在 ARM64 上通过。修法留待后续版本：AMD64 的 `-kernel` 镜像照豫行文件的布局把大段放到 0x8000000 起（验证机加内存，内核按段映射），或让裸机壳只带精简的拼音数据。

另：文件修改时间 10-07 起取写入序号（6befe3fed），2026-10-10 起随 ext4 改为节点里的墙钟秒；`普通探针/盘/状态子任务-一。期望` 随之改为“修改时间合理：是”（子程序核对它落在 QEMU 时钟起点前十秒到起点后一小时之间）。

网卡（2026-10-13，持续改进目标「开放硬件驱动」第 1、2 步）：`--只验 网卡` 跑网卡探针（`普通探针/网卡/网卡。脚本。豫`），对每种 QEMU 网卡型号（虚拟网卡 virtio-net-pci、英特尔千兆 e1000、英特尔千兆e e1000e、英特尔高级 igb、通用串行网卡 usb-net（挂在 xHCI 上；以太地址明定为 40:54:00:12:34:56，因为 usb-net 把它放在描述符的 MAC 串里，各版本 QEMU 写的首字节不尽相同），期望文件 `普通探针/网卡/型号。期望`）在两种架构上各跑一项。QEMU 接用户网络，10.0.2.100 的 7 号端口转给宿主上的 `cat`；探针查设备接口的「问网卡」（网络栈随即 DHCP 取得 10.0.2.15），印出驱动名、以太地址与地址设定，与宿主 TCP 往返一行字，再解析 example.com（要宿主能上网）。别的项不另接网卡，QEMU 照常给默认网卡（ARM64 virt 为 virtio-net-pci，AMD64 q35 为 e1000e），开机时内核的网卡驱动也会初置它们。

**WASI**：WASI preview1 兼容层由 `客体二号/瓦西名称。底层。豫` 与 `瓦西分派。底层。豫` 部分接入。22 个样例各至少在一个原生目标运行过；裸机的随机数读处理器随机指令（RNDR、RDRAND；cortex-a53 与 qemu64 没有，返回失败而不终止任务），底层文件代办仍待实现（WASI 暂缓）。

**当前限制**：执行器的解释路径没有 SIMD（直接降级成机器码的底层程序用硬件浮点、NEON／SSE 向量与原子指令，见[数值降级](文档/数值降级.汉语.md)）；墙钟精度一秒，单调时钟精度一个内核滴答（10 毫秒）；文件与目录内容缓存上限 409600 字节；接在 UHCI/OHCI 伴随控制器上的全速 USB 键盘、租约续期与地址冲突检测留待后续版本。

已实现 ARM64、AMD64 的 QEMU 裸机启动验证。标准 Wasm 整数核心模块经过自有提前编译后，在真实用户态执行；最小特权核心提供页权限、同步异常入口、定时中断和受控服务。机器字节、重定位、启动头和页表全部由豫言生成，没有汇编源文件，也不调用外部汇编器或链接器。

内核是双架构微内核，任务、调度与内存管理由底层豫言写的豫言内核实现（见[动态任务](文档/动态任务.汉语.md)、[多核](文档/多核.汉语.md)），任务按需创建、子进程可以再起子进程，AMD64 与 ARM64 共用一份实现。以下各节描述内核的最小验证器 `裸机验证`：直接把标准 Wasm 整数模块提前编译成机器码运行，不经用户态执行器。普通豫言程序（完整 WasmGC）、持久文件系统、以普通豫言写的壳、子进程与动态装载都在用户态执行器 `客体二号` 上，见上文总览，各阶段实测证据见[阶段记录](文档/阶段记录.汉语.md)。

## 一条命令验证

在仓库根目录、安装 QEMU 后运行：

```sh
./豫构。林檎。豫行 文件 豫言操作系统/裸机/验证。豫 --输出 裸机验证.wasm -j 24
env 豫言初始堆兆数=1024 node --no-liftoff 豫言操作系统/宿主/节点/宿主.cjs 裸机验证.wasm     # 可加 -j 分片数、--只验 名称
```

验证器用豫言异步子进程运行 QEMU。父进程先构建豫言内核并验证设备能力，再按 `-j`（缺省为在线处理器数的一半）起同样多的分片子进程（本程序自身，带 `--分片 片号`）：每个子进程载入父进程造好的内核，准备本片各项的镜像，同时至多运行两个 QEMU，把每项结果写进临时目录的 `结果/序号`；父进程按原次序（ARM64 各项在前、AMD64 在后）打印。`-j 1` 在本进程里跑，不起子进程。分片按方式分组：同一方式的两种架构同片（共用首次计算出的客体模块）；共用持久盘、先写后读的两项（磁盘写入、磁盘重启读取）连同两种架构同片，片内按原次序依次运行。每项的镜像、模块、串口与日志放在临时目录下以“架构-方式”为名的子目录里，共用的持久盘放在临时目录本层，各项的文件名互不相同：QEMU 的监视器关闭（`-monitor none`），串口用各项自己的管道或标准输出，进程号文件各项一份。失败不中止：每项记成败，前项失败的同链后项记为跳过；全部跑完后打印汇总与失败清单，有失败则退出码为一；子进程异常退出时，它没交回的项记为失败并附其错误输出。等待步可以标为急等（标记一出现就要送入下一步，例如客体步数有限的循环程序）：有急等的用例时，子进程暂不启动新用例，改以十毫秒轮询。每个交互等待步与交互完后的等待各至多五分钟，超时按本轮独立进程号文件终止模拟器。豫构与编译器缺省同普通豫言验证（有原生用原生）。测试用到宿主的 `mktemp`、`mkdir`、`mkfifo`、`dd` 和 `/bin/kill`；`dd` 只用于负对照改动页表或中断标志，不参与正常镜像生成。

最初的六项基础检查如下；当前验证器另包含定时器、抢占、结构控制、存储、算术及外部模块等扩展用例，具体数量由运行结果计算：

| 检查 | 客体必须发生的行为 |
|---|---|
| 正常 | 在用户态完成函数调用、局部更新、溢出回绕及乘法核验，然后正常退出 |
| 隔离 | 完成同样核验后，读取内核私有页，产生权限异常；核心核对异常来源及地址 |
| 错误结果 | 将预期四十二改为四十三，核心必须报失败 |
| 放开权限 | 只改受测页表的用户访问位；探测不再陷入，验证必须报失败 |
| 操作数栈越界 | 保持 Wasm 类型正确，压入超过客体栈限额的值；运行时必须报失败 |
| 调用栈越界 | 有效模块进入递归，调用帧越界前必须报失败 |

检查同时匹配退出码和串口文字；负对照禁止出现成功标记。AMD64 使用模拟退出设备：通过退出码为三十三，拒绝为三十五。ARM64 使用半主机退出：通过为零，拒绝为一。串口输出都来自客体实际访问设备；退出机制仅用于结束模拟，不承担程序计算或打印。

## 模块契约与实现边界

输入必须导出无参数、无结果的「启动」。只允许以下函数导入，名字和签名均检查：

| 模块与名称 | 参数、结果 | 实现 |
|---|---|---|
| 平台／写字节 | 一个三十二位整数，无结果 | 经系统调用访问串口，检查字节范围 |
| 平台／核验 | 两个三十二位整数，无结果 | 比较实值与期值，失败立即停止验证 |
| 平台／用户态 | 无参数，一个三十二位结果 | 核心先检查保存的硬件用户态状态，才返回一 |
| 平台／读字节 | 无参数，一个三十二位结果 | 非阻塞读取串口，无数据返回负一 |
| 平台／时钟滴答 | 无参数，一个三十二位结果 | 返回已处理的定时中断计数 |
| 平台／任务编号 | 无参数，一个三十二位结果 | 返回当前静态任务编号 |
| 平台／任务状态 | 一个三十二位参数、一个三十二位结果 | 查询运行状态位，无效编号返回负一 |

当前启动验证协议要求正常结束前恰好完成四次核验；这属于测试协议，不是通用系统调用标准。不能将这些宿主接口误称为 WAT 规定的操作系统接口：模块导入及类型是标准的，平台服务语义由本项目定义。

函数参数、结果置于独立的非 GC 操作数栈，局部变量置于真实调用帧。两套后端均支持整数核心的所有现有指令。操作数栈限一百二十八千字节，调用栈约一百二十八千字节，二者有间隔；压值和分配调用帧时检查边界，超限进入失败路径。函数参数与附加局部合计至多一百二十八项；用户代码至多一兆字节。尚未做寄存器分配或跨函数栈检查消除。

ARM64 以自有 ELF64 头装载，在一级异常层安装页表和异常向量，通过异常返回进入零级用户态。AMD64 以多重引导首版地址头装载，从三十二位保护模式切换到六十四位长模式，安装页表、全局描述符、任务状态段及中断门，再进入第三特权环。QEMU、BIOS 与 UEFI 固件都能装载镜像：BIOS 走自有引导的 MBR 第二级，UEFI 走 `BOOTX64.EFI`／`BOOTAA64.EFI`。

两端采用静态两兆字节页映射。AMD64 核心位于低两兆，用户域位于二至四兆；ARM64 核心位于 `0x40000000` 区域，用户域位于 `0x40200000`，另有 `0x40400000` 私有受测页。串口只由特权核心访问。用户代码与用户栈尚在同一可读写用户映射中，未实现页级写入／执行互斥；这些限制不影响当前内核页隔离检查，但还不足以成为不可信程序的生产沙箱。

镜像生成阶段可以在无工具搜索路径时运行。生成器自身目前仍由既有豫言编译器构建；通过 Wasm 执行生成器也仍借助现有宿主。不能把客体无外部编译器与库依赖等同于整个自举工具链已经独立。

回收下限在本轮分配量达到当前回收阈时翻倍，空间不足引起的提前回收沿用原下限；每次回收清扫完再按存活量把它收缩到「起步下限」与「回收倍数×存活」的较大者（只降不升，升仍靠翻倍）：长跑服务一阵大分配之后闲下来，存活只剩几兆，下限却停在一两吉，下次回收要等再攒那么多垃圾，期间分配尽落新页、常驻不回落（2026-10-24，议题 442）。裸机较小的回收下限（常驻进程与编译器工作进程都是 64 MiB）只用于小内存裸机（平台号 1 且空闲内存不到 32 GiB）；豫行启动器下的客体按宿主的下限办（提案 00021）。退游程先把尚未记账的内联分配计入本轮，随后判断，清扫时归零计数；判断时扣掉新大对象表里的字节，因为直接在老区分配的大对象多是逐块读大文件时的块、每块读完即丢，按它们翻倍会让两次回收之间的垃圾翻一番，常驻内存随文件长大；带型调用进宿主原语之前也按分配计先收一次，宿主原语里分配的块才等得到回收（2026-10-24，议题 472）。起步下限、最大下限、工作进程下限、存活量倍数与全收间隔沿用原值。`回收下限。底层。测试。豫` 以十六页合成状态覆盖提前回收、阈值触发、游程结算、最大下限与工作进程。

## 模块

`构建摘要` 补齐构建基础的 `取今程序沙二五六` 与 `取卷沙二五六` 宿主导入，使用普通豫言底层三十二位运算返回小写十六进制摘要。当前程序取本实例嵌入的 Wasm 内容；文件摘要取指定路径的内容。AOT 程序的命令行程序名仍指可执行容器，核对程序摘要时须指定原始 Wasm 文件。预编二生成的原生程序里，生成器已算好客体的摘要（客体字节的 SHA-256；编译器直出的原生程序与由汇编树码造的豫行文件取客体汇编树码的 SHA-256）并写进 `预编摘要可用`、`预编摘要字零` 至 `预编摘要字一五` 这些占位导出（64 个十六进制字符按小端每四个拼成一个字），`取今程序沙二五六` 直接返回它，不再在每个进程启动后对整个客体算一遍；解释执行时这些占位为零，照旧现算。

`布局` 内存布局与状态格常量；`基础` 输出、变长整数、内存与宽整数助手；其余模块依依赖顺序排列。语言约定见 `应用/豫言编译器/文档/底层模式.汉语.md`。

`域名报文` 用普通豫言底层模式写 DNS 单问题查询及 A、AAAA 回答的编解码，支持回答名的压缩指针；原生进程在 Linux 上经 UDP 使用它。固定报文探针覆盖两种记录及无效指针。

`网卡`、`网络栈`（提案 00012 第 4 步）：初始任务里的网卡接口（2026-10-13 起两架构都经内核服务 61–63 收发，内核先用自己的原生网卡驱动，见内核 `网卡表`）与以太网、ARP、IPv4、UDP、TCP、环回的网络栈（本机 10.0.2.15/24，网关 10.0.2.2，32 个 TCP 连接、16 个 UDP 端点；2026-10-22 起收包验 IPv4 头、TCP 与 UDP 的校验和，帧比 IP 总长短的截短包丢弃，两类丢弃各计一列），经底层服务（底层网络的 TCP、数据报与套接字地址，见下文“底层转送”）供子任务与林兼容层使用；网络区在开机流程里（初始化堆之前）预留。

网卡（2026-10-13 起）：执行器只经内核服务 61 网帧收、62 网帧发、63 网卡信息（见平台接口规范）收发，内核先用原生网卡（虚拟网卡 virtio-net、英特尔千兆 e1000 与 e1000e 等），没有原生网卡或链路都没通时用驱动客体交来的网卡；以网卡自己的以太地址收发，链路通了才算就绪，未通时每次网络请求再问一次。原先 ARM64 执行器里的用户态 virtio-net 已删去。`裸机传输控制`（2026-10-13）：初始任务里，标准库的传输控制协议原语 77–90 直接用网络栈的套接字，开始连接的主机名按数字地址（点分十进制或 IPv6 字面量）、localhost、A 记录或（配出全局 IPv6 地址后优先）AAAA 记录解析，连 IPv6 时先试六版、连不上回落四版，开机程序与壳里直接运行的豫言句因此能连网；子任务（没有网络区）仍返回不支持，待办事项。`公共网卡原语`（2026-10-13）：设备接口的「问网卡」（原语 245，壳命令「网络态」用），经服务 75 读各网卡记录，并报网络栈的地址设定（IPv4 五量、IPv6 的链路本地、全局、缺省路由、前缀长与状态，以及收包丢弃计数：校验和错、截短）。网卡第一次就绪时网络栈先用 DHCP 取址（广播 DISCOVER、REQUEST，每步至多约 1 秒、四轮），得到本机址、网关、掩码与域名服务器，失败则用默认的 10.0.2.15/24、网关 10.0.2.2、域名服务 10.0.2.3，并在控制台报一行。林程序发往 10.0.2.3 或 127.0.0.1（林根没有 resolv.conf 时 glibc 的默认）53 端口的报文改发实际的域名服务器，回报的来源再改回原址。租约续期与地址冲突检测留待后续版本。

网络闲办（2026-10-22，议题 315）：裸机的网卡与 TCP 定时都靠轮询，初始任务等终端键（`主机` 的「等待终端键」）与桌面等事件（`主机` 的「显示轮办」）的空当里各补一轮「网络轮询」（`底层服务` 的「网络闲办」）：没人发网络请求时也收帧、回 ARP、退回重传，对没有监听者的端口按 RFC 793 回 RST；开机壳等键空闲满一秒时清一次属主已结束的转柄并关掉它们的套接字，死掉的服务端留下的监听口因此在一两秒内消失，连接方立即看到拒绝而不必等到超时。等键的空当里还每秒交回一次“没有键”，让开机壳办「候键余事」（看护开机自启的服务、进入桌面）。2026-10-23（议题 420）：等键的空当里一有子任务就交回，空闲满一秒的这一步常常轮不到，所以「收死子」回收已结束的遣使子任务之前先清一遍属主已结束的转柄（回收以后槽会被新任务占用，动态句柄没有代际，旧转柄就清不掉了）；显式绑定端口只与同端口的监听口、已绑定还没用的套接字冲突（同 SO_REUSEADDR），死掉的服务端留下的旧连接还在关闭途中时，重起的服务照样能监听。

屏幕与输入（2026-10-17，远程界面调试）：设备接口的 `观屏`、`拟键`、`拟指`、`拟钮` 映射到原语 205–208（`屏键原语`）。观屏先经内核服务 103 以容量 0 问尺寸，借第 1 个中转缓冲读回整屏 RGBA，再拷成字节串交出 `屏照已得`；三个拟入原语把参数编成服务 104 的种与值。原生系统返回资源暂不可用，豫行启动器对两个服务返回 −1，也得资源暂不可用。

## 启动

`入口` 的 启动一次 先运行客体模块的 `_start`（按测试名运行时改为该名的导出），再处理挂起的请求。`_start` 由编译器生成，先做静态初始化，再调用入口函数「入口」（提案 00006）；入口函数里未接住的异常交给与 `_start` 相同的未捕获处理（打印后以 1 退出）。原生宿主（macOS、Linux）上，`_start` 正常返回、结果打完以后，出口把捕获的输出交清，就以零退出、直接交操作系统结束进程，与「辞」同路（议题 522）；标准输出与标准错误逐字节直接写系统调用，没有要冲刷的缓冲。裸机上照旧返回，交给内核的启动循环清场后重启下一个程序；轩窗的入口返回后自己调 ExitProcess。

## 豫言操作系统底层接口：裸机后端

`裸机底层状态码`、`裸机底层基础`、`裸机底层句柄`、`裸机底层文件`、`裸机底层终端`、`裸机底层网络`、`裸机底层进程` 七个模块，是[豫言操作系统底层接口](../../../豫寓底榫卯/总纲.汉语.md)在裸机上的实现（45 个函数，方案见[底层接口方案](../../../文档/豫言操作系统底层接口方案.汉语.md)）。它们是**新增、独立**的模块：直接复用既有的文件系统（`文件系统读文件`、`文件系统写文件`、`文件系统建目录`、`文件系统删除`等）、控制台（`读字节`、`读行`、`打印串`）与时钟（`时钟滴答`、`墙钟秒`）原语，不改动这些既有实现；入口只在启动时新增一次 `底柄初始化` 调用（在固定状态格 3664、3668 保存动态句柄表地址与终端模式；表头保存行输入剩余状态，经 `取区域` 分配句柄表、路径缓冲与内容缓冲，暂存缓冲仍供文件和时钟操作临时使用）。

子任务重启会清空动态区；`重启准备` 同时清除旧句柄表指针，下一次启动重新分配句柄表并建立根句柄 3。当前子任务没有块设备，底层文件操作仍需由初始任务经独立邮箱协议代办；GC 文件原语已有自己的对象协议。

- **句柄模型**：句柄 0/1/2 是标准三流；句柄 3 恒为根目录（唯一的预开目录）；4 起的 13 个槽按需分配给已打开的文件与目录，每槽有独立的路径缓冲（22400 字节）与内容缓冲（409600 字节，整文件缓存）。底层文件另从动态区取得临时路径和数据缓冲。
- **路径解析**：相对目录句柄解析，不含当前目录，`..` 越出目录句柄子树报错，与既有 `主机文件` 里依赖“当前目录”状态的路径规范化是两套独立的逻辑。
- **已知限制**（均已在各文件的双语注释里逐条注明）：`底层网络`、`底层进程` 全部返回“不支持”（网络因裸机无网络栈；进程因桥接既有的 GC 对象参数子进程机制不在本轮范围）；`建管道`、`取终端尺寸` 返回“不支持”；`填随机字节` 读处理器随机数（ARM64 RNDR、AMD64 RDRAND，目标内建导入“硬件随机”），处理器不支持时返回“不支持”（安全随机字节串原语 98 这时改用熵池，见下文“后备熵源”）；文件与目录内容缓存上限 409600 字节，超过则相应操作返回“溢出”；单调时钟精度 10 毫秒（内核滴答），墙钟毫秒级（内核开机读一次实时钟作基准，此后按滴答与周期计数推算，再带对时设下的偏移，见下条）。
- **GC shim 的改接**：控制台输出原语（1–4 号）经本接口的 `写`；Linux 上的文件原语经本接口的 Linux 后端（见下节）。裸机上的文件原语仍直接用执行器内的文件系统（待办事项：放大整文件缓存的上限后改经本接口）。

## 多平台：同一份执行器在 Linux 与 macOS 上运行

执行器是同一份整数 Wasm 模块，由寄存器降级按目标生成裸机镜像、Linux 可执行文件或 macOS 可执行文件。运行时靠目标内建导入 `导入：目标：平台号`（降级时绑定为常量：裸机 1、Linux 2、macOS 3、Windows 4）选择平台实现；其他目标的导入降级为陷阱桩，不会被执行。各平台的导入都声明在 `平台接口/` 的接口文件里（`林纳`、`林檎`、`轩窗`、`平台`、`目标`），导入模块名就是接口文件名。

- `林系统`、`苹系统`：Linux 系统调用包装（导入模块名“林纳”）与 macOS libSystem 包装（导入模块名“林檎”，返回 -1 时导入桩已换成 -errno），以及 `是林`、`是苹` 与各自的 errno 转换表（两个系统的 errno 编号不同）。`原生系统` 在两者之间分派写、读、退出、时钟与终端判断。
- `平台`：写字节、读字节、退出、时钟滴答、墙钟、中断查询在原生系统上改走系统调用或 libSystem；任务与邮箱服务在原生系统上尚未实现，按失败返回（待办事项）。
- `林启动`、`苹启动`：启动时写程序名区、参数区与环境块。Linux 先读 `/proc/self/cmdline`：程序名取第 0 项（链接本身，不解析符号链接），含斜线时与当前目录拼成绝对路径，取不到再退回 `/proc/self/exe` 的目标；参数与 `/proc/self/environ` 照旧。macOS 用 `sysctl` 的 `KERN_PROCARGS2`（缓冲是启动时新增长的两页），程序名是启动时记下的路径。两平台的「自号」由此同义，按程序名分派角色的程序（如测试替身）经符号链接启动时认得自己的名字。之后的宿主原语不必区分平台。
- `轩窗系统`、`轩窗启动`、`轩窗底层`：Windows（平台号 4）。系统入口经 kernel32、ntdll、bcrypt（导入模块名“轩窗”）；标准流读写、单调与墙钟（64 位计数用本模块的逐位长除与 MulDiv 换算）、UTF-16 与 UTF-8 互转；启动时由 GetModuleFileNameW 与 NtQueryInformationProcess（命令行）写程序名区与参数区（按 Windows 规则拆参数），路径写成执行器内部的 `/C:/a/b` 形式；暂存区（1 MiB，前 256 KiB 保持 Linux 布局）与 Linux 后端共用同一个状态格。文件（CreateFileW 等，旗标 FILE_FLAG_BACKUP_SEMANTICS|FILE_ATTRIBUTE_NORMAL）已实现；启动时用 GetEnvironmentStringsW 取本进程的全量环境写进环境块（宽字符逐字经 RtlMoveMemory 拷进线性内存，再转 UTF-8；盘符当前目录项跳过），「问俗」、按名找程序的 PATH 搜索与子程序都读这一块，按名取环境变量（GetEnvironmentVariableW）仍可用；宿主原语十（寓轩窗）按平台号四返回阳，本机系统因而在轩窗上取轩窗。`轩窗进程`：建管道（CreatePipe）、运行程序（CreateProcessW，按 MSVCRT 规则拼命令行，环境块转 UTF-16，三个标准流临时设为可继承）、进程表（与 Linux 同布局）、取退出码、终止、关闭与轮询式等待（进程、管道、控制台、套接字）；管道可设为不阻塞（登记表，读前用 PeekNamedPipe 看可读字节数，没有数据回暂不可用）。TCP 经 ws2_32（套接字登记表区分套接字与其他句柄，Winsock 错误码按 Linux 映射对齐）。导入参数类别 5 为可空指针。待办事项：Windows 的 hosts 与 DNS、控制台模式、目录句柄与工作目录句柄。
- `轩窗缺页`：Windows 上碰到才提交（提案 00021）。Windows 上提交的内存不论碰没碰过都计入系统的提交上限；Windows AMD64 的执行器入口只预留动态区，并以 AddVectoredExceptionHandler 注册缺页桩（后端 `兼降级本术` 的「兼轩窗缺页桩」，只把 Win64 调用约定转成本降级的内部约定），缺页桩调导出「轩窗缺页处理」：访问违例的故障地址落在执行器自己的动态区，或落在豫行启动器给客体预留、已经求过块的动态区（状态视客记里的启动器记录）里时，就地提交所在的一块（32 MiB）再重新执行；同一块刚提交过又出错就交还系统；提交失败时往标准错误写一行再交还系统。进程于是只按碰过的内存计提交，`-j` 大时也起得来工作进程。Windows ARM64 的入口仍一次提交整个动态区（待办事项）。

## 常驻工作进程（提案 00007 议三）

macOS 与 Linux 原生里，编译器并行编译起“本程序 `--mode=worker` …”的异步子进程时，执行器把参数写成任务帧交给常驻的工作者（本程序 `--常驻工作者`，标准输入接任务管、标准输出接结果管）。工作者读一个任务帧到参数区，`启动一次` 跑完任务；任务写往标准输出与标准错误的字节先截留在两块缓冲里（`常驻` 模块，各 16 MiB），任务结束后连同退出码作一个结果帧交回父进程；随后清场（`常驻清场`：清零回收堆里本任务用到的那段对应的标记位图与卡表，再清状态格与回收格），读下一个任务。任务中途调用退出、或回收堆用过 256 MiB 以上时，工作者发退出帧后退出，父进程照常继续调度，下次取闲时再收回它。父进程一侧（`原生子进程`）把派出的任务照常登记在异步表里，表项读工作者的结果管，凑满一帧就完成；结果管读到尾而帧没凑满（工作者意外退出）时以它的退出码完成，说明里带退出码（被信号杀死时是 128 加信号）。文件读写、删除、改名失败这类要印出原因并以退出码结束进程的路径，工作者先把原因与退出码写成退出帧再退出，父进程因此能把原因照样报出来，不再只剩一句“意外退出”（议题 #238）。池满（64 个）、参数放不进参数区（64 KiB）时照常另起进程。省掉的是每个任务的进程启动、执行器与客体初始化与新内存的缺页：本机冷编豫言系统约快 4%，完整构建豫言编译器 24–28 秒降到约 23–24 秒，产物逐字节相同。清场按址读写堆基、位图、卡表与常驻顶。动态区与回收堆的字节都不清：清场把区脏顶（状态格 9116）抬到本任务的区域顶，之后 `取区域` 取到区脏顶以下的地方先清零，先写后读的栈与缓冲（值栈等栈、栈复制缓冲、截留缓冲、栈图表、中转缓冲、底柄内容缓冲、清扫线程栈）用 `取区域不清`；回收堆的分配本来就把要读的地方写好。栈图表每个任务落在同一处，第一个任务复制以后各任务直接用（常驻栈图，状态格 9332）。这样每个任务少清零约八十兆字节、少复制约十二兆字节（十程序无改动合编，原先清场与复制栈图表每个任务约十毫秒）。全局初值也不再每个任务都求（`全局初值`）：第一个任务求完后把回收堆里它分配的那段（连同位图、卡表、全局表、大块桶表与状态格里被它改过的字）拍成快照，放在线性地址 1.75 GiB 起的快照区；第二个任务先清零那段回收堆、照常求值并逐字节核对，相同才启用；之后的任务把快照放回（编译器约三万八千个全局、22 MB）：Linux 上回收堆那段能整页对齐的部分事先写进 /dev/shm 里的一个临时文件（放不下再放 /tmp，建好即删名，只留句柄），每个任务开始时按 16 KiB 页写时复制映射回去，没碰到的页（拼音表这类大常量多半整张不读）不拷，头尾不满一页的部分与位图、卡表、全局表照旧拷回，每个工作者第一次映回后逐字节核对一遍，十程序无改动合编的前端快约一成；macOS 上缺页比拷贝贵，整段拷回。动态区长到快照区时停用快照（状态格 9336）。豫行启动器下的豫行客体（提案 00021，宿主门中，2026-10-14 起）与原生走同一套：父客体按原生的做法建池、派任务（`原生子进程`），运行程序、建管道、等待经底层转送交启动器办理，豫行文件由启动器改起为“启动器 `--豫行` 程序 `--常驻工作者`”；工作者里的客体照样经句柄 0、1 收发任务帧（读写经「常驻门转」交启动器），任务输出截留在客体里，见 `豫行启动` 与下文“底层转送”。裸机与 Windows 的常驻工作进程留待后续版本。

父进程还看着每一件派出的任务：任务派出五秒仍没有一个字节交回时，向那个工作者写一个探问帧（参数是 `--常驻问` 加四字节时刻）；工作者闲在等活就立刻回一个问答帧，父进程据此知道这件任务的结果帧丢了（派出的任务或交回的结果在中途丢了）。每件常驻任务派出时，父进程把任务帧抄一份进池项的副本区（至多 65024 字节，更长的帧没有副本）；判丢了以后，这一项还没有重派过、又有副本时，先照副本把任务重派给一个闲的工作者（多半就是刚回到等活的原来那个），换掉异步项里记的工作者、结果管与池槽号，派出时刻与探问时刻重新起算，这一项继续等，构建照常往下走。重派不成功、任务帧太长没有副本、或重派之后又丢，才把那件任务按“常驻工作进程已回到等活（池槽 N），这一件任务的结果没有交回：结果帧在中途丢了，重派过一次仍未交回……”记失败，构建随即以非零退出，不再永远等（议题 #312、#337）。工作者忙着就等手头这件完了再答，答复里的时刻与这一问对不上（旧问的答复）时直接丢掉。工作者的进程已经退出、结果管却因为孙进程握着写端而没有读到尾时，父进程照查到的退出码把那件任务记失败并收回池槽（议题 #312）。

带境任务帧（提案 00035，2026-10-17）：原语 210「遣使于境」（标准库「东道带列」的「遣使于境」，接收程序名、参数列、工作目录与环境块）能交常驻工作者的，写成带境任务帧（魔数“YYCD”，帧头之后依次是参数区内容、工作目录与环境块，环境块是若干以零结尾的“名=值”）；工作者把目录与环境块放在参数区内容之后，任务境三格（状态格 9104 环境址、9108 环境长、9112 目录址）指向它们：`启动一次` 里继承当前目录之前先把进程工作目录切到任务目录，取环境变量（原语 9）、取全部环境（原语 211「风俗」）与起子进程都改用任务的环境块。普通任务帧把三格清零，照用工作者启动时的目录与环境。不能交常驻工作者的另起子进程：目录与环境块抄进中转缓冲三，临时写进三格，`原生起程` 把环境块填进运行程序块 +20、+24，把目录打开成句柄填进 +40，起完关掉、三格复原。构建服务（将作）的代役靠它在各工作树的目录里、照各自的环境执行任务。macOS 的管道两端都设 FD_CLOEXEC（Linux 的 pipe2 本来带 O_CLOEXEC），子进程只继承经文件动作复制到 0、1、2 的三条标准流，长驻的子孙（如构建服务）不再握着祖辈等待读完的管道。

## 预编：WasmGC 函数直接成为机器码（路二乙档第一版）

第一版预编的转译器（「预编并入」）已在 2026-10-11 删除（提案 00007 收尾），现在只用第二版（见下文“预编二”一节），执行器一侧的 `预编接口。底层。豫` 由第二版沿用；本节记录第一版的设计。第一版把客体 WasmGC 模块的每个函数转译成一个整数 Wasm 函数，并入执行器模块后一起经寄存器降级生成机器码；执行器照常解析模块、建类型表、初始化全局与数据，但不再解释函数体。转译器在 `库/裸机后端/预编转译。豫`，执行器一侧的运行时接口在 `预编接口。底层。豫`。编译器直出的原生产物现在都用下文的预编二。

- **值都在值栈上**：布局与解释器相同（每槽 8 字节，引用与 32 位整数在低字），所以保守回收照常看得见；转译函数的签名是（帧）→ i32，参数与局部变量从帧起，操作数栈在其上，调用者把参数放在栈顶、被调用者的帧就从那里开始。
- **简单指令内联，复杂指令调解释器的处理函数**：局部变量、常量、i32 运算与比较、少数 i64 指令、引用判空与相等、控制流直接写成整数指令；结构、数组、类型转换、i64 其余与浮点、访存、表与杂项指令调用执行器导出的“预编”函数（就是解释器的指令处理函数），传入立即数在模块字节中的地址。
- **控制流一一对应**：块、循环、条件对应整数 Wasm 的同名结构，分支先把携带的值搬到目标槽；尾调用（return_call 及间接、引用尾调用）先把参数搬到帧首，再“调用后立即返回”，寄存器降级把这种形状变成尾跳；间接调用经执行器导出的 `预编派发`（按函数号二分，叶子上尾跳到转译函数）。
- **异常用标志传播**：抛出时记下载荷并置 `状态预编异常`，每次调用转译函数后检查，在尝试表里就跳到它的处理代码，否则返回；最外层仍有异常即按未捕获异常退出（137）。
- **大模块**：超过 448 KiB 模块窗口的客体（如编译器）不嵌入窗口，而作为尾块写进可执行文件（Linux 与 Windows 附在文件末尾，macOS 放在 __LINKEDIT 里签名之前），执行器启动时读回到动态区开头；Windows 上由 `原生装载` 经 CreateFileW、GetFileInformationByHandle、SetFilePointerEx 与 ReadFile 读自身的文件；Linux 上读 /proc/self/exe（程序名区取的是 cmdline 第 0 项，可能是虚根路径或别名，不能拿来开自身）。Linux 代码太大时单独放一个载入段（ARM64 在 0x10000000，x86-64 在 0x50000000）。预编二的原生文件（2026-10-09 起，提案 00007 第 1 步）嵌入的是预编侧表而不是客体模块，侧表超过 448 KiB 时同样作尾块，执行器认出侧表就直接装表，不解析模块。
- **降级器随之扩充**：“调用后立即返回”变尾跳；每 512 KiB 代码插一个陷阱岛，越界与除零检查跳到最近的岛；大函数（超过 2 万条指令）的条件跳转改用“反条件跳过 + b”；汇编器只在条件分支上计算 19 位位移（原先 b、bl 超过 1 MiB 也会误报超程）。

现状（2026-09-28）：macOS arm64 上普通探针、文件探针与原生探针共 12 项在预编模式下与参照输出逐字一致；短程序比解释执行快约两倍（多为启动开销）。待办事项：内联更多热指令（ref.cast、struct.get、array.get、i31）、非引用值留在寄存器里、Linux 上的预编验证、编译器本身的预编与原生自举。

续记（2026-09-29）：Linux ARM64 的完整预编一致性组 15 项通过，普通、文件与原生探针均与裸机或 Node 参照逐字相同。Linux x86-64 的解释模式打印探针通过；同机 Docker 的 Rosetta 在装载较大的预编产物时报告 `failed to mmap segment: 22`，尚须在真实 Linux x86-64 运行器上验预编。编译器自身的原生自举仍待完成。

## 预编二：客体的值放进寄存器与原生栈（路二乙档第二版）

结构对象头宽八字节。引用字段宽一个址宽（八字节，见下节），其他字段保留八字节，各字段按自身宽度对齐，对象总长按八字节对齐且至少十六字节。继承字段从完整字段序列计算偏移，父类型末尾的填充不参与子类型字段偏移。值栈槽宽八字节，引用读入值栈时高字清零；数组布局保持原有约定。执行器与预编生成器须使用同一份结构布局，变更布局后须成套重建，已有原生可执行文件保留其内嵌执行器和生成代码。

预编二用新的转译器（`库/裸机后端/预编二转译。豫`），编译器 `--目标 本机` 直出的原生产物都由它生成。与第一版的区别：

- **客体的值不再放在执行器的值栈上**：每个客体函数转译成一个宽整数函数（`库/裸机后端/宽降级原语。豫`），参数、局部变量与操作数就是这个函数自己的参数、局部与操作数；每个值六十四位（i32 与引用零扩展），由寄存器降级放进寄存器与原生栈帧。i64 运算写成内在调用，降级器就地展开为六十四位指令。
- **调用直接传参**：客体函数之间直接调用；call_ref 与 call_indirect 经跳表零（每个客体函数一项）；执行器经 `预编派发` 调用客体函数时走跳表一里的适配函数（从值栈帧读参数、写回结果）。客体导入由导入桩经 `预编调用导入` 调用执行器。
- **内联的热指令**：结构与数组的读写与长度、i31、判空、精确类型的 ref.test/ref.cast 直接写成整数指令；struct.new、struct.new_default 与 array.new_fixed 在当前游程里碰撞分配（游标、游限两个状态格；新游标用常址写四写回，两个头字拼成一个八字节常量一次写入，对象起始位由专用内在置位，ARM64 八条），不够时调用 `预编分配`。按常数下标的数组取值不装下标：长度直接与常数比较，元素按立即偏移读取。下标已知小于数组长度时（转译事实：br_if 落空路径上“下标局部无号小于某局部”，且那个局部是该数组的 array.len）不查界。其余指令把操作数写进执行器值栈的暂存区（起址在 `状态预编栈顶`，由适配函数设置），再调用解释器的处理函数。
- **转译时内联**：直接调用或直接尾调用另一个客体函数，且其代码体不超过 60 字节、不含尝试表与旧式异常指令时，不发调用，而在调用处接着转译它的体。参数与局部借一段块临时，实参弹进参数、其余局部清零，体包进一个结果数相同的块；被调函数里的 return 跳出这个块，尾调用改成普通调用加异常检查再跳出；展开在尾调用处时，二者照旧是调用者的返回与尾调用，块后补一个返回。转译事实（非空、类型、界）因此跨过函数边界。只内联一层，不内联自己。降级之前另有整数层的小叶函数内联（`库/裸机后端/内联小函数。豫`）。并入时客体定义函数只放占位（签名、零个局部、空体），降级与整数层内联要用函数体时才经 `降级取体` 的钩转译：内联准备只留下不超过内联上限的小函数体，大函数只留占位，降级完就把钩复位；遍历两万多个函数用尾递归的带序映射（标准库「遍序」经「遍二」非尾递归，原生保守扫描时两万多层栈帧里留着各函数降级的临时数据）。这样原生程序生成原生产物时，同时存着的只有执行器自身的中间表示、小函数体与已降级的机器码。
- **回收看原生栈**：`预编二可用` 为 1 时，启动时预留栈复制缓冲（原生 258 MiB，与 macOS、Linux 上 ARM64 约 256 MiB 的原生栈相配，只占虚拟地址；裸机见下）；回收时经目标内建导入 `栈复制` 把被调用者保存寄存器与当前原生栈复制进来，逐四字节保守扫描。
- **栈图**（提案 00020）：模块带预编客体时，降级器在每个函数入口放一条函数展开记（帧大与序言保存寄存器的次序），连接时在代码之后接一张栈图表（`冶铸` 机器编码的「写栈图表」）。执行器启动时调占位导出“栈图表复制”（新降级器把它换成复制桩，旧降级器编出的本体返回零）把表复制进动态区（`栈图` 模块「栈图表装入」，地址记在状态格 9072）；ARM64 的栈复制缓冲前 96 字节是 x19 至 x30，AMD64 前 48 字节是 rbx、rbp、r12 至 r15。编译开关「栈图诊断」为一时，每次回收在栈复制之后按表逐帧走一遍原生栈并打印帧数、停因与各帧码偏，回收照旧保守扫描。第 2 步起表里另有调用点栈图（栈图表第二版的调点项与内容，见 `冶铸` 机器编码的「写栈图表」），「栈图表装入」另取 256 字节记寄位表（状态格 9076）。编译开关「栈图核对」为一时，每次回收在栈复制之后逐帧走栈，并跟踪被调用者保存寄存器存在哪一格（栈复制头或某帧的保存格）：旗带二位的客体帧按调点项取精确根，核对每个指到堆里的都是对象起点（坏根），再逐个八字节看本帧的局部与溢出槽，数保守扫描找得到、精确根没报的对象指针（保守独有）；每次回收打印一行 `栈图核对：帧 … 客帧 … 精确 … 不精确 … 无图 … 根 … 坏根 … 保守独有 … 停因 …` 与至多若干条明细，回收照旧保守扫描。
- **精确客体帧**（提案 00020 第 3 步）：启动时「栈图表装入」以空表试调一次占位导出“栈回写”，新降级器的桩返回零，记状态格 9080 为一（旧降级器编出的本体返回负一，记零）。六十四位地址构建在有第二版栈图表、栈回写可用且编译开关「精确客帧」为一时，回收照常栈复制之后逐帧走栈（`堆` 模块「精确走栈」）：带精确调用点栈图的客体帧按栈图标记引用、不钉住，引用所在格（缓冲里的帧槽，或某帧的保存格、栈复制头里的寄存器）的线性地址记进缓冲里栈数据之后的槽表；执行器帧与没有精确栈图的帧标记局部与溢出槽，以及本帧序言保存过的寄存器此刻所在格的值；查不到函数、走出代码或到栈复制末尾时，其余的栈与各寄存器所在格一并保守扫描。保守扫到的对象在整理时照旧钉住。整理搬走了对象时，「精确改写」按槽表改写缓冲里的格，回收函数再直接调用“栈回写”桩：它与栈复制同在回收函数这一帧，sp 相同，把表里改过的帧槽按缓冲偏移写回原生栈，并把仍只在寄存器里的引用（走栈时没有哪一帧保存过，回收函数自己也不用）按掩码装回寄存器。整理压力打开时，搬移与改写之后把疏散的块填成 0xEE（「整理毒化」），漏改的引用一用就读到毒值。三十二位构建与开关为零时照旧整段保守扫描。
- **堆**：小块分配从游程里递增切出（游程取自堆顶的一段或空闲大块；都没有时取不小于所需的最大小类空闲块整块作游程，余下的由预编二的内联分配接着切，碎堆里不再一次分配调一次执行器），结束游程时按实际用量计入已分配字节数。回收只用标记位图（不写对象头），清扫后把标记位图拷成对象起始位图。
- **分代回收**：标记位图在回收后保留，已标记的对象就是老对象；第零次及每八次做全量回收，其余次要回收只标记新对象。写屏障是卡表（每 512 字节一字节）：struct.set、array.set 写引用前用内在九十一万、九十二万（窥看次顶、第三项的对象），引用数组的 array.copy 之后用内在九十万（弹出目标数组），把对象头所在的卡写零，ARM64 三条指令（ldr 卡表、add 加址右移九、strb wzr）；预编与解释器、宿主的 `设元组项` 用普通指令记卡。次要回收只扫描既脏又有老对象的卡（老卡表：清扫时给每个存活对象的卡记一）上起始的老对象。分配取不到空间时：上次回收以来分配的量不到先增堆界就先增长堆（回收刚做过，再收腾不出多少；非移动的堆碎片多时大块屡屡取不到，原先每次先回收，回收空转）。先增堆界在宿主上的非工作进程是回收阈本身，在裸机与编译器工作进程是回收阈的四分之一（提案 00020 第 2 步：最终链接按四分之一的界每轮只分配到阈的四分之一就因取不到中等大小的块而回收，回收次数翻倍；改后原生生成豫构回收约 230 → 85 次、墙钟约减四分之一到四成，峰值内存约多三成）；到了界时先照常回收一次、仍不够再增长堆；堆已到内存上限时强制做一次全量回收（次要回收不收老垃圾），之后仍不够才报堆内存不足。回收下限：编译器工作进程（命令行第一个参数是 --mode=worker）固定 64 MiB，其他进程从 32 MiB 起每次回收翻倍到 1 GiB（裸机到 256 MiB）；完整构建要起一千五百多个短命工作进程，下限一律 1 GiB 时它们不等回收就把全部分配落在新页上（本机一次完整构建缺页 6300 万次、系统态二百多秒），现在是一千多万次、三十多秒，单进程冷编不变。回收阈与回收后预留按存活量的三倍（回收倍数）定：原先阈值虽是两倍存活，堆限只预留到“存活＋下限”，实际约每分配一倍存活就回收一次；存活量大的任务每次清扫都要重走全部存活对象，次数一多就贵。改后编译器最终链接回收 26 → 13 次、指令 −26%，最慢的类型检查任务指令 −20%，代价是这两个任务的峰值内存多五到七成。原生的线性内存上限是 65535 页（约 4 GiB）；六十四位地址构建的上限更大（macOS 与 Linux 68 TiB），见下节。
- **复制式新生代**（提案 00020 第 4 步）：六十四位地址构建在精确客帧可用且编译开关「新生代开」为一时打开（新生记录在状态格 9084）。堆开头留一段新生区（小内存裸机保留 64 MiB，其余 1 GiB，只占虚拟地址；编译器工作进程短命、存活多，不开新生代，常驻工作者也不开），老区与堆顶从它之后的 2 MiB 边界起。不超过 256 KiB 的对象在新生区里碰撞分配（游程是新生区里钉住的对象之间的空隙，预编二的内联分配照旧用游标、游限），更大的直接在老区分配，并记进新大对象表（至多 65536 项），次要回收没标记到的当轮释放（保守根指到它内部也算标到），放不下的留给全量回收；新生区起始用 16 MiB，次要回收后老区跨度超过它的两倍时翻倍。新生区用完时做次要回收：先标记保守根（值栈、执行器帧与没有精确栈图的帧、全局与表等），落在新生区里的对象原地钉住（候选字指到对象内部也算）；再处理客体帧的精确根、脏卡上的老对象与标记栈：新生区里未钉住的对象复制到老区（旧头第 31 位置一表示已转发，新址写在 +8），老区里上次回收以来新分配的对象原地标记；复制出来的对象逐个扫描。之后由栈回写桩写回客体帧的根，新生区只剩钉住的对象，起始位图换成标记位图，对象之间的空隙重新排成游程，卡表全部置净。晋升与直接在老区分配的字节计入分配计，到了回收阈（三倍老区存活）或有强制、整理请求时，次要回收之后接着做全量回收：清标记位图、从根重新标记，按需整理，从老区起点清扫，再重置新生区。macOS 后台清扫与常驻清场都从老区起点起（常驻清场另清新生区用到的部分）。标记栈溢出后的重扫改按标记位图逐个取已标记的对象。整理压力下新生区的空隙填 0xEE。
- **精确根**（提案 00020 第 5 步）：复制式新生代打开且编译开关「精确根」为一时（平常如此），回收不再保守扫描值栈、执行器帧、其余根、异常槽与实例全局。可能回收的执行器处理（struct.new、array.new、array.new_fixed 的操作数，单元派发期间导入调用的结果）把值栈上的活槽登记进值栈根表（状态格 9096），回收按结构类型、数组元素类别或函数类型的编码精确处理这些槽，值栈其余部分不看；求全局初值期间禁止回收。异常对象的槽与传播中的异常载荷按标签函数类型的参数编码只处理引用槽。临时根、程序缓存、捕获缓冲、输入与请求格、子表与原生异步表里的引用格、实例全局与表都按引用精确处理：次要回收复制并改写，全量回收标记而不钉住，整理搬移后改写。子表项里的引用格是 +8、+24 捕获缓冲，+40 画面，+48 事件队列，+120 输入缓冲，+144 外壳请求队，+160 外壳来信队（「其余根精确处理」）；子表项新添引用字段时要同时登记进这里。后两格 2026-10-18 补进：此前精确回收认不出这两个队列的字节数组，收掉之后初始任务按悬空引用读写队列，读出乱的已用字节数，下一次入队越界陷阱（退出码 132）；初始任务一停，桌面、网络与远程登录随之停住。桌面开着任务管理器（它不停发外壳请求）时一两分钟内必现，2026-10-18 mbp13 实机上 ssh 截屏时整机卡死就是这一次初始任务陷阱，截屏只是恰好同时在跑。执行器帧不扫描（执行器原语执行期间禁止回收，可能回收的处理不在帧里留引用）；只有装载后回收、安全回收这两处在宿主调用里主动回收时（宿主回收窗，状态格 9100）照旧保守扫描执行器帧。没有精确栈图的客体帧与走栈走不下去的部分照旧保守扫描、整理时钉住；栈复制仍是执行器读原生栈的办法。开关为零时照旧。待办事项：全局按类型只处理引用全局；没有精确栈图的客体帧补栈图。
- **交还内存**（裸机，2026-10-09）：每次回收清扫时，把大空隙里头 16 字节之后的整 2 MiB 块、清扫后把堆顶以上到堆限之下的整 2 MiB 块经平台服务 `归还内存块`（内核服务 44）交还内核；内核只收已提交的块，这些地方以后再用到时由缺页重新提交、整块清零（分配本来就清零载荷）。空闲块只用头 16 字节（头与下一块），清扫与标记只读存活对象与位图，所以交还空闲块内部不影响回收；裸机没有后台清扫，清扫时也没有当前游程。这样任务的物理内存随存活量涨落，空下来的内存可以给别的任务用。裸机上回收阈还按空闲物理内存压低（内核服务 45 `空闲内存块数`：不超过空闲内存的一半，不低于 16 MiB），常驻进程的回收下限只翻倍到 256 MiB，几个任务合起来不会远超物理内存。macOS 与 Linux 原生（六十四位地址构建，提案 00020 第 6 步）同样交还这些整块：把这段换成新的匿名零页（mmap MAP_FIXED，旧的物理页随之释放），Linux 直接调 映射内存长，macOS 用启动时按名查到的 mmap 经动态调用块调用（不分配，后台清扫线程里也能调）；本机一个反复造大列表的探针最大常驻 1.60 GB → 1.01 GB。
- **堆上限**（裸机，2026-10-23，议题 384）：两张位图与两张卡表按页上限预留，但内核长内存只抬容量、碰到才提交，回收器的清零、拷贝与扫卡又都只做到堆顶，所以预留再大也只占实际用到的那几块物理内存。豫行工具任务（ssh 会话、桌面终端、「行」「后台行」起的程序）因此和别的平台一样用「可行页上限」：裸机六十四位实际登记到约 127 TiB（页容量 2130706432 页，页 64 KiB，堆区起在 4 GiB），不再压到 512 MiB 或空闲内存的一半；物理用量仍由上一条的回收阈跟着空闲内存走。真耗尽时是缺页提交要不到块、任务以 139 结束，不走「堆不足诊断」（2026-10-24，议题 368 的 KVM 验收：20 GiB 客机上工具任务用满 19.4 GiB 后以 139 结束）。总内存不到 1.5 GiB 的机器上，初始任务仍取「小内存初页上限」（议题 387）。
- **整理回收**（提案 00017）：块表接在老卡表之后（每个 2 MiB 块一项：块内起始的存活字节、钉住与疏散标志、块内起始对象的最远末端），前面是 512 字节的整理记录。裸机上三处触发整理（默认搬移）：装载后回收（父任务堆跨度达到 1 GiB，另打印统计行）、分配取不到空间时的强制全量回收、每八次一次的全量回收碰上碎片率高（本任务已提交的动态块不少于 64 块且块数 × 2 MiB 超过上次存活的两倍时先统计，标记完再按有存活对象的块数 × 2 MiB 超过本次存活的两倍才搬）。整理时，标记根之前清零块表，标记根时根指到的对象所在块钉住（`钉标候选`），扫描异常对象时槽指到的对象也钉住，标记完按标记位图逐块统计存活（一兆以上的大对象钉住它覆盖的块），选出疏散块：整块落在 [堆基, 堆顶) 里、没钉住、存活不到块长一半；不疏散的块里起始的对象伸进下一块时下一块也不疏散；按存活分档从低往高取，搬移量受堆的内存上限与内核池空闲块数（减 64 块余量）限制。装载后回收的整理在裸机控台直接打印一行：`整理：跨度 … 兆 已提交 … 块 有存活 … 块 存活 … 兆 钉住 … 块 候选 … 块 疏散 … 块 搬移 … 兆 填隙 … 兆 新占 … 块 空闲 … 块`（填隙是填进不疏散块空隙的字节，新占是堆顶以上实际用的块），清扫交还之后再打印 `整理后：已提交 … 块 跨度 … 兆 交还 … 块`（交还是这次清扫交还内核的块数）。搬移：内存先长到 堆顶 + 搬移字节，按块序逐个疏散块依地址顺序搬走存活对象：不超过 2 KiB 的对象先填进不疏散块里存活对象之间的空隙（这些块本来就占着；空隙不跨块界，前一块疏散时从它起始对象的最远末端之后算起，不会盖住还没搬走的对象），空隙走完或对象更大时碰撞分配到堆顶以上；复制整个对象、给新对象置标记位，旧对象头的头一个址宽写成新地址；再逐块走不疏散的块（含新对象）改写结构的引用字段与引用数组的元素（指向疏散块的换成旧头里的新址；异常对象的槽不动，它们指到的对象都已钉住）；清掉疏散块的标记位后照常清扫，疏散块成为空隙、整块交还（清扫把 2 MiB 以上空隙里的整块交还内核，夹在两个保留块之间的单个疏散块也能交还），起始位图、卡表与老卡表照旧由清扫重建。压力模式（`布局` 的编译开关 整理压力）：为一或二时每次全量回收疏散全部未钉住的块、每两次回收做一次全量回收、疏散余量降到 2 块；为一时回收阈固定为 4 MiB（小程序也回收很多次，验证机用），为二时回收阈照旧（编译器这样的大工作量用）。宽格区 8848–8879 的四格（输入缓冲、两个请求参数、远程结果）改为整段作根，远程结果取出后即清零。宿主测试 `整理回收。底层。测试。豫` 要用平台导入，全树测试用原生豫构把它编成本机程序运行（议题 538）。

## 六十四位地址：64 TiB 以上的回收堆

```sh
./豫构。林檎。豫行 构建 客体二号 --输出 执行器。树码
```

执行器入口声明 memory64（最大 2130706432 页），工具链只用这一种构建（2026-10-13 起），实际上限由降级器按平台定：macOS 与 Linux 68 TiB，裸机 AMD64 与 ARM64 127 TiB。回收堆从 4 GiB 以上开始，一直用到这个上限（两张位图与两张卡表按上限预留，macOS 与 Linux 上约 2.4 TiB），所以堆本身能到 64 TiB 以上。Windows 与 macOS x86-64 的上限是 8 GiB（Windows 入口用 VirtualAlloc 一次提交，macOS x86-64 是数据段里的零填充区），回收堆约 3.7 GiB；这两个平台按需映射、堆更大，留待后续版本。

三十二位构建保留，用来做性能对比，工具链不启用：加编译开关 `--三十二位地址` 构建，`./豫构。林檎。豫行 构建 客体二号 --输出 执行器三二。树码 -j 24 -- --三十二位地址`；以它为 `--执行器` 编出的程序就是三十二位版（4 GiB 堆，引用四字节），例如 `./豫构。林檎。豫行 构建 豫构 --输出 豫构三二。林檎。豫行 -j 24 -- --目标 本机 --执行器 执行器三二。树码`。

- **址与引用宽度**：堆地址、对象引用、堆的大小与回收计数都写成“址”（`库/底层库/址运算`，执行器里是 i64）。引用宽度 W 取自 `基础` 的 `引宽于 零`（8）。它把参数原样转给原语，调用处直接是常量，热路径上的小函数照旧能被原生降级内联。
- **对象布局**：对象头 8 字节（字零是类型号、实例号与种类，字一是总字节数，单个对象小于 2 GiB）。结构的引用字段占 W 字节、按 W 对齐，其余字段占 8 字节；数组依次是头、长度 4 字节、填充 4 字节、元素，引用元素占 W 字节；表项占 W 字节，表描述每表 16 字节；全局变量与值栈每槽 8 字节，引用占低 W 字节。i31 引用与函数引用按 32 位算好再零扩展，空引用是 0。
- **宽格区**（8448–9215，每格 8 字节，一律用 `读址`、`写址` 读写）：游标 8448、游限 8456、位图偏 8464、卡表 8472；堆基 8480、堆顶 8488、堆限 8496、位图基 8504、位图字节 8512、游起 8520、分配计 8528、回收阈 8536、活字节 8544、回收下限 8552、扫描中 8560；自由表从 8576 起 33 格（每格 W 字节）；老卡 8840、输入缓冲 8848、请求参一 8856、请求参二 8864、远程结果 8872；输出捕获组 8880 与错误捕获组 8896（每组 16 字节：引用槽 8 字节，+8 长度，+12 容量）；临时根从 8912 起 16 格（每格 W 字节）；中转区从 9040 起 3 个槽（每槽 8 字节：低址、容量）。8480 起的 360 字节是回收格，重启准备时清零。预编栈顶（1520）、全局表（1080）、表描述（1088）等四字节格存放低于 4 GiB 的地址。
- **内存布局**：模块窗口、状态格、动态区（`取区域`）、各种栈与表、实例记录都在 4 GiB 以下，动态区的顶越过 4 GiB 时以 120 退出；两张位图从 4 GiB 起，卡表与老卡表紧随其后，回收堆再接在后面，所以堆地址都在 4 GiB 以上。内存长不到为页上限预留的位图与卡表时，页上限减半再试（不低于 8 GiB）。
- **平台边界**：平台接口的地址参数是三十二位，宿主原语经低址中转缓冲转手：`中转缓于 槽 长` 在动态区取缓冲（四个槽：路径、数据、第二个路径、显示画面；至少 64 KiB，八字节对齐并倍增，位于动态区末尾时原地扩容，否则另取缓冲），`低址副本` 把堆里的字节拷进缓冲，`低址目标` 与 `低址回写` 把平台写进缓冲的结果拷回堆；文件读写按 1 MiB 分段。
- **子任务表与异步表**：每项的捕获组 16 字节（引用槽 8 字节），子表项长 192 字节（+40 起是子程序显示代办的字段，+120 起是交互子程序的输入通道，+144 起是外壳请求队与外壳来信队，+176 起是初始任务替子任务起的子进程），异步项长 128 字节（+72 起是原生子程序显示代办的字段），异步表 131072 字节；异步项保存退出峰值及其可用标志。
- **回收**：保守扫描每个址宽读一个候选字，标记栈每项一个址宽。原生的标记栈 16 Mi 项（裸机 128 Ki 项）；结构对象的第一个引用字段最后入栈，列表单元的“首”先扫，栈深不随列表长度增长。清扫记录（64 字节）的 +40、+48、+56 是下段分界与两段存活字节数，各 8 字节。空闲块的长度写在四字节头字里，超过 1 GiB 的空隙按 1 GiB 切开再放回；单个数组载荷的上限是 2 GiB 减 64 字节。
- **原生生成**：六十四位执行器经数值转译（导出“预编二起号”），`库/裸机后端/系统构造` 把大客体的启动前奏（增长内存、从被动段复制客体）接在已有的窄入口“启动”开头。

验证（2026-10-07，macOS arm64，解释执行）：六十四位执行器运行普通探针 12 项与原生探针 4 项，输出与默认构建相同；运行源码格式化工具（大客体），输出与 Node 相同；运行一个分配 5 GiB 字节缓冲（40 块，每块 128 MiB，带哨兵）、一百万节点链表与一百万个字符串的程序，结果正确并以 0 退出（约 13 秒）。默认构建的执行器预编二出原生编译器，构建源码格式化的产物与 `编译器.wasm` 构建的逐字节相同，编译用时与改动前持平。

同步与异步子程序装载完成后，父任务的堆达到 1 GiB 时先全量回收并交还空闲整块。异步路径先登记子任务与捕获缓冲，再回收父任务的临时对象。

后续版本的事项：`取存`、`取实例区` 的块取自动态区，实例卸载时回收；中转缓冲跨槽释放旧块；单个超过 4 GiB 的文件；裸机内核一侧的六十四位地址支持。

## 装载单元（提案 00003 第 2 步）

`单元装载。底层。豫` 给豫构的「运行」提供装载单元用的原语 186–191（经「营造」的带类型导入调用，见 `库/营造/营东道。接口。豫`）。单元装进实例零：执行器只做随实例零内部布局而变的事，解析单元文件、规范化类型、解析跨单元名字与重定位都在豫构里用豫言做（`豫言操作系统/裸机/库/冶铸/单元装入。豫`）。

- 186 单元现况：64 字节，每四字节一项：类型数、函数数、全局数、零号表大小、数据段数、标签数、宿主对象的五个类型号、跳表二地址的低与高三十二位、可用。“可用”在 macOS 与豫言操作系统（平台号 1）上、且程序带跳表二时为一。第一次调用时先追加两个全局槽，存「运行」时脚本看到的程序名与参数。
- 187 单元存：把字节串拷进常驻区，返回线性地址。地址按三十二位有号整数返回，过二吉时为负，由调用者换回无号。常驻区是从堆里取的十六兆字节原始块（登记在实例零，回收时保留），按八字节对齐依次切出。
- 188 单元并入：按种类追加类型条、函数条（表末仍留全零哨兵）、全局槽、数据段条、零号表元素、单元调度表项与单元适配表项。各表留有余量（容量记在装载记录里）：够时直接接在表后，不够时整张表搬到常驻区里容量为所需两倍的新地方，旧表不再使用。
- 189 单元带型码：按（模块名，字段名）给出带类型宿主导入的码；原语号在本平台未具时（见 `供籍`）给出码的相反数。
- 190 单元装代码：豫言操作系统上把机器码放进常驻区（AMD64 用户页都可执行），起址是线性内存基址加偏移；相继装入的单元挤进同一个代码块，每装好一个单元就调服务 60 映射；代码块从一个另取的单元代码区（一百二十八兆字节一块，区内依次排）里切出，同样的单元次序在各任务里落在同样的虚址上，内核按内容去重、各任务里同址同内容的代码块共用物理块，挤进已映射的块之前先调服务 76「代码块启缄」（与别的任务共用的块先由内核复制成私有块）（2026-10-20，提案 00038 第一步、议题 #122；此前换新块时交服务 77 共用的做法由它取代）；服务 60 返回去重改映到别的块上的块数，越界或映射失败返回 −1，装入按负值判失败；macOS 上 mmap 一块 MAP_JIT 内存，给种二重定位各处加上起址，关写保护、拷入、开写保护、冲指令缓存，返回起址；Linux（x86-64）上把相继装入的单元按 64 字节对齐挤进共用的二兆字节对齐块，拷入前把涉及的块改成可读可写可执行、拷完改回只读可执行，放不下再取新块（2026-10-21：原先每个单元独占一块并另留两兆对齐余量，豫构的五百多个单元光代码块就预留二点一吉，清单装入越过 4 GiB，议题 #245）。
- 191 单元运行：存好程序名与参数的覆盖值（原语 6、7 改交覆盖值），在状态格 9212 登记函数号；这次导入调用返回时 `预编调用导入` 经预编派发运行它，运行完撤销覆盖。

状态格 9200–9215：单元调度表地址（按全局函数号每项八字节存代码地址，单元的间接调用与跨单元调用从这里取址）、装载记录地址、单元适配表地址（预编派发调用函数号不小于客体函数数的函数时从这里取适配函数的地址）、运行请求。导入了「单元现况」的预编二原生程序（豫构）带跳表二（执行器每个函数一项），占位导出 `预编表二址低`、`预编表二址高` 换成它的地址，单元里调用执行器函数的跳板按它填地址；别的程序没有跳表二，占位为零，「单元现况」报不可用。

## 代办大文件时桌面照常响应（2026-10-11）

桌面跑在初始任务里，初始任务又替所有子任务代办文件；读写一律逐个 512 字节扇区经 USB 同步进行。为了让系统内造盘时桌面照常响应：

- **扇区缓存**：文件系统的扇区读写经 `盘扇读`、`盘扇写`，读过的扇区留在内存里（写直通，至多 64 MiB），同一程序第二次起只拷内存，见[客体文件系统](../文档/客体文件系统.汉语.md)的“扇区缓存与光标随动”。

## 林纳空指针参数（2026-10-22，议题 #313）

林纳（Linux）两架构系统调用桩的地址参数分两类：类别 1 一律加线性内存基址，类别 5 是可空地址（0 仍传空指针，非零才加基址）。降级器的 Linux 入口表把 `带信号掩码轮询`（ppoll）的时限与信号集、`等子进程4`（wait4）的状态与资源、`设信号动作`（rt_sigaction）的旧动作、`接受连接4`（accept4）的地址与长度、`发送到`（sendto）与 `接收自`（recvfrom）的地址与长度登成类别 5。此前 ppoll 的时限 0 也被加上基址，内核读到线性内存开头的全零 timespec，`待入事` 的无限等待退化成零时限轮询、进程空转满核（议题 #299 的底层原因）。改后空指针照旧送到内核，无时限的等待真正阻塞。x86-64 的第六个参数自带 r11，类别 5 用 rax 暂存；ARM64 用 x17 加六十四位条件选择。生成的机器码变了，编译语义号已换。

## 后备熵源（2026-10-14）

处理器没有随机指令（RDRAND、RNDR）时，安全随机字节串（原语 98）由 `熵池。底层。豫` 产出，ThinkPad E40（Arrandale）与 QEMU 的 qemu64、cortex-a53 上也能做 SSH 握手、TLS 与主机钥生成。开机时没有用户按键也够用：等键空当里的小睡与收包都记事件熵，首次播种还要采 512 次计时抖动、读盘上的种子文件，这些都不依赖输入；2026-10-23 在 KVM 客机上关掉处理器的 RDRAND 与 RDSEED 实测，盘上没有主机私种、串口一句也没输入时，DHCP 取得地址约四秒后 22 端口就有欢迎横幅，主机钥照常生成。

- **熵池**：布局 `状态熵池`（9424 起 176 字节）里 32 字节的沙256 状态，加出计、已播标志、事件熵、存种秒与 128 字节消息区。
- **播种**：首次取用时混进任务号、时钟滴答、墙钟秒、周期计数、事件熵与数据盘上的种子文件 `/系统/随机种子`（前 64 字节；先问文件在不在，不在就跳过，第一次开机还没有这个文件，2026-10-24，议题 #532），再采 512 次计时抖动（读周期计数、搅一段内存、再读，差值进池，每 16 次求一次沙256）。
- **周期计数**：目标内建导入“周期计数”，AMD64 是 RDTSC，ARM64 是 CNTVCT_EL0，各取低三十二位。
- **事件熵**：小睡醒来（时钟与设备中断的时刻）、按键、收包时把周期计数混进事件熵格（`平台` 的 `记熵事件`，网络栈的 `收包记熵`）。
- **种子文件**：播种后立即由池单向导出 64 字节写进 `/系统/随机种子`，此后每小时再写一次；壳命令「关机」「重启」动手前也写一次。下次开机读入的是新种子。
- **取数**：每 32 字节出计加一，把池、出计、周期计数、任务号、滴答、事件熵求一次沙256；取完池再单向更新。复制出来的子任务带着父任务的池，取数时混进自己的任务号与周期计数。
- 处理器有随机指令时照旧用它；原生平台照旧用操作系统的随机源。获取随机整数与获取随机小数（原语 96、97）照旧退用备用随机四字。

## 数据盘扩容（2026-10-14）

`数据盘扩展` 把数据盘上的 ext4 就地扩到设备末尾：旧的组与文件原样保留，新空间以整组接在末尾（每组自带位图与写零的节点表），组描述块不够时打开 META_BG，最后在一个日志事务里改超级块、旧的最后一个描述块与旧末组的位图；未挂载的盘（安装系统写好的目标盘）直接写，超级块最后写。原语 47 查询数据盘、48 扩展数据盘（任务监测接口 0.4.0）与 49 扩展磁盘数据区（磁盘接口 0.2.0）都由持有文件系统缓冲的初始任务办理，子任务经远程原语转过去。文件系统的 `盘组描述块` 按 META_BG 找描述块。做法与盘面见 [客体文件系统](../文档/客体文件系统.汉语.md) 的“扩容”。

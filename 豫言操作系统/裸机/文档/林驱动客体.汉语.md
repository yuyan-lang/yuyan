# 内置 Linux 驱动客体

这是以豫言内核为宿主、以内置 Linux 虚拟机承载现成驱动与用户态组件的实施方案。本文记录拟议分工与验收条件；尚未实现虚拟机进入或 Linux 嵌套启动。

## 开发机核实

用户确认 pit-mac 可随时使用；pit-pc-ubuntu 连接不稳定，随后明确授权其用于测试。开发优先本机与 pit-mac，x86 KVM 测试使用 pit-pc-ubuntu。该机现已安装 QEMU 10.2.1，用户 zc 加入 kvm 组，`/dev/kvm` 可读写，嵌套 KVM 为 Y。

`林虚拟化探测。豫` 使用现有豫言内核长模式启动代码，生成专用 Multiboot 镜像；初始化片实际执行 CPUID 叶一，检查 ECX 位五，然后输出结果并停机。镜像 SHA-256 为 `96f42f123e8a8fde3bf322aebe1f2cbfc97f26f34aed2a2e12a80bb83415590f`。同一镜像在 pit-pc-ubuntu 上以 `-machine pc,accel=kvm -cpu host,+vmx,enforce` 启动，串口实得“豫言核心启动”“客体可见VMX”；以 `-machine pc,accel=tcg -cpu qemu64` 启动，实得“客体不支持VMX”。两次均输出探测结束标记，随后由十秒 timeout 终止。此验已证第一层豫言内核可见 VMX；尚未读 VMX MSR、执行 VMXON、建立 EPT 或进入第二层客体。

2026-10-03 只读检查：当前开发机为 ARM64 macOS；受信任开发机 pit-mac 为 Apple M2 Max、ARM64。它们不能提供本次所需的原生 x86 VMX 验收环境。

pit-pc-ubuntu 为 x86-64、Intel Core i9-14900K，CPU 报告 VMX、EPT，`/dev/kvm` 存在，`/sys/module/kvm_intel/parameters/nested` 为 `Y`。当前 SSH 用户 zc 的组列表未含 kvm，对 `/dev/kvm` 的读写检查未通过。标准 `/usr/bin`、`/usr/local/bin` 未找到 qemu-system-x86_64。须安装 QEMU 并取得 KVM 使用权，随后以豫言内核自身探测和真实虚拟机进入核实暴露给第一层客体的能力。检测到宿主标志尚不足以宣告嵌套虚拟机可用。

外层采用 QEMU/KVM、`-cpu host`；不把普通 TCG 当作 VMX/SVM 的替代验收。开发机的 Linux 是验证外层模拟器的环境，产品启动路径仍为豫言内核承载 Linux 客体。

## 三个里程碑

### EPT 准备与指针实测

专用镜像已读取 IA32_VMX_EPT_VPID_CAP，要求四级遍历、WB 和二 MiB 大页。三页表分别位于宿主物理 0x06003000、0x06004000、0x06005000；将客体物理零至二 MiB 以可读、可写、可执行的 WB 大页映到宿主物理 0x04000000 起，余项清零。EPT_POINTER（0x201A）设为 0x0600301E，VMWRITE/VMREAD 实际读回一致。KVM 日志出现“EPT能力及指针读回已验证；映射尚未执行”，随后 VMCS 回收、VMXOFF 及探测结束。

探测片扩大时，固定内核代码区重叠检测拒绝原布局。现以极小跳转片从内核初始化入口进入物理六 MiB 的专用代码区；该区原内容须全零才写入，串口输出使用本片独立函数。普通内核布局和 ABI 未改。修正后 KVM 与 TCG 入口均实测通过，构建、类型检查通过；当前镜像 SHA-256 为 `a99bdc7b30b4f62647633e72d588fdae1c764cf128c4c71ef92b6c83235556a4`。EPT 执行控制、完整宿主与客体状态及 VMLAUNCH 尚未完成；当前证据只覆盖能力检查、表准备和指针读写。

### VMX 根操作进入实测

后续 VMCS 操作实测：专用镜像在物理 0x06002000 准备一页 VMCS，复制 VMX_BASIC 的版本号，VMCLEAR 后 VMPTRLD；以 VMWRITE 向 GUEST_RIP（0x681E）写 1048576，以 VMREAD 读回并比较。每条 VMX 指令即时检查 CF/ZF；结束时再次 VMCLEAR 并检查结果，再 VMXOFF。KVM 实际日志出现“VMCS清空装入及字段读写已验证”“VMCS回收已执行”，随后根操作退出及探测结束；十秒 timeout 终止测试。当前镜像 SHA-256 为 `ecb8616aff970b6238939e00d511f0bae7786f1a88299252b203ec22454d4986`。构建和独立类型检查通过。VMCS 基本操作已得到执行证据；完整字段初始化、EPT、VMLAUNCH、第二层客体执行仍未完成。

能力探测首版之后，专用工具已加入 VMXON/VMXOFF。先检查 IA32_FEATURE_CONTROL 的锁定位和 SMX 外允许位；未锁时仅在此测试客体内设置允许并锁定。检查 IA32_VMX_BASIC 的区域大小不超过一页、内存类型为 WB，按 CR0/CR4 固定位要求调整寄存器。专用镜像在物理 0x06000000 清一页、写入版本号，在 0x06001000 存其物理指针；须至少 128 MiB RAM。VMXON 后直接检查 CF/ZF，成功时执行 VMXOFF，两条返回路径均恢复原 CR4 和 CR0。通用路径的动态分配与 MSR 异常恢复留作待办事项。

2026-10-03 在同一授权测试机、相同 QEMU 参数下，KVM 串口实得“VMXON及VMXOFF已执行”，继得探测结束标记；TCG 实得不支持标记及探测结束，无 VMX 指令执行。两次由十秒 timeout 结束。镜像 SHA-256 为 `f2c3f6cb15700497ac0cb523e8eeac189c2498117d07f085e0ab2638446db34f`。此验只证明豫言内核进入和退出 VMX 根操作；VMCS、EPT、第二层极小客体进入及退出分派尚未验证。依据为 [Intel 系统手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html) 与固定 Linux 源码中的 MSR 定义。

极小客体准备工具为 `林极小客体准备。豫`，构建入口为 `豫言裸机 林极小客体准备`。运行 `yy林极小客体准备.wasm yy极小客体.bin` 生成 98 字节长模式指令，拟装载入口为 1048576。先向 COM1 的 LCR（0x3FB）写三，配置八位数据；继向 0x3F8 写出 UTF-8 标记“豫言极小客体已执行”及换行，最后 HLT。无需栈或中断；宿主须提供长模式及可执行客体映射，处理每次 I/O 退出后按退出指令长度推进 RIP，处理 HLT 后继续宿主。

本机 LLVM 独立反汇编确认一次配置输出、二十八次数据输出及末尾 HLT；工具类型检查通过。产物 SHA-256 为 `47aba03543b8d23c49da8414627f8886b041d99450b8ab2d82d39ec77e9b2d46`。这仅证明准备出的指令与预期相符；尚无真实客体执行、VMX 退出或宿主续行证据。

硬件会话尚未收到本次架构转向指令；本方向不会假定其已开始实现 VMX，也不重复修改内核虚拟化代码。下述为待联调的内部约定，具体代码接口在硬件分工确认后落定。

## 首个 Linux 客体

内核固定为 Linux 6.12.112（2026-10-03 官方长期维护版本）。源码已下载到 `/private/tmp/yyLinux-6.12.112.tar.xz`，SHA-256 为 `164dc9d1f6c93c61a15e1f071c48379b467f2b17c469cce7223471968208ed03`，与官网清单一致；已在 pit-pc-ubuntu 用临时目录依赖构建成功。现有 `/boot/vmlinuz-7.0.0-34-generic` 无读取权限，未用它验证解析。Linux 内核作为外部客体组件保留其原有语言、配置格式与构建系统；仓内装载器、设备模型、验证器和客体服务新增源码使用豫言，不转写 Linux 驱动。实际配置保存在 `豫言操作系统/宿主/林驱动客体/内核配置`，构建信息见该目录双语说明。

第一版设一个 vCPU、512 MiB 独占 RAM，直接装载 x86-64 bzImage 和 initramfs，不引入客体 BIOS、UEFI、图形、PCI 扫描或真实设备直通。initramfs 只需 `/init`、控制台设备和用于验收的服务程序；初期服务可复用仓库已有 Linux 原生执行路径，须先确认生成物可作为独立 init 运行。

装载器核验 bzImage 的 boot flag、HdrS、协议版本、64 位入口支持、setup_sects、syssize、kernel_alignment、pref_address、init_size、命令行容量与 initrd 上界。按内核头部计算压缩主体位置，不把整个 bzImage 当作入口代码。建立全零 boot_params，复制 setup header，填写命令行、initrd 和 E820。64 位入口为装载主体地址加 0x200；RSI 指向 boot_params，按协议设置段寄存器、关闭中断，并恒等映射解压所需范围、参数页和命令行。布局必须由实际 init_size 与 initrd 大小计算，避免重叠。

## 最小设备与 CPU 契约

日志串口拟为 16550 COM1（0x3F8），服务串口拟为 COM2（0x2F8）。由豫言截获客体端口 I/O，模拟收发寄存器、线路状态及初始化所需寄存器；客体日志输出转到宿主日志，不能放行对实体串口的任意访问。

Linux 早期日志可用轮询串口，完整启动仍需可工作的计时和中断。已核对固定版本 `arch/x86/Kconfig`：X86_64 会选入 X86_LOCAL_APIC，其后选入 X86_IO_APIC，不能靠关闭 SMP 从构建中去掉它们。首轮评估单处理器、关闭 ACPI 与 PCI，`noapic` 禁用 IOAPIC 路径、`nox2apic` 禁用 x2APIC，保留 LAPIC 与 PIC/PIT；实际启动仍须验证，不能宣称只做 UART 就能启动 Linux。CPUID、控制寄存器、MSR、异常与 EPT 退出须与暴露给 Linux 的能力一致，不暴露尚未实现的 kvmclock 或其他半虚拟化特性。

先使早期串口 banner 可见，再完成时钟、中断和 init；每步保留完整启动日志及首个未处理退出原因。参照 QEMU microvm 的精简设备范围，不把其设备实现当作已存在于豫言。

## 首条服务

为最快完成往返，先用独立串口上的可打印单行协议：请求 `编号 回声 内容`，响应 `编号 成功 内容`。日志与服务分开；一时只有一个在途请求。请求单行预算先取 65536 字节，越界时返回错误；字节编码为 UTF-8，首轮测试内容不含换行。此为内部验收协议，不建立公开应用 ABI。

Linux 服务初期只返回所收内容；由豫言检查编号与内容，随后停机并确认宿主可继续运行。无线网络与 CUDA 将来在 Linux 客体内执行，通过专门服务提交任务、取结果；真实 DMA 设备分配、中断隔离、IOMMU、设备复位与 CUDA 驱动版本匹配属于后续阶段。E40 CPU、无线网卡 ID 与 VT-d 尚未知，本方案不据此承诺其设备直通可用。

## 装载准备代码

## 串口模型进展

`林客体串口。豫` 已实现内部双串口状态、DLAB 除数闩、IER/LCR/MCR/SCR、轮询线路状态、65536 字节接收环、回环探测、收发中断原因与发送确认。写发送寄存器返回输出字节，由未来 VMX 退出分派转发到日志或服务端；其余写返回负一，不访问实体串口。OUT2 控制中断线路使能；读取接收寄存器消费队列，读取 IIR 确认发送中断。FIFO 当前只模拟开关和接收清空，门槛、接收超时、线路错误、调制变化中断及波特率计时留待 Linux 联调。

`林客体串口。测试。豫` 已在节点宿主通过初始化、除数、UTF-8 输出、零字节接收、双端口隔离、回环与中断确认等 28 项检查，模型类型检查通过。尚未接入 VMX I/O 退出，也未证明真实 Linux 驱动运行。

## 初进程与服务基线

`原生样例/林初进程` 是新增底层豫言包「原生林初进程」，通过既有原生生成器生成静态 x86-64 ELF。只复用既有 read、write、openat、ioctl、ppoll 绑定；PID 1 不依赖动态库或 WasmGC 执行器，先打印启动标记，再以原始 termios 打开 `/dev/ttyS1` 服务。

`林初盘格式。豫` 与 `林初盘准备。豫` 生成标准 newc initramfs，包含可执行 `/init`、`/dev/console`（5:1）、`/dev/ttyS0`（4:64）、`/dev/ttyS1`（4:65），路径、权限与设备号经系统 cpio 及 Linux 自身解包核验。

```text
节点 yy豫构.wasm 构建 原生林初进程 --输出 yy林初进程.wasm -j 24
节点 yy豫构.wasm 构建 豫言裸机 原生生成 --输出 yy原生生成.wasm -j 24
节点 yy原生生成.wasm Linux 兼容六十四 yy林初进程.wasm yy林初进程
节点 yy豫构.wasm 构建 豫言裸机 林初盘准备 --输出 yy林初盘准备.wasm -j 24
节点 yy林初盘准备.wasm yy林初进程 yy林初盘.cpio
节点 yy林客体准备.wasm yy林内核6.12.112 yy林初盘.cpio yy林含初盘客体
```

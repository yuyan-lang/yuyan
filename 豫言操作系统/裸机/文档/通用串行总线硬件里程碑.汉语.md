## 两架构共用的扩展主控驱动（2026-10-11）

AMD64 的扩展主控（xHCI）改用豫言内核里两种架构共用的驱动 `内核/扩展主控。底层。豫`（原 ARM64 的 `键鼠。底层。豫`），取代手写的那份；键盘、鼠标（含滚轮字节）、U 盘都归它。开机“初始化 USB”一步手写内核先经导出「扩展主控开机」调它：找到扩展主控并初置成功就跳过手写的根端入口与开机诊断，`『控台收入』` 经导出「扩展主控轮询」处理事件；没有扩展主控时（只有 EHCI）由增强主控驱动接管（见下文“两架构共用的增强主控驱动”）。驱动要点：PCI 配置空间 AMD64 经端口原语「端口读四」「端口写四」（配置机制一）读写；寄存器映到共享页目录 `0x11F000` 第 511 项（虚址 `0xBFE00000` 起，不可缓存）；环、上下文与 U 盘缓冲放在旧池两块（物理 `0x7C00000` 起，各地址空间恒等映射）；接过固件的 USB 遗留支持、关掉 SMI；根端口编址失败等 100 毫秒重试，至多三次；根端口连接变化在轮询里重新编址或释放槽；等命令与传输时收到的键鼠报告照常处理。U 盘走 bulk-only：TEST UNIT READY、READ CAPACITY(10)，按 ext4 超级块在盘首或 64 MiB 的 1 至 16 倍处找数据区，READ(10)、WRITE(10) 一条命令至多 2048 个扇区（超速设备；其余 240 个），SYNCHRONIZE CACHE(10) 报命令失败也当成功。服务 29、30 改为三个参数（扇区、线性地址、长度为 512 的整数倍），内核直接与调用者线性内存拷贝，见客体二号平台接口规范“持久块服务”。AMD64 内核模块基址从 `0x1C0000` 挪到 `0x1A4000`（容量 288 KiB，驱动加 U 盘后约 158 KiB）。

QEMU 11.1（Q35、TCG）验收：U 盘启动的合成镜像上，新驱动在 128 MiB 处认出数据区（`通用串行 盘 1 起 0x40000`），执行器挂上 ext4，命令壳列目录、写文件、读文件都对，换次启动仍读出；`i8042=off` 加 `usb-kbd`、`usb-mouse` 时命令壳收字、桌面按键事件（每键按下、抬起各一）、鼠标四字节包与滚轮字节（`mouse_move 0 0 1` 后第三包末字节 0xFF）与旧驱动逐项相同；光驱启动、只接 `ich9-usb-ehci1` 加 U 盘时当时走手写的 EHCI 后备（现已由增强主控取代），写、读文件都对。ARM64（edk2、HVF）从 U 盘启动，键盘、集线器后的鼠标照旧，内核认出数据盘；执行器开机挂盘留待后续版本。

这是硬件支持方向的最小实施路线。现有 xHCI 已有 PCI 发现、固件交接、控制器启动、DMA 环、根端口复位、Enable Slot 与 Address Device 代码。现有持久文件系统使用 Virtio 块设备；裸机源码中尚未发现 AHCI、NVMe 驱动。

本次先验收首个直连根端口设备寻址：等待异步 Enable Slot 完成事件，避免只扫描一遍就判定失败；修正 Address Device 等待的事件回收目标，使 ERDP 写入运行寄存器基址加 `0x38`；独立保存等待预算，避免槽号与完成标记覆盖计数；从输出槽上下文原始双字读取槽状态，保留 USB 地址。实现仍使用现有诊断区，不新增 ABI。

集成位置是裸机后端的 `兼汇编。豫` 中 `兼容根端口扫描`。`0x1039B0` 为寻址状态（0 未尝试、1 等待、2 成功、3 失败），`0x1039B4` 为命令完成码，`0x1039B8` 为完成槽号，`0x1039BC` 为 USB 地址，`0x1039C0` 为槽状态，`0x1039C4` 为 EP0 状态。控制器运行寄存器基址保存在 `0x10395C`，事件环软件出队指针保存在 `0x10399C`，二者必须分开。

`兼容核心。豫` 的 BAR 映射检查忽略共享 PDPT 项的已访问位：帧缓冲先访问该目录后，硬件会置此位，目录仍然有效。原有逐位比较会跳过 BAR 映射，使后续控制器启动访问未映射地址。

控制器复位保留“内存位图已初始化”检查，去掉以位图第零位为退出条件的旧检查；第零位是内核保留块，正常启动恒置位。旧检查使控制器未复位就换用内核 DMA 环，固件的设备槽仍占据端口，Address Device 返回 TRB Error。

64 位 BAR 的高地址校验从 PCI 记录 `0x103948` 读取 BAR0 高双字；原代码误读 `0x103940` 的设备类码，导致正常的 64 位 BAR 也跳过复位。上述两个复位条件须一并修正。

后续顺序：配置直连 HID boot 键盘并接入现有字符收入；再在存储方向选择 AHCI 或 USB 大容量存储，将读写接入现有文件系统。新增接口或 ABI 须先另行确认。

EP0 控制传输先取设备描述符前 8 字节：在 `0x07C01000` 放置 Setup、IN Data、OUT Status 三个 TRB，数据写入 `0x07C02000`，仅 Status 请求完成事件。它验证描述符头的长度与类型，记录 USB 版本、设备类码和 EP0 包大小；随后需按包大小更新上下文，再读取完整设备描述符与配置。内部状态 `0x1039C8` 取 0 未试、1 等待、2 成功、3 失败；`0x1039CC` 为完成码、`0x1039D0` 为前四字节、`0x1039D8` 为读取字节数、`0x1039DC` 为第 4～7 字节。该状态区止于中文解码状态 `0x1039E0` 之前，并避开 PS/2 初置标记 `0x1039F8`。

本次未实施鼠标、显示模式切换、网络、音频、ACPI、多核、AHCI、NVMe、USB 大容量传输或完整 HID 输入。待办事项：64 字节上下文、多设备与集线器拓扑、热插拔须另行实现。QEMU 验证不能代替 ThinkPad E40 与其他实体机实测。

在 `6570ba6ee` 基线复用根端入口处理内核内部请求，操作 1 为 READ(10)、2 为 WRITE(10)、3 为 SYNCHRONIZE CACHE(10)，读写均为一个 512 字节块，缓冲仍在 `0x07C0B000`。请求未接应用 ABI 或调度，只有内部调用者明确置待办后才执行，启动探测继续只读。状态块偏移 148 为操作、152 为 LBA、156 为请求状态（1 待办、4 处理中、2 成功、3 失败），160 为结果（0 成功、1 失败）；164/168 为 IN/OUT 周回位，176 为当前队列字段地址，188 为命令标签计数。拒绝非法操作和越界 LBA。两环到达 Link 时更新其周回位，再翻转生产者位并返回环首。

首次主动调用因控制器启动代码先清状态、再按旧启动标记退出，请求仍停在待办。根端入口改为先核对启动标记及扫描结束态，已枚举时直接处理请求；并保存恢复标志，避免重复启动。修正版 ISO SHA-256 为 `59897d3c64ee89a070a317a3973220cce9f16b6f63207115802322ffadf91b12`。

QEMU 参数沿用前轮，光驱启动，两份独立 8 MiB 空白 USB 模拟盘；BIOS 全速键盘、UEFI 高速键盘，PS/2 关闭。以 LLDB 暂停客体并模拟调用既有根端入口，BIOS 向 LBA 7 写测试块、回读、同步均成功，完整 512 字节与盘文件对应扇区一致；随后 130 对写读、共 260 次请求全部成功，两条 bulk 环周回位均翻为 0，跨周回后同步内容仍一致。关闭 BIOS 模拟器再重启，实际 READ LBA 7 的完整 512 字节仍相同。UEFI 向 LBA 9 写入，清空缓冲后回读恢复数据，同步及盘上 512 字节比较通过；越界 LBA 和非法操作均返回状态 3、结果 1，随后有效读取恢复状态 2、结果 0。

键盘事件夹具在正常报告入口前暂停真实 `h` 报告，DMA 为 usage 11、报告数 0；禁用入口断点，改以临时返回断点执行内部块读取，存储等待调用报告片后报告数增至 1，块请求状态 2、结果 0。该夹具证明真实排队报告在存储等待中被处理，未计为应用调度验收；夹具结束即关闭该客体。另在 BIOS 重启实例和 UEFI 实例以 USB 正式回显，均输出“你好”。本侧模拟器和调试器均已退出；包检查、修正版核心依赖类型检查、格式及差异检查通过。

## 两架构共用的增强主控驱动（2026-10-13）

EHCI（USB 2.0）主控改用豫言内核里两种架构共用的驱动 `内核/增强主控。底层。豫`（驱动号 5，「设备列表」里叫“增强主控”），取代只有 AMD64 才有的手写机器码那份（`裸机后端` 的 24 个 `增强*。豫` 文件与 `兼容核心。豫` 里的调用点已全部删去，它们当年的验证记录留在 git 历史里，最后一个含手写 EHCI 的提交是 `c95e1d8a9`）。

USB 设备层 `通用串行` 与键鼠、存储、集线器类驱动不分主控：类驱动照旧把命令写成 xHCI 风格的 TRB 环和端点上下文，薄分派层 `内核/主控分派。底层。豫` 在增强主控启用时把控制传输、编址、释放槽、配端点、按铃、发令、取事件等转给增强主控；增强主控把环里新写的 TRB 转成 qTD 链挂到异步调度的队列头，完成后写成与 xHCI 同构的传输事件，类驱动源码不必改。

- 启用：没有 xHCI 时由设备层启用；按外设互连的顺序找类码 0x0C0320 的主控，最多启动 2 个实例（ThinkPad E40 有两个 EHCI），各实例的根端口依次连续编成设备层看到的逻辑口号（实例 0 的口从 1 起），共用块 A、块 B（与扩展主控同款，2 MiB，4 GiB 以下）和设备槽（槽状态记所属实例）。
- 启动：开访存与总线主控，经「设备控块授权」授权（ARM64 的 SMMU 需要），沿 HCCPARAMS 的 EECP 链接过 BIOS 的 USB 所有权（USBLEGSUP），停机、复位，设好异步环（自环的头队列头加一个哨兵 qTD）并运行（只开异步调度，不开中断），置 CONFIGFLAG 把端口路由给增强主控，端口上电。
- 传输：控制与批量走异步调度的队列头与 qTD，中断端点在设备层轮询时当异步传输做；数据翻位由软件记；高速集线器后的全速、低速设备带上集线器地址与端口号，由集线器的事务转换器做分割事务。
- 热插拔：端口状态变化在轮询里检测，随后重新编址或释放槽。
- 屏幕诊断：开机时每个实例印一行“增强主控 序 位置 标 栏 口”（成功）或“增强主控 败 步 位置”（失败，步 1 至 5 见源码注释），每个有设备的根端口印“增强主控 口 果”（果 1 为高速设备，2 为交给伴随控制器，全一为失败）；这些行经控台字节上屏也进串口，其后是通用串行层印的集线器行、设备行与存储行。
- 待办事项：伴随控制器（UHCI/OHCI，全速、低速设备直接接在根端口上要靠它），周期调度与中断，同一端点同时多个提交，64 位寻址，超过 2 个增强主控，两种主控并存，网卡类驱动在增强主控上。

验证（2026-10-13，QEMU 11.1.1，只接 `usb-ehci`、不接 xHCI，U 盘与 `usb-kbd` 接在 EHCI 上）：

- AMD64（pit-pc-ubuntu，KVM，q35、SeaBIOS）与 ARM64（hvf，UEFI，SMMU v3）开机都进命令壳；键盘（监视器 sendkey）输入进壳；「设备列表」列出增强主控、大容量存储与键盘，均为已驱动；`「文件」之「写入」`、`「读取」` 经 EHCI 上的数据区（192 MiB 处）往返正确；热插拔 `usb-kbd` 的 `device_add`、`device_del` 能增减设备；同一 EHCI 上再接 `usb-mouse`、`usb-tablet`，键盘、鼠标可用（数位板没有类驱动）。
- 两个 `usb-ehci`：U 盘、键盘分在两个控制器上，两种排布（U 盘在前或在后）在两种架构上都能开机、输入、读写文件；设备列表里两个增强主控各一行，逻辑口号从 1 与从 7 起。
- 有 xHCI 的原路径照常：`qemu-xhci` 加 U 盘与键盘，两种架构的设备列表为扩展主控，文件读写与键盘输入正确；AMD64 BIOS 与 UEFI（OVMF）冒烟通过。
- 集线器：QEMU 的 `usb-hub` 只有全速描述符，接不上 EHCI 根端口（报 speed mismatch），QEMU 的 EHCI 也不模拟分割事务，所以集线器后的设备（ThinkPad E40 的全部外部设备都在速率匹配集线器后）与事务转换只能在实机上验；集线器的枚举、各口上电与复位走设备层里与 xHCI 共用的代码。

## E40 实体资料

Lenovo 的[旧机型 PSREF](https://psrefstuff.lenovo.com/syspool/Sys/PDF/withdrawnbook/lslwbook.pdf)中，Edge 14 的 Intel 0578 配置列出 HM55、USB 2.0 和 SATA 磁盘；[Intel 5 系列/3400 系列数据手册](https://www.intel.com/content/dam/www/public/us/en/documents/datasheets/5-chipset-3400-chipset-datasheet.pdf)列出 EHCI 控制器及集成 SATA/AHCI。用户提供的 Windows 10 照片确认 Type 0579-4PC 的 E40 有两个 Intel USB Enhanced Host Controller（3B34、3B3C），SATA AHCI 为 `8086:3B29`，Generic USB Hub 为 `8087:0020`（速率匹配集线器）。实机测得（2026-10-13）：3b34 在 `00:1d.0`、3b3c 在 `00:1a.0`，都只经各自的速率匹配集线器（USB 2 集线器，接在根端口 1）接外部设备，没有伴随控制器，所以 U 盘与键盘一定在这个集线器后面；高速 U 盘在它后面不需要事务转换，全速、低速键盘需要。E40 的实机验收见 `持续改进目标/裸机实机.md`。

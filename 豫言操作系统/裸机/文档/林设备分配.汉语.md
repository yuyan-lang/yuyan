# Linux 客体设备分配

这是“真实硬件 → 豫言操作系统 → Linux 客体 → GPU、网卡”的后续实施工作。Linux 客体使用现成驱动并运行应用；豫言管理设备分配、CPU 地址映射、DMA 地址空间和中断转交。已有 Linux 启动、串口服务往返与极小客体验收继续保留。

## 本轮状态

专属工作树为 `林设备分配`，从已验证的 Linux 客体提交 `ebd67a092` 起步。现有固定 Linux 镜像关闭 PCI 和网络；客体物理零至 512 MiB 经 EPT 映到宿主一 GiB 起。设备 DMA 须另经 IOMMU 转换，CPU 的 EPT 映射不能代替它。[Intel VT-d 架构规范](https://cdrdv2-public.intel.com/831418/vt-directed-io-spec.pdf)

现已加入显式 `设备隔离` 参数的初置代码，并于 2026-10-04 在 pit-pc-ubuntu 的 QEMU 10.2.1、Q35/KVM 上通过开启确认。只供明确配置的 QEMU Q35、Intel VT-d 平台：宿主专用页表映射 `0xFED90000` 寄存器所在块；检查版本和四级地址转换能力；清零位于 `0x0600D000` 的根表，设置根表指针，等待 GSTS 确认，再开启翻译并等待确认。根表保持空授权，不开放网卡 DMA；不能据此宣称实际 DMA 隔离已经通过。

带 IOMMU 的极小客体完成 CPUID、跨退出寄存器、512 MiB 末页写入、HLT 退出和 VMCS/VMX 回收；移除 IOMMU 的同平台对照输出能力或开启确认失败，未进入客体。完整 Linux 6.12.112 启动到豫言 PID 1 服务就绪，同一虚拟机中两个独立客户端均通过编号、UTF-8、空白、错误后继续、空内容及超长行恢复验收。构建、类型检查通过；测试虚拟机由外层超时结束，未操作实体设备。

## DMA 页授权实测

2026-10-04 在同一 Q35/KVM 平台增加 EDU `00:04.0`，以真实设备传输验证 VT-d。BAR 为 `0xC0000000`，位于二 GiB RAM 之外；宿主以 supervisor-only、不可缓存大页访问。上下文与四级转换表保留在 `0x0600E000` 至 `0x06012000`；设备地址 `0x1000` 映到宿主 `0x58000000`，属于 Linux 客体的宿主物理区。客体 EPT 不含这些表页或设备寄存器。

EDU 先把设备内四字节零值写入授权页，核对目标确已改变及相邻哨兵未变。随后向 `0x2000` 发出未映请求、将原叶项改只读后重试、撤销原叶项后重试，均通过。每次改权限前等待设备传输完成并关闭总线主控；改叶项后刷新全局 IOTLB 并核对硬件完成与实际失效范围。每次拒绝均核对哨兵、故障待处理位、目标地址、设备编号 `0x20`、写访问与无写权限原因码五，再清故障记录并确认待处理位消失。[EDU 设备协议](https://www.qemu.org/docs/master/specs/edu.html)、[QEMU VT-d 寄存器与故障码](https://github.com/qemu/qemu/blob/v10.2.1/hw/i386/intel_iommu_internal.h)

`设备保护对照` 故意在只读阶段保留写权限。实测先观察保护区已被改写，随后保护核验失败并停机，未进入客体。正常路径四项 DMA 验收后，极小客体回归通过；完整 Linux 启到 PID 1，同一虚拟机两个独立客户端均通过六项服务验收。最终源码构建、类型检查通过，测试虚拟机均由外层超时结束。

生成方式：`节点 yy林虚拟化探测.wasm yy林设备传输.bin 设备传输`；负对照末参数为 `设备保护对照`。完整 Linux 回归在原内核、初盘参数后加 `设备传输`。QEMU 在前述 Q35/IOMMU 参数之外增加 `-device edu,addr=04.0,dma_mask=0xffffffff`。不带诊断参数保留原客体路径。

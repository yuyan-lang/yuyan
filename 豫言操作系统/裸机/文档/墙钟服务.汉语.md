# 墙钟服务：实时钟基准、毫秒墙钟与对时偏移

内核的墙钟分三层：服务 26「墙钟秒」逐次读硬件实时钟，返回自 1970-01-01 00:00:00 UTC 起的秒数（三十二位无符号，可用到 2106 年）；服务 121「读墙钟基准」给出开机时读一次硬件钟记下的基准秒与基准滴答，以及服务 122「设墙钟偏移」设下的偏移；执行器的墙钟纳秒按基准加单调计时推算，并加上对时的偏移，给出毫秒级的读数。服务 142「读墙钟偏移」把 122 设下的偏移交回对时客户端，客户端据此在当前偏移上累加（2026-10-22，议题 326）。服务 123「写起居注」让执行器往内核日志里记行（网络对时的成败用它）。此前系统只有开机以来的时钟滴答（服务 5，每滴答 10 毫秒）与只到秒的墙钟，说不出“今天几号几点几秒几毫秒”；现在用户态执行器据此实现标准库的 `今时` 与壳的 `日期`，网络对时客户端（`库/几席/对时令。豫`）据此算偏移。

## 硬件与读数

| | ARM64 | AMD64 |
|---|---|---|
| 硬件 | PL031 实时时钟，QEMU `virt` 里在 `0x09010000` | 传统 CMOS 实时时钟（MC146818），端口 `0x70`（索引）、`0x71`（数据） |
| 读法 | 平台号为零时一条加载得秒数；平台号不为零（如 VMware）时取引导程序从 UEFI 写进开机参数 +72 的开机墙钟秒 | 读年月日时分秒，用民用历法折成秒数 |
| 代码 | 内核取基准时读一次 | 内核取基准时读一次，约 320 字节 |

服务 26 的旧路径照旧存在（ARM64 读 PL031、AMD64 读 CMOS、VMware 用开机参数加虚拟计数），备用随机四字等仍可用它。服务 121 的基准只在第一次调用时取：读硬件钟得基准秒，同时记下此刻的全局滴答（服务 5 的计数）与已取标志；硬件钟读不出时返回 −1，执行器退回逐次读硬件钟的旧路。AMD64 的换算用 Howard Hinnant 的 `days_from_civil`：先把一月二月算作上一年的十三、十四月（`y -= m < 3`），`era = y / 400`、`yoe = y % 400`，`doy = (153·(m>2 ? m−3 : m+9) + 2)/5 + d − 1`，`doe = yoe·365 + yoe/4 − yoe/100 + doy`，天数 = `era·146097 + doe − 719468`；秒数 = 天数·86400 + 时·3600 + 分·60 + 秒。三十二位乘法的低 32 位与无符号数一致，所以到 2106 年都对。同一算法先用 JavaScript 对照 `Date.UTC` 检查了 1970–2105 年每个月的 1 日、28 日、月末与 15 日的三个时刻（共 19 584 个），全部相同。

## 基准、偏移与服务

全局区记五个格：基准秒（+640）、基准滴答（+644）、偏移毫秒（+648，有符号）、已取（+652）、偏移秒（+656，有符号）。服务 121 把基准秒、基准滴答、偏移秒、偏移毫秒各四字节写给调用者（写到它的线性内存里，越界或还没取到基准返回 −1）；服务 122 收偏移的秒与毫秒两个有符号数，秒与毫分开传，跨数年的跳时也装得下；服务 142 把 122 设下的偏移秒与偏移毫秒各四字节写给调用者（目的越出线性内存或旧内核返回 −1），对时客户端据此在当前偏移上累加；服务 123 把调用者线性内存里的一段字节写进起居注（内核日志的 2 MiB 环），返回写进去的字节数；来源须在低址中转缓冲里（六十四位地址构建的回收堆在 4 GiB 以上，平台的地址只收三十二位），执行器的「注起居」先抄进去再交。服务号 121–123 与 142 落在手写内核交给豫言内核的分派范围里（服务号不小于 37 的转给内核），两种架构共用一份豫言代码。

## 执行器的毫秒墙钟

执行器的「读墙钟纳秒」（`裸机底层基础。底层。豫`）在裸机上这样算：

1. 第一次调用时问服务 121 要基准，把基准秒、基准滴答、偏移秒、偏移毫秒与此刻的周期计数记进本任务的状态格；基准取不到就退回旧路（逐次读服务 26 的秒数、按看到秒变以来的滴答补毫秒）。
2. 每次调用读服务 5 的时钟滴答与目标内建导入「周期计数」（AMD64 是 `RDTSC`，ARM64 是 `CNTVCT_EL0`）。滴答走了一格以上时，用这一段的（周期差÷滴答差）重估每滴的周期数；格数超过十（约一百毫秒）时周期计数可能已经绕回，不估。
3. 本格内已走的毫秒 =（周期计数 − 上次看到滴答变时的计数）÷（每滴的周期数÷十），至多九毫；毫总 =（滴答差×十）+ 格内毫 + 偏移毫；毫总为负时向秒借一，得整秒与 [0, 1000) 的毫余。
4. 秒 = 基准秒 + 偏移秒 + 借得的秒，结果乘成六十四位纳秒（秒×10⁹ + 毫余×10⁶）。

所以墙钟一次开机只读一次硬件钟，秒与秒之间的边界不再随本任务看到秒变的时刻漂移；同一实例里不倒退。取基准时的秒内相位（真时的那一刻在基准秒之后多少）没有测，在对时之前最多差一秒，对时设下的偏移会把它一并补上。

原生系统（林檎、林纳、轩窗）上「读墙钟纳秒」仍直接取系统时钟，不设偏移。

## 网络对时

壳命令「对时」按 RFC 4330 的简单网络时间协议第四版（SNTPv4）、RFC 5905 的客户端模式取时：向服务器的 UDP 123 端口发一个四十八字节的请求（首字节 `0x23`，其余为零），从回答的接收时刻（偏移 32）与发送时刻（偏移 40）算

- 偏移 =（（接收时刻 − 发出时的本地时刻）+（发送时刻 − 收到时的本地时刻））÷ 2
- 往返延迟 =（收到 − 发出）−（发送 − 接收）

时间戳是自 1900-01-01 起的整秒与三十二位分数；折成纪元毫秒时秒减 2 208 988 800，分数取高十六位乘一千再右移十六位（误差不超过一毫）。设墙钟偏移（服务 122）收的是绝对偏移，所以「施偏移」先经服务 142 读内核此刻的偏移，加上这次量出的偏移再交给内核：偏移超过一秒时先把初偏加在当前偏移上跳过去，再询一次取残差，第二次把残差加在跳后的偏移上（首次的往返延迟会把大跳算歪），小于一秒也直接设。同一次开机里第二次「对时」量出的只是几十毫秒的残差，加在开机时的大跳上，不会把二十五年的修正冲掉。服务器缺省按 `pool.ntp.org`、`time.cloudflare.com`、`time.google.com` 依次试；给了「服务器」就只试它一个。得手后把偏移经服务 122 交给内核（原生系统上不改系统时间，只印宿主时钟），并把上次对时的本地时刻、偏移、延迟与服务器写进数据盘上的 `/系统/对时。数据。豫`。

开机自启的开头句里有一句「自动对时」：设置里「开」为阳（缺省）时开机联网后对一次，成败都往起居注记一行，失败不挡开机；为阴时什么也不做。开关用壳命令「设对时」于「开」曰阳／阴 改，`「时态」` 印出时钟来源、开关与上次对时的结果。

## 验收

`裸机验证` 原有的四个方式照旧覆盖服务 26 的两种硬件读法与 AMD64 的换算（`-rtc base=` 置成闰世纪朔日、年末前十秒、非闰世纪朔日与闰日正午；用户模块先读一次、空转三百万次后再读一次，以无符号比较断言不倒退、不超前八秒）。

新增的对时验收在 QEMU 里做：以 `-rtc base=2001-01-01T00:00:00` 开机，让实时钟差着二十五年；开机联网后「自动对时」跑一次，`「日期」` 应与 `date -u` 相差一秒之内，`「对时」` 印出偏移与延迟，`「时态」` 印出时钟来源与上次对时；随后在同一次开机里再下一次「对时」，`「日期」` 仍与 `date -u` 相差一秒之内（不再退回 2001 年），印出的偏移只有几十毫秒；不带网卡（`-nic none`）开机时对时失败，开机与别的命令不受影响。

## 边界

- 服务 26 仍是只有秒的精度；毫秒来自基准加单调计时，开机后不再跟随硬件钟（改了硬件钟要重新开机才看得到）。
- 执行器取基准时没有测秒内相位，对时之前的秒内毫秒可能整体偏最多一秒；对时之后正确。
- AMD64 未处理十二小时制、也不检查 CMOS 的电池状态位；QEMU 里两者都是默认值。
- 用户态执行器用它实现标准库的 `今时` 与 `今时依式`（见[客体二号](客体二号.汉语.md)的“时间与杂项原语”）。原先 WASI 的实时钟（以第一次读到的墙钟秒为锚、靠滴答走，精度 10 毫秒）随 WASI 一起拆出，见 [瓦西库](../瓦西库/说明.汉语.md)。

E40 临时诊断：初始化及原始键码同时输出到 COM1 和可用帧缓。`PS2 STATUS=XX` 是首次读状态口的十六进制值；`CONFIG=XX` 是原控制器命令字节；`STAGE=01` 表示将发送读命令字，`02` 表示将发送写命令字，`03` 表示将写入新命令字节，`04` 表示将明确启用第一端口，`05` 表示将发送键盘扫描启用命令。新配置关闭两个端口 IRQ 与辅助端口，保留 Set 2 到 Set 1 转换；`CONFIG2` 是启用第一端口后的配置回读，`ACK` 是扫描启用命令后读到的字节，`TIMEOUT STATUS` 是等待失败时的控制器状态。新增读写等待各至多轮询 6553600 次，此数为次数上界，非校准时长。后续每个从数据口收到的字节输出为 `PS2 RAW=XX`，包含应答与按下、松开扫描码。此为临时诊断，待定位后删除。

E40 首次照片记录：`STATUS=14`、`CONFIG=47`，旧诊断到 `STAGE=04`，内置键盘无响应，未见 RAW 或键盘应答。当前修改用于明确启用端口并确认配置及应答，真机结果仍待复测。读写等待及配置处理参照 [Linux i8042 驱动](https://github.com/torvalds/linux/blob/master/drivers/input/serio/i8042.c)。

此前内核对控制台输入什么也不缓存：服务 4 每次直接读一个串口字节，没人读就留在串口里。所以一个不读输入的死循环程序无法被打断——按下的 Ctrl-C 只是串口里的一个字节，没有任何代码会去看它。现在内核自己收下串口字节，并把 Ctrl-C 变成一个可查询的“中断标志”；AMD64 首次收入时有界初始化 i8042，启用键盘口与 Set 2 到 Set 1 转换，再把 PS/2 扫描码转换成 ASCII 字节，放进同一输入环。

## 设计

- **输入环**：内核在**每次时钟中断里**、以及**服务 4 读入之前**，把串口接收 FIFO 里的字节取出来；AMD64 同时轮询 i8042/PS/2 键盘，把 Set 1 美国布局按键转成字节，支持左右 Shift、Caps Lock、字母大小写及常用标点移位。修饰键状态字节位于 `0x10392C`，启动时清零。两种输入进入同一个 256 字节环。
- **Ctrl-C**：取到字节 3（0x03）不放进环，只把“中断标志”置 1。用户程序看不到这个字节，就像终端的行规程吞掉 `^C` 一样。
- **服务 4（读一字节）**：先 `控台冲刷当前`（原有行为：把待输出的整行先刷出去），再收入，然后从环里取一字节；环空返回 -1（与原来“串口没有字节”一致）。所以**提前敲入的命令仍按序留给下一个读者**——脚本一次性贴进串口，子进程不读输入，这些命令依旧原样留给壳。
- **服务 27（`平台.中断查询`，无参数、一个结果）**：返回中断标志（0 或 1）并清零。

| | ARM64 | AMD64 |
|---|---|---|
| 环头（头 4 字节、尾 4 字节、中断标志 4 字节，环体从偏移 16 起，共 272 字节） | `0x400B0400` | `0x103800` |
| AMD64 引导信息 | — | Multiboot 信息指针存于 `0x10380C`；帧缓冲元数据记录位于 `0x103910`，长 28 字节，紧接输入环之后 |
| 串口 | PL011 `0x09000000`，看 FR 的 RXFE 位（bit 4） | 16550 端口 `0x3F8`，看 LSR（`0x3FD`）的 DR 位（bit 0） |
| PS/2 键盘 | — | 首次收入时有界配置 i8042 并启用扫描，随后轮询状态口 `0x64`、数据口 `0x60`；Set 1 美国键位，支持 Shift/Caps Lock、Esc、F2，扩展码仍忽略 |
| 收入子程序 | `控台收入`（`bl`／`call`，只用 x0–x8／eax、ecx、edx，中断上下文已整体保存） | 同 |
| 挂接点 | `时钟中断` 里在轮转任务之前调用一次；服务 4 内调用一次 | 同 |

新增的机器码全部是带标号的小片段（`豫言操作系统/裸机/库/裸机后端/控台输入。豫`，服务号在 `整数降级。豫` 的映射里加了 `中断查询` → 27），分支一律走标号重定位，没有手算偏移。

AMD64 启动入口先把 Multiboot 信息指针存于 `0x10380C`。若引导器提供帧缓冲字段，核心会把地址、行距、宽、高、色深、类型及六个 RGB 掩码字节复制到 `0x103910` 起的 28 字节记录；按规范偏移复制，即取 Multiboot 信息偏移 108 与 112 处各四字节放在记录 +20、+24。Limine 给的色彩信息比规范晚两字节（从偏移 112 起），所以经 Limine 启动时记录 +22、+23（`0x103926`、`0x103927`）为零、红位在 `0x103928`，蓝位两字节不在记录里；内核控台绘制不用这几个掩码，帧服务两种排法都认。待办事项：按引导器区分偏移、补齐蓝位。输入环占用 `0x103800` 起的 272 字节，PS/2 修饰键状态字节位于其后空隙 `0x10392C`，初置魔数字另存 `0x1039F8`。键盘侧可输入大小写字母、数字与美式移位标点，以及空格、回车、退格、Esc、F2。壳已接入 Noto UTF-8 帧缓显示、命令补全与简单拼音输入；串口保留 UTF-8。PS/2 Ctrl 组合键、扩展键与 USB HID 键盘尚未接入。

## 用户态如何使用

内核只负责“记下 Ctrl-C”，怎么响应是用户态的事（见[客体二号](客体二号.汉语.md)的“控制台中断”一节）：

- **子任务里的程序**：执行器在每次进入 Wasm 函数体和每次跳回循环头时数一下，每 4096 次向内核问一次；问到标志就以退出码 130（128 + SIGINT，与 POSIX 相同）结束本任务，壳照常打印 `退出码：130`。所以死循环、深递归、忙等都能被打断；在等输入的程序也会在等待的循环里检查。
- **壳（首任务）**：读一行时先照常读完环里的字符（并回显），读不到字节且见到 Ctrl-C 标志才打印 `^C`、放弃这一行、回到提示符；起子进程之前先清掉遗留的标志；运行程序期间壳自己不占用 CPU，标志留给子任务。

## 验收

- 裸机验证新增 `控制台中断`：测试程序先打印“输入就绪”，harness 随后往串口写入 `a`、0x03、`b` 三个字节；程序（每一步限时三秒）依次读到 `a`、等到 `中断查询` 返回 1、再读到 `b`（0x03 不会出现在字节流里）、再查得 0；两个架构都通过。AMD64 的 16550 在无 FIFO 模式一次只收一个字节，后两个字节要等前一个被读走、内核在时钟中断里继续收入才到，所以这个方式同时覆盖“时钟中断里收入”与“服务 4 读环”。
- QEMU 手工键盘复测：SeaBIOS + i440fx/UHCI 与 OVMF + Q35/xHCI 均启动到 shell；向 PS/2 模型注入 `help`、回车，shell 收到完整 ASCII 行并返回“未知命令：help”。这是 QEMU PS/2 输入验证，尚未在 E40 或实体键盘上测试。
- 2026-10-02 修饰键复测：同一 BIOS/UEFI 混合 USB ISO 在 QEMU Penryn + Q35 + xHCI 下分别经 SeaBIOS BIOS/MBR 与 OVMF UEFI 启动到 `壳>`。监视器注入左 Shift+`a`、Caps Lock+`a` 得到 `A`；Caps Lock+Shift+`a` 得到 `a`；Shift+`1`、`2`、`-` 得到 `!`、`@`、`_`；另注入右 Shift+`b` 得到 `B`。这是 QEMU PS/2 模型验证，ThinkPad E40 实机尚待测试。
- 2026-10-02 USB 键盘缺口复测：QEMU 11.1.1 的 Q35 + Penryn + xHCI 挂载同一混合 ISO 与 `usb-kbd`（接在 `xhci.0`）；SeaBIOS 和 OVMF 都能启动到 `壳>`。QEMU `info usb` 显示 USB Keyboard 设备已挂到端口，但此时 `sendkey h/e/l/p/ret` 没有形成 shell 输入。移除 `usb-kbd` 后，相同 SeaBIOS 配置的 PS/2 注入可读出 `help` 并返回“未知命令：help”。这只证明 QEMU 设备模型配置下系统当前不能用 USB 键盘；QEMU 显示设备存在不代表内核已枚举它。xHCI 控制器启动、DMA 环与 HID 枚举仍待实现。
- 原有的控制台输入（`控制台输入`、`控制台错误`、`控制台行原子`）与依赖提前输入的全部壳测试（脚本一次性写进串口）都照常通过，说明环没有丢字节、没有乱序。
- 壳测试 `中断`（见[客体二号](客体二号.汉语.md)）在两个架构上逐字验证：豫言写的 `死循环`（尾递归空转）被 Ctrl-C 打断得到退出码 130，在提示符下敲了半行再按 Ctrl-C 得到 `^C`，之后壳仍可用。
- 2026-10-02 默认壳 ASCII 别名实测：新增 `help`、`echo 文字`、`exit`，`普通-壳-ASCII别名` 用例在 ARM64 与 AMD64 均通过。新版 BIOS/UEFI 混合 USB ISO 在 QEMU qemu64 + Q35 + xHCI 下，经 SeaBIOS 与 OVMF 启动后，monitor 向 PS/2 注入 `help`、`echo ps2 ok`、`exit`，三令皆正确回显并结束用户任务。此项只验 QEMU PS/2 模型，实体键盘与屏幕输出仍待实机验证。
- 2026-10-03 xHCI 命令完成复测：QEMU 11.1.1 Penryn + Q35 + qemu-xhci 挂载 USB 存储；同一 ISO 经 SeaBIOS BIOS/MBR 与 OVMF UEFI 均启动到 `壳>`。监视器读得 Enable Slot 槽号 2、槽状态 2、完成码 1，事件环出队指针前进一个事件。此项只验证命令环与命令完成事件处理；USB HID 键盘输入仍未实现。
- 2026-10-03 xHCI 根端口复位复测：启动阶段对首个已连接根端口置 PORTSC.PP 与 PR，并以掩码保留可写控制位；QEMU 11.1.1 Q35 + qemu-xhci + USB 存储下，默认 CPU 和 Penryn 分别经 SeaBIOS BIOS/MBR、OVMF UEFI 启动到 `壳>`。四种组合的 PORTSC 均读到 CCS、PED、PRC 置位且 PR 清零，证明 QEMU 端口复位完成。此项只验证模拟器中的根端口复位；USB HID、设备寻址、端点配置与 USB 存储传输仍未实现，ThinkPad E40 尚未实测。

## 边界

- 环满（256 字节的提前输入还没被读走）时后来的 Ctrl-C 要等环里腾出位置才会被收到；串口字节不会丢，只是 Ctrl-C 的识别被延后。
- 所有任务共用一个环与一个标志，谁先读谁得到；当前一次只有一个子进程，所以标志总是归它。
- 程序不能“捕获”Ctrl-C，也没有信号或前后台作业的概念；Ctrl-C 只对子进程生效（首任务壳自己按行处理）。
- 中断只在解释器的检查点被发现：一个陷在**宿主原语**里很久的调用（例如极大的文件读写）要等它返回后才会响应。
- **终端里的 Ctrl-C**：QEMU 的 `-serial stdio` 默认让终端的 Ctrl-C 产生 SIGINT、直接结束 QEMU（实测 “terminating on signal 2”），字节 3 到不了系统里。`yy豫言系统` 现在把串口接在 `-chardev stdio,mux=on,signal=off` 上（监视器仍是 `-monitor none`），Ctrl-C 于是作为字节 3 送进系统，行为如上；代价是终端不再能用 Ctrl-C 杀掉 QEMU，系统卡死时按 **Ctrl-A 再按 X** 强制结束（复用 QEMU 的 mux 快捷键，实测退出码 0）。自动测试仍用命名管道送入 0x03。
- PS/2 键盘映射 Set 1 美国布局的 ASCII，已支持左右 Shift 与 Caps Lock；PS/2 Ctrl 组合键、扩展键、USB 键盘尚未支持。默认壳保留 `help`、`echo 文字`、`exit`，以及基础中文版临时验收命令 `tmp-help`、`tmp-echo 文字`、`tmp-exit`。Tab 补令与 F2 拼音输入见《中文支持》，终端编辑按键见《终端编辑》。无 COM1 时，FF 状态直接转向键盘轮询。

# 豫言、OCaml 与 C：程序性能复测及提速方案

2026-09-19，Apple M5 Pro，18 核，48 GB，macOS arm64。本轮使用当前工作区已通过自举的 `yy3_bs`，不使用历史报告中的旧编译器成绩。**豫言 Wasm 尚未接近 C：较长的递归、矩阵、排序任务中，端到端耗时是同一 V8 上 C/Wasm 的约 5.7–9.8 倍。** 与 OCaml 原生比较，这三项约为 4.4–18.4 倍。短任务大量时间消耗在宿主启动，不能套用这些倍数。

## 实测

单位：秒；每格为五次新进程执行的中位数，另有一轮预热。编译时间不计入，启动、JIT、运行时初始化、计算及输出均计入。前四种方式逐轮交替运行；C/Wasm 为后续独立批次，不是五种方式同时交替。没有在正式计时期间运行本任务的构建或采样。

| 程序与输入 | C 原生 | OCaml 原生 | C/Wasm，V8 | 豫言 WasmGC，V8 | 豫言原生 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 递归斐波那契 38 | 0.0610 | 0.0958 | 0.1131 | **1.1049** | 2.1358 |
| 素数筛 2,000,000 | 0.00477 | 0.00847 | 0.0678 | **0.1100** | 0.1609 |
| 整数矩阵乘法 300×300 | 0.00904 | 0.02757 | 0.0898 | **0.5076** | 1.1592 |
| 快速排序 1,000,000 | 0.01231 | 0.11664 | 0.0744 | **0.5078** | 1.0367 |
| 满二叉树，深度 18 | 0.01412 | 0.00807 | 0.0757 | **0.0907** | 0.0113 |
| 填充数组并求和 2,000,000 | 0.00457 | 0.00689 | 0.0646 | **0.0938** | 0.0828 |
| 启动基线：斐波那契 0 | 0.00301 | 0.00323 | 0.0591 | **0.0699** | 0.00495 |

这不是一个统一的“语言慢多少倍”：豫言原生在树测试中接近 OCaml、快于此 C 实现，却在矩阵中很慢。豫言 Wasm 的短任务包含约 70 ms 宿主固定成本；其实例执行计时中位数分别为：素数筛 45.1 ms、树 24.3 ms、数组 27.3 ms。该内部计时包含实例化、执行中的 JIT 和输出，不能称作纯内核时间，也不与另一语言的进程时间混算倍数。没有机械扣除启动基线。

峰值 RSS 中位数，单位 MiB，包括引擎和运行时，不是仅活跃对象大小：

| 程序 | C 原生 | OCaml 原生 | 豫言 WasmGC | 豫言原生 |
| --- | ---: | ---: | ---: | ---: |
| 矩阵 | 3.48 | 4.50 | 71.53 | 129.73 |
| 排序 | 9.06 | 9.95 | 77.91 | 129.75 |
| 数组 | 16.70 | 17.55 | 84.39 | 373.00 |
| 树 | 17.50 | 9.44 | 124.38 | 29.73 |
| 启动 | 1.39 | 2.28 | 59.64 | 1.70 |

豫言原生统一使用 `YY_GC_INITIAL_HEAP_SIZE_MB=64`，避免大数组初始堆不足；它不是内存上限。Node、OCaml 保持默认堆策略。原生数组和素数筛的约 373 MiB 峰值值得继续追踪，当前未证明是泄漏。完整五种方式的 RSS、范围及实例计时见《汇总.json》；234 份原始记录包含主实验 210 次运行和外提实验 24 次运行。

## 已定位的原因与小规模验证

1. **去柯里化与函数参数优化尚未实现。** `库/编译器核心/编译步骤/优化/跨文件优化/去柯里化。豫` 的 `去柯里化顶层`、`优化/函数参数优化。豫` 的 `函数参数优化顶层` 都直接返回输入表达式。这不等于整个编译器完全没有多参数调用支持，但这些优化入口当前没有做工作。
2. **矩阵热点仍有大量闭包和间接调用。** 当前生成 WAT 的 `f786`，在乘加及递归步之间出现 `array.new_fixed $tuple`、逐层取闭包函数号和 `call_indirect`，最后以 `return_call_indirect` 递归。见《矩阵热点片段.wat》。600×600 的独立 CPU 采样中，该函数合计 2695/2874 个命中，约 93.8%；GC 为 149/2874，约 5.2%。这不是精确计时，且分配指令成本仍可能归在函数内；不能理解为分配只有 5.2%。
3. **整数和数组表示过于通用。** `运行时.wat` 中小整数使用 i31，超出 −2³⁰…2³⁰−1 后分配含 i64 的结构体。算术反复检查类型、拆箱、再装箱；引用数组每项为通用引用。矩阵的小值也要走检查；数组累加结果越过 i31 范围后可能持续分配大整数盒。此处来自代码审阅，尚未单独量化各项占比。
4. **不是频繁 JS 调用拖慢矩阵。** 此采样整次运行只有 5 次宿主调用，热点在 Wasm 内部。因此继续优化 JS 原语名缓存不是这类任务的主要方向。

为验证第一项，没有修改编译器，而新增《矩阵不变参数外提。豫》：保留相同三重循环和矩阵布局，只让内层递归捕获不变的数组、边长、行列，递归时仅传序数与累加和。

| 同算法局部实验 | 原版 | 参数外提 | 墙钟降低 |
| --- | ---: | ---: | ---: |
| 300×300，五轮中位数 | 0.509922 s | 0.317383 s | **37.8%** |
| 600×600，五轮中位数 | 3.677825 s | 2.045324 s | **44.4%** |

两种规模所有输出均与 C 相同；另验边长 1、2、7、31。该实验改变了闭包组织，不能将全部收益归给某一条指令；它验证了优化方向，**没有完成编译器自动去柯里化，也不是语言全局获得 44.4% 提速**。

## 提速实施顺序

以下均为保留语义的方案；预计收益是待测假设，不作交付承诺。

| 优先级 | 修改内容与落点 | 为什么先做 | 验收方式 |
| --- | --- | --- | --- |
| P0 | 实现去柯里化：识别已知函数及完整参数应用，生成多参数入口；保留部分应用包装。接入已有闭包转换的多参数形和 Wasm 多参数调用。 | 两个相关优化入口为空；矩阵实验已证明闭包组织有明显成本。 | 完整应用热点不再逐参造闭包；矩阵至少接近此次外提结果；部分应用、函数逃逸、求值顺序、副作用、异常全部保持。 |
| P0 | 循环不变参数外提、已知调用目标直接化；自尾调用转循环，互递归继续保持正确尾调用。 | 当前每次迭代重复取闭包与传相同数组，尾调用虽不涨栈却仍有调用成本。 | 检查热点 WAT，并复测递归、矩阵和排序；不能只用文件变小作成功标准。 |
| P1 | 在类型擦除前保留计算表示信息，将确定的整数/浮点参数和局部变量直接降为 i64/f64；只在多态边界装箱。 | 减少类型检查、大整数盒及数值循环 GC 压力。 | i64 极值、溢出行为、异常和多态传递不变；数组累加及数值循环的分配明显减少。不得把 64 位整数改成 31 位。 |
| P1 | 数组专门化：整数用数值数组、布尔用紧凑标记；消除可证明冗余的边界检查和索引计算。 | 当前 C/OCaml 筛使用字节标记，豫言使用通用引用数组；数值数组也有额外装拆箱。 | 保留索引错误语义和数组别名行为；复测筛、矩阵、排序，报告时间和 RSS。 |
| P2 | 按闭包环境和代数类型形状生成专用 WasmGC struct，消除不逃逸的临时对象。 | 通用 tuple 造成额外间接访问；树测试提示对象布局值得考察。 | 混合构造器、递归类型、捕获变量和 GC 压力测试通过；用树与真实 AST/解析器负载验收。 |
| P2 | 给短任务提供可复用的轻量宿主/批处理入口，独立测常驻实例吞吐。 | 冷启动约 70 ms，短算法会被掩盖。 | 同时公布冷启动和常驻吞吐，不能用常驻成绩替代冷启动或自举指标。 |
| P3 | 追踪原生运行时的闭包分配、堆增长和高 RSS，继续保留原生作为对照。 | 当前重点是 Wasm，但原生内存与数值性能也有明显问题。 | 分配/存活对象/峰值三者分开记录，确认根保留及堆增长机制后再改 GC。 |

建议先完成 P0，再按新的 profile 决定 P1 的先后。第一阶段目标是消除已观测的浪费；之后再争取长计算中进入同引擎 C/Wasm 的 2 倍以内。这是目标，不是当前结论。所有阶段继续以 **完整冷缓存自举 ≤30 秒** 为硬门槛，同时禁止已测程序出现可重复的明显退步；任何编译器语义相关改动均执行仓库规定的三级自举、二进制一致性及类型检查。

## 公平性、工具链与复现

源码：前四题复用 `../跨语言比较` 的豫言/C/OCaml 实现；树与数组复用 `../网页汇编直生/基准库。豫`、`原生入口。豫`、`原生对照.c`，补齐《结构基准.ml》。没有更换排序算法、矩阵循环次序或使用 BLAS。

输入和输出：斐波那契 38 → 39088169；筛 2000000 → 148933；矩阵 300 → 103320050；排序 1000000 → 1500002；树 18 → 262144；数组 2000000 → 2000001000000。每次检查退出成功及输出一致。矩阵和排序沿用既有校验和，不声称逐项比较了整个结果数组。

整数范围均未超过 OCaml 的有符号机器整数范围；本实验不比较溢出语义。C 使用专用数值数组，OCaml 使用整数数组/字节数组，豫言使用其现有标准库数组，这反映实现选择而非统一对象布局。C 树逐节点 malloc 并显式 free，GC 语言不强迫退出前完成全堆回收，OCaml 常量叶节点可能共享；树结果不是纯 GC 优劣排名。

工具：原生 clang 22.1.7 `-O3`；WASI SDK clang 23.1.0 `-O3`（既有本地 SDK，在相邻工作区）；OCaml 5.5.0 `ocamlopt -O3`，`flambda: false`，未用 `-unsafe`；Node 26.3.0 / V8 14.6.202.34-node.20，默认引擎配置。C/Wasm 与豫言 Wasm 均为新 Node 加一个 Worker，线程栈上限 128 MiB；C 使用 WASI Preview1，链接时线性栈 16 MiB。二者运行时接口不同，仍非完全相同宿主。没有测 OCaml/Wasm，不能从 OCaml 原生差距推导 OCaml 在同一 Wasm 引擎的成绩。

```sh
clang -O3 性能研究/跨语言比较/性能基准.c -o yy横比C
ocamlopt -O3 -o yy横比OCaml 性能研究/跨语言比较/性能基准.ml
clang -O3 性能研究/网页汇编直生/原生对照.c -o yy横比结构C
ocamlopt -O3 -o yy横比结构OCaml 性能研究/横向复测/结构基准.ml
# 将下行 SDK 路径替换为本机路径；结构对照同样构建为 yy横比结构C.wasm。
yy_wasi_sdk/bin/clang -O3 性能研究/跨语言比较/性能基准.c -Wl,-z,stack-size=16777216 -o yy横比C.wasm
# 每题依次构建；结构组使用 性能研究/网页汇编直生/原生入口。豫。
./yy3_bs 性能研究/跨语言比较/矩阵乘法。豫 --parallel -c -o yy横比矩阵乘法原生
./yy3_bs 性能研究/跨语言比较/矩阵乘法。豫 --parallel --target=wasmgc -c -o yy横比矩阵乘法.wasm
mkdir -p 性能研究/横向复测/记录
./yy3_bs 性能研究/横向复测/计时。豫 --parallel -c -o yy横比计时
./yy横比计时 矩阵乘法 300
```

计时器用豫言编写。macOS `time -l` 的系统统计在本环境需要沙箱外权限；此前执行已获批准。本轮只新增基准、计时器、数据与方案，没有修改编译器，不重跑不必要的全自举。新增豫言文件均成功编译，外提实验另有输出回归。

本轮没有锁定 CPU 频率，只有一台机器和有限工作负载，不提供统计置信区间。下一组应用级测试应选 JSON 解析/序列化、文本分词、哈希表聚合和小型解释器，以验证本次微基准优化是否转化为实际应用收益。

# ANF 直接生成 Wasm GC 的原型与实测

已实现可运行原型：**现有闭包 IR → 现有 ANF → Wasm GC 文本 → Wasmtime**。程序后端没有经过 LLVM，没有链接 C 运行时，也没有豫言线性内存虚拟栈。生成的模块没有 `memory` 和 `import`。工具本身仍用现有原生豫言编译器构建；WAT 的解析与引擎机器码编译仍是必要准备步骤。

结论是：这条架构能运行，但当前原型**没有追平原生**；相对旧 Wasm，递归与数组改善，树反而退化。**尚未支持完整编译器，因此没有直接 GC 后端的自举时间，不能据此批准全面迁移。**

## 正式样本

Apple M5 Pro，macOS arm64，Wasmtime 48.0.1。每项预热一次，正式三次，表中为秒数中位数。前三种豫言执行路径共用《基准库。豫》，C 是另外手写的专用类型参照，不是同一个编译器后端。

| 计算内核 | 手写 C 参照 | 豫言原生 | 旧 LLVM/WASI | 直接 GC／复制式／初始总堆 128 MiB |
| --- | ---: | ---: | ---: | ---: |
| 斐波那契 35 | 0.0173 | 0.5424 | 3.7453 | **1.0228** |
| 深度 20 的树：构建与求和 | 0.0433 | 0.1135 | 0.5265 | **1.3179** |
| 百万元素数组：分配、填充与求和 | 0.0035 | 0.0995 | 0.5578 | **0.2068** |

直接 GC 相对旧 Wasm，递归约快 3.66 倍，数组约快 2.70 倍，树则慢约 2.50 倍。相对同源豫言原生，三项仍分别慢约 1.89、11.61、2.08 倍。

计时包含进程启动、实例化、执行和退出，不包括生成代码与 AOT 准备。所有 Wasm 路径都预编译后执行。C 的短样本明显受进程启动影响，不能用表中比例推导纯循环指令速度。C 使用专用 `uint64_t` 数组和固定字段结构，手工释放树；豫言三条路径则有通用值、闭包与自动回收，分配数量及优化行为并非完全相同。默认 GC 配置的五种方式按轮交替运行，128 MiB 组另测；不是统计意义上的严格随机实验。

## 收集器和初始堆不能省略

| Wasm GC 配置 | 递归 | 树 | 数组 |
| --- | ---: | ---: | ---: |
| 复制式，其他 GC 配置默认 | 1.1745 | 1.5838 | 7.7074 |
| DRC 引用计数，其他 GC 配置默认 | 7.1337 | 2.8190 | 1.4777 |
| 复制式，初始总堆 128 MiB | 1.0228 | 1.3179 | 0.2068 |

`collector=drc` 是显式选择，不称为“引擎默认收集器”。早期 CSV 标签 `GC默认` 已纠正为 `GC计数`，数值未改。128 MiB 参数是 `gc-heap-initial-size=134217728`，不是线性内存参数；复制式收集器使用两个半空间。原生参照设置 64 MiB 初始单堆，旧 Wasm 构建宿主也为 64 MiB 初始单堆，但不同引擎的分配布局和成长策略仍不相同。

百万元素数组对初始 GC 堆很敏感，不能只测引擎默认配置就断言 Wasm GC 分配必然很慢。Wasmtime 的[收集器说明](https://docs.wasmtime.dev/api/wasmtime/enum.Collector.html)及[配置说明](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html)也说明了半空间、初始堆与增长行为的区别；本次具体收益来自本机实测。

## 已实现的直接路径

《工具/网页汇编直生/入口。豫》读取真实的 `.闭包形式.json`，调用 `处理闭包函数定义` 与 `求值正则变换`，然后直接生成 WAT。没有另造一份手写算法冒充 ANF 输出，也没有使用旧 LLVM IR 转译。

这里必须绕开现有 `求值正则变换/顶层。豫` 的最后一步：那个入口在 ANF 之后还会执行 CPS。普通调用现在映射为 Wasm 调用，尾调用为 `return_call_indirect`。特别处理 `let x = call in x`，否则 ANF 产生的身份绑定会让尾递归退化成普通递归；百万元素数组已验证不会因为该循环耗尽调用栈。

- 小整数使用 i31，大整数使用含 i64 的 GC struct，保留完整有符号 64 位结果。
- 元组、引用数组和闭包环境使用 GC array；函数引用目前是表索引，调用使用 `call_indirect`。
- 代数构造器使用带标签的 GC struct，字段保存在 GC array 中。
- GC 对象由引擎追踪；旧的“登记 C GC 根”节点不再需要调用，Wasm globals、locals、参数中的引用由引擎管理。
- 未实现的外部调用、跨模块链接明确拒绝；内部函数最多八个参数。任意异常、call/cc、字符串操作、通用 FFI 和完整标准库尚未支持。

使用的分配原语是标准 [`struct.new`、`array.new`、`array.new_fixed`](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP.md)，并不存在一个适合所有对象的 `WasmGCAllocate` C 函数。Wasm GC 引用也不能直接当成原有 C 库的线性内存指针。

## 为什么仍然慢

1. **当前输入是无类型 ANF。** 通用引用表示需要动态解箱、类型转换；超过 i31 的整数还会装箱分配。直接输出 Wasm 并不会自动恢复已经擦除的类型。
2. **构造器布局还很粗糙。** 原生把构造器标记放入现有值的位域，不额外分配标签对象；原型则分配“字段数组＋标签 struct”两层对象。树的分配数量、对象头和扫描负担增加，这是代码中已确认的实现差异，不是对整段耗时的百分比归因。
3. **闭包和调用仍然通用。** 普通函数指针仍从 GC 环境取出，经整数解箱后走表调用；还没有直接调用识别、闭包消除、类型化函数引用和针对 Wasm 的优化。
4. **LLVM 原来承担的优化不会自动转移。** 原型只是语义下放，不具有完整的常量传播、标量替换与针对对象布局的优化链。

更合适的下一版是：保留类型及对象形状信息，让整数局部变量直接为 i64，让具体 ADT 对应直接含字段的 GC struct，让闭包含类型化函数引用；只有需要捕获的续延才显式堆分配。不能把普通 Wasm 调用栈当成完整 call/cc 的实现。

## 验证与复现

24 项执行检查覆盖两种 GC 的递归、构造器、零长度数组、超过 i31 的数组求和、负大整数及 i64 最小值，并验证负数和超过 wasm32 的数组长度拒绝。另有未知外部调用及跨模块链接拒绝测试。全部正式计时运行都与 C 参照核对输出；百万次尾循环成功。生成 WAT 无内存与导入，新版工具重复生成的 WAT 与计时版本逐字节一致。

原生按仓库要求完成自举，三级／四级逐字节一致，完整类型检查通过。旧 `yy_bs_stable` 规定首命令及未重定向复跑仍因旧包布局找不到标准库；首级通过现有编译器和豫构建立，后两级采用规定命令。新后端工具单独构建并通过类型检查。

```sh
./yy豫构 构建 网页汇编直生 --编译器 ./yy3_bs --输出 yy网页汇编直生 -j 4
./yy豫构 文件 性能研究/网页汇编直生/基准库。豫 --编译器 ./yy3_bs --输出 yy_直生基准原生 -j 4
# 从上述构建缓存选取本模块的 .闭包形式.json：
rg --files -uuu .yybuild | rg '网页汇编直生/基准库.闭包形式.json'
# 以下第一个参数替换为实际缓存文件：
./yy网页汇编直生 '<闭包形式.json>' 性能研究/网页汇编直生/基准库。豫 斐波那契 yy_直生_斐波那契.wat
./yy_wasmtime compile -C cache=n -C collector=copying -O gc-heap-initial-size=134217728 yy_直生_斐波那契.wat -o yy_直生_斐波那契_GC复制128.cwasm
./yy_wasmtime run -C cache=n -C collector=copying -O gc-heap-initial-size=134217728 --allow-precompiled --invoke run yy_直生_斐波那契_GC复制128.cwasm 35
```

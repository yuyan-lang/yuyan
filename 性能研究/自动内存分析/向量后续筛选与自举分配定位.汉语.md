# 向量后续筛选与自举分配定位

2026-09-20。以已验收的 `yy向量原生栈快速排序.wasm` 为运行时基线。以下实验均为隔离 WAT 原型，没有接入正式代码生成器；未据单次接近 C 的结果宣布目标完成。

## 没有保留的运行时原型

各组内部轮换版本顺序，每进程六轮，首轮与后五轮分开；不同组之间不直接比较绝对时间。热运行中位数如下。

| 实验 | 同组基线 | 原型 | 判定 |
|---|---:|---:|---|
| 十六项填充，独立九进程复测 | 33.595 ms | 33.560 ms | 初测优势未稳定复现 |
| 三十二项填充，同组九进程 | 33.595 ms | 33.764 ms | 不采用 |
| 32 位私有排序索引，保留分区守卫 | 34.656 ms | 36.962 ms | 明显变慢 |
| 32 位索引，直接调用分区快体 | 34.656 ms | 36.596 ms | 明显变慢 |
| 32 位索引，显式内联分区 | 33.526 ms | 33.921 ms | 没有收益 |
| 重复读取复用 | 33.291 ms | 33.449 ms | 没有可靠收益 |
| 重复读取及同地址存储转发 | 33.291 ms | 33.417 ms | 没有可靠收益 |
| 64 字节载荷对齐，独立九进程 | 33.501 ms | 33.513 ms | 初测优势未复现 |
| 双步分区循环改为尾检 | 33.046 ms | 33.711 ms | 不采用 |

证据分别见 [批宽初测](向量批宽探索实测.json)、[宽批复测](向量宽批九进程复测.json)、[窄索引](窄索引排序原型实测.json)、[窄索引内联](窄索引内联原型实测.json)、[值复用](栈值复用原型实测.json)、[对齐初测](向量载荷对齐原型实测.json)、[对齐复测](向量载荷对齐独立复测.json)、[尾检](分区尾检原型实测.json)。

批宽原型逐项验证 0 至 129 项及所有合法起点，每个原型 8,515 个案例、732,290 次内容检查。两个窄索引原型各有 7,959 个差分案例；内联原型另有 1,000 个随机差分案例；尾检有 10,287 个分区差分案例。值复用和对齐仅完成基准校验和检查，未达到正式接入所需的完整语义验证。

[窄索引内联追踪](窄索引内联追踪.txt) 显示，较短的递归排序函数使 V8 优先内联多层自调用，分区体因预算不足未内联。显式合并分区后仍未超越基线。因此不能仅凭指令变短或索引变窄推定运行更快。

## 编译器自身的栈分配覆盖

用同一原生编译器、相同并行方式分别生成默认编译器与 `--wasm-stack` 编译器，得到完全相同的 3,923,153 字节产物，SHA256 为 `7cb9bc90c737bad190700a5f926acdc93fd1ec1530d73476af0ea99b15bcb87a`。实际栈根和私有栈函数均为零，见 [覆盖结果](自动栈编译器覆盖探索.json)。因此既有栈优化尚未让编译器自身的冷自举变快。

通过已有 `--debug-print-add 内存分配` 取得 [静态分配诊断](编译器分配诊断摘要.json)：25,559 个分配位置，包括 17,810 个元组、7,597 个构造器、147 个初始化数组、5 个未初始化数组。这里统计的是中间表示中的静态位置，不是执行次数，也不代表所有对象实际逃逸。

[152 个数组分配点](编译器数组分配点.json) 中，63 个被报告为进入其他对象且容器生命周期未跟踪，71 个属于目前没有非逃逸证明的用途，其余为返回、写数组或未知调用等。报告没有任何已证明的非 GC 栈数组候选。后续需要追踪容器与闭包的生命周期，以及补齐原语和跨调用的效果摘要；不能把进入一个临时容器直接等同于逃到整个调用之外。

## 自举运行时内存画像

采用原始生产编译器，完整禁用编译缓存，以 18 个工作进程运行自举，启用 V8 GC 诊断。第二次诊断通过临时 Node Worker 构造器代理记录线程与任务的对应关系，生产宿主与编译器源码没有为此修改。得到 1,092 条任务线程映射、39,220 条可解析 GC 事件；输出仍与原编译器逐字节相同。

下表是 V8 在已记录区间报告的累计分配字节，包含宿主 JS 与 WasmGC；不是常驻内存，也不包含每个线程最后一次 GC 之后的全部分配。

| 阶段 | 累计报告分配 |
|---|---:|
| 类型检查与擦除 | 276.78 GiB |
| 闭包转换前处理 | 88.80 GiB |
| 跨模块优化 | 58.18 GiB |

类型检查与擦除约占总量的 57%。不同线程的暂停会重叠，不能把 GC 暂停之和当作自举墙钟损失。诊断运行也不作为性能验收计时。原始映射、聚合及压缩事件见 [分阶段 GC](编译器自举分阶段GC.json)、[线程任务](编译器自举线程任务.json)、[事件](编译器自举分阶段GC事件.json.gz)。

## 已定位的下一处代码热点

对 `统一网页汇编。豫` 的类型检查与擦除任务单独采样，工作线程约 1.88 秒的样本中，GC 自耗时约 266 ms；名称解析包含耗时约 949 ms，其中 `查找下个名称源码范围` 包含耗时约 391 ms。包含耗时存在调用嵌套，不能相加。见 [符号化采样](统一网页汇编类型阶段采样.json) 和 [CPU 采样文件](统一网页汇编类型阶段.cpuprofile)。函数编号来自同一正则模块顺序的调用逃逸报告，共 5,023 个函数。

源码检查发现，名称定位反复将十个固定声明后缀拆成字符列表；通用 `以起否` 使用严格求值的 `且`，会在首字符已不同时继续处理后续字符。这给源码搜索增加了重复转换、闭包调用和临时分配。

已经据此实现编译器内部的纯字符串前缀短路比较，以及直接匹配已有字符列表的声明后缀判定。保留通用列表函数的原求值语义，不关闭语言服务，不删除名称定位结果。10,516 个差分案例及完整自举通过；八次冷自举对照显示平均缩短约3.3%，已保留。详见 [独立验收报告](源码前缀分配消除.汉语.md)。

# 自动容器逃逸分析

新增按分配位置与字段区分的函数内指向图分析，作为自动非 GC 内存分配的证明基础。目前通过 `--debug-print-add 内存分配` 输出诊断，尚未参与分配代码生成；默认编译不执行该分析。

此前把“修改字段或存进另一对象”统一列为保守障碍。新分析跟踪局部容器之间的引用关系：对象存进局部盒子并不自动逃逸；盒子返回或交给未知调用时，其可达对象才随之逃逸。元组字段分别处理，数组元素合并处理。条件分支取并集，字段更新保留旧来源，形成保守的流不敏感分析。

未知调用仍被视为可能保留参数。已逃逸对象的字段加入外部来源，防止外部修改后读出新别名、再经该别名写入局部对象而漏判。不把已有“不保留参数”摘要误当作“只读”证明。深链和环的逃逸传播使用工作列表。

证书只证明对象不逃出当前函数，不证明唯一所有权、线性使用、无 GC 引用载荷或栈分配资格。输入须是合法 SSA；未支持的控制形式、超过 256 个局部值、超过 64 个字段或 32 轮未收敛均不给证书。普通条件分支已建模，结果块和循环尚未建模。

## 编译器自身的发现

- 5,073 个函数中，362 个因控制形式或预算未获证书。
- 已建模的 12,360 个分配点中，1,076 个元组被证明不逃出函数；其中 1,070 个在模块初始化函数中。
- 153 个数组分配点仍全部可能逃逸；这不等于它们运行时必然逃逸，而是当前证明不足。
- 这些是静态分配点数量，不能解释为动态分配次数或节省的字节数。

见 [诊断摘要](容器图编译器诊断摘要.json) 和 [原始诊断](容器图编译器诊断原始.txt)。

对其中 1,072 个单字段对象做过 WAT 原型：进一步检查全部使用方式后，将字段值直接保存在局部变量中，消除盒子。相同当前源码的 ABBA 完整冷自举结果：基线 22.02、23.48 秒，原型 22.64、22.93 秒；均值分别为 22.750 和 22.785 秒，四次输出一致。未发现有用的墙钟收益，因此没有接入正式代码生成。见 [转换记录](容器单槽原型转换.json)、[冷自举记录](容器单槽原型冷自举.json)。

## 验证与墙钟验收

`测试/编译器/容器逃逸。测试。豫` 在原生与 Wasm 上通过 1,020 个用例：19 个边界及保守拒绝用例、1,000 个三节点引用图穷举用例、一个 40 节点逆编号深链。穷举用独立可达性预期检查所有分配点和逃逸标志，覆盖返回与未知调用两种外传方式。见 [验证记录](容器逃逸单元验证.json)。

按仓库规定完成 stable → 二代 → 三代 → 四代原生自举，第三代和第四代逐字节相同；两项类型检查通过。随后从原生生成 Wasm 种子，再做两代完整冷自举，用时 **21.57 秒、23.01 秒**；种子、二代、三代逐字节相同。使用 18 个工作线程和 `--do-not-load-cache`，未清空操作系统页缓存，计时期间没有并发构建。这是低于 30 秒门槛的验收，不是相对上一版本提速的对照实验。见 [哈希及验收摘要](容器图验收摘要.json)。

六个运行内核及默认 GC 排序另行重编译，并与上一版本逐字节比较，记录在 [内核一致性](容器图六核一致.json)。本轮不改变运行时分配代码，不增加运行内核提速结论。

## 下一步

优先建立跨函数的内存效果摘要，区分全局保留、返回参数或其可达对象、写入参数可达容器，以及写入值的来源。调用者局部容器接收另一个局部对象时应建立边；只有容器外传后才传播逃逸。返回内部对象必须映射其可达关系，不能仅映射参数根。

闭包捕获和高阶调用需要进一步证明；非 GC 线性内存还须排除无法安全表示的 GC 引用，并处理生命周期、多个分配点、容量失败及回退。这些分析由编译器自动完成，不要求用户增加所有权或局部性标注。当前未证明所有基准达到 C，也未完成通用自动栈分配。

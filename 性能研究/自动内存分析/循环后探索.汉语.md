# 循环范围优化后的进一步探索

本轮保持已验证的默认编译器不变，针对剩余排序差距进行了八种生成代码原型实验。以下数字不能算作新的正式语言提速；原始基线为 `yy循环实排序.wasm`。

四百万项排序，每个进程六轮，首轮单列，后五轮计入稳态。除死局部实验使用七进程外，其余各五进程，交替或轮换实现顺序，无并发构建。各实验组应只和本组基线比较，不能把不同组的小幅变化混作收益。排序所有轮次校验值一致，但这不代替逐项正确性与异常语义验证。

| 实验组 | 本组基线毫秒 | 原型毫秒 | 结论 |
|---|---:|---:|---|
| 已有守卫内改用 i32 索引 | 49.266 | 50.786 | 未加速 |
| 复用比较时已读出的元素 | 49.266 | 49.726 | 未加速 |
| i32 索引加读取复用 | 49.266 | 50.132 | 未加速 |
| GC 数组元素改成 i32 | 48.768 | 48.695 | 无明显稳态收益 |
| 元素与索引均 i32 | 48.768 | 49.108 | 未加速 |
| 清理无读取的局部变量 | 48.964 | 48.529 | 稳态差异较小 |
| 外层排序另加范围守卫 | 48.796 | 48.225 | 约 1%，不足以据此增加复杂证明 |
| 后备体改为私有函数引用尾调用 | 49.008 | 49.687 | 未加速 |

窄索引原型只在现有范围守卫成功后使用，返回时无符号扩展为 i64；元素和枢轴保持 i64。窄元素原型直接缩窄了私有数组类型，**不保持任意全宽元素语义**，只是诊断当前输入范围的布局成本，不能作为默认优化。没有引入持久线性内存缓冲。

外层原型依赖分区返回值位于入口扫描位置与上界之间，不能仅凭局部宽度证明启用。它还保留原体、失败守卫和全部 GC 数组边界检查。若将来实现，应先建立通用跨函数返回关系摘要；当前约 1% 的单组收益不够支持这项额外复杂度。

## 无读取局部变量

原型按函数识别从未被 `local.get` 读取的局部声明，将其写入改为 `drop`，保留产生值的操作及副作用，再去掉无效的空引用丢弃。排序去掉 5,691 个声明、2,964 次无读取写入。七进程首轮中位数从 71.838 降至 69.233 毫秒，约减少 3.6%。

其他程序五进程交替复测结果：

| 程序 | 稳态旧/新毫秒 | 首轮中位旧/新毫秒 |
|---|---:|---:|
| 斐波那契 40 | 104.868 / 107.242 | 106.758 / 107.925 |
| 素数筛一千万 | 19.219 / 18.955 | 43.722 / 42.730 |
| 虚拟数组一千万 | 3.533 / 3.506 | 22.966 / 22.993 |

未显示普遍的首轮改善，斐波那契在本组还略慢，因此也暂不接入默认编译器。这不能证明清理局部变量普遍有害，只能说明当前结果不支持直接将其视为性能胜利。

## 机器码观察

使用本机 V8 的 `--no-liftoff --print-wasm-code` 单独诊断，保留排序函数 `d762` 的 TurboFan 输出于 `循环排序机器码.txt`。这是强制优化编译的诊断，不能代表正常首次执行，也不能用其计时替代默认引擎数据。

在这份输出中，分区快体与后备体已被内联进排序，比较后重复读取被复用；快路径仍存在 GC 数组长度比较和地址计算。因此不能把源码层面的调用次数或重复读取次数直接当作最终机器码成本。也不能据此宣布 GC 数组或豫言已到性能极限。

## 当前决定

八种原型均未达到默认启用条件，保留上一轮自动循环范围优化。接下来应重新按实际成本评估跨函数关系、分配生命周期和首次执行开销，避免反复尝试已经无收益的窄化与读取复用。任何新的内存渠道都必须符合不保留私有缓冲的要求，且不能用丢失整数或数组语义换速度。

数据分别见 `循环后窄索引探索.json`、`循环后窄元素探索.json`、`循环后死局部探索.json`、`死局部其他基准探索.json`、`循环外层关系探索.json`、`循环冷后备探索.json`。每个排序原型有对应补丁，哈希见 `循环后探索摘要.json`。默认源码未修改，本轮未重复完整自举。整体目标尚未完成。

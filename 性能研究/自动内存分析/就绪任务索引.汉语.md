# 就绪任务索引降低协调开销

本轮保留 `库/构建基础/调度器。豫` 的就绪检查优化：每次检查临时建立 64 个桶，按任务名称的字节长度分桶；依赖仍以完整字符串比较。逆序插入保持原列表中重名任务“取第一个”的行为。索引保存原任务引用，不复制状态，也不跨检查缓存任务图。派发前的依赖复查、优先级排序、失败停派和动态添加任务逻辑保持原样。

这是豫言调度器自身的通用算法改进，没有改变公开任务结构或后端 ABI，没有跳过编译阶段。长度相同或模 64 相同的名称允许碰撞，桶内仍线性查找；不声称最坏情况变为常数时间。

## 完整冷自举

相同当前源码、同一宿主默认有界线程复用、18 个工作任务、独立 Node 进程、`--do-not-load-cache`，无并发构建，未清空系统页缓存。先按旧—新—新—旧，再按新—旧—旧—新运行。

| 对照组 | 旧编译器秒数 | 索引版秒数 |
|---|---|---|
| 第一组 | 16.07、16.89 | 16.27、15.95 |
| 反转顺序复测 | 16.95、16.70 | 15.80、16.03 |
| 四次平均 | 16.6525 | 16.0125 |

平均用时减少 **0.64 秒，约 3.84%**。八次均生成同一个新版编译器产物，排除通过少做编译工作获取数字的情况。见 [首组](就绪索引冷自举探索.json)、[复测](就绪索引冷自举复测.json)、[汇总](就绪索引实测摘要.json)。这些是本机对照，不外推为所有项目都能获得同等幅度。

## 定位证据与语义验证

复用线程后的协调 Worker CPU 采样中，原任务名称查找 `f1113` 的自身归因时间约 **3545 ms**。新实现约 **782 ms**；已核对该函数在两版 WAT 中规范化空白后完全相同，变化来自调用者传入较短的桶列表。采样可能包含调度影响，不等同于所有线程 CPU 总量；并行工作有重叠，不能把采样减少量直接当作墙钟收益。见 [改前采样](线程复用调度采样摘要.json)、[改后采样](就绪索引采样摘要.json)。

`测试/编译器/调度就绪索引。测试。豫` 保留原线性就绪算法作为对照，**904 个差分案例**在 Wasm 和原生上均通过。覆盖状态组合、重名及相反排列、缺失依赖、失败状态、循环、空名称、状态更新、等长度图替换，以及 512 个名称全部进入同一个桶的情况。按独立任务编号比较返回顺序，避免重名字符串掩盖错误。测试包新增对 `构建基础` 的直接依赖，以遵守包导入约束。

## 并发度探索

在改动就绪检查之前，初筛 12/18/8/16 个工作任务分别为 15.77/16.16/17.48/16.86 秒。随后使用相同的 20 ms RSS 采样，交替复核 18—12—12—18：

| 并发上限 | 两次进程内墙钟秒数 | 两次采样峰值 RSS 字节 |
|---|---|---|
| 18 | 15.694、16.100 | 3276718080、3164438528 |
| 12 | 15.986、15.951 | 2783444992、2640035840 |

12 与 18 的时间接近，12 的采样内存更低；没有证据支持改动默认并发选择。需要减少内存时可显式使用 `-j 12`，本轮正式速度对照继续使用 `-j 18`。采样峰值不是硬内存上限，进程内观测也不混入无采样的正式墙钟表。见 [初筛](线程复用并发度探索.json)、[交替复核](线程复用并发度复核.json)。

## 定稿验收

按仓库指定流程完成 stable → 二代 → 三代 → 四代原生自举，第三代和第四代逐字节相同，随后两项类型检查通过。以新版原生编译器产生的 Wasm 种子与探索候选相同；再完成两代禁用编译缓存的自举，用时 **15.29、15.84 秒**，种子和两代产物逐字节相同。这两次是独立定稿验收，不混入前述八次对照平均值。

六个运行内核及默认 GC 排序经新编译器重编译，均与本轮前逐字节相同。本轮收益来自编译协调，不能声称六个计算内核也获得同等提速。见 [六核验证](就绪索引六核验证.json) 和 [完整验收、源码及产物哈希](就绪索引验收摘要.json)。整体 C 性能目标及统计容差问题仍独立保留，未宣称完成。

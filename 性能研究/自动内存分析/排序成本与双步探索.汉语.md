# 排序成本拆分与双步循环

本轮没有修改默认编译器。先分阶段测量，再根据机器码尝试循环结构变换；找到一个跨规模有效的双步原型，仍需通用证明和代码生成实现。

## 分配并非当前排序差距的主因

在正式生成的豫言 Wasm 中增加观测导出，调用原分配、填充、排序函数。C 对照通过 `排序阶段对照.c` 包含既有 `原生内核.c`，只增加同样的导出，算法不变，WASI SDK clang `-O3 -mexec-model=reactor -Wl,-z,stack-size=16777216` 构建。

每项五进程交替执行，各六轮，首轮排除后 25 样本取中位数，单位毫秒：

| 实现 | 分配 | 填充 | 排序 | 总计 |
|---|---:|---:|---:|---:|
| 豫言 | 1.048 | 1.427 | 46.028 | 48.397 |
| C/Wasm | 0.001 | 0.625 | 31.884 | 32.522 |

各列中位数并不必然相加等于总计中位数。跨导出观测改变了调用边界，不能视作无扰动的精确剖析，但总计与未拆分测量接近，足以说明此基准的大部分差距在排序本身。GC 数组在观测端只是解除引用，不能把它与 C 的 `free` 混称为立即释放；后续 GC 的费用仍可能出现在后续轮次。结论仅适用于此排序，不能推断其他程序的分配优化不重要。

## 引擎成本诊断

单独测试 V8 明确标为 unsafe 的跳过数组边界检查选项，仅运行已知合法固定输入，绝不用于正式编译器或边界测试。默认 48.819 毫秒，跳过检查 45.850；关闭循环展开则 53.447，同时两者为 49.517。说明数组检查解释了一部分成本，但不足以解释全部差距，关闭循环展开也不是出路。原始记录有明确诊断标记，见 `排序引擎成本诊断.json`。

正常引擎输出的 C 排序 TurboFan 机器码显示：编译后的循环按两步处理，使用地址步进和剩余数量计数。记录见 `C排序机器码.txt`。这提供变换方向，不是把不同编译阶段的代码尺寸直接解释为性能比例。

两个未采纳原型：字节单位归纳变量为 50.102 / 基线 48.628 毫秒；对同位交换增加分支以省读写为 52.634 / 基线 49.434 毫秒。二者都没有收益。

## 双步循环原型

在现有范围守卫成功后的分区快体中，先处理奇数余项，再每轮依次执行两次原循环体。所有 GC 数组读取、写入及其边界检查保留；没有不安全引擎选项，没有私有缓冲。原守卫失败时仍进入原实现。

四百万项五进程交替执行，每进程六轮，后 25 样本取中位数：

| 实现 | 稳态毫秒 | 首轮范围毫秒 |
|---|---:|---:|
| 正式循环范围优化 | 48.361 | 71.252～73.393 |
| 双步原型 | 44.323 | 58.043～60.165 |

稳态减少约 8.3%。三个进程的跨规模复测：百万项 11.609→10.516 毫秒，八百万项 106.112→96.371 毫秒，均减少约 9%。本轮未重跑完整 C 对照，不能把不同实验组的数字当作新的正式 C 差距。

对正式分区入口和双步原型做 94,500 组边界比较：返回值、异常类别与消息、完整数组以及失败前写入全部相同，其中 85,077 组失败、8,008 组满足快入口守卫。数组长度覆盖 0、1、2、3、4、5、16，初值 `23−17×索引`；参数包含全宽整数端点、负数、零至九及 wasm32 宽度边界。原始记录见 `循环双步边界.json`。

## 通用实现必须补齐的证明

已有循环关系证明只保证范围不变，不保证前进速度，不能直接用于双步化。例如扫描序数不增加的无限循环也可能保持全部范围关系。

接入时必须额外证明：

1. 循环入口具有 `0≤扫描≤上界≤UINT32_MAX`，上界在每条回边保持不变。
2. 每次原循环体都恰好令扫描增加一；所有分支都以满足该条件的自尾调用结束，不能出现提前返回、非尾递归或未知调用。
3. 扫描等于上界的退出分支与原结果保持一致；原比较结果若被循环体使用，也必须保持其已知值。
4. 新参数仍同时赋值；两次迭代的读写和异常顺序不得交换。第一步失败时不能提前执行第二步。
5. 奇数余项、零轮、计数差与加法均有不溢出证明。缺少任何前提就回退到当前实现。

可考虑在现有尾递归参数赋值后跳出单步代码块，再依次组合一个余项和两个单步；重复生成时保留原表示事实与作用域隔离。不能按函数名、编号或排序算法匹配。正式接入后仍需完整自举、冷缓存时限、公开边界及多程序回归。

原型补丁与哈希见 `循环双步原型.补丁`、`排序成本与双步摘要.json`。当前默认编译器仍为上一轮已验证版本，本轮未重复完整自举。整体目标未完成。

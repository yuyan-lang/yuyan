# Fox 项目与豫言系统编程设计研究

日期：2026-09-21。本文是设计建议，不代表功能已经实现；未修改编译器或现有语言语义。

建议保留豫言的主体语法、类型与模块机制，新增可检查的系统代码约束、机器表示类型和小型硬件能力接口，在现有原生后端上发展 freestanding 目标。无须先设计另一门语言，但不能只靠后端优化启发式宣称普通代码已经适合中断、页表或 DMA。

## Fox 的实际经验

Fox 从高级语言与系统构造相互促进出发，FoxNet 使用 Standard ML 的模块和类型机制组织 TCP/IP。官方介绍明确称其为用户态协议栈；另列夏威夷大学 Hello 项目把它移植到裸机的工作。因此不能把 FoxNet 本身描述成完整的裸机操作系统。[FoxNet 项目页](https://www.cs.cmu.edu/~fox/foxnet.html)

FoxNet 总结论文讨论了机器字装箱、外部内存、数组访问与 GC，指出当时 SML 的能力不足以高效地用自身实现 GC。论文的部分网络性能结果不错，但并没有证明所有系统场景都达到 C，也没有给出硬实时保证。[Biagioni、Harper、Lee，2001，§4.5、§5.2、§6.1](https://www.cs.cmu.edu/~rwh/papers/foxnet/hosc.pdf)

Fox 的 TIL/TILT 路线强调在优化中保留类型信息，让中间结果可检查。这对豫言尤其有用：无 GC、生命周期和机器表示的证据，应一直保留到代码生成，而非在前端接受后即丢失。[项目说明](https://www.cs.cmu.edu/~fox/til.html)

TIL 作者后来也提醒，早期的小基准、整程序优化和高编译成本限制了结论。这与豫言的冷自举预算直接相关：不应为每个局部优化增加无界的全程序分析，也不能把排序成绩当作内核适用性证明。[TIL 回顾](https://www.cs.cmu.edu/~rwh/papers/til-retro/retrospective.pdf)

作为补充，House 展示了保留 Haskell、通过受控硬件接口构建裸机系统的路线。它说明“高级语言加小型硬件边界”确有实践先例，不要求表层语言变成 C。[作者论文页，ICFP 2005](https://ogi.altocumulus.org/~hallgren/ICFP2005/)

## 当前豫言的起点

本次核对的实现包括：

- `统一原生直生。豫`：当前原生后端由统一 ANF 生成直接调用 C，再交 clang/LLVM；存在影子根与回收检查。
- `运行时支持库/原生/直接调用.h`：直接函数接收通用豫言值，返回通用豫言值；每模块按实际最大元数生成参数声明。
- `运行时支持库/原生/类型定义.h`：通用值容器为 `__uint128_t`，不代表语言整数是 128 位。
- `运行时支持库/原生/入口.c`：当前宿主入口使用 main、命令行、随机数及时间等设施，不能直接充当裸机启动入口。
- `网页汇编栈后端。豫`、`网页汇编线性栈基础。豫`：有受限的非 GC 整数数组栈化，但容量或资格失败时回退 GC，且不能存 GC 引用。
- `统一正则数据。豫`：已有基本值类及代码值，尚不是本文建议的区域、效果和硬件能力 IR。

旧的 `原生二进制接口.汉语.md` 记载旧 LLVM 帧接口；不能把其中的 `void(i128,i128)` 当作当前默认直接调用后端的完整事实。系统扩展应以当前生成器与运行时为依据，并另行版本化系统 ABI。

Wasm 线性内存里的栈是 guest 存储，不是 CPU 特权态、物理内存或中断机制。保留 Wasm 用于应用与验证是合理的；裸机内核建议走原生目标。若选 Wasm 内核，则还必须先提供执行引擎及特权宿主，工程责任不会消失。

## 语言设计需要补的能力

| 能力 | 建议设计 | 不能以何者代替 |
|---|---|---|
| 机器数值与布局 | 增加明确位宽的有符号/无符号数、位运算、转换与溢出规则；外部结构声明尺寸、对齐、字段偏移、字节序 | 通用整数与元组不自动等于硬件布局 |
| 非 GC 存储 | 允许编译器选择寄存器、栈、调用者区域、页分配器、固定地址缓冲区；区分存储域与对象生命周期 | 不逃逸不能单独证明唯一性；逃逸也不意味着必须用 GC |
| 效果约束 | 推断托管分配、可能 GC、阻塞、挂起、非局部退出、硬件访问等效果，检查完整可达调用图 | 只标记顶层函数为 no-GC 不足够 |
| 生命周期与资源 | 普通借用和唯一使用自动推断；区域及设备接口有明确所有权/状态契约 | 编译器不能从任意外部函数名推断 DMA 已完成 |
| 并发与设备内存 | 分离普通、原子、MMIO 访问；提供原子序、屏障与架构相关 cache/DMA 操作；能力限定可访问范围 | volatile 不等于原子同步，也不等于 DMA 一致性协议 |
| 外部调用 | 明确导入/导出符号、目标调用约定、布局、回调上下文及外部效果摘要 | 一对一 C 函数映射不保证无分配或中断安全 |
| 异常和执行上下文 | 内核入口定义错误返回、panic、展开策略；中断与线程有独立约束，栈预算可检查 | 无 GC 不等于有界时间，也不等于不会栈溢出 |

原子与 volatile 必须分别建模；LLVM 文档同样区分这些语义。[LLVM 原子与并发说明](https://llvm.org/docs/Atomics.html)

建议首先定义“托管模式”和“受约束系统模式”。它们是同一语言的使用约束：允许的源程序保持相同含义，系统模式拒绝不能满足约束的代码，不静默改变整数、异常或分配失败语义。

效果至少区分“不触发 GC”和“不动态分配”。区域分配器可以不触发 GC，但可能耗尽、阻塞或上锁；中断上下文应使用预分配且不会阻塞的资源。硬实时还需算法与栈空间的界，不能从 no-GC 推出。

## 与全自动分析的关系

用户不必在每个对象上写 local、stack、linear。编译器自动推断别名、逃逸、调用借用、捕获和最后使用点，产生区域及效果摘要。在普通模式中证明不足可保留 GC；在禁止托管分配的系统入口下，证明不足必须报错，给出具体调用链和隐含装箱点。

对闭包的要求是生命周期和效果可证，不应全局禁止高阶函数。已知回调可以专门化或把环境放在栈/调用者区域；未知回调需要可验证的效果约束，否则不能进入中断路径。跨模块摘要需包括保留参数、返回别名、写入可达对象及可能执行的效果，不能把“不保留参数”误当成“只读”。

自动推断不可能对任意程序总是得到精确结果。入口的执行约束、外部函数契约以及硬件完成事件必须有定义。它们是模块与外界交互的语义，不是让程序员替编译器逐个选择对象放在哪里。

建议将分析结果保存在类型化 IR 中，优化和降级后复查：包括闭包环境、装箱、异常对象、格式化、隐式栈扩展及外部包装是否引入受禁止效果。分开编译时保存带版本的摘要，链接时核验；受限分析超预算时保守拒绝或保留普通实现，不牺牲自举预算换无限分析。

## “特殊函数”应拆成三个独立概念

1. **C ABI 入口**：定义二进制参数与返回规则。无捕获的具体机器类型函数可以导出成 C 可调用符号；带捕获闭包需要显式上下文与寿命协议。没有必要要求每个豫言函数对应一个 C 函数，内部仍可内联、专门化、消除。
2. **系统入口约束**：定义该入口及其可达调用的效果要求，例如禁止托管分配、阻塞、挂起和跨边界异常展开。C ABI 本身不提供这些保证。
3. **硬件原语**：提供 MMIO、读写特权寄存器、屏障、切换地址空间等编译器认识的操作。通过小型受信任模块构造能力，普通模块不能从任意整数伪造硬件权限。

第一阶段可以保留当前应用 ABI，新增独立的系统表示及桥接；无需把所有应用函数改成机器整数/裸指针签名。桥接自身也必须进入效果分析：会装箱的桥不能进入禁止分配的路径。中断入口的保存现场、切栈和返回通常由架构入口桩完成，随后才调用受约束豫言函数，不能假设普通 C 函数入口就是中断入口。

## 一个网卡中断例子

以下是建议的接口语义，不是已经可编译的豫言语法：

```text
入口：处理网卡中断
约束：禁止托管分配、GC、阻塞、挂起、异常跨界
输入：设备寄存器能力、预分配描述符环、完成队列
行为：读取状态 → 确认已完成描述符 → 将缓冲区句柄放入队列 → 应答中断
```

局部描述符视图由编译器自动放入寄存器或栈。真正的收包缓冲区活过本次中断，而且设备会访问它，必须由预先分配的非 GC 内存池持有，不能因局部变量不逃逸就把载荷置于中断栈。

提交给设备时，接口将缓冲区的访问状态转为“设备持有”；收到符合协议的完成通知，才转回“CPU 可访问”。编译器检查程序如何使用这些状态，设备协议定义何时能够转换；物理地址、总线地址/IOMMU 映射、对齐及一致性仍须由平台实现保证。

## 推荐落地顺序与验收

1. **先做系统编译剖面**：沿用语法，补充机器类型、外部布局及效果摘要；选择一条经过审核的无 GC 调用链，输出可与 C 测试程序互调的目标文件。测试双向 ABI、整数边界、布局、失败路径，并审计生成代码中的隐藏分配。
2. **再做最小裸机内核**：建议先选单核 QEMU 平台，例如 RV64 的 virt，实际目标需用户选择。小段汇编/C 完成启动、异常入口与硬件原语，豫言实现串口输出、页分配、定时器和最小调度。继续使用现有 C/clang 编码路线是可行的起点，不必先重写机器码后端。
3. **加入真实外部内存工作负载**：预分配队列、缓冲池、设备完成通知、包解析与校验和；测尾延迟、峰值内存、栈界和中断处理成本，不只测吞吐。
4. **再扩大语言与内核能力**：按需要引入托管服务、更多驱动及多核。将托管服务放到用户态可简化边界；若在内核引入 GC，就必须设计线程/CPU 根、抢占、安全点、屏障、固定地址引用及停顿策略。

Freestanding 是新增的运行环境契约，不是简单去掉 main。必须审计链接进来的 libc、平台函数、编译器辅助例程和初始化依赖；即使 C 编译器的 freestanding 模式也可能要求提供特定内存例程。[GCC 环境说明](https://gcc.gnu.org/onlinedocs/gcc/Standards.html)

真正需要用户决定的事项是：首个硬件目标、是否允许内核高层组件使用 GC、是否接受初期小型 C/汇编受信任层。调研阶段无需先决定微内核还是宏内核，也无需批准一整套复杂新类型系统；先以小内核和真实驱动需求检验这些设计。

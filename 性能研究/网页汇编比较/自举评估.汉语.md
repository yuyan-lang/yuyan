# 以自举时间评估网页汇编迁移

最新结果（2026-09-08）：Wasm 编译器已连续自举成功，同名三级与四级逐字节一致。带栈检查的完整 Wasm 自举 369.11 秒，同版本原生直接入口 62.72 秒，约 5.89 倍耗时；各一次、4 worker。详见[当前验证](../../工具/网页汇编宿主/验证.汉语.md)。以下全部保留为桥接实现之前的历史快照，其中“尚未成功”等结论不代表当前状态。

2026-09-07，美东。对应文言本见《自举评估.文言.md》。此次以编译器自身为工作负载，不再用斐波那契等小程序推断自举性能。

## 结论边界

当前源码能够完成原生自编译，但 Wasm 编译器在最终链接阶段失败，尚未获得可运行的 Wasm 编译器。因此 **Wasm 自举时间不可测，性能比值为“未取得”，不是零，也不是超时**。上轮小程序的 2–4 倍耗时不能直接外推到编译器自举。

严格的指标应为：用 Wasm 编译器执行同版本源码，生成下一代 Wasm 编译器，并继续验证固定点。原生编译器生成 Wasm 编译器只算交叉编译准备，不能当作 Wasm 自举。

## 实测时间

| 阶段 | 墙钟时间 | 用户态时间 | 内核态时间 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 既有原生编译器 → 原生二级 | 106.74 秒 | 291.85 秒 | 82.98 秒 | 成功，二级能运行 |
| 新生成原生二级 → 原生三级 | **119.77 秒** | 309.50 秒 | 90.81 秒 | 成功，二级与三级逐字节相同 |
| 原生二级 → Wasm 编译器 | 74.31 秒 | 221.74 秒 | 55.84 秒 | 最终链接失败，不是 Wasm 自举时间 |
| Wasm 编译器 → 下一代 Wasm 编译器 | **未取得** | — | — | 前置 Wasm 编译器未生成 |

最直接的有效基线是 **119.77 秒／单级自举**：新生成的编译器已经重新编译自身，并产生与自身逐字节一致的下一代。`cmp yy_自举_原生二级 yy_自举_原生三级` 返回 0，SHA-256 见《自举记录/汇总.json》。前两项是不同世代各一次观测，不是同一测量的两次重复，不能据此计算可靠误差范围。

用户态与内核态统计包含子进程累计 CPU 时间，因 4 并发而可超过墙钟时间。上表没有将失败的 74.31 秒当作更快的后端成绩。

两次原生构建命令分别为：

```sh
./yy豫构 构建 豫言编译器 --编译器 ./yy编译器 \
  --输出 yy_自举_原生二级 -j 4 -- --do-not-load-cache
./yy豫构 构建 豫言编译器 --编译器 ./yy_自举_原生二级 \
  --输出 yy_自举_原生三级 -j 4 -- --do-not-load-cache
cmp yy_自举_原生二级 yy_自举_原生三级
```

这是使用当前包构建入口完成的两代自编译实验，保留了工作区原有 `yy2_bs`、`yy3_bs`、`yy4_bs`；不是重新执行旧单文件命令的三阶段验证流水线。

## 条件

- Apple M5 Pro，Darwin 25.5.0，arm64；原生 LLVM/Clang 22.1.7，WASI SDK 34 / Clang 23.1.0。
- 源码为 `1a1bb90f`；初始编译器使用既有 `yy编译器`。新生成二级编译器再参与后续编译。
- 经当前包构建入口 `yy豫构`，4 个并发工作进程，关闭豫言缓存读取 `--do-not-load-cache`；使用默认编译优化配置，未额外开启上轮小程序所用的 `--optimize --whole-program-opt`。
- 两次原生构建及交叉编译先后执行，不同时运行其他编译实验。没有固定 CPU 核心或频率。
- 测量包含豫构调用、语言编译各阶段、LLVM 和最终链接；已有运行时与原生包 C 缓存可复用，不包含从零安装或重建全部工具链。操作系统文件缓存未清除。
- 用 `/usr/bin/time -p` 记录墙钟、用户态与内核态时间。每一阶段实测一次，不宣称统计稳定的中位数。

## Wasm 阻断证据

先使用原生二级编译器执行：

```sh
./yy_自举_原生二级 豫言编译器/入口。豫 \
  --package-context .yybuild/豫构上下文/17.上下文 \
  --target=wasm --parallel -j 4 --do-not-load-cache \
  -o yy_自举_编译器.wasm
```

包上下文 `17.上下文` 由此次豫构为编译器生成，声明了编译器的直接依赖；上轮用于性能研究的 `16.上下文` 不能代替它。本次先复用了旧上下文，收到“未声明直接依赖”后已纠正；该快速失败不计为自举结果。

交叉编译耗时 **74.31 秒**，最终退出 1。实际完成了编译器及依赖的 Wasm 对象生成，最后缺少：

```text
豫言_在线处理器数量
豫言_启动异步子进程
豫言_尝试收取异步子进程
豫言_字符串按字节在前
豫言_存放包上下文
```

前四个符号定义于 `运行时支持库/原生/子进程.c`，而 Wasm Makefile 明确排除此文件。字符串比较本身不需要子进程，但因放在同一源文件中也被排除了。最后一个符号属于包原生扩展，Wasm 链接没有收集它。

随后不修改源码，实际将 `库/构建基础/包上下文.c` 编译成 Wasm 对象并追加到原来的链接命令。该 C 文件能够编译，但最终链接新增：

```text
yy_自举_包上下文.o: undefined symbol: flock
```

其余四个符号仍缺失。所安装 P1 libc 没有定义 `flock`。这是实际链接限制，而不只是从 API 文档推断的潜在问题。没有通过忽略未定义符号、空实现文件锁、假子进程或放宽链接错误来制造“成功”产物。

即使补齐这些链接符号，还必须实现运行所需的包上下文文件系统语义、子进程调度和 LLVM 工具调用。当前同步子进程 Wasm 桩会明确退出失败，不能凭链接成功就认定可自举。

## 后续测试应如何落地

先明确是否允许一个提供能力的原生宿主。若允许，给 Wasm 编译器提供受控的构建任务接口，由宿主执行相同 LLVM 工具，并以多个 Wasm 工作实例对应当前 4 并发调度。该实验能比较“编译器运行于 Wasm”对自举的影响，但仍依赖原生 LLVM。

若要求 LLVM 工具链和调度本身也全部是标准 Wasm，则需另做工具链移植或直接 Wasm 生成与链接，自举性能不能在这些功能存在前测得。

补齐后应以相同源码、优化参数、并发数、堆栈预算做两组测试：先比较相同宿主工具链下的原生编译器和 AOT Wasm 编译器，再比较完整部署方案。分别记录编译器处理时间、宿主工具时间、启动/通信、峰值内存、缓存命中情况，并以第二、第三代产物固定点作为正确性门槛。

本次只新增实验记录和报告，没有修改编译器或运行时。

## 补充核对：WASI 0.3

上一节完整编译实验针对 P1，不能据此声称 P3 缺少一般异步能力。随后核对官方 0.3 发布说明、0.3.1 文件系统 WIT，并使用本机 SDK 的 `wasm32-wasip3` 做了实编探针。

| 所需能力 | WASI 0.3 情况 | 对豫言的含义 |
| --- | --- | --- |
| 异步函数、流、完成通知 | 有 `async func`、`stream<T>`、`future<T>` | 可以重做协作式调度与 I/O 桥接 |
| 网络、HTTP、文件操作 | 有相应接口，文件操作大量采用异步形式 | P1 的网络失败桩不代表 P3 标准缺失 |
| 运行一个命令组件 | command world 导出 `run: async func() -> result` | 宿主可以调用已连接的组件入口 |
| 按路径启动任意原生可执行程序 | 正式 CLI 接口没有通用 spawn／exec／wait 服务 | `run` 导出不是 guest 端的 `posix_spawn` 导入；调用 clang 仍须构建宿主或工具链组件 |
| POSIX `flock` 文件锁 | 已核对的 0.3.1 filesystem WIT 未提供锁操作 | 不能只改目标名就复用现有锁代码 |

依据：[WASI 0.3 概览](https://wasi.dev/releases/wasi-p3)、[正式接口范围](https://wasi.dev/releases)、[command WIT](https://raw.githubusercontent.com/WebAssembly/WASI/main/proposals/cli/wit/command.wit)、[run WIT](https://raw.githubusercontent.com/WebAssembly/WASI/main/proposals/cli/wit/run.wit)、[0.3.1 文件系统 WIT](https://raw.githubusercontent.com/WebAssembly/WASI/v0.3.1/proposals/filesystem/wit/types.wit)。文件系统的 `no-lock` 是错误枚举，注释明确说明某些错误仅为与 POSIX 对齐而保留，并不能据此认定存在文件锁 API。

本机实测：

1. 包上下文 C 文件以 `--target=wasm32-wasip3` 编译成功。
2. 现有子进程 C 文件改为同一 P3 目标，仍因 `spawn.h` 不存在而编译失败，同时报告信号需要额外仿真配置。
3. 将可移植运行时核心及现有宿主适配全部重新编译为 P3，在独立的 `yy_自举三运行时` 中归档，再与 P3 包上下文对象链接；最终仅报 `undefined symbol: flock`。此结果没有混入 P1 运行时。早先混入 P1 对象的诊断另外保存，不用作 P3 功能判定。
4. P3 libc 符号检查找到 `sysconf`，未找到 `flock`、`fork`、`posix_spawn`、`execve`、`waitpid` 的定义。这里只验证链接符号，没有实测 `sysconf` 是否返回真实可用 CPU 数。

日志位于《自举记录/第三版子进程编译日志.txt》《自举记录/第三版运行时编译日志.txt》《自举记录/第三版同目标文件锁链接日志.txt》。没有重跑完整 P3 编译器自举，因为这些前置接口仍未接通；不能给出新的 P3 自举时间。

设计判断因此应更积极也更具体：P3 能承载编译任务的异步组件协议，现有 OS 子进程 API 可以在迁移时被组件任务接口替换，不必永久保留同一套 POSIX 形状。多核 CPU 并行仍需明确实例与宿主线程调度，异步任务不自动等于多核并行。缓存可改为宿主管理的单写者或隔离目录，避免 guest 依赖共享文件锁；这需要设计并验证，不能简单把 flock 变为空操作。

另有 WASIX 的 `proc_spawn` 扩展，但它不是 WASI 0.3 标准接口；若采用，应单独评估运行宿主和可移植范围。[WASIX 官方接口](https://wasix.org/docs/api-reference/wasix/proc_spawn)。

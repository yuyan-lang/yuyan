# 豫言纯网页汇编后端与组件互操作评估

后续已加入[可选编译宿主](../../工具/网页汇编宿主/说明.汉语.md)，为可信 P1 程序提供原生进程、进程事件等待、真实路径与包上下文真锁。这是自定义宿主扩展；WIT 双向绑定和完整 Wasm 自举仍未完成。

调研日期：2026-09-07（美东）。源码基线：`1a1bb90f`。对应文言本见《迁移评估.文言.md》。本次只增加实验和报告，没有修改编译器或运行时。

## 判断

豫言可以把应用的主要执行后端迁到 WebAssembly，并用 Component Model 建立跨语言接口。现有 LLVM 后端已经能输出 WASI Preview 1 模块，本次进一步把实际豫言程序链接成了可校验、可执行的命令组件。但现在还不能在保持全部系统功能与性能的前提下删除原生后端，也不能把命令组件的成功运行当成任意跨语言函数互调已实现。

需要区分三个目标：

1. **应用只发布 Wasm 组件：可行，已有端到端实验基础。** C 编写的核心运行时可以一并编译进 Wasm，用户不必另外安装豫言的原生动态库；宿主仍需 Wasm 引擎及相应接口实现。
2. **编译器本身也运行于标准 WASI：还需要工具链重构。** 当前编译器启动 `llvm-as`、`opt`、`clang`、`make` 等原生工具，并行调度使用子进程。标准组件接口不会自动提供这些进程。可以让编译器前端成为组件，由宿主执行 LLVM 工具链；若要求整个编译环境也不依赖原生程序，则需移植工具链，或实现直接 Wasm 代码生成与链接。
3. **与任意现有软件无缝互调：需要双方接口支持。** 原生应用可嵌入支持组件的宿主，或提供 WIT 导入实现；已有 C ABI、Python 扩展、操作系统框架不会仅因豫言生成 Wasm 就自动可用。[组件宿主 API](https://docs.wasmtime.dev/api/wasmtime/component/index.html)、[语言支持](https://component-model.bytecodealliance.org/language-support.html)。

## 实际源码边界

| 部分 | 当前情况 | 迁移工作 |
| --- | --- | --- |
| LLVM、十六字节值、显式栈、复制式 GC | Wasm 已可运行；续延转移依赖 `musttail` | 可继续复用，先优化 Wasm 代码生成与内存行为 |
| 外部函数调用 | 内部采用豫言 `i128` 值约定 | 增加 WIT 与 Canonical ABI 绑定，不能直接公开内部 ABI |
| 包构建 | 豫构强制添加原生链接清单，WASI 路径拒绝它 | 按目标建立原生库与 Wasm 库的依赖和链接清单 |
| 网络、I/O 等待 | 当前 Wasm 宿主适配是明确失败桩 | 接入 WASI sockets、HTTP、异步接口；P1 适配器不会补出网络实现 |
| 子进程、终端原始模式、拼音转换 | 现有 POSIX／平台实现不能直接复用 | 自定义宿主能力、可移植实现或明确限制；标准 WASI 不等于 POSIX |
| 大内存 | 本后端固定 256 MiB 线性内存上限，默认单堆上限 64 MiB | 参数化内存预算并验证 GC 峰值；本限制不是 Wasm 的通用内存上限 |

证据位置：`库/编译器核心/编译步骤/代码生成/低级虚拟机/网页汇编。豫`、`直接代码生成。豫`、`原生链接。豫`、`工具/豫构/入口。豫`、`运行时支持库/网页汇编/宿主适配.c`、`运行时支持库/原生/运行时栈.c`。

## 组件接口设计

WIT 是接口契约，Canonical ABI 负责跨边界的数据传递，WASI 是一组系统能力接口；三者不是同一个层次。按当前官方路线图，WASI 0.3 已发布并引入原生异步，不能继续把它当作只有未来计划的功能。本机使用的 Wasmtime 48.0.1 也列出了组件异步选项，但本次实际组件实验采用 P1→P2 command 适配，没有测试 P3 异步。[WASI 路线图](https://wasi.dev/roadmap)、[Canonical ABI](https://component-model.bytecodealliance.org/advanced/canonical-abi.html)。

建议公开的第一组类型为整数、小数、字符串、字节串、记录、有限变体、可选值和结果。泛型须在边界具体化；闭包、可变引用、对象图和续延不能作为内部指针直接跨组件传递，可用资源句柄与方法表达。豫言异常在公共入口转换为明确结果；不可让任意续延跳出外部调用的生命周期。移动 GC 与资源句柄表需要共同维护根，销毁和借用也需有明确约束。

WIT 名称限制为 ASCII kebab-case，中文豫言名称应保留在语言侧，并配置稳定的外部名称映射。资源的 own/borrow 语义也需要绑定层实现，而不是仅做类型改名。[WIT 参考](https://component-model.bytecodealliance.org/design/wit.html)。

字符串与列表跨独立组件内存通常涉及分配、复制及可能的编码转换；资源句柄可以避免复制整个对象，却不会使读取对象内容自动零拷贝。因此应把解析、排序、批量计算等完整操作作为组件方法，避免逐元素跨边界调用。内部模块仍可静态链接进同一组件，保留优化机会。[Canonical ABI 字符串与列表规则](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md)。

## 推荐次序

1. 保留原生后端作性能参照，先加入正式组件输出及按目标构建依赖。命令组件与可复用库组件分开设计。
2. 实现最小双向绑定，验收“另一语言调用豫言”和“豫言调用另一语言”，覆盖中文字符串、列表、错误与资源释放。
3. 设计与豫言协作式调度器匹配的 WASI 0.3 异步桥接，验证暂停、恢复、取消、资源生命周期及重入。组件的异步能力不能直接等同于现有 POSIX 等待接口。
4. 补充跨组件小调用与批量调用、字符串复制、真实 HTTP、编译器工作负载、内存峰值测试，再决定是否将 Wasm 设为默认。
5. 只有在系统能力、真实应用性能和自举流程都达标后，才讨论删除原生后端。没有必要为了获得组件互操作而先重写 GC 或摆脱 LLVM。

线程和组件 memory64 等特性应以所固定的工具链逐项验证，不能从核心 Wasm 支持某特性推导组件和 C 库也完整支持。[Wasmtime 特性状态](https://docs.wasmtime.dev/stability-wasm-proposals.html)、[WASI SDK 限制](https://github.com/WebAssembly/wasi-sdk#notable-limitations)。

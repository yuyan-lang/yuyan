# WasmGC 自举性能调查

验收目标：本机完整冷编译缓存自举不超过 30 秒，且不以生成程序明显变慢换取数字。主攻 Node/V8 WasmGC；这不是浏览器、其他引擎或所有程序已达到 C 性能的证明。

最终版本连续三代分别 **21.14、21.45、21.82 秒**，中位数 **21.45 秒**，均低于 30 秒；种子与三代输出逐字节一致。相对初始串行 118.54 秒，中位数墙钟降低 81.9%（约 5.53 倍）；其中包含并行化与引擎复用的收益，不能将全部加速解释为生成代码的单线程提升。

| 最终冷自举 | 墙钟秒 | 用户 CPU 秒 | 系统 CPU 秒 |
| --- | ---: | ---: | ---: |
| 种子 → 第一代 | 21.14 | 116.26 | 8.14 |
| 第一代 → 第二代 | 21.45 | 118.90 | 8.09 |
| 第二代 → 第三代 | 21.82 | 119.64 | 8.36 |

记录日期：2026-09-19。源码基于 `03e4d5f4c5bf721bac563e705c0849d0dc44c929` 加本次工作区修改。最终 Wasm 共 3,062,613 字节，四份一致的 SHA-256：`51e55088ce1c976bbfc1cc26d66d8010a2cc9eb6d9152796fe0af673d9bed0f0`。

同一最终编译器的完整串行冷自举为 **83.33 秒**（用户 CPU 93.07 秒、系统 CPU 4.98 秒），比初始串行 118.54 秒减少 **29.7%**。这提供了编译器工作负载本身没有因追求并行自举数字而变慢的证据；它包含 Wasm 代码与宿主边界优化，不能外推为所有生成程序均加速 29.7%。

同一最终编译器改用 `YY_NODE_COMPILER_WORKERS=process`，并行 18 的冷自举为 **39.97 秒**（用户 CPU 426.46 秒、系统 CPU 38.63 秒），输出与线程模式逐字节一致。线程模式中位数较此减少 **46.3%**，同时显著减少重复 JIT 的 CPU 消耗。

## 测量边界

本机 Apple M5 Pro、18 核、48 GB，Node 26.3.0，V8 14.6.202.34-node.20。编译器和编译任务均执行 WasmGC；最后 WAT 到 Wasm 的组装由既有原生 `yy网页汇编宿主` 完成。豫构包上下文事先准备。测量包括新 Node 进程启动、JIT、实例化、依赖分析、类型检查、代码生成及最终组装，不包括安装工具和生成初始编译器。

冷缓存指没有可复用的豫言编译产物；不清空操作系统文件页缓存。每代使用不同输入编译器路径及 `--do-not-load-cache -c`，独立启动 Node，不采用 `YY_NODE_REPEAT` 或跨轮机器码缓存。并行度固定 18；保持正常完整输出，不以省略编译阶段降低耗时。

## 调查记录

下列为探索阶段单次结果，不应把相邻两次的小差异当成统计结论。

| 同次构建共享编译器模块机器码 | 20.95 | 保留，最终版本另行复测 |

CPU 采样中的一个类型检查任务，GC 占样本约 34%，列表态射约 15%。原语计数记录到约 534 万次整数转字符串。优化据此集中于分配及 Wasm/JS 边界，而非降低优化等级。

最大收益来自消除数百个内部任务重复启动引擎和编译同一 Wasm 模块。默认线程模式仅匹配同一编译器的内部 `--mode=worker` 命令：每个任务仍有新的 Worker、Wasm 实例、GC 堆和宿主状态，同次构建共享 `WebAssembly.Module`。任务图及编译算法仍由豫言执行。线程共享宿主 PID，隔离边界不等同于独立操作系统进程。`YY_NODE_COMPILER_WORKERS=process` 可回到独立进程模式；普通子进程不受替换。

## 复现

先按仓库构建流程准备 `yy网页汇编宿主`、原生编译器与编译器包上下文。上下文编号因工作区而异，此次使用 `11.上下文`。

```sh
./yy网页汇编宿主 --组装 工具/节点网页汇编宿主/值桥接.wat yy节点值桥接.wasm
./yy2_bs 豫言编译器/入口。豫 --parallel --target=wasmgc --do-not-load-cache -c -o yy网页最终种子.wasm
/usr/bin/time -p node 工具/节点网页汇编宿主/宿主.cjs yy网页最终种子.wasm 豫言编译器/入口。豫 --package-context .yybuild/豫构上下文/11.上下文 --target=wasmgc --parallel -j 18 --do-not-load-cache -c -o yy网页终一.wasm
```

下一代以上一代输出作为输入，另取输出路径，最后使用 `cmp` 比较各代字节。串行和并行的历史新名字编号不同，不将跨模式字节差异直接解释为本次回归。

## ThinLTO

ThinLTO 是 LLVM 的轻量链接时优化：先汇总各模块的信息，再并行执行跨模块优化及机器码生成。它针对当前原生 LLVM 路径，不是本轮 Node/V8 WasmGC 的关键优化。保留 `--native-lto=thin` 实验选项，默认仍为完整 LTO。原生实验中 ThinLTO 虽减少链接时间，却使同一前端工作负载从 21.69 秒增至 32.79 秒，故未把它作为默认提速方案。详见 `../原生链接/首轮结果.汉语.md`。

## 验证与边界

最终源码依次完成稳定编译器 → `yy2_bs` → `yy3_bs` → `yy4_bs` 的规定原生自举流程，`yy3_bs` 与 `yy4_bs` 逐字节一致；`./yy` 类型检查及最终 `yy3_bs` 并行类型检查均通过。Wasm 连续三代为完整 856 个任务，均成功退出，四份编译器字节一致；最终 `yy网页终三.wasm` 自身执行编译器并行类型检查亦通过。

新增回归覆盖 i64 极值、短列表求值顺序与异常、变量绑定冲突与替换、七类字符串转义和深层 JSON、异步等待边界；沿用长列表及异步子进程测试。失败任务能通过线程桥接返回非零状态并结束调度；某些语法错误仍显示现有 Wasm 异常路径的 `illegal cast`，不将其描述为诊断质量已解决。

本轮结果只证明指定机器及 Node/V8 上的编译器工作负载。浏览器宿主、其他 Wasm 引擎、通用应用基准和完整商用稳定性尚需独立验证。

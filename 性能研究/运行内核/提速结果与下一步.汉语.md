# OCaml 性能目标：本轮结果

2026-09-19，当前工作区。结论：冷缓存 Wasm 自举已稳定低于 30 秒；生成程序在递归、排序、树处理上已超过本机 OCaml 原生对照，但数组密集计算尚未全面达到 OCaml。不能据此宣布豫言整体已达到 OCaml 或 C，也不能宣布商用验收完成。

中位数 **18.30 秒**。种子与连续三代逐字节一致。这里“冷”指禁用豫言编译缓存并重新启动引擎，不指清空操作系统文件页缓存。同一次构建中，内部任务共享编译后的 Wasm 模块，仍各有独立实例与堆，这是此前已实现的默认宿主行为。

## 已实现的优化

1. 无捕获且只完整自调用的递归函数提升为静态多参数入口。保留外部柯里化接口；部分应用、函数逃逸和捕获边界有独立回归。
2. 原语包装在局部化简后发布给下游模块；函数头内联产生 let 时，继续消除剩余应用，同时保持求值顺序并避免变量捕获。整数“小于”直接使用交换参数的大于原语。
3. 纯整数递归函数生成 i64 内部入口，外部仍使用引用 ABI。整数参数必须在入口无条件受到整数原语约束；不凭未执行分支强行拆箱。
4. 混合函数保留原始 i64 局部与整数分支结果；分支推断的整数或数组参数经入口守卫，不符合时进入通用后备体。未知类型的递归实参重新检查。数组类型守卫的独立收益尚未得到明确证实，本轮不单独归功于它。
5. 静态尾递归变成 Wasm 循环，先计算全部新参数，再逆序赋值，保留交叉依赖和交换参数的含义。异常处理范围内仍禁止相关尾调用变换。
6. 数组索引直接消费 i64，保留负数、超过 32 位及数组自身越界检查，没有通过取消检查获取成绩。
7. 构造器的不可变字面载荷可以共享。仅接受整数、爻、单元；载荷元组只使用一次才省略分配。普通元组、含可变引用或存在载荷别名的对象不合并。

## 正确性验证

按 AGENTS.md 顺序完成稳定编译器 → `yy2_bs` → `yy3_bs` → `yy4_bs`；三代与四代字节一致。`./yy` 类型检查、最终原生编译器并行类型检查、最终 Wasm 编译器自身并行类型检查均通过。

十五项 Wasm 回归运行成功且输出与 `.成功` 文件一致：基础、大数组、长打表、深栈、递归回收、整数文本、短列态射、替换共享、癸象转义、进程等待、整数专门化、数组索引边界、构造常量、满参递归、去柯里化边界。新增数组入口守卫回退例亦通过。整数专门化、构造常量、满参递归、去柯里化边界四项另在原生后端通过。

覆盖了 i64 极值与回绕、未执行分支的泛型/非数组值、异常及副作用顺序、十万层尾递归参数交换、非法索引子进程失败和可变对象隔离。最终编译器生成的六份基准与试验编译器生成的六份基准字节一致。`git diff --check` 通过。

## 下一步与待决策事项

**先解决数组表示。** 当前泛型数组存放引用；筛选程序的 OCaml 对照使用字节数组。建议新增专用可变字节数组和 i64 整数数组，在 WasmGC 中分别采用紧凑 i8 与 i64 数组，保持边界检查及整数语义。现有泛型 API 继续可用，性能敏感程序显式选择专用类型。这是公开标准库接口选择，已向用户询问，尚未据此实施。

若用户要求现有代码自动获得相同效果，则应走类型驱动的数组表示专门化：在类型擦除前保留元素信息，为读写、别名及跨函数调用建立一致表示。工作量和正确性风险高于新增显式类型，不能只在分配点偷偷更换底层数组。

之后按顺序验证：

- 两种数组表示的同算法对照，保留当前通用数组结果，不用新 API 的分数覆盖旧 API 的回归。
- 在可证明安全的循环中消除冗余范围检查；不能取消外部输入的检查或默默把 i64 缩成 i32。
- 扩展完整应用识别到跨函数调用、叶函数内联，针对排序与 C 的剩余差距继续定位。
- 加入字符串、映射表、文本解析等真实库负载，并测其他 Wasm 引擎与浏览器。当前只有 Node/V8 与本机 OCaml 原生对照。

每轮继续以完整冷编译缓存自举 ≤30 秒及生成程序不出现明确回退为约束。是否将 Node 冷启动也纳入“达到 OCaml”的程序性能门槛，仍应单独确认；这里没有用进程内成绩掩盖冷启动差距。

# 原生自举考绩

二〇二六年九月十九日，考于 macOS arm64，clang 22.1.7，十八工并作。初本为 `03e4d5f4`。以全程自举之实历为准，分段之数惟供察病，不得代全程，亦不得据以称齐于 C、OCaml、Haskell。

修旧运行库后，依定法三举。末举新用编译缓存，实历六十三点四〇秒；第三、第四本字节皆同，其 SHA-256 为 `75c9bd734c42f702883155c64e66e3025ce814c4720560a4b14b8b2f3a689eb5`，类型检查亦过。此为加对照选项前之本。运行库与系统页缓存仍用旧备，不谓磁盘全冷。

同一 C 卷，一千九百一十万三千〇六十六字节，次第试之，各一测：完整 LTO 配 `-O3`，实历四十二点三六秒；配 `-O2`，三十九点九四秒；ThinLTO 配 `-O3`，十三点二五秒。首测附 clang 计时报，其数非同次全程之精确分摊。

再使所成编译器重治同源，禁读编译缓存而止于前端：完整 LTO 本用二十一点六九秒，ThinLTO 本用三十二点七九秒，后者慢约五成一。故造器虽速，器之行未必速，不可遽改常制。此数惟证此编译负载，不概诸程序。

旧运行库未随源码更新，旧入口兼有参数处理，致 `main` 与全局参数重名。重建而解。失败之二十六点四七秒不入成绩，旧存第三本亦不冒充新成。全运行库改用 ThinLTO，链接器复报 `Unsupported stack probing method`；未撤栈探测以求苟通，正常运行库未换。新选项初遭旧缓存，遂依例触种子以别缓存，重举验之。

今增 `--native-lto=full`、`--native-lto=thin` 以供对照，常制仍全，优化仍 `-O3`。前端诸制与语言义不改。ThinLTO 之法见 [LLVM 原典](https://clang.llvm.org/docs/ThinLTO.html)。今全卷仍合为一 C 编译单元，尚未分模块并治原生后端。

新选项既入，手审并验旧入口之类型检查，皆过。别旧缓存，依定法复三举，末举实历六十四点九七秒；第三、第四本皆 `f590ffc7dc659b44583ad08d0b3ef8303d98be8d141a7c3ede1090ee2ac915c4`，字节相同，复验并行类型检查亦过。非法选项见拒。常制未变，不称默认自举已速。

以同源全链接本造薄链接甲，用三十七点一四秒，此惟备种，非持续自举之绩。使甲自造乙，禁读旧编译缓存，用四十八点七九秒，较全链接同源样本少约二成五。甲乙字节皆同，散列为 `591bb7b635da9229f6499b4692f94f9aaea21664616aa30a66cb0f196d67fd50`；所生 C 亦与全链接途同。然器之行有退，故常制未改。

复使乙造丙，用四十九点〇四秒，丙与甲乙字节皆同，所生 C 同，类型检查亦过。两次自举均数四十八点九一五秒，较同源全链接单测少约二成四七；样本尚寡，不概久测之绩。静察机器码，薄链接本尚多整数加与元组读取之调用，全链接本则无相应直接调用；此惟静态调用点，非行时次数，宜继察运行库内联之异。

后当先察链接与运行库，解工具链之病，试分大卷；继按剖析所见，治阶段读写、调度、装箱与闭包调用。值制、回收之更易，须别验。全程当限几秒，造器之速可否损器之行，待用户定之；未可称商用已足，亦未可称与 C 齐。详数与复现边界见同名汉语篇。

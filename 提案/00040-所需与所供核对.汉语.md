## 一、拟定事项

| 议 | 内容 |
| --- | --- |
| 议一 | 各平台共用一套宿主接口：原语号与带型导入名不分平台。 |
| 议二 | **所需**：程序的宿主导入表就是所需清单，编译期已定，不另造格式；00038 的清单另附一份摘要，供装入之前先查。 |
| 议三 | **所供**：各平台的未具表在编译期写进执行器（供籍），只登“该有而没写”的缺口；按设计只在部分平台才有的原语不登。 |
| 议四 | **核对**：整程序与单元都在装载时核对，导入了本平台未具的宿主函数就拒绝装入，并一次列出全部缺项。 |
| 议五 | **防走样**：执行器里每个返回暂不可用（失败果四四、五八）的定义都要在兜底登记里登明品与处数；格式检查逐个核对，新添的兜底一出现就报。 |

## 二、动机

### 2.1 现在缺口要跑到才暴露

- 执行器只有一份树码，林檎、林纳、裸机共用。`是苹`、`是林` 读「目标」内建导入 `平台号`（`平台接口/目标。底层接口。豫`），冶铸（原生后端）降级时才在每个目标上填成常数：裸机一、林纳二、林檎三。类型检查在降级之前，只看到一个整数。
- 按平台分派是运行时的「若」：执行器里有一百二十八处 `若「是苹」于「元」则 … 否则 …`，二十七个定义里共三十九处返回 `失败果 44` 或 `失败果 58`（暂不可用）。
- 装载时其实已经逐个解析宿主导入：模块实例化（`模块` 的「装导入们」）与单元装载（原语 189）都按「带型名」表，把（模块名，字段名）解析成原语号。但这张表各平台相同，只回答“认不认得这个名字”，回答不了“本平台实现了没有”。
- 网页各适配有 `宿主提供.json`，可原生的适配（如“图形显示原生”）一份同时代表林檎与林纳，也到不了原语这一层。

### 2.2 00039 第三步撞到的实例

第三步把下面这些原语在林纳或原生上补齐了。补齐之前，它们都落进兜底：

- **取字样（原语 108，豫寓字模之「取字样」）**：原先只写了林檎的路径。`字体按旗试开`、`字体定读` 在非裸机时直接调 `苹开`、`苹定读`，林纳没有分支，落进兜底返回 44，无头桌面一个字也不画。
- **观屏、拟键、拟指、拟钮（205–208）**：林檎与林纳原生一律回 58；第三步改成经屏块办理。
- **息、更始（241、242）**：原生一律回 58；第三步改成问行在服务 241、242。
- **子程序显示的父程序一侧（182–185）**：分派只认林檎，林纳落进兜底；第三步让林纳也分派。
- **外壳请求与来信（235–238）**：只在裸机分派，原生落进兜底；第三步改为裸机或分了子表的原生进程。

反例，所需与所供的核对挡不住这一类：

- **原语 7 不去宿主选项**：第三步让「原生显示选项」在林纳上也解析宿主选项，读方原语 7 却仍只在林檎上跳过它们，桌面程序在林纳上把 `--显示面代办` 当成窗口种类、全开成了终端。两个平台都实现了原语 7，错在两处条件不一致，要靠测试。

### 2.3 导入多于所需

整程序的导入表比它真正要用的多。豫构与壳会话把各平台的命令都编了进去，导入了起居注、网卡、设备、扩盘这类按设计只在裸机才有的宿主函数，运行时再看结果办。若这类函数登成“林檎未具”，豫构在林檎上就起不来。所以未具表只登“该有而没写”的缺口；按设计只在部分平台才有的原语，由调用方按运行时的结果办，在兜底登记里归为“可缺”。

### 2.4 手工登记会走样

未具表是手写的。108 那次的缺口出在一个本来就有兜底的定义里：字体找不到时，「显原取字体」本就返回 44。加了只有林檎的分支，没人会想到去登记，只按定义名登记也发现不了。所以兜底登记写明每个定义的兜底处数，格式检查逐个定义核对，处数一变就报。新添的兜底由此必须过一道手：判明它属于环境、可缺还是未具；属于未具的，原语号登进未具表。

## 三、设计

### 3.1 供籍：平台所供

- 执行器新模块 `供籍。底层。豫`（底层文件只能导入底层文件，不能导入数据文件，所以写成静态串）：
  - 每个平台一张未具表（`裸机未具`、`林纳未具`、`林檎未具`、`轩窗未具`），内容是逗号分隔的原语号。第三步之后，“该有而没写”的缺口一个也没有，四张表都是空的。
  - 一份兜底登记「兜底登记」，每项写成“定义名=品处数”。品有三种：环，取决于运行环境（有没有显示、有没有加入行在、字体文件在不在、资源用尽）；缺，可缺，按设计只在部分平台有；未，未具。现有二十七项，都是环或缺。
- 豫行启动器里的客体与裸机共用裸机那张表。

### 3.2 所需

- 程序的宿主导入（模块名，字段名）编译期就写进了代码，这就是所需清单，不另造格式。
- 00038 的清单另附“所需原语号”的摘要，供安装软件与包仓库在装入之前先判断（第二步）。

### 3.3 核对点

- **整程序（豫行文件与本机程序）**：「装导入们」配导入时查本平台的未具表。未具的逐项往标准错误报“本平台（林纳）未具：模块之字段”；配完全部导入后，以退出码 126 退出，不运行程序。
- **单元**：原语 189（单元带型码）遇到未具的原语号时，给出码的相反数。冶铸的单元装入据此一次列出全部缺项，报“单元装入：本平台未具 模块之字段、…”，不予装入。
- **兜底登记检查**：格式检查 `--兜底` 扫执行器的源文件，逐个顶格定义数兜底处数，与兜底登记对照。没登记的、处数不符的、登记了而源码里已没有的、品不认得的，逐条列出并发一条警告。持续集成的格式检查作业跑这一步，只警告、不挡合入。
- 00038 第二步做“节”时，同一处一并查“所授之节”：所需必须同时属于所授与所供。

### 3.4 名字

| 用处 | 名字 | 说明 |
| --- | --- | --- |
| 平台所供的登记 | 供籍 | “籍”取名籍之义，与行在的“在籍”同族；合成词，古书无成例 |
| 未具表 | 林纳未具 等 | 平台名加“未具” |
| 本平台未具 | 本台未具 | 合成词，古书无成例 |
| 兜底登记的一项 | 兜底项 | 字段为 名、品、处数 |

## 四、仍在运行时的

- **资源在不在**：系统里没装思源字体、没有显示器、没有加入行在。这些兜底登记为“环”。
- **操作系统语义的差异**：林檎建管道时两端带 FD_CLOEXEC，posix_spawn 起的子进程拿不到这两端；林纳的 O_NOFOLLOW 两种架构取值不同（x86-64 是 0o400000，臂六十四是 0o100000），林纳打开字体时暂不带这个旗（00039 第三步实测）。
- **同一功能内部的逻辑不一致**：见 2.2 的反例。
- **资源策略**：原语里分配的大对象禁收、只增堆，回收迟迟不触发（00039 第三步实测）。

## 五、兼容与迁移

- 旧豫行文件不用改：所需就是它的导入表。
- 自举不受影响：未具表是空的；原语 189 只在未具时给负数，持续集成自举一级用的旧执行器不给负数，新的冶铸照样装入。
- 诺驿、浏览器、云工照旧用各适配的 `宿主提供.json`；供籍只管执行器这一侧。

## 六、未决问题

1. 供籍的粒度：按原语号，还是按（模块名，字段名）。一个原语号下有多种子操作时，要不要分得更细。
2. 随机器而变的能力（有没有显示器、图形处理器）都归“环”，要不要再细分。
3. 本机程序要不要在豫构链接时就报（目标平台已定），而不只在启动时报。

## 七、实施步骤

1. **供籍、装载时核对与兜底登记检查**（已做，见实施记录）：验收是在林檎上把取字样（108）临时登成未具，编出的图形桌面启动时报出缺项、以 126 退出；`--兜底` 报“与登记相符”。
2. **链接时提示与开关**：豫构链接本机程序时按目标平台列出未具的导入；加环境变量开关放行；原语分派按未具表统一返回暂不可用。
3. **并入节**：随 00038 第二步，把“所授之节”并进同一个核对点；清单附所需摘要。

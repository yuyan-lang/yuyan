## 一、拟定事项

| 议 | 内容 |
| --- | --- |
| 议一 | 各平台共用一套宿主接口：原语号与带型导入名不分平台。 |
| 议二 | **所需**：程序的宿主导入表就是所需清单，编译期已定，不另造格式；00038 的清单另附一份摘要，供装入之前先查。 |
| 议三 | **所供**：每个平台实现了哪些原语，在编译期登记成一份数据文件（供籍），执行器与豫构共用。 |
| 议四 | **核对**：本机程序在链接时核对，豫行文件与单元在装载时核对（00038 的同一个装入器，连同“所授之节”）。缺了就拒绝，一次列出全部缺项。 |
| 议五 | 运行时的“暂不可用”只留给两种情况：供籍里登记为未具的项，与真正的资源缺失。实现函数里不再写按平台的兜底。 |

## 二、动机

### 2.1 现在缺口要跑到才暴露

- 执行器只有一份树码，林檎、林纳、裸机共用。`是苹`、`是林` 读「目标」内建导入 `平台号`（`平台接口/目标。底层接口。豫`），冶铸（原生后端）降级时才在每个目标上填成常数：裸机一、林纳二、林檎三。类型检查在降级之前，只看到一个整数。
- 按平台分派是运行时的「若」：执行器里有一百二十八处 `若「是苹」于「元」则 … 否则 …`，三十八处返回 `失败果 44` 或 `失败果 58`（暂不可用）。“否则”就是其余平台的兜底。
- 装载时其实已经逐个解析宿主导入：模块实例化（`模块`）与单元装载（原语 189）都按「带型名」表，把（模块名，字段名）解析成原语号。但这张表各平台相同，只回答“认不认得这个名字”，回答不了“本平台实现了没有”；表里查不到的名字记成零类，装载照样往下走。
- 网页各适配有 `宿主提供.json`，可原生的适配（如“图形显示原生”）一份同时代表林檎与林纳，也到不了原语这一层。

### 2.2 00039 第三步撞到的实例

- **林纳上取字样**：原语 108（豫寓字模之「取字样」）只写了林檎的路径（`苹开`、`苹寻`、`苹定读` 与 /System/Library/Fonts 下的文件），林纳落进兜底返回 44，无头桌面一个字也不画。按本提案，桌面程序在林纳上链接或装载时就会报“本平台未具：豫寓字模之取字样”。
- **反例：原语 7 不去宿主选项**：第三步让「原生显示选项」在林纳上也解析宿主选项，读方原语 7 却仍只在林檎上跳过它们，桌面程序在林纳上把 `--显示面代办` 当成窗口种类、全开成了终端。两个平台都实现了原语 7，错在两处条件不一致，所需与所供的核对挡不住这一类，要靠测试。

## 三、设计

### 3.1 供籍：平台所供

- 一份数据文件 `豫言操作系统/裸机/客体二号/供籍。数据。豫`（数据子语言，提案 00028）：每个原语号一条记录，写明在哪些平台上已具（裸机、林纳、林檎、轩窗、豫行启动器）。没有记录的原语视为各平台都具。
- 执行器在编译期导入它，生成按平台的位图；豫构链接本机程序时也读它。
- 原语分派先查位图：本平台未具，就返回统一的“未具”错误码，不进实现函数。实现函数里不再写 `否则 失败果 44/58` 这类按平台的兜底。供籍是唯一来源，运行时的行为与装载时的核对不会两样。
- 行在、豫行启动器经服务门代办的服务（00021、00039）也登进同一张表。

### 3.2 所需

- 程序的宿主导入（模块名，字段名）编译期就写进了代码，这就是所需清单，不另造格式。
- 00038 的清单另附“所需原语号”的摘要。安装软件与包仓库据此在下载、装入之前，就能判断程序能不能在某个平台上运行。

### 3.3 核对点

- **链接时（本机程序）**：豫构经冶铸降级时目标平台已定，把程序的宿主导入经带型名解析成原语号，再对照供籍。有缺就链接失败，列出全部缺项。
- **装载时（豫行文件与单元）**：模块实例化与单元装载在解析导入时同时查本平台的位图，全部解析完再报。有缺就拒绝启动或拒绝装入，列出全部缺项，不是遇到第一个就退。带型名里查不到的名字也在这一步报错，不再记成零类往下走。
- 00038 第二步做“节”时，同一处一并查“所授之节”：所需必须同时属于所授与所供。

### 3.4 拟名（候选，交用户挑）

| 用处 | 候选 | 说明 |
| --- | --- | --- |
| 平台所供的登记表 | 供籍 | “籍”取名籍之义，与行在的“在籍”同族；合成词，古书无成例 |
| 装载时的核对 | 点验、验供 | “点验”是按籍核点实物的公文用语，出处待核；“验供”为合成词 |
| 错误：本平台未具 | 未具 | 古书无成例 |

## 四、仍在运行时的

- **资源在不在**：系统里没装思源字体、没有显示器、网卡没插。取字样在林纳上登记为已具以后，字体文件不存在时照旧返回 44。
- **操作系统语义的差异**：林檎建管道时两端带 FD_CLOEXEC，posix_spawn 起的子进程拿不到这两端（00039 第三步实测）。
- **同一功能内部的逻辑不一致**：见 2.2 的反例。
- **资源策略**：原语里分配的大对象禁收、只增堆，回收迟迟不触发（00039 第三步实测）。

## 五、兼容与迁移

- 供籍起初只登记已知的缺口，其余视为各平台都具；以后逐步把执行器里按平台的兜底挪进供籍。
- 旧豫行文件不用改：所需就是它的导入表。
- 自举不受影响：工具链用到的原语在林檎、林纳上都已具。
- 诺驿、浏览器、云工照旧用各适配的 `宿主提供.json`；供籍只管执行器这一侧。

## 六、未决问题

1. 供籍的粒度：按原语号，还是按（模块名，字段名）。一个原语号下有多种子操作时，要不要分得更细。
2. 随机器而变的能力（有没有显示器、图形处理器）算“所供”还是“资源”。
3. 交叉编译时，链接时的缺项报错还是只警告。

## 七、实施步骤

1. **供籍与链接时核对**：建供籍，先登记已知的林纳缺口；豫构链接本机程序时核对。验收：在林纳上编一个调用未具原语的程序，链接失败并列出缺项。
2. **装载时核对与统一错误码**：模块实例化与单元装载查本平台位图、汇总报错；原语分派按位图统一返回“未具”。验收：把一个只在林檎实现的原语登成林纳未具，在林纳上起用到它的豫行文件，启动前就报出缺项。
3. **并入节**：随 00038 第二步，把“所授之节”并进同一个核对点。

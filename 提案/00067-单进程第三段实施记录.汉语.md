做完提案 00067 第三版第七至十步，照第 9.9 节的验收表逐条验收。做法照用户原话：“bring existing code from yuyanos to a shared infra and redo hardware abstraction”“just bringing some existing yuyanOS code above the 底层接口 to the adapter”，由本会话亲手做，不派子代理。

## 已查清的事实

- 宿主现场存在每个任务的运行记录里：进入豫行桩把启动器的栈指针与 x28 写进记录，服务入口桩按记录切回宿主栈。所以每条宿主线程各进各的任务没有冲突。
- 府 +4 是“当前槽”，只在主循环（`豫行启动。底层。豫`「豫行主轮」）与行窖挑块处（`行窖。底层。豫` 约第 276 行）用。改为“此刻持锁、在核心里办事的任务”；“谁在跑”看槽里的“正在运行”位。
- 「行机」的运行环（「导出：机环插」「导出：机环出」）是内核「任务」那份的逐行抄本，偏移相同。
- 原子库「一气算」齐全，但等待与唤醒（定码二〇八、二〇九）在宿主上还是单线程桩（冶铸「一气降级」注释：待办“多线之时真候真唤”）。第一个里程碑不靠它：锁用比较交换加退让，空闲核睡管道。
- 「建线程」目前只有林檎臂六十四（pthread_create）；林纳入口表有 clone，没有 futex、tgkill、sigaltstack、gettid、rt_sigprocmask、madvise。新入口要先单独合入冶铸、换链后再用（#1402）。

### 里程碑一：林檎多处理器（2026-10-29 完成）

**做法改成主从式。** 起初照内核的对称多处理器做：大锁、任意处理器线程都能办服务。实测第一个子任务一结束整个启动器就崩（`助手增长` 后的边界陷阱，回溯在执行器的新生复制里）。查明两条执行器的约束：

- 线性内存的大小在每条线程自己的寄存器（ARM64 的 x15）里。一条线程增长了启动器的内存，别的线程看不见，再按旧界访问或再增长就越界、甚至把页数格写小。
- 执行器的回收只扫主线程的栈。处理器线程上办服务时触发回收，主线程栈上启动器程序（豫行启动器。豫）引的对象不会被更新。

所以启动器自己的代码（服务、调度、宿主等待、回收、内存增长）只能在主线程跑。改成主从式：主线程是唯一的“内核线程”，处理器线程只跑客体代码。每个处理器一块核区，兼作线程记录与信箱（零闲、一行、二请、三续、四归、五毕，原子读写）；主线程挑任务写进核区、置行并写唤醒管道；客体调服务时处理器置请、叫醒主线程，主线程代办后置续或归。不需要大锁。

**搬进共用核心。** 调度环的插入、摘除与后继原先在内核「任务」与宿主「行机」里各抄一份，经实约机的机环插、机环出、机环后转来；现收进「任务簿」（`环插`、`环出`、`环后` 等），内核与宿主都调这一份，实约机删去这三项。挑任务（「豫行择行」）用共用核心的「可行」，另加“不在别的处理器上跑”（槽六十，与内核多核时的判断相同）；任务在处理器上跑时被打断，共用核心记待打断，下次服务由主线程按打断退出（同内核在系统调用入口查）。

**改动的文件。** `客体二号/行机`（核控区、核区、信箱、唤醒管道、起线程）、`客体二号/豫行启动`（服务转交与代办、处理器循环、主线程总循环、计页与入役出役等从单线程主循环拆出共用）、`客体二号/入口`（线程入口按核线记号分派）、`行在核/任务簿`（调度环）、`行在核/实约机`、`内核/任务`、`内核/机约`；测试 `客体二号/测试/虚机多核。测试。豫`。

### 里程碑四（第一部分）：空等任务换出、不占池（#1208 场景，#1395，2026-10-29）

#1395 的四十任务探针挂住，查下来是四条根因叠在一起（前两条钩深「钩议虚机腾挪」查出，后几条本段查出）：

1. **地址空间不够。** 林檎的虚机任务各预留 8 TiB 动态区，与函数说明的 1 TiB 不符；四十个合 320 TiB，超过臂六十四的 128 TiB，第十七个起装不进。改 1 TiB（与林纳的首选一致），任务里的执行器回收堆照“长不到就把页上限减半再试”自己落到能映的大小（实测落在约五百七十六 GiB）。
2. **撤映写死 8 TiB。** 任务退出时「豫行收映」在林檎上按写死的 8 TiB munmap；预留改小后，一个任务退出就把后面几个任务的区域连代码一并撤掉，下一个任务一进入就跳到未映射的入口（单线程、多核都崩）。改按记录二百八十的块数算长度，同林纳那一支。
3. **固定段按大小记账。** 每个任务一登记，仓就按程序各段的大小记“固定块”（虚机多核探针是六十八块、一百三十六兆，大半是没碰过的静态区），三十个任务就把 1.8 G 的池记满，又没有一页能换出，候存与候行的任务互等。改按实际驻留记：装入后量一次，计页时每两秒重量（「豫行固住块」，mincore 逐二兆块数驻留页），写进槽一百二十四，任务簿与行窖照旧读「机固块数」。
4. **主循环没有出口。** 只剩等内存的任务、或全空而根任务未结束时，原先落进无限期等待。主循环与多处理器总循环的处境写成底层小变体「候境」（有行、唯候事、唯候存、全空），用鉴穷尽处理：唯候存报池况以一百二十退出，全空而根任务未结束以一百二十一退出；腾仓需求也把候存任务里最大的请求算进去（钩深改法）。

另修一处退步：启动器先试“自带豫行”，读到自己文件尾的 YUYANMOD 尾块（那是启动器自己的程序码块 YYCB，不是豫行）就报“不是豫行文件”，凡不带 `--豫行` 的调用都失败（当前 yybs 编出的启动器都这样）。自带模式下尾块不是豫行就当没有自带豫行。

四十任务探针本身还挂：它靠父任务边跑边读子任务标准输出上的就绪帧，而虚机等子任务句柄只等到退出，另提 [#1414](https://github.com/yuyan-lang/yuyan/issues/1414)。#1208 的场景改用新加的验法（`虚机多核。测试。豫` 第二参数“换”）：

| 项目（池 2048 兆） | 八个虚拟处理器 | 单线程 |
| --- | --- | --- |
| 三十个子任务各摸 200 兆后空等三十秒，五秒后起快任务 | 快任务 50 毫秒放行，全部 86 秒，失败 0 | 快任务 220 毫秒放行，全部 86 秒，失败 0 |

第一段回归（并行、占核、父子、单任务、宿主分流、三百次槽复用、无参用法）两种模式都过。

补：八核下这个验法起初偶发超过二百六十秒的外层时限；放宽到十分钟连跑三次都过（166、190、200 秒），整轮本来就要近两百秒（子任务空等九十秒），不是死等。顺带把总循环改为先理核、再计页保余：任务在理核里挂起后，它的块这一轮就能换出，不必等下一个事件。

### 里程碑二：林纳多处理器（2026-10-29，第一步合入、第二步等换链）

**做法。** 冶铸加林纳的「建线程」导入（不在系统调用入口表里，单独绑一段桩）：臂六十四与兼容六十四各一段 clone（标志 0x50F00：VM、FS、FILES、SIGHAND、THREAD、SYSVSEM）带新栈；子线程从核区装线性内存基址、全局基址与内存字节数，调导出「后台线程入口」（按核线记号分派到处理器循环），返回后 exit（不是 exit_group）。新导入分两步合：第一步只合冶铸与接口声明（执行器不调用，编出的树码里没有林纳「建线程」导入，旧冶铸照常编）；第二步等连续版本换上新冶铸，再让「核起线」在林纳上调它、「豫行虚核数」在林纳上取在线核数。轩窗的 CreateThread 与按线程找任务的缺页处理留待后续版本。

**林纳验收与换页（2026-10-30，pit-pc 林纳兼容六十四）。** 第二步（林纳打开多处理器与核区线号）连同陷阱、抢占、工具链进虚机各段摘到分支 行在虚机林纳合，在 pit-pc 上逐项验：

1. 陷阱从没生效过：strace 见 rt_sigaction 装的 sa_handler 是 0x3a70 这样的小值、没有 SA_RESTORER，x86-64 内核建不了信号帧，撞 int3 当场改发 SIGSEGV 整进程崩。正是 #1456（冶铸「兼陷阱桩址桩」只写了两字节）。修法 95afe2362c 早就有，只是先前编启动器用的豫构不带它；改用本分支源码编出的豫构以后，SIGTRAP 装的是绝对地址的处理桩、带回程桩。
2. 抢占信号也会崩：「豫行设信号」的林纳标志写成四个十进制大数，不复位又带回程的那个多了一位（0x7800004C，没有 SA_RESTORER），第一回抢占信号就整进程崩。改为按位拼（SA_SIGINFO、SA_ONSTACK、SA_RESTORER、SA_RESETHAND）。
3. 野写验法只认臂六十四的门：测试补「门七位兼」「兼断点帛」，把调门七的 call rel32 换成 int3 加四个 nop。验法通过：探针以 119 结束，同进程的算力任务以 0 结束。
4. 四十任务探针在林纳上卡住，先后两层原因。其一是测试程序编时没带 --执行器，用的是编译器自带的旧执行器（早于 #1414 的“已报长”修正），父任务等子任务输出永远等不到；测试程序一律带 --执行器 用当前源码编的执行器。其二是驻留计量：林纳原先每算一个任务就流式读一遍整个 /proc/self/smaps，三十来个任务时主线程整段耗在这里，处理器直办抢不到底层锁，每次底层调用要隔六秒左右（追踪的时间戳一目了然）。改读 /proc/self/pagemap，只读任务用界那段（「宿候」之「林区私页」），池一万六千兆时 30.9 秒跑完。
5. 林纳换页（#1403）：行窖的换块、住页、开窖、写满、映档原先只在林檎上办，林纳池满只能候存、互相等死。补上林纳分支：住页读 pagemap（四千字节一页，「页千字」折千字节），窖文件在 /tmp 上以 O_TMPFILE 建（无名，不留残文件），写用 pwrite64，映档用 mmap MAP_FIXED|MAP_PRIVATE；林纳的 mmap 声明里偏移只有三十二位，窖文件写到四吉字节就换一个（「林换窖」）。

### 里程碑三之一：抢占轮询（2026-10-29）

**做法照提案第九节“抢占轮询”。** 冶铸给豫行用户程序（服务门开着）在每个循环头与每个函数入口（序言与局部初值之后、函数体之前）插一段轮询：读该让格（名义地址，用户区末尾十六字节的头四字节，紧挨动态区基址格：ARM64 0x403FFFF0，AMD64 0x3FFFF0），为零就跳过；非零就经服务门调服务一百二十六「让行」。门项除返回值外不动别的寄存器，所以轮询只存返回值寄存器与返回地址（ARM64 在栈上存 x0、x30，AMD64 压 rax）；读格用降级的暂用寄存器（x16、r11），循环头的浮点值已由浮化片搬回整数寄存器。函数入口那一处让尾调用自己（续体传递式的循环跳回重入标）、经尾调桩进别的函数、长递归都能让出。快路径 ARM64 是 movz/movk、ldr、cbz，AMD64 是 mov、test、jz。编译语义号换新。

「让行」收进共用核心「任务簿」：结果置零，经硬件层「机让行」调度（裸机内核换下一个可运行任务，宿主虚机把任务交回主线程，任务照旧可运行）。内核在动态服务里接上一百二十六（裸机以时钟中断分时，不置该让格，只为同一个豫行程序在各平台一致）。服务号原想用五十三，查出五十三、五十四是裸机的按键模式与读按键，改用没人用的一百二十六。

宿主虚机的主线程照内核时钟中断的轮转：派完核还有任务等核时，逐个看虚拟处理器，在跑客体、从切入（槽一百的毫秒滴答）到此刻已满时间片（十毫秒）的，把它任务的该让格置一（「豫行示让」）；这时宿主等待也只等一个时间片（多订一个十毫秒的时钟）。任务切入时（「豫行入役」）清零该让格。写客体内存走各宿主现成的「豫行放字节」（林纳经 /proc/self/mem），运行记录四百五十六记着上次写进去的值，相同不再写。

### 里程碑三之二：陷阱只结束出事的任务（2026-10-29，第一步冶铸先合、第二步等换链）

**做法照提案第九节“陷阱”。** 每个虚拟处理器占一块六十四千字节、按六十四千字节对齐的块：核区在块首，第四千零九十六字节起到块尾是这个处理器线程的信号栈（sigaltstack）。主线程在起处理器线程之前给 SIGSEGV、SIGBUS、SIGILL、SIGFPE、SIGTRAP 装冶铸新生成的陷阱信号桩（SA_SIGINFO、SA_ONSTACK；林纳兼容六十四另给 SA_RESTORER 与信号回程桩）。信号落在虚拟处理器线程上时桩跑在信号栈上，栈指针清掉低十六位就是核区（核区第十二字节是核线记号，不是就直接返回）；桩由核区装执行器的固定寄存器，调导出「陷阱信号处理」。它看核区正在跑客体、现场里的程序计数器落在当前任务的程序段预留区里、任务做过服务调用，就把现场改成去走该任务的服务门七（程序计数器指向门项七，栈指针取上次服务调用时的客体栈指针再往下四千零九十六字节，栈溢出时也有地方落脚）：客体像自己陷阱那样调服务七，任务以一百一十九结束，别的任务照跑，走的是现成的“客体陷阱”退出路径，不另写退出代码。落在启动器自己的代码里、或在主线程上，就把信号恢复缺省再返回，再撞一次照常崩溃、留现场。处理只用底层读写与直接的系统调用：处理器线程上不许分配、不许碰回收，所以林檎的 sigaction、sigaltstack 也像林纳那样进冶铸的导入表，不经动态符号调用。

**分两步合。** 第一步只合冶铸：目标内建导入「陷阱桩址」（取陷阱信号桩、信号回程桩的绝对地址）、三种陷阱信号桩（林檎与林纳的臂六十四、林纳的兼容六十四）、林纳入口表的 sigaltstack 与林檎入口表的 sigaction、sigaltstack；执行器还不调用，旧冶铸照常编。第二步等连续版本换上新冶铸，再合执行器的核区块、装处理、设信号栈与「陷阱信号处理」。验法是 `虚机多核。测试。豫` 的“野”：野写探针（`原生样例/你好/豫行野写。底层。豫`）调别的目标的导入，豫行里本绑成服务七的软陷阱；测试先把探针里跳门七的指令改成 brk 存成新文件（「断点帛」），再同时起它与一个算力任务：改过的探针撞上宿主的真陷阱（SIGTRAP），该以一百一十九结束，算力任务照常算完。豫行用户程序的访存都对线性内存字节数查界，越界只走软陷阱，客体里不改指令撞不出宿主陷阱，所以这样注入。轩窗走向量化异常处理，留待后续版本。

### 里程碑三之三：异步抢占（2026-10-29，第一步冶铸入口已合、第二步等换链）

**00070《过所》议定抢占以异步为主**（用户议定，经「证明语言设计」会话转达），冶铸轮询（里程碑三之一）只作快路。做法照内核时钟中断：主线程见虚拟处理器上的任务置了该让格又过了一个时间片还没让行（没有轮询的循环），就给这条线程发 SIGURG（林檎 pthread_kill，林纳 tgkill，冶铸入口表第一步已合入 3fc8722ac7），每次切入只发一回。处理（与陷阱同一个信号桩，导出按信号分派）看核区在跑客体、现场的基址寄存器是任务的、程序计数器在任务程序段里却不在服务门区，就把整份宿主现场（通用寄存器、栈指针、程序计数器、状态、浮点与向量寄存器）存进任务槽区第六万五千五百三十六字节起的帧，再把现场改成去调服务一百二十六让行（栈往下让出四千零九十六字节）：任务照常经服务门交回主线程，照旧可运行，运行记录四百八十八记一。下次派出时（「豫行入役」）入口改指服务门保留区第三千九百项（门模板里是断点），动作置零、四百八十八置二；任务一进去就撞 SIGTRAP，处理认出是续行，把帧里的全现场填回现场，内核按它恢复，任务从被抢下的那条指令接着跑，再还原入口、重新装上 SIGTRAP 的处理。这样存取全现场都由内核的信号帧代劳，冶铸只多两行入口表，不用新写恢复寄存器的桩。服务门区与服务入口桩里不换（会把服务调用搅乱），那时任务很快自己出来。待办事项：林纳兼容六十四只搬 fxsave 区，AVX 上半没存。

### 里程碑三之四：阻塞改挂起（2026-10-29）

**查出的毛病。** 里程碑五起头把将作、构建客放进虚机试跑，构建客做完依赖分析就整机不动。采样看到虚机主线程（内核）整段停在宿主 `read` 上：客体经底层转送读套接字，启动器在主线程上直接调宿主的阻塞读，读不到就把整台虚机的内核停住，别的任务的服务一概办不了。底层等待（订阅）早已改成挂起任务，读、写、接受还是同步调宿主。

**做法照提案第 9.4 节“阻塞”。** 虚机里（运行记录三百四十四非零）客体照阻塞办的读、写、接受：启动器先取宿主句柄的状态旗，客体没设非阻塞的，临时把宿主句柄设成非阻塞办一次、办完复原；宿主答“暂不可用”（底码六）就把任务挂起，订阅这个句柄可读（读、接受）或可写（写），完成类别记四；句柄就绪后「豫行待毕」照客体原请求重办一次（又不就绪就再挂）。客体只觉得这次调用阻塞了一会儿，内核照常办别的任务。客体自己设了非阻塞的照旧答六。林檎上 accept 出的新连接会沿袭监听句柄临时设的非阻塞位，收到后清掉。旗只在办这一次时改动，与本进程以外共用同一打开文件的程序只在这一瞬看得到。轩窗待办（改用重叠读写与完成端口）。

### 里程碑五：工具链进虚机（2026-10-29 起）

**结构。** 行在就是虚机进程：林檎、林纳上设了 `豫言行在虚机=开`（本机部署验收前先要显式开启，验收后改缺省）、原生豫构旁边 虚机/ 下有豫行启动器与豫构豫行版时，`豫构 行在 启动` 就在后台起豫行启动器，首任务是豫构豫行版的“行在 --目录 会所 运行 --后台”；虚机里的行在写好门文件后再起一个虚机门任务。宿主上原生豫构的构建类命令照第二段的办法当瘦客户端托进虚机；虚机里的豫构用虚机里的将作，代役与编译工作进程都是豫构豫行版的任务。宿主上只剩虚机这一个进程（外加瘦客户端与 git、ssh 等外部命令）。

**宿主虚机里的程序怎样认宿主。** 虚机里问所寓得豫言（裸机、虚机都算豫言系统），而文件、套接字、宿主进程都直通宿主。启动器给每个任务的环境放“豫行宿主=林檎/林纳/轩窗”与“豫行宿主进程=虚机进程号”（原先只在轩窗上放豫行宿主），豫章「水土」新加「宿主系统」：原生答本系统，宿主虚机里答“豫行宿主”，裸机答空。凡按宿主办的事改问它：「探将作」能不能用将作、将作本机目标与同僚段的平台、行在建会所目录与本机后缀。虚机里的行在用“豫行宿主进程”作门文件的进程号：宿主上的客据此认行在在不在，启动器补问行在时认出门是自己的、不去登记。

**本器用豫行版自己。** 第二段让虚机里的豫构借原生豫构作本器（环境变量 豫言虚机编译器），器纹、默认编译器、将作派役都按原生链，编译仍在宿主上做；现在去掉这个变量，本器就是豫构豫行版，将作照豫行链派代役与编译工作进程。找执行器与源也在它旁边，虚机目录里放执行器与源的链接（装工具链时摆好）。设置里的“服务程序”在虚机里须是豫行文件才用（按文件头认），否则用本程序，免得在宿主上另起原生将作。

**空闲不空转（2026-10-29）。** 私有虚机行在空闲时整进程占一核的 16%–20%。行在与虚机门两个任务每秒共醒六十多回（客体自己的定时等待），每回主线程进宿主等待前空转两千轮扫十八个核、办完一次请求再紧转至多三百轮，处理器线程空下来先空转两万圈，都是没有谁会递请求时白转。改成：主线程只在有核正跑客体（行、续、归）时空转（「豫行核况」）；处理器只在等主线程回话（请、毕）或主线程记了“还有任务等核”（核控区「待核」，府七九七六）时空转，否则直接睡；虚机门没有客时一直等到来了新连接。空闲二十秒窗口内处理器时间由约 3.5 秒降到 0.9 秒，主线程九成六时间睡在 poll 里；余下主要是切入任务时逐块标热（「记热」）与两秒一次的计页。

**行在状态的虚机任务名。** 宿主「导出：机拷任务名」原先把任务线性内存里的绝对地址当成启动器线性内存的偏移来写，名字写到了别处，虚机任务都显示“任务”；偏移也差四字节、少了长度。改照内核格式（四字节长度加至多八十四字节名字）经行在核「内核」之「复制字节」按长地址拷，宿主路径超过八十四字节时取末尾，读的一端取末段即得文件名。

**等子任务的输出（#1414）。** 客体收子任务输出走任务间信箱：子任务把输出当消息发给父任务、父任务逐条确认（裸机「排空捕获」）；父任务在底层等待里订阅子任务籍句柄的“可读”。虚机「豫行合候」原先只在子任务结束时才算这条订阅就绪，于是子任务等确认、父任务等结束，互等挂死。改成等待者信箱里有该子任务来的信（行在核「投递」写的信箱格，来信者句柄在第八字）也算就绪（「豫行有信来自」）。

**虚机内部池以行在池上限为顶（#1408）。** 虚机行在不受别的行在管，启动器原先以整机物理内存为内部仓的容量，虚机里的任务吃满整机才换页。现在原生豫构起虚机时给首任务加参数“--池兆 N”（N 是行在的池上限折兆，「行在内存上」），启动器从首任务启动块读它（「豫行首参后数」，同「豫行首参是门」），不受管时以它或 豫言虚机内存 为内部仓的容量。瘦客户端遇门三十秒不回“受”或没应答就断，先关连接（门那头见客断会停掉可能已起的子任务）再退回本进程照旧做。

**四十任务换页探针（#1429、#1414，2026-10-30，pit-mac）。** 探针起四十个子任务各摸二百兆后挂起（池两千兆），再放行一个新任务，然后逐个唤醒校验。一路查出并修掉十二处：

1. 边跑边取子任务输出等不到（#1414）：原生「异步算事件」对子进程句柄只在结束时报可读，运行中新收进捕获缓冲的输出不报；异步项加一格“已报长”（项长一百三十六改一百四十四，八字节对齐），捕获缓冲比上回报时又多了新输出也报可读，「取使者出」取走时清零。
2. 第三十七个子任务起不来：全部任务共用一个进程的描述符表，林檎缺省软上限二百五十六；启动器起多任务时先「提句柄上限」（林檎取 OPEN_MAX、硬上限与 kern.maxfilesperproc 的小者）。
3. 主线程大半耗在 dyld：「单元系统调用」每次按名字现查符号（dlsym），挑块时每块都调一回 mincore；加符号缓存（状态区九千零四十存表址，按静态串地址查）。
4. 求块时整段重算驻留：每长一块都把任务整段区间走一遍宿主区域查询；只对换出过块的任务重算，其余交两秒一次的计页。
5. 已换出的块被一换再换：「住页」只看 mincore 的在核位，林檎对文件映射的页只要在页缓存里就报在核；改为只数私有驻留页（在核且匿名或写时复制）。
6. 启动器自己的堆被旧窖换出去：每起一个子任务都把父启动块整块八兆多拷一遍、再把八兆参数区写零，「豫行取块」也把取到的区再整块清零，全都成了启动器堆里的驻留页，逼着堆向外层行在要额、行在一说紧执行器就把这堆（府、槽、运行记录都在里面）换出去，主线程整段耗在拷贝、定位写与重映射里；改为只拷父块参数区之后那段，参数区只清旧参数用到的那截，「豫行取块」不再重复清零。
7. 预订批不下来时虚机不封顶：「虚机预订块」原先退成整机物理内存，改为照 豫言虚机内存 给内部仓定容。
8. 池限形同虚设：子任务在处理器上涨内存不经主线程，账只靠计页抽样；急抽（五十毫秒一回）原先要“有任务等内存或池已用过八成”才开，可这两样看的正是账本身，账不抽就不动，驻留冲到池限的五倍。主线程又常无限期睡在宿主等待里（有任务在处理器上跑也一样），计页根本不跑。改为切入过或在跑的任务每个急抽周期抽一次；主线程宿主等待在有处理器跑客体、有切入过还没抽的任务或有等内存的任务时设急抽周期长的时钟（「豫行该抽」），单线程主循环同样。
9. 腾仓每换一块就把整个任务的区域重走一遍：换得越多映射越碎、走得越慢，几十个任务各换上百块时主线程卡住几十秒到几分钟，候行的新任务等不到块，看着就是挂死。改为一个任务连换到补足缺口或无块可换（「连换」，「换块」返回换出的私有驻留页数）再重查一次。
10. 腾仓每轮都把空等任务逐块再问一遍 mincore（找不到可换的块还要绕两圈），几十个任务一轮几万次系统调用：一块也换不出的任务记“换尽”（运行记录三百三十二），到它再切入（「记热」清掉）之前跳过。
11. 驻留查询、挑块与记热都按已映块数走，而虚机里每个任务的动态区一律预留一 TiB：客体按“能预留多大就多大”定页上限（约十六太字节），位图与卡表按它预留在线性内存里，线性内存约五百九十 GiB、大而稀疏，林檎又按一百二十八兆把大块匿名映射切成一段段，四十个任务十几万段；「苹住块」查一个任务要走四千多段，「换块」一圈要问几十万次 mincore。改为三处：虚机任务的动态区容量取虚机内存的两倍、至少六十四 GiB（「豫行动区容块」，页上限约一太字节，堆仍可长到二十多 GiB）；只走用界，即客体线性内存页数格（名义地址臂六十四 0x402FFFFC）折成的二兆块数（「宿候」之「用界」）；「换块」挑块时冷块落在未知区段就先问一次所在宿主区域的私有驻留页（「宿候」之「苹区私页」，「苹住块」也改用它），没有就整段跳过。
12. 第 8 条改成在跑的任务一律五十毫秒一抽以后，私有虚机行在冷编全树时主线程八成时间耗在宿主区域查询上（编译工作进程堆大，十一个任务每秒抽二百多回），处理器空等它办服务，整进程只用两三核。急抽改为只在有任务等内存或池压时开；池压按虚机进程的足迹判（「豫行池压」，「原生底层」之「原底问号实占」一次系统调用，到池限八成为压），不随账走；主线程定时醒来的条件里，“有待抽任务”也要配上池压，空闲时不白醒。

**虚机比原生慢在哪（#1477，2026-10-30；用户定性能暂不追，“只要不是离谱得慢就行”）。** 冷编全树类型检查（`豫构 类型检查 豫言编译器`，2121 件），虚机比原生慢约一成到两成：十八槽、机器较闲时虚机 469、460 秒，原生 381、416 秒；八槽、机器很忙（负载十五到二十四）时原生 616、601 秒，八个虚拟处理器的虚机 664 秒，十八个虚拟处理器的虚机 720 秒。用客户端日志逐件比“启动—完成”，开销分两处：

1. 虚拟处理器不比槽多时派活跟不上。八个虚拟处理器、八槽：虚机里单件合计 4048 秒，比原生 4836 秒还少，可平均同时只跑 6.1 件（原生 7.85 件）。客户端、将作、代役、行在、虚机门这些服务任务与编译任务抢同一批虚拟处理器，派活要等时间片，编译槽空着。缺省配置（虚拟处理器数等于宿主核数）没有这个问题：十八个虚拟处理器、八槽时同时 7.91 件（原生 7.59 件）。
2. 每件任务的服务往返。虚拟处理器给够以后，虚机单件合计 5624 秒，比原生 4532 秒多约两成半。早上十八槽时对虚机进程采样六秒：处理器线程等主线程回话或等底层锁的空转合计约占一核；主线程替客体做 openat（406 次采样）、renameat（126）、write（73）、fstatat（64），往客体拷数据的 memmove（146）。原因是不在直办名单里的服务（内存增长、起子任务、等待、任务间消息，以及改名、删文件、建目录、同步、设长度、时钟）都排在主线程一处；在直办名单里的文件服务也串在一把全局底层锁上（锁护的是全进程共用的请求、路径与一兆数据中转暂存）；计页抽驻留时持着这把锁，处理器直办跟着停。

试过的改法（每个处理器一套暂存、林檎上直办不抢锁、直办名单扩大，见 #1477）存在分支 行在虚机按核暂存（97eff9a378），没合入：本机重负载下没量出提速，第一版把套接字读写交回主线程反而更慢（八核 710.6 秒对改前 663.7 秒）。以后续做的方向：在安静的机器上量，先采样分清主线程时间；数据直接在客体内存与文件之间读写，省掉一兆中转槽的来回拷贝（「豫行底数据容」的待办事项）；起子任务、等待、任务间消息挪出主线程；处理器等回话按主线程积压决定空转还是睡；虚机调度给服务任务优先。

**多核虚机重负载下偶发崩溃（2026-10-30，查明前不翻缺省）。** 十八个虚拟处理器、本机负载约二十时冷编全树，改前的启动器也会崩（四遍崩一遍），两种表现：一是主线程正在 munmap，处理器线程接着执行就在已撤映射的客体映像区里段错误，崩溃任务的代码、全局区与栈都在被撤的那段里，像是对仍在处理器上跑的任务做了收映；二是处理器线程在启动器代码里栈指针为零、访问空地址，同时主线程在往客体拷字节。机器较闲时十八槽连跑两遍没崩。

根因：任务在处理器上调“退出”，主线程办完、信箱置“归”后就接着干别的；处理器线程要等被叫醒才回到服务入口桩，再读运行记录里的动作决定是回处理器循环还是接着跑客体。宿主重负载下这个线程常被抢占几毫秒，这段时间里父任务已被唤醒、派上别的核，回收了这个任务的槽，「导出：机槽位清」当场把槽与运行记录交还空槽链，紧接着起子任务的「豫行承记」把这份记录拿去清零重用。处理器线程这才读动作，读到零就接着跑客体：栈指针取记录八十（已清零），或接着执行已撤映射的映像区。服务入口桩反汇编对得上：读动作为零后取记录八十作栈指针，崩溃时栈指针正是零。修法：「导出：机槽位清」见这个任务还挂在处理器上（「核寻记」找得到），就把槽记在那个核的核区里（核区栏新加「待还槽」「待还籍」），等「核收」时再交还空槽链；籍号表那一格照旧立刻清，籍号若先被新任务占去，「豫行理核」收回处理器时核对籍号对应的运行记录不是这个核记着的那份，就不做「出役」，免得清掉新任务的正在运行。验证：修后本机十八个虚拟处理器、八槽冷编全树连跑三遍全过（1145、464、429 秒；第一遍负载十四到二十四，后两遍本机构建停摆、负载六到十），四十任务换页探针 pit-mac 连跑三遍全过。

### 里程碑六：本机部署查出的句柄泄漏与僵尸（2026-10-30）

本机第二趟部署跑了半天，虚机进程积到三百多条 IPv4 连接、一百多条管道，pit-pc 的将作远客断不了（#1498 的鬼客）。根因：虚机里客体的句柄就是启动器进程的宿主句柄，任务退出时宿主不替它关；原生进程退出时这事由内核做。修法照原生语义：启动器按句柄软上限立属主表，建句柄的服务（打开、监听、连接开始、接受、建管道、建数据报、运行程序）办成时登记，关闭先除名再关，任务收场时把仍记在它名下的句柄一并关掉（eb7d9d868）。同一处还有僵尸：关进程句柄只把进程表格清零，子进程退出后无人收；启动器长驻，任务收场又替它关进程句柄，僵尸越积越多。改成运行中关句柄的格记为已弃，起新进程前非阻塞地收一遍（bcf2a11d18）。

### 余下各步的做法（2026-10-29 记）

- **里程碑二（林纳、轩窗多处理器）**：林纳没有 libc，线程要冶铸新加一段桩：clone（CLONE_VM、FS、FILES、SIGHAND、THREAD、SYSVSEM）带新栈，子线程按记录装 x28、x25、x15 与栈，调导出「后台线程入口」，返回后 exit（不是 exit_group）；臂六十四与兼容六十四各一段。轩窗用 kernel32 的 CreateThread，线程函数按 Win64 约定接记录。冶铸的入口表与接口声明要先单独合入、等连续版本换上新链再用（#1402）。轩窗的缺页处理按全局「状态视客记」找任务，多处理器时要改成按线程找（TLS 或按缺页地址查任务区间）。
- **里程碑三（抢占与陷阱）**：执行器现有的信号设施只有 signal(SIG_IGN/SIG_DFL)。抢占可走两条路：信号（处理桩改 ucontext，把正在跑客体代码的处理器拐进“让行”跳板）或编译器在循环回边插轮询（提案第九节的“抢占轮询”，要换语义号）。陷阱只结束出事的任务、栈保护页也要信号处理桩（林檎 SIGSEGV/SIGBUS、林纳同、轩窗 VEH 已有缺页桩）。
- **里程碑五（工具链进虚机）**：现在托进虚机的构建，编译仍在宿主上：虚机里的豫构是将作的客，活由宿主将作派给宿主上的代役。要进虚机得把将作、代役、编译工作进程都起成虚机里的豫行任务：将作在虚机里只认自己的豫行链（同语义号的客照收），代役与编译工作进程起豫构豫行版；行在即虚机进程。#1414（等子任务句柄只等到退出）若撞上管道帧协议要先修。

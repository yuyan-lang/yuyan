这是豫言基础库的提案与实施规格。常见的 Linux 发行版里，几乎所有程序都间接依赖同一批基础库（zlib、libpng、libjpeg、ICU、PCRE2、OpenSSL、libcurl、SQLite 等）；AI 工程师在此之上还要用 NumPy、SciPy、safetensors、tokenizers、Hugging Face Hub 客户端等。本提案以它们为参照，列出豫言要有的全部基础库，用纯豫言写成；一份实现，在浏览器、诺节、原生与裸机上同源可用。例如图像解码库写一次，浏览器显示网页图片、桌面预览图片、裸机上的看图程序都用它。

基础库以「豫言基础库 0.1.0」的名义随豫言操作系统第一公测版一同发布。实施由用户指派的一个代理负责（可派子代理），本文就是它的完整任务书：第四节是逐库的规格，第五节是共同规矩，第六节是发布门槛，第十节是实施步骤，末尾是进度表。

## 二、动机

### 同一能力或只在某个宿主上有，或各写一份

2026-10-06 在 yybs（400b5ba35 与 1b63033c1）上检索 `库/`、`应用/`、`豫言操作系统/` 与 `豫言操作系统接口/` 所得：

- `豫言操作系统接口/` 已有「压缩」「密码摘要」「口令派生」「文字规整」「网址」「关系数据库」等接口，适配只在云工或浏览器上，都转交宿主（DecompressionStream、Web Crypto、String 与 RegExp、D1）；原生与裸机上没有实现。
- `库/云工宿主` 的压缩流、密码、编码与持久对象 SQL 都是云端平台的接口；`库/安全外壳/安全外壳密码` 的 SHA-256、X25519、Ed25519、AES-256-GCM 由宿主实现，诺节工具宿主用 `node:crypto`。
- `库/标准库/网络` 的 TCP 是宿主接口，其上有纯豫言的 HTTP/1.1 报文编解，不解分块编码；终端浏览器取网页走宿主的 HTTP(S) 请求接口；各平台都没有纯豫言的 TLS。
- 纯豫言的实现散在各处：终端浏览器有 ChaCha20、Poly1305、HKDF、SHA-256、HMAC，只被它自己的测试使用，其中 SHA-256 与 ChaCha20 用 `0`/`1` 字符串表示比特，很慢；安全外壳协议的公钥与私钥文本自带 Base64；壳核心自带拼音数据；静态站自带前言（YAML）的简易解析；深度学习的预分词因“仓里没有正则引擎”按码点手写 Qwen2 的正则，`\p{L}`、`\p{N}` 只用近似的码段表判断；UTF-16 列号换算在包配置的语言服务里另写一份。
- 发布工具打包时调用系统的 zip、unzip 与 tar（`应用/发布/批量发布/发行材料。豫`）；造启动盘要系统的 xorriso。
- 没有图像解码：终端浏览器的 `<img>` 只显示替代文字，仓里没有 PNG 或 JPEG 解码器。
- 没有通用正则：终端浏览器的 JavaScript 字符串方法还不支持正则（见其包说明）。

### AI 工程的缺口

- 已有：深度学习框架（张量与自动微分、卷积、循环网络、变换器、SGD 与 Adam、MNIST 与 CIFAR-10 读取），千问三、千问三混合专家与千问三点五的推理，GGUF 文件头解析，字节级 BPE 分词，CUDA 与 Metal 的算子。
- 缺：safetensors、NPY 与 PyTorch 权重文件；Hugging Face 的分词器格式与聊天模板；矩阵分解与 FFT；随机数只有六十四位线性同余、只出二十四位；GGUF 的双精度元数据与嵌套数组不解析；本地推理只读本机 Ollama 目录、只在命令行打印。

### 使用者在等

- 豫言操作系统：看图、解压安装包、校验文件、转码、搜索文字、简繁转换。
- 浏览器：图片、正则、HTTPS（现在由宿主代办）、字体整形、SVG。
- 桌面应用：图片预览、归档、文件类型识别、数据格式。
- 工具链与包管理：压缩、归档、签名校验、差异比较。
- AI 工程：模型格式、分词器、聊天模板、模型下载、推理服务、数值计算、数据集与图表。

### 与规矩一致

AGENTS.md 已定诺节不引第三方库，各后端靠“只用豫言自己的库”保持功能一致；共用基础库是这条规矩能落地的前提。

## 三、目标与范围

- 目标：第四节列出的全部库按第六节的门槛完成，以「豫言基础库 0.1.0」随第一公测版发布。
- 范围内：纯计算的库（编解码、压缩、密码、解析、文字处理、二维光栅化、数值计算）；与平台无关的协议层（HTTP、TLS、DNS 等，写成“字节进、字节出”的状态机，读写经公共接口）；同类操作系统接口在原生与裸机上的适配；每个库的第一个使用者；公测镜像里的示例程序。
- 范围外（另立目标）：设备驱动与内核里的 TCP/IP 协议栈；视频编解码（H.264、AV1 等）与 AVIF、HEIC、JPEG XL 图像；完整的 JavaScript 引擎；GPU 后端（Vulkan、ROCm）与多卡分布式训练；Jupyter 式笔记本；办公文档与 PDF 的阅读渲染；与现有 C 库的接口兼容（只求能力，不求同名同参）。

## 四、设计：库清单

### 读法

- 每个库一节：标题写包名与批次。「必须有」是最小可用（甲级）的要求，「完整版」是完整（乙级）另外要做的，「测试」是测试与对照的来源，「依赖与使用者」写依赖哪些库、先接哪个使用者。
- 目录为 `库/基础库/<组>/<包名>/`。组也是父包，名为「<组>基础库」，例如 `库/基础库/文字/统一码` 属于「文字基础库」。已有的库（字体、结森工具）留在原处，只扩充。
- 包名与现有包冲突时（用 `节点 yy豫构.wasm 发现 --树` 查），在名前加「基础」。
- 批次决定开工顺序与发布门槛（第六节）。

### 第一组 校验与编码（`库/基础库/校验与编码`）

#### 「校验」 · 第一批
- 必须有：CRC-32（IEEE）、CRC-32C、CRC-64（XZ 用的 ECMA 多项式）、Adler-32、xxHash（XXH32、XXH64、XXH3 的六十四位与一百二十八位）、MurmurHash3、FNV-1a、SipHash-2-4；都有一次算完与流式两种接口。
- 完整版：查表提速（每次八字节）；与系统实现比性能。
- 测试：各算法对“123456789”的标准校验值、xxHash 官方测试向量、SipHash 论文附录。
- 依赖与使用者：只依赖标准库；压缩、归档、图像编解码、训练记录（CRC-32C）用它。

#### 「字节编码」 · 第一批
- 必须有：Base16、Base32、Base64（RFC 4648，含网址安全字母表与可省填充）、Ascii85、可打印引用编码（quoted-printable）、百分号编码（RFC 3986 与 WHATWG 的各个编码集）。
- 完整版：流式编解码；严格与宽松两种解码。
- 测试：RFC 4648 第十节的向量；随机往返。
- 依赖与使用者：只依赖标准库；安全外壳协议的公钥与私钥文本改用它，证书（PEM）、邮件格式、网址解析、模型仓库用它。

### 第二组 压缩与归档（`库/基础库/压缩与归档`）

#### 「压缩」 · 第一批
- 必须有：DEFLATE 解压与压缩（零至九级；存储、固定与动态霍夫曼；惰性匹配），zlib 与 gzip 封装（gzip 支持多成员与头部字段），一次与流式接口，解压量上限。
- 完整版：zstd 解压（含字典与校验）与一至三级压缩；LZ4 块与帧格式；Snappy 原始与分帧格式；Brotli 解压；xz（LZMA2）解压；bzip2 解压。
- 测试：与系统 gzip、zlib 互相解压对照；zstd 的 decodecorpus 样本、Brotli 与 xz 官方测试文件；随机往返；损坏与截断输入。
- 依赖与使用者：校验；图像编解码（PNG）、超文本传输的内容编码、归档、列存数据、字体（WOFF、WOFF2）、发布工具用它。

#### 「归档」 · 第一批
- 必须有：tar（ustar、pax 扩展头、GNU 长名）读写；zip 读写（存储与 DEFLATE、zip64、UTF-8 文件名标志、数据描述符、CRC 校验）；解包时拒绝 `..`、绝对路径与指向外面的符号链接。
- 完整版：cpio（newc，初始内存盘用）、ar（.deb 外层）；zip 的 zstd 方法；GBK 编码的 zip 文件名（经编码转换）；.tar.gz、.tar.zst、.tar.xz 的一步读写。
- 测试：系统 tar、zip、bsdtar 造的样本；往返；恶意路径样本。
- 依赖与使用者：压缩、校验；发布工具改用它取代系统的 zip 与 tar，张量格式（.npz、.pt）、数据集（WebDataset）、操作系统的安装包用它。

### 第三组 文字（`库/基础库/文字`）

#### 「统一码」 · 第一批
- 必须有：取当时最新版本的统一码字符数据库生成属性表（一般类别、文字、东亚宽度、行断、字素与词与句的切分属性、双向类别、组合类、分解、大小写与大小写折叠、表情属性；谚文音节按算法）；规范化 NFC、NFD、NFKC、NFKD；字素簇、词与句的切分（UAX 29）；大小写转换与折叠；东亚宽度（终端列宽）。
- 完整版：行断（UAX 14，含中日韩禁则）、双向文字（UAX 9，含括号对）、IDNA（UTS 46）与 Punycode、标识符属性（UAX 31）、排序（UCA 与 DUCET）。
- 测试：统一码官方测试文件（NormalizationTest、GraphemeBreakTest、WordBreakTest、SentenceBreakTest、LineBreakTest、BidiTest、BidiCharacterTest、IdnaTestV2、CollationTest）。
- 依赖与使用者：只依赖标准库；文字排版、正则、分词器、浏览器、编辑器、命令壳、预分词用它；「文字规整」接口的原生与裸机适配用它。表格用两级查找表压紧；排序表另立「统一码排序数据」包。

#### 「编码转换」 · 第一批
- 必须有：WHATWG 编码标准的全部编码与标签：UTF-8（替换与严格两种出错方式，BOM）、UTF-16LE 与 UTF-16BE、GBK、gb18030（含四字节区）、Big5、EUC-JP、ISO-2022-JP、Shift_JIS、EUC-KR、各单字节编码；另加 UTF-32。
- 完整版：流式转换；编码探测（BOM，加 UTF-8 与 GBK 的启发式判断）。
- 测试：WHATWG 的编码索引文件与 web-platform-tests 的编码测试；往返。
- 依赖与使用者：只依赖标准库；浏览器（网页字符集）、文件预览与编辑器（中文环境常见 GBK 文件）、归档（Windows 造的 zip 文件名）、邮件格式用它；语言服务的 UTF-16 换算改用它。

#### 「正则」 · 第一批
- 必须有：线性时间引擎（解析成 NFA，用 Pike 虚拟机与惰性 DFA 执行）；捕获组、命名组、非贪婪、计数重复、锚点、统一码词边界、`\p{…}` 统一码属性与文字（经统一码库）、按统一码折叠的不区分大小写、`imsxu` 标志；Perl 与 RE2 式语法；查找、全部查找、替换（`$1`、`$<名>`、`$&`）、分割；字符串与字节串两种输入；通配符模块（POSIX fnmatch、`**`、花括号展开）。
- 完整版：ECMAScript（2025）语法，含前瞻、后顾、反向引用与 `v` 标志的集合运算；用到这些特性的模式改走回溯引擎，设步数上限（往大里定）。
- 测试：RE2 与 Rust regex 的测试表、PCRE 测试数据的子集、test262 的 RegExp 部分；ECMAScript 语法以诺节的 RegExp 为对照，做随机模式的差分测试。
- 依赖与使用者：统一码；浏览器的 JavaScript、编辑器的搜索替换、分词器、预分词、命令壳的搜索工具、约束解码用它。

#### 「中文处理」 · 第二批
- 必须有：简繁转换（照 OpenCC 数据，词组最长匹配，含台湾与香港用字）；汉字转拼音（多音字按词组，带调号、数字调或无调）；拼音排序与笔画排序；全角半角转换；中文数字与阿拉伯数字互转（含大写金额）。
- 完整版：中文分词（词典加隐马尔可夫模型，类似 jieba）；拼音输入用的词库与按词频排序。
- 测试：OpenCC 自带的测试用例；拼音数据抽样核对；分词以 jieba 的输出为对照。
- 依赖与使用者：统一码；壳核心的拼音输入改用它的词库，文件管理（按拼音排序）、搜索、浏览器、分词器用它。词典另立「中文处理数据」包。

#### 「字体」（扩充现有 `库/字体`） · 第二批
- 必须有：CFF 与 CFF2 轮廓（思源与 Noto 的中日韩 OpenType 字体用 CFF）；WOFF 与 WOFF2（经压缩库的 zlib 与 Brotli）；彩色表情（COLR v0 与 CPAL；CBDT 与 sbix 的 PNG 位图）。
- 完整版：可变字体（fvar、gvar、avar、HVAR）。
- 测试：各格式的真实字体文件；与系统字体的栅格化结果比覆盖度（容差）。
- 依赖与使用者：压缩、图像编解码（彩色位图）；显示控件、浏览器、用户态桌面用它。

#### 「文字整形」 · 第二批
- 必须有：OpenType 排版表 GSUB（单一、多重、替换、连字、上下文、链式上下文、反向链式）与 GPOS（单一、成对、草书连接、标记到基字、标记到标记、上下文）；按文字与语言选特性（ccmp、locl、liga、calt、kern、mark、mkmk，竖排的 vert 与 vrt2，阿拉伯的 init、medi、fina、isol、rlig）；默认整形器（拉丁、中日韩）与阿拉伯、希伯来整形器；输出字形号、前进量、偏移与簇映射。
- 完整版：通用整形引擎（USE）与印度诸文字整形器；没有排版表的字体退用 kern 表。
- 测试：HarfBuzz 测试集里的整形用例（字形号与位置对照）；可用 hb-shape 生成对照数据，提交为样例。
- 依赖与使用者：字体、统一码；文字排版、浏览器、显示控件用它。

#### 「文字排版」 · 第二批
- 必须有：段落排版：按文字、方向与字体回退切分成段，整形，按 UAX 14 与中日韩禁则断行，双向重排，输出定位好的字形段；两端对齐。
- 完整版：竖排；行内图片的占位；制表位。
- 测试：典型的中英混排、阿拉伯与希伯来混排段落的断行与位置样例。
- 依赖与使用者：文字整形、统一码、字体；显示控件的文字绘制与断行、浏览器的行内排版、终端改用它。

### 第四组 密码与安全（`库/基础库/密码与安全`）

#### 「密码」 · 第一批
- 必须有：散列 SHA-1、SHA-224、SHA-256、SHA-384、SHA-512、SHA-512/256、SHA-3 与 SHAKE、BLAKE2b 与 BLAKE2s、BLAKE3、MD5（只供校验旧文件，标明不安全）；HMAC、HKDF、PBKDF2；AES-128、AES-192、AES-256 的 GCM 与 CTR 模式；ChaCha20、Poly1305 与 ChaCha20-Poly1305；X25519、Ed25519；ECDSA 与 ECDH（P-256、P-384）；RSA 验签（PKCS#1 v1.5 与 PSS）；密码学安全的随机数发生器（以 ChaCha20 为核心，用安全随机接口播种）；常数时间比较。
- 完整版：scrypt、Argon2id；AES-CBC、XChaCha20-Poly1305；RSA 签名、OAEP 与密钥生成；P-521；ML-KEM-768（FIPS 203）；ML-DSA（FIPS 204）。
- 测试：RFC 附录（8439、7748、8032、5869、4231、7914、9106）、NIST 的 CAVP 与 ACVP 向量、Wycheproof 的全部相关文件；与诺节的 `node:crypto` 和系统 openssl 做随机差分对照。
- 依赖与使用者：校验、大数（只用于公开数据的运算）；证书、安全传输、安全外壳（原生与裸机）、包签名、「密码摘要」「口令派生」接口的原生与裸机适配用它；终端浏览器的密码模块迁入并改用字节表示。常数时间：秘密数据不决定分支与访存下标，包说明逐个算法写明做法。

#### 「证书」 · 第二批
- 必须有：ASN.1 DER 解码与编码、对象标识、PEM；密钥格式（PKCS#1、PKCS#8、SEC1、SPKI、OpenSSH 公钥与私钥）；X.509 v3 证书与常用扩展（SAN、基本约束、密钥用途、扩展密钥用途、名称约束）；证书链构建与路径验证（RFC 5280 的签名、有效期、基本约束、用途）；主机名核对（RFC 9525，含通配符与 IP 地址）；根证书库（由 Mozilla 的 CA 证书集生成，含 TLS 信任位）及其更新方法。
- 完整版：名称约束的完整检查；CRL 解析；OCSP；证书签名请求（PKCS#10）与自签证书生成。
- 测试：C2SP 的 x509-limbo 路径验证测试集、Wycheproof 的签名解析用例；与系统 openssl verify 对照。
- 依赖与使用者：密码、字节编码、日历（时间比较）；安全传输、包签名、安全外壳的已知主机、浏览器的证书出错提示用它。根证书另立「根证书数据」包。

#### 「安全传输」 · 第二批
- 必须有：TLS 1.3 客户端（RFC 8446）：AES-128-GCM、AES-256-GCM、ChaCha20-Poly1305 三个套件；X25519 与 P-256 密钥交换；ECDSA、RSA-PSS、Ed25519 签名；SNI、ALPN、HelloRetryRequest、KeyUpdate；证书验证接证书库。写成“字节进、字节出”的状态机，不绑定传输层，另附接标准库 TCP 的薄层。
- 完整版：会话票据与 PSK 恢复；X25519MLKEM768 混合密钥交换；TLS 1.2 客户端（ECDHE 加 AES-GCM 或 ChaCha20-Poly1305，扩展主密钥）；TLS 1.3 服务端（供本机 HTTPS 服务）。不做 0-RTT。
- 测试：RFC 8448 的握手样例逐字节重放；与本机 `openssl s_server` 的多种配置互通；过期、主机名不符、自签、不受信根等出错样例。
- 依赖与使用者：密码、证书；超文本传输（HTTPS）、模型仓库、浏览器在原生与裸机上取网页、包管理用它。

### 第五组 网络（`库/基础库/网络`）

- 依赖与使用者：统一码、字节编码；浏览器（替换自带的网址处理）、超文本传输、模型仓库用它；「网址」接口的原生与裸机适配用它。

#### 「超文本传输」 · 第二批
- 必须有：HTTP/1.1 报文的解析与序列化（RFC 9110、9112：分块、尾部字段、长度、保持连接），写成状态机；客户端：重定向、Cookie（RFC 6265bis）、Range 断点续传、内容编码 gzip、deflate、br、zstd（经压缩库）、multipart/form-data、HTTPS（经安全传输）；服务端：流式请求与响应、服务器发送事件（SSE）、静态文件（Range、ETag、媒体类型）；WebSocket 客户端与服务端（RFC 6455）。

- 依赖与使用者：压缩、安全传输、网址解析、字节编码、文件类型；浏览器、模型仓库、推理服务、包管理、简易网页服务器与云设备代理用它。

#### 「域名解析」 · 第二批
- 必须有：DNS 报文编解（RFC 1035、EDNS0；A、AAAA、CNAME、MX、TXT、SRV、HTTPS 与 SVCB 记录）；经 TCP 的存根解析器与经 HTTPS 的 DoH；hosts 文件与 resolv.conf 解析；按 TTL 缓存。
- 完整版：经 UDP 的查询（等有 UDP 接口；没有时留待办事项）。
- 测试：抓包样例的往返；对公共 DoH 服务的手工核对。
- 依赖与使用者：超文本传输（DoH）；没有宿主域名解析的平台、网络诊断工具用它。

#### 「邮件格式」 · 第三批
- 必须有：RFC 5322 头部解析与生成；MIME 多部分、Base64 与可打印引用编码、RFC 2047 编码字（UTF-8、GBK 等）。
- 完整版：SMTP 客户端（RFC 5321，STARTTLS 经安全传输）。
- 测试：RFC 样例与真实邮件样本。
- 依赖与使用者：字节编码、编码转换、日历；邮件类应用用它。

#### 「协议缓冲」 · 第二批

### 第七组 图像与图形（`库/基础库/图像与图形`）

#### 「图像编解码」 · 第一批
- 必须有：PNG 解码（全部颜色类型与位深、调色板与透明、Adam7 隔行；gAMA、sRGB、iCCP 等块原样带出）与编码（滤波选择、压缩级）；JPEG 解码（基线与渐进霍夫曼、重启标记、4:4:4、4:2:2、4:2:0 采样、Adobe 的 CMYK 与 YCCK、EXIF 方向），用整数 IDCT；GIF 解码（含动画、处置方式、透明、隔行）；BMP 与 DIB（1、4、8、16、24、32 位，RLE4、RLE8、位域）及 ICO、CUR 的解码与编码；netpbm（PBM、PGM、PPM、PAM）与 QOI 的读写；统一的图像类型（宽、高、像素格式、行距、像素字节）。
- 完整版：WebP（VP8L 无损解码与编码、VP8 有损解码、透明、动画）；APNG；JPEG 基线编码（质量参数、4:2:0 与 4:4:4）与算术编码解码；GIF 编码（调色板量化）；TIFF 基线解码（未压缩、PackBits、LZW、Deflate，条带与分块）；TGA。
- 测试：PngSuite；libjpeg-turbo 的测试图像，与 djpeg 的结果比（PSNR 不低于 45 dB）；GIF、BMP 与 WebP 的公开测试图；全部解码器做模糊测试。
- 依赖与使用者：压缩、校验；用户态桌面的文件预览与看图程序、浏览器的 `<img>` 与背景图、截图（PNG 编码）、图标、字体的彩色表情、图像处理与 AI 视觉预处理用它。

#### 「图像处理」 · 第一批
- 必须有：像素格式互转（灰度、灰度加透明、RGB、RGBA、BGRA，八位、十六位与单精度；预乘透明）；sRGB 与线性互转；YCbCr（BT.601 与 BT.709）与 RGB 互转；缩放（最近邻、双线性、双三次、Lanczos3、面积平均，缩小时抗锯齿；另有定点算法供裸机用）；裁剪、填边、翻转、旋转九十度的倍数；Porter-Duff 合成；按 EXIF 方向摆正；缩略图；AI 预处理预设（短边缩放、中心裁剪、按均值与标准差归一，输出 CHW 或 HWC 的单精度数据，与 torchvision 和 Pillow 的结果对齐）。
- 完整版：HSV 与 HSL；ICC v2 与 v4（矩阵加曲线）的颜色转换；任意角旋转与仿射变换；卷积（盒式与高斯模糊、锐化、Sobel）；直方图、色阶与伽马；抖动（Floyd–Steinberg）与调色板量化（中位切分、八叉树，与 GIF 编码共用）。
- 测试：恒等与对称性质测试；与 ImageMagick 的结果比（容差）；AI 预设与 Pillow 的输出比（对照数据一次生成后提交，不提交脚本）。
- 依赖与使用者：图像编解码；看图（适应窗口）、浏览器的图片缩放、缩略图、AI 视觉模型的预处理、二维码识别用它。

#### 「二维绘图」 · 第二批
- 必须有：路径（直线、二次与三次贝塞尔、圆弧、椭圆、圆角矩形）、仿射变换；填充（非零与奇偶规则，按覆盖度解析抗锯齿）；描边（线宽，斜接、圆、斜切三种连接，平、圆、方三种线帽，斜接上限，虚线）；颜料（纯色，线性、径向与锥形渐变及延展方式，图像图案）；路径裁剪；Porter-Duff 合成与可分离的混合模式；带不透明度的图层；用字体轮廓画矢量文字；输出与显示控件画布一致的 RGBA 缓冲。

- 测试：覆盖度与解析解对照；与参考渲染的图像比（容差）。
- 依赖与使用者：字体、文字排版、图像编解码；显示控件与界面、浏览器（边框、圆角、渐变，以后的 canvas 2D）、矢量图、图表、二维码、便携文档用它。

- 完整版：为命令壳、bash 与 zsh 生成补全脚本。
- 测试：表格驱动的解析用例。
- 依赖与使用者：只依赖标准库；新写的命令行工具（`yy模型` 等）与示例程序用它，现有工具逐步改用（不强求）。

#### 「行编辑」 · 第二批
- 必须有：按 UTF-8 与东亚宽度移动光标；Emacs 式按键；历史（可存文件）与 Ctrl-R 增量搜索；补全回调。
- 完整版：多行编辑；语法高亮钩子。
- 测试：按键序列驱动的状态测试。
- 依赖与使用者：统一码、终端界面；命令壳、交互求值（提案 00003）、数据库与模型的命令行工具用它。

#### 「终端界面」 · 第二批
- 必须有：ANSI 与 VT 转义序列（十六色、二百五十六色、真彩色、样式、光标控制）；能力探测（TERM、COLORTERM、NO_COLOR）；进度条与转圈提示。
- 完整版：屏幕缓冲与差量刷新；控件（列表、表格、文本输入、对话框）；SGR 鼠标事件；窗口大小变化。

- 依赖与使用者：统一码；豫构的进度、模型仓库的下载进度、系统监视类工具用它。

#### 「差异比较」 · 第二批
- 必须有：Myers 差异（线性空间）、patience 与 histogram 差异；按行、词与字符（字素簇）比较；统一格式输出；补丁解析与应用（带模糊匹配）；相似度。
- 完整版：三方合并（diff3）与冲突标记。
- 测试：与 GNU diff 和 git diff 的输出比（对照数据一次生成后提交）；补丁往返。
- 依赖与使用者：统一码；编辑器、全树测试的期望差异显示、版本库、文档历史用它。

#### 「文件类型」 · 第一批
- 必须有：按文件头魔数识别媒体类型（图像、音频、视频、归档、压缩、PDF、字体、ELF、Mach-O、PE、Wasm、带 BOM 的文本）；按扩展名查媒体类型（IANA 与 shared-mime-info 的数据）。

- 依赖与使用者：编码转换与归档（完整版）；用户态桌面的文件浏览器（按类型分派预览与打开方式）、超文本传输的静态文件服务、浏览器用它。

## 五、设计：共同规矩

### 两级验收

- **最小可用（甲级）**：「必须有」全部实现；测试在诺节与原生上全部通过；包说明双语写全（功能、接口、限制、数据出处与许可）；在父包登记；接上第一个使用者；在进度表登记。
- **完整（乙级）**：在甲级之上，「完整版」全部实现；解码器与解析器做过模糊测试（每个入口至少一百万个变异输入，无崩溃、无超时、无超限分配）；性能量过并记进包说明；适用的库在裸机上跑通测试；迁移项完成。

### 写法

- **纯豫言、宿主无关**：只依赖标准库、豫言自己的库与公共接口；输入输出用字节串；在浏览器、诺节、原生、裸机上同源可用。网络类写成“字节进、字节出”的状态机，传输另做薄层。
- **接口**：对外给“字节串进、结构化结果出”的函数，需要时加流式接口；名称用中文，外来名词照下文「译名」；可恢复的数据问题用结果值返回（照「压缩」接口的状态码惯例），参数违规抛豫言异常。
- **性能**：先写普通豫言，量过再优化；热点可改底层模式（无回收）或交原生工具链优化；裸机的小数走软浮点，解码与重采样等优先整数或定点运算；密码的比较、查表与标量乘法要常数时间。目标：原生上与同机的 C 实现（系统工具或库）相比，第一批在三倍以内，其余在五倍以内；达不到不挡合入与发布，在进度表记下差距，交原生工具链目标。
- **上限**：输入长度、解压比、图像尺寸、递归深度、实体展开、回溯步数都设上限（往大里定），超限明确报错。
- **数据**：外部数据下载到仓外的数据目录 `/Users/zc/repos/yuyan-worktrees/豫言数据`；生成工具用豫言写，产出的表格提交入库；超过 1 MiB 的数据表另立「X数据」包，按需依赖，压缩后提交；包说明写明出处、版本与许可（如统一码数据许可、tzdata 为公有领域、Mozilla 根证书为 MPL 2.0、OpenCC 为 Apache 2.0）。
- **对照数据**：可用系统工具与他人实现（gzip、openssl、djpeg、hb-shape、ImageMagick、jinja2、NumPy、Hugging Face tokenizers 等）一次生成参考输出，提交为样例数据；仓内不提交 Python、shell 或 JS 脚本（AGENTS.md）。
- **测试布局**：测试放各包的 `测试/`；进 CI 的测试（`X。测试。豫`，全树测试自动发现）每个包合计在一分钟以内；大测试集、模糊测试与性能测量放 `测试/全量/`，在本机或 pit-mac 跑，并在 `应用/开发工具/全树测试/测试规则.tsv` 登记为跳过。
- **各平台的验收**：诺节用豫构构建后直接运行；原生用 `yy原生生成.wasm` 生成原生程序运行（生成器与执行器须同源重建，见 `持续改进目标/原生工具链.md`「规矩」）；裸机把测试程序放进一个预置目录，用 `yy豫言系统.wasm 构建 --预置 <目录>` 造盘，在 QEMU 里从命令壳运行（见 `豫言操作系统/裸机/说明.汉语.md`「构建并运行」）；浏览器在乙级时抽样运行。
- **共同设施**（第一批开工前先做）：测试向量的读取（十六进制、结森、按行的“键 = 值”格式）；模糊测试工具（种子语料、变异、超时与崩溃判定，用子进程隔离）；基准工具（预热、多次取中位数）；各数据生成工具。库放 `库/基础库/测试设施`（包「基础库测试设施」），工具放 `应用/开发工具/`。
- **组织**：`库/基础库/` 是父包「豫言基础库」（「包含在」共用库）；十二个组各是父包「<组>基础库」；每个库一个子包；照 AGENTS.md 在父包「包含包」登记并写「包含在」，测试包登记在上一级父包。版本统一从 0.1.0 起。

### 译名

库名、标识符与文档里的外来名词一律用中文名。起名的原则与诺节、结森的由来见官网[译名](https://yuyan-lang.org/译名/)，要点：

- **短**：两三个字最好，便于组词，如便图解码、合档读取。
- **能猜**：看名字大致知道来历或用途。
- **像专名**：产品与格式的名字用新组合的词。
- **四种办法按术语挑**：音义兼译（结森、诺节）、意造（统算、网页图算）、直译（金属）、沿用通行译名（中央处理器、统一码）。
- **固定语素**（2026-10-07 随用户选定的格式译名一同采用）：格式名用固定的字收尾，表明类别：图（图像格式）、档（归档）、压（压缩）、码（文本记法）、象（对象表示）、列（列式数据）、量（张量）、浮（浮点）。例：便图、捷图、网图；合档、压档；吉压、泽标压；雅码；简象；箭列、羽列；安量；脑浮16。新造格式名先照这些语素。

用法：

- 下面两张表的名字，实施时照用。第一张列出常见 Linux 库在基础库里的对应，第二张是格式与协议的译名。
- 表外的名词，实施者照上述原则自拟。任何译名第一次进代码时，登记进 `库/编译器核心/文档/翻译列表` 的汉语稿与文言稿。用户改名时全树替换（照 2026-09-30 癸象改结森的做法）。
- 版本号、位数与变体字母照原样接在译名后，如循环校验32C、比压2、网页字体2。
- 三类名词照原样写：密码算法与参数（SHA-256、AES-GCM、ChaCha20-Poly1305、X25519、Ed25519、ECDSA、RSA、HMAC、HKDF、ML-KEM 等，它们是各种语言通用的标准标识）；标准编号（RFC 8446、ISO 9660）；文字编码名（UTF-8、UTF-16、Shift_JIS、EUC-KR 等；国标扩展、国标18030、大五码见下表）。
- 以人名命名的算法用通行音译：霍夫曼编码、傅里叶变换、迈尔斯差异、卡拉楚巴乘法、梅森旋转。

## 六、设计：随第一公测版发布

- 发布物：「豫言基础库 0.1.0」，即 `库/基础库/` 下的全部包，加上扩充过的字体与核对过的结森工具。
- 发布门槛：
  - 第一批全部达到完整（乙级），并在裸机（QEMU）上跑通测试；
  - 第二批全部达到完整（乙级），网络类在诺节与原生上验收（第一公测版没有网络）；
  - 第三批全部达到最小可用（甲级）；
  - 公测版其余部分已就绪而门槛未满足时，由用户决定等待还是先发。
- 发布步骤：
  1. 全部包的版本定为 0.1.0，核对进度表；
  2. 公测镜像预置基础库的示例程序（放在 `豫言操作系统/应用/`）：看图（PNG、JPEG、GIF、BMP、WebP、SVG）、解压（zip、tar、gz、zst、xz）、校验和（CRC-32、SHA-256、BLAKE3）、转码（GBK 与 UTF-8 等）、正则搜索、简繁转换；用户态桌面的文件预览能显示图片；
  3. 发行说明列出基础库清单、每个库的级别与已知限制；
  4. 用 `yy批量发布 --发布` 发布到包仓库（发布动作由用户授权）；官网的包页面随部署生成。
- 公开测试版的会话不实施基础库，只在发布时核对门槛，把以上内容收进发行物。

## 七、兼容与迁移

- 不改语言与编译器，只新增库；标准库不依赖基础库（依赖方向不变）。
- 迁移（各在对应的库达到最小可用后做）：
  - 终端浏览器的密码模块 → 「密码」（改用字节表示）；
  - 安全外壳协议里的 Base64 → 「字节编码」；安全外壳密码在原生与裸机上 → 「密码」；
  - 壳核心的拼音数据 → 「中文处理」；
  - 静态站的前言解析 → 「配置格式」；站点地图的 XML 写出 → 「可扩展标记」；
  - 深度学习的 GGUF 解析 → 「张量格式」；BPE 分词与手写的预分词 → 「分词器」与「正则」；伪随机源 → 「随机数」；
  - 深度学习框架的数据读取 → 「数据集」；
  - 本地推理写死的千问对话模板 → 「模板」；
  - 语言服务的 UTF-16 换算 → 「编码转换」；
  - 发布工具对系统 zip、unzip 与 tar 的调用 → 「归档」与「压缩」；
  - 标准库的 HTTP 报文编解保留，新代码改用「超文本传输」。
- 操作系统接口：「压缩」「密码摘要」「口令派生」「文字规整」「网址」「关系数据库」的签名不变；原生与裸机的适配用新库实现；云工与浏览器的适配先保留宿主实现，等纯豫言实现的速度量过再定（未决问题 1）。
- 用户态桌面与本地推理另有会话在改；接第一个使用者时改动从小，合入时变基解决冲突。

## 八、备选方案

- 把 zlib、libpng 等 C 库编成 Wasm 再包一层：违背“不引入第三方库”与“豫言写一切”，裸机上也要另外移植，不采用。
- 只靠宿主能力（浏览器与云端的平台接口、诺节内置模块）：原生与裸机上没有，各后端功能不一致，不采用。
- 等用到再写：已经出现重复实现与手写替代，改为一次盘点、统一规划，实现按批次推进。
- 基础库与 AI 工程栈分成两个提案：用户定为一套，全面覆盖、随公测版一同发布，不采用。

## 九、未决问题

1. 宿主已有同等能力时（Web Crypto、DecompressionStream、`node:crypto`），云工、浏览器与诺节是否继续用宿主实现以求速度（云工的 CPU 时间有限），还是一律改用纯豫言。
2. 根证书库更新的推送方式：随系统更新，还是单独的数据包更新。
3. 公测之后的版本节奏：基础库与操作系统同步发版，还是各自发版。

### 校验（甲级）

- 已做：CRC-32、CRC-32C、CRC-64/XZ、Adler-32、FNV-1a（32 与 64）、MurmurHash3（x86 32 与 x64 128）、SipHash-2-4、XXH32、XXH64、XXH3（64 与 128），各有一次算完与流式两种接口；测试在网页临时算力上（Wasm 与诺节）329 项全部通过，覆盖各算法对「123456789」的标准值、xxHash 官方向量（含空输入与 XXH3 的各长度分支：0、1–3、4–8、9–16、17–128、129–240、240 以上）、SipHash 论文附录向量、分块流式与一次算完相符，以及迁移核对（本库的 32 位 FNV-1a 与「持久盘构造。豫」旧日手写者逐长一致，0 至 128 每个长度各两种子）。
- 组织：库包「校验」只依赖「标准库」（提案 00004 第四节）；测试需要单元测试框架，故另立库包「校验测试」（依赖「标准库」「单元测试」与「校验」），登记在父包「校验与编码基础库」下，测试文件在「校验」包的 `测试/校验。测试。豫`，避免「校验」反向依赖「单元测试」。
- 参考值来源：`xxhsum` 0.8.3 的官方向量与诺节内置 zlib 的核对；常量与默认秘钥照各算法官方实现。
- 流式状态：循环校验、阿德勒32 与福诺沃1a 只保存当前的数值状态，分块喂入与一次算完等价，占用与输入长度无关；低语散列3、啜饮散列2之4、极速散列32/64 与极速散列3 的 `续` 缓冲已喂入的字节，取果时按整体长度收尾（低语散列3 的 32 位按四字节块、128 位按十六字节块；啜饮散列2之4 按八字节块；极速散列32 与 64 按十六字节块；极速散列3 按六十四字节块，并按长度分支收尾）。定长缓冲与超长输入的增量状态见后续版本。
- 出处与许可：CRC 参数目录（Greg Cook，<https://reveng.sourceforge.io/crc-catalogue/>）给出 CRC-32 与 CRC-32C 的多项式与校验值；其来源程序 CRC RevEng 按 GPLv3+ 发布（<https://reveng.sourceforge.io/>），本包按目录给出的参数用豫言实现。CRC-64/XZ 照 xz 规范（<https://tukaani.org/xz/xz-file-format.txt>）；Adler-32 照 zlib（zlib 许可）；FNV-1a 的常量与测试向量照 FNV 官方页（Landon Curt Noll 等置于公有领域）；MurmurHash3 照 Austin Appleby 的参考实现（公有领域，亦可按 MIT 使用）；SipHash-2-4 照论文《SipHash: a fast short-input PRF》与官方参考仓（<https://github.com/veorq/SipHash>，CC0、MIT、Apache-2.0 附 LLVM 例外多许可，本包选择 MIT）；xxHash 0.8.3 为 BSD-2-Clause（<https://github.com/Cyan4973/xxHash>）。
- 原生验收已做：用同源重建的 `yy原生生成.wasm` 与 `yy执行器.wasm` 生成 Mach-O arm64 程序，本机原生 329 项成功、0 失败；诺节与本机原生的完整输出逐字节一致（源码 101a816260aa6c0e2f5bf6fd273a7404a5f912c2）。浏览器与裸机上的验收见后续版本。
- 第一个使用者：`豫言操作系统/裸机/库/裸机后端/持久盘构造。豫`（离线造盘，带 GC 的镜像构造工具包）里的手写 32 位 FNV-1a 换成本库的 `福诺沃1a32初值`、`福诺沃1a32续` 与 `福诺沃1a32取果`，种子仍用原来的 `盘校验初值`，结果照旧截到 32 位；包配置加了直接依赖，双语包说明同步登记，删去了本地的八位异或与常数。盘格式与字节输出不变（算法与种子皆同），`yy造盘` 实测可造出盘。归档校验现由宿主承担（云工用 `DecompressionStream`、诺节用 `node:zlib`），接入本库后可在豫言里算；`豫言操作系统/裸机/客体二号/文件系统。豫` 里的同种校验属底层模式（无垃圾回收）包，待后续在底层父包下另设一份底层实现；`库/界面/文字工具。豫` 的散列按「先加字节再乘」的变体计算，替换会改变 CSS 类名。以上各处的接入情况记在包说明「使用者」一节。

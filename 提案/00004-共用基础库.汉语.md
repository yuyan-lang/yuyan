# 提案 00004：共用基础库

| 项 | 内容 |
| --- | --- |
| 编号 | 00004 |
| 状态 | 草案 |
| 提出 | 2026-10-06 |
| 范围 | 新增一组纯豫言的共用基础库（压缩、图像编解码、统一码与编码转换、正则、密码、证书、安全传输、网络协议、字体整形、数据格式、归档、二维绘图等），放在 `库/` 下按领域分组，供操作系统、浏览器、桌面应用、工具链与云端共用；同类的操作系统接口在原生与裸机上的适配改用这些库实现；不改语言与编译器 |

这是给豫言补齐基础库的提案。常见的 Linux 发行版里，几乎所有程序都间接依赖同一小批基础库（zlib、libpng、libjpeg、ICU、PCRE2、OpenSSL、libcurl 等）。本提案以它们为参照，先盘点豫言缺哪些，再按使用者的急迫程度，用纯豫言逐个写出来；一份实现，在浏览器、诺节、原生与裸机上同源可用。例如图像解码库写一次，浏览器显示网页图片、桌面预览图片、裸机上的看图程序都用它。

本文与[文言稿](00004-共用基础库.文言.md)同步。

## 一、拟定事项

| 编号 | 拟定 |
| --- | --- |
| 议一 | 操作系统、浏览器与应用都会用到的基础能力，做成纯豫言的共用库，放在 `库/` 下按领域分组；一份实现，各平台共用 |
| 议二 | 库只依赖标准库与豫言自己的库：不引入第三方库，也不调用宿主的同类能力（如 DecompressionStream、Web Crypto、`node:crypto`）；与 AGENTS.md「诺节（Node）后端」的硬性要求一致 |
| 议三 | 先盘点再动手：以常见 Linux 发行版的基础库为参照列出缺口（第一版见第四节），按使用者的急迫程度分三批 |
| 议四 | 每个库先做够用的最小集，格式与协议先做最常见的部分；边角情形留“待办事项”注释 |
| 议五 | 正确性靠公开测试向量与对照：密码用 RFC 附录、NIST 与 Wycheproof 的向量，图像用公开测试图集，压缩与系统自带工具互相解压对照，协议用 RFC 样例 |
| 议六 | 性能：先写普通豫言，量过再优化；热点可改底层模式或交原生工具链优化；密码实现常数时间 |
| 议七 | 安全：解码器与解析器面对不可信输入，设长度、解压比、尺寸与递归深度的上限（往大里定），并做模糊测试 |
| 议八 | 现有散落的实现迁入新库：终端浏览器自带的 ChaCha20、Poly1305、HKDF、SHA-256、HMAC，深度学习预分词手写的 Qwen2 正则，包配置语言服务里的 UTF-16 列号换算 |
| 议九 | 已有的同类操作系统接口（「压缩」「密码摘要」「口令派生」「文字规整」「网址」）不改；新代码直接依赖新库；这些接口在原生与裸机上的适配用新库实现 |

## 二、动机

### 同一能力或只在某个宿主上有，或各写一份

2026-10-06 在 yybs（400b5ba35）上检索 `库/`、`应用/`、`豫言操作系统/` 与 `豫言操作系统接口/` 所得：

- `豫言操作系统接口/` 已有「压缩」「密码摘要」「口令派生」「文字规整」「网址」等接口，适配只在云工或浏览器上，都转交宿主的 JS（DecompressionStream、Web Crypto、String 与 RegExp）；原生与裸机上没有实现。
- `库/云工宿主` 的压缩流、密码、编码与持久对象 SQL 都是云端平台的接口；`库/安全外壳/安全外壳密码` 的 SHA-256、X25519、Ed25519、AES-256-GCM 由宿主实现，诺节工具宿主用 `node:crypto`。
- `库/标准库/网络` 的 TCP 是宿主接口，其上有纯豫言的 HTTP/1.1 报文编解，不解分块编码；终端浏览器取网页走宿主的 HTTP(S) 请求接口；各平台都没有纯豫言的 TLS。
- 纯豫言的实现散在各处：终端浏览器有 ChaCha20、Poly1305、HKDF、SHA-256、HMAC，只被它自己的测试使用，其中 SHA-256 与 ChaCha20 用 `0`/`1` 字符串表示比特，很慢；深度学习的预分词因“仓里没有正则引擎”按码点手写 Qwen2 的正则，`\p{L}`、`\p{N}` 只用近似的码段表判断；UTF-16 列号换算在包配置的语言服务里另写一份。
- 发布工具打包时调用系统的 zip、unzip 与 tar（`应用/发布/批量发布/发行材料。豫`）。
- 没有图像解码：终端浏览器的 `<img>` 只显示替代文字，仓里没有 PNG 或 JPEG 解码器。
- 没有通用正则：终端浏览器的 JavaScript 字符串方法还不支持正则（见其包说明）。

### 使用者在等

- 豫言操作系统：看图、解压安装包、校验签名、联网下载。
- 浏览器：图片、正则、HTTPS（现在由宿主代办）、字体整形。
- 桌面应用：图片预览、归档、数据格式。
- 工具链与包管理：压缩、归档、签名校验。

### 与规矩一致

AGENTS.md 已定诺节不引第三方库，各后端靠“只用豫言自己的库”保持功能一致；共用基础库是这条规矩能落地的前提。

## 三、目标与范围

- 目标：第四节缺口清单的第一批库，在浏览器、诺节、原生、裸机上都能用，带测试向量，并各接上第一个使用者。
- 范围内：纯计算的库（编解码、压缩、密码、解析、文字处理、二维光栅化）；与平台无关的协议层（HTTP、TLS、DNS 的报文与状态机，读写经公共接口）；同类操作系统接口在原生与裸机上的适配。
- 范围外（另立目标）：设备驱动与内核里的 TCP/IP 协议栈；音视频编解码；完整的 JavaScript 引擎；与现有 C 库的接口兼容（只求能力，不求同名同参）。

## 五、设计：共同规矩

- **纯豫言、宿主无关**：只依赖标准库与豫言自己的库；输入输出用字节串，文件与网络经公共接口读写；在浏览器、诺节、原生、裸机上同源可用。
- **接口**：对外给“字节串进、结构化结果出”的函数，需要时加流式接口；名称用中文；可恢复的数据问题用结果值返回（照「压缩」接口的状态码惯例），参数违规抛豫言异常。
- **测试**：每个库带公开测试向量与对照测试，并注明来源；解码器与解析器做模糊测试；性能基准与同机的系统工具对照。
- **性能**：先写普通豫言，量过再优化；热点可改底层模式（无回收）或交原生工具链优化；密码的比较与标量乘法要常数时间。
- **上限**：输入长度、解压比、图像尺寸、递归深度都设上限（往大里定），超限明确报错。
- **组织**：在 `库/` 下按领域设父包（例如「媒体」「密码学」「网络协议」「文字」），子包各自独立；照 AGENTS.md 在父包「包含包」登记并写「包含在」。
- **第一个使用者**：每个库合入时至少接上一个真实使用者，例如 PNG 接上桌面的文件预览与浏览器的 `<img>`。

## 六、兼容与迁移

- 不改语言与编译器，只新增库。
- 迁移：终端浏览器的密码模块迁入「密码」并改用字节表示；深度学习的预分词改用「正则」与「统一码」；语言服务的 UTF-16 换算改用「编码转换」；发布工具的打包改用「归档」与「压缩」。
- 操作系统接口：「压缩」「密码摘要」「口令派生」「文字规整」「网址」的签名不变；原生与裸机的适配用新库实现；云工与浏览器的适配先保留宿主实现，等纯豫言实现的速度量过再定（见未决问题 1）。
- 安全外壳密码：原生与裸机上改由「密码」实现；诺节与云工是否也改用「密码」，随未决问题 1 一起定。

## 七、备选方案

- 把 zlib、libpng 等 C 库编成 Wasm 再包一层：违背“不引入第三方库”与“豫言写一切”，裸机上也要另外移植，不采用。
- 只靠宿主能力（浏览器与云端的平台接口、诺节内置模块）：原生与裸机上没有，各后端功能不一致，不采用。
- 等用到再写：已经出现重复实现与手写替代（终端浏览器的密码、预分词的正则），所以改为先盘点、统一规划，但实现仍按使用者的急迫程度分批。

## 八、未决问题

1. 宿主已有同等能力时（Web Crypto、DecompressionStream、`node:crypto`），云工、浏览器与诺节是否继续用宿主实现以求速度（云工的 CPU 时间有限），还是一律改用纯豫言。
2. TLS 只做 1.3，还是兼做 1.2 以兼容旧站点。
3. 根证书库从哪里来、怎么更新（例如随发行带一份 Mozilla 的根证书，许可与更新流程）。
4. 正则的语法：兼容 ECMAScript（浏览器的 JavaScript 需要），还是取 RE2 或 PCRE 的子集；反向引用这类需要回溯的特性要不要。
5. 父包的分组与包名。
6. 性能目标，例如解压比系统 gzip 慢多少以内可以接受。

## 九、实施步骤

1. **盘点**：在第四节的基础上逐项复核仓库现状（含各宿主接口与适配里已有的能力），补全清单与使用者，写回本提案，定下第一批。
2. **第一批**：压缩（DEFLATE、zlib、gzip）→ 图像编解码（PNG，依赖压缩；再 JPEG、GIF、BMP）→ 统一码与编码转换 → 正则 → 密码（迁入现有实现并补齐）。
3. **第二批**：证书与 TLS 1.3 客户端、HTTP/1.1 客户端与 URL、DNS 报文、归档、XML、二维绘图与 SVG 子集、字体整形。
4. **第三批**：嵌入数据库、时间与时区。
5. 每个库：先写最小集与测试向量，在诺节与原生上验证，再在裸机上验证；接上第一个使用者后合入。
6. 由一个代理负责到底，可派子代理分库并行，各用自己的工作树；每完成一个库，在本提案末尾的进度表登记。

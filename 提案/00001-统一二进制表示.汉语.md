# 提案 00001：统一二进制表示

| 项 | 内容 |
| --- | --- |
| 编号 | 00001 |
| 状态 | 草案 |
| 提出 | 2026-10-03 |
| 范围 | 编译器核心的中间产物缓存；云端存放的签名与最终链接所需的产物 |

这是豫言语法树统一二进制表示（下称“树码”）的提案：编译器各阶段的「表达式树组」用同一种紧凑、规范的二进制编码存取，取代现在的 JSON 缓存，并作为云端存放签名与链接单元的格式。

本文与[文言稿](00001-统一二进制表示.文言.md)同步。

## 一、拟定事项

| 编号 | 拟定 |
| --- | --- |
| 议一 | 格式名为「树码」，文件扩展名 `.树码`，开头六字节是“树码”二字的 UTF-8：`E6 A0 91 E7 A0 81` |
| 议二 | 一种格式覆盖全部阶段：凡「表达式树组」（即「文件定义列」）都用它；另设「串列」一种，供依赖表等字符串列表缓存 |
| 议三 | 结构由结构表给出：「节点名称」与各嵌套枚举的构造器按表中次序编号，表的摘要写进文件头；摘要不符的文件按缓存未命中处理 |
| 议四 | 字符串只存一次：定义名、字符串载荷、自由变量名、绑定的名字提示都进串表，正文只写串号 |
| 议五 | 文件路径进路径表，记成所有者、包名、包内路径三段，正文只写径号 |
| 议六 | 规范形式：同样的树组配同样的结构表，总编成同样的字节，摘要可直接用于去重与签名 |
| 议七 | 第一版不做子式共享，标签 4 保留给它；测量后再决定是否进入第二版 |
| 议八 | 先作为可选格式接入编译器缓存，验收通过后改为默认，同时把「导出中间文本」改为默认关闭，`。豫` 文本只在调试时写 |
| 议九 | 绑定的名字提示按“前缀加末尾十进制序号”拆开写：前缀进串表，序号写在正文。编译器生成的名示大多是“常量内联参数值58”这类带序号的名字，拆开后同一前缀只存一次 |

## 二、动机

以下数据于 2026-10-03 在本机测得。

1. **缓存太大**。本机 `.yybuild` 合计 325 GB，共 163 个缓存目录；`yy4_bs` 编译器的缓存目录有 22 GB，涉及 3916 个源文件。「导出中间文本」默认打开，每个阶段除 JSON 外还另写一份 `。豫` 文本：这个目录里 JSON 占 14.3 GiB，`。豫` 占 7.5 GiB。
2. **冗余在结构上**。中间产物是逐层展开的 JSON 树，每个结点都重写一遍键与名，例如 `{"类型":"式节点","节点名称":{"名称":"拉姆达抽象","参式":"显式"},"参数":[…]}`。抽 200 个「闭包形式」文件，原文 31.8 MB，`gzip -9` 之后 0.77 MB，约为四十一分之一。
3. **读写都慢**。读缓存要先把整个 JSON 文字解析成「结森」值，再转成表达式：9 MB 的「闭包形式」要读 484 毫秒，其中解析占 74%；写同一个文件，JSON 编码要 1.72 秒。二进制可以一遍直接建出表达式，见第十节的对比。
4. **云端要用**。按《重建豫言云开发平台》的新方向，构建只在接入的计算机上跑，云上只放每个文件的「签名元数」（一次编译器构建共 36.4 MiB）与最终链接的输入「闭包形式」（JSON 共 582.2 MiB）。体积直接决定上传占用的带宽。
5. **摘要要稳定**。内容寻址、去重与构建签名都要求同样的内容得出同样的字节；现在的产物还带着本机绝对路径（如 `豫言模块__Users_zc_…`），两台机器上得出的字节不同。

## 三、目标与范围

目标：

1. 压缩前，「闭包形式」的树码小于同内容 JSON 的十分之一。
2. 读取比 JSON 快，写入不慢于 JSON。
3. 编码规范：同样的输入总得同样的字节。
4. 与路径无关：同一个包在两台机器上编出的树码相同（以第七节所述的编译器改动为前提）。
5. 一个编解码器覆盖全部阶段；新增节点名称时，只需改结构表与对应的载荷编码。

范围：编译器核心缓存里的「表达式树组」与「串列」；云端存放的签名元数与链接单元。

暂不涉及：给人读的写法（仍用 `。豫` 文本，调试时生成）；传输压缩（交给 HTTP）；原地修改与随机写；Wasm 产物本身（它已是二进制）。

## 四、数据模型

树码表示的值就是编译器里的这些类型，定义见 `库/编译器核心/编译数据/抽象绑定树结构/抽象语法树/抽象语法树数据。豫`：

```yuyan
「表达式」立「元类型」也。
  「式节点」立化「节点名称」而化（「列」于「表达式」）而「表达式」也。
  「绑定」立化（「或可有」于「字符串」）而化「表达式」而「表达式」也。
  「绑定变量」立化「整数」而「表达式」也。
  「自由变量」立化「字符串」而「表达式」也。

「文件定义列」即「列」于（「字符串」合「爻」合「表达式」）也。
「表达式树组」即「文件定义列」也。
```

- 「式节点」是带名字的结点，名字是「节点名称」的 93 个构造器之一，各带自己的载荷。
- 「绑定」引入一个变量，名字只作提示；「绑定变量」用 de Bruijn 序数指向外层的绑定。
- 「自由变量」以名字引用。
- 一个树组是若干定义，每个定义有名字、公开性与内容，定义的先后有意义。

载荷里出现的类型：整数（64 位有符号）、小数（64 位浮点）、字符串、爻、列、或可有、元组，以及五个嵌套枚举——「参数形式」5 个构造器、「内建常量」17 个、「结构名称操作」7 个、「定义透明性」2 个、「注释方向」2 个。「源码范围」是（文件，开始行，开始列，结束行，结束列）。

## 五、编码

### 5.1 基本单位

| 写法 | 编码 |
| --- | --- |
| 无符号整数 | LEB128，取最短写法 |
| 有符号整数 | 有符号 LEB128（与 Wasm 相同），取最短写法 |
| 小数 | 8 字节小端 IEEE 754；NaN 一律写成 `7FF8000000000000` |
| 爻 | 1 字节，阴为 0，阳为 1 |
| 串号、径号、个数、序数 | 无符号整数 |

LEB128 的编码沿用 `库/编译器核心/网页汇编核心/二进制生成。豫` 的「网页无符号编码」「网页有符号编码」，解码用同目录的二进制读取模块。

### 5.2 文件布局

```text
文件       = 魔数 版本 种类 结构表摘要 串表 路径表 内容
魔数       = E6 A0 91 E7 A0 81
版本       = 无符号整数，本提案为 1
种类       = 字节长 UTF-8字节，如“闭包形式”“签名元数”“串列”
结构表摘要 = 32 字节 SHA-256
串表       = 个数 { 字节长 UTF-8字节 }
路径表     = 个数 { 路径条目 }
内容       = 树组内容 | 串列内容
树组内容   = 定义个数 { 名串号 公开 体字节长 体 }
串列内容   = 个数 { 串号 }
```

- 每个定义记下体的字节长，读者可以跳过用不到的定义，也能并行解码。
- 种类沿用现在缓存的信息名（「闭包形式」「签名元数」等），文件名为 `<源文件路径>.<信息名>.树码`。

### 5.3 表达式

表达式按先序写出，每个结点以一个标签（无符号整数）开头：

| 标签 | 含义 | 其后 |
| --- | --- | --- |
| 0 | 自由变量 | 串号 |
| 1 | 绑定变量 | 序数 |
| 2 | 绑定，无名字提示 | 体 |
| 3 | 绑定，有名字提示 | 前缀串号、序号加一、体 |
| 4 | 保留给子式共享（第一版不用） | — |
| 5 起 | 式节点，节点名称的构造号为标签减 5 | 载荷、子式个数、各子式 |

93 个节点名称的标签都在 5 至 97 之间，各占一个字节。

名字提示的拆号：提示末尾若是十进制数（恰为 0，或不以 0 开头），就把它与前缀分开，前缀进串表，正文写序号加一；其余提示整串进串表，正文写 0。例如“常量内联参数值58”写成“常量内联参数值”的串号与 59。

### 5.4 载荷

每个构造器的载荷字段按结构表依次写出：

| 字段类型 | 编码 |
| --- | --- |
| 整 | 有符号整数 |
| 小 | 小数 |
| 串 | 串号 |
| 径 | 径号（见 5.6） |
| 爻 | 爻 |
| 列于 T | 个数，再依次写各项 |
| 可 T | 0 表示无；1 表示有，其后写值 |
| 组〔T…〕 | 各项依次写出 |
| 枚举名 | 该枚举的构造号，再写该构造器的载荷 |

例如「源码范围」是 组〔径，整，整，整，整〕；「小数节点」的载荷是 小 加 组〔串，串〕（十进制的两段写法）。

### 5.5 串表

- 所有字符串都进串表，正文只写串号：定义名、字符串载荷、自由变量名、绑定的名字提示（带序号的只存前缀），以及路径的三段。
- 编码器的串表要用散列表。标准库的「串典」按列表线性查找，一个文件里有三万多个不同的串时，编码会退化成平方时间。
- 编号按首次引用的先后：先第一个定义的名字，再第一个定义的体（先序），然后第二个定义，依此类推。

### 5.6 路径表

结构表里标为 径 的字段是文件路径，例如「文件引用节点」「文件定义引用节点」「唯一构造器节点」等结点里的路径，以及「源码范围」的文件；完整清单以结构表为准。它们进路径表：

```text
路径条目 = 0 所有者串号 包名串号 包内路径串号
         | 1 绝对路径串号
```

- 编码时按包上下文把绝对路径换成所有者、包名与包内路径；读取时再按本机的包上下文换回绝对路径。
- 找不到所属包的路径写成第二种形式。这样的文件离开本机就恢复不出原路径，构建清单要把它标为“与本机有关”。
- 径号按首次引用的先后编号，路径的三段串随之依次进串表。

### 5.7 规范形式

同样的树组配同样的结构表，只有一种字节：

1. 定义保持原有顺序。
2. 串号与径号按 5.5、5.6 的首次引用次序编号。
3. 整数取最短写法；NaN 只有一种位型；负零照原样保留。
4. 名字提示按 5.3 的规则拆号，能拆的一律拆。
5. 第一版没有任何可选项：不压缩、不共享、不对齐。

文件的摘要就是整个文件字节的 SHA-256，可以直接作内容地址。

### 5.8 例子（示意）

设「拉姆达抽象」的构造号为 0，「显式」为「参数形式」的构造号 1；下面的表达式是定义「恒同」的体，「恒同」占串号 0。

```text
式节点（拉姆达抽象（显式），【绑定（可有『甲』，绑定变量 0）】）
```

它在 JSON 里是 147 字节：

```json
{"类型":"式节点","节点名称":{"名称":"拉姆达抽象","参式":"显式"},"参数":[{"类型":"绑定","可能名":"甲","绑定体":0}]}
```

在树码正文里是 8 字节：

```text
05        式节点，构造号 0（拉姆达抽象）
01        载荷：参数形式的构造号 1（显式）
01        子式个数 1
03        绑定，有名字提示
01        前缀串号 1（『甲』）
00        没有序号
01        绑定变量
00        序数 0
```

另加串表里『甲』的 4 字节（字节长 `03`，加 `E7 94 B2`）；以后各处再出现『甲』，都只写一个串号。

## 六、结构表与版本

- 结构表列出「节点名称」及各嵌套枚举的构造器，每个构造器写名字与载荷字段类型，例如：

```text
节点名称 拉姆达抽象 参数形式
节点名称 字符串节点 串
节点名称 文件定义引用节点 径 串 整
参数形式 多参数形 整
```

- 构造号就是构造器在所属枚举中的次序，从 0 起。
- 规范文本：每行写“枚举名 构造器名 字段类型…”，行与行以换行分隔，枚举按固定次序排列；摘要是这段文本的 UTF-8 字节的 SHA-256。
- 结构表写成豫言数据，与编解码器放在同一目录：`库/编译器核心/编译数据/抽象绑定树结构/抽象语法树/序列化/树码结构表。豫`。豫言没有反射，载荷的编码与解码按构造器逐个手写，与现有的 JSON 序列化同一做法；测试逐个构造器做往返，核对结构表与编解码器一致。
- 摘要在构建时求出并写成常量（构建宿主已有「获取文件SHA256」），测试核对它与规范文本的摘要相同。
- 增删或调换构造器都会改变摘要。编译器读到摘要不同的缓存文件，按未命中处理并重建；工具可以按摘要从内容库取回当时的结构表，再解码旧文件。
- 版本号只在编码规则本身改变时加一，例如加入子式共享。

## 七、路径无关

路径表处理了结构化字段里的路径，但还有两处会把本机路径带进产物：

1. 模块名由绝对路径转义生成：`库/编译器核心/编译步骤/总体过程/编译过程工具。豫` 里的 `『豫言模块_』附（「标识符转义」于「路径」）` 得出 `豫言模块__Users_zc_repos_…` 这样的名字，散在各处字符串载荷里。
2. 「源码范围」的文件。

第一处要改编译器：模块名改由所有者、包名与包内路径生成。这是一项独立的改动，树码不依赖它也能用，只是在它完成以前，不同机器编出的树码字节不同。第二处走路径表。

## 八、接入编译器缓存

1. 编解码器放进编译器核心的序列化目录，分「树码编码」「树码解码」「树码结构表」三个模块。
2. 新增编译选项 `--中间格式 结森|树码`，先默认 `结森`。
3. `库/编译器核心/编译步骤/总体过程/编译文件缓存工具。豫`：
    - 「写树组缓存」按选项写 `.树码` 或 `.json`；`。豫` 文本照旧由「导出中间文本」控制。
    - 「读树组缓存」先找 `.树码`，没有再读 `.json`；按开头的魔数判断格式。
    - 「读串列缓存」「写串列缓存」与文件依赖的读写改用「串列」一种。
4. 文件读写用标准库 `操作系统/文件系统` 的「读文件字节串」「写文件字节串」。
5. 验收通过后把默认改为 `树码`，「导出中间文本」改为默认关闭；JSON 的读取保留给调试工具。

## 九、工具

新增开发工具 `yy树码`，放在 `应用/开发工具/树码/`，用豫言编写：

- `转换 <文件>`：在 `.json`、`.树码` 与 `。豫` 三种写法之间互转。
- `统计 <缓存目录>`：按阶段列出文件数、JSON 与树码的字节数及其比值。
- `核对 <缓存目录>`：对每个文件做“JSON → 树码 → 表达式”往返，与直接解析 JSON 的结果逐棵比较。

## 十、三种写法的对比

按 2026-10-03 在本机的测量：读取时 JSON 的大头是解析，`。豫` 源码重解析比读 JSON 慢约三十倍；树码估计读取快 1.1 到 4.6 倍、写入快 1.3 到 25 倍，文件越大差得越多；整套缓存约为 JSON 的十二分之一，连同默认写出的 `。豫` 在内，从 21.7 GiB 降到约 1.2 GiB。

### 10.1 测量方法

- 样本取自本机 `yy4_bs` 编译器的缓存目录，共四个文件：「多态列」的签名元数与词法形式、「表达式解析」的闭包形式、「客体执行用例」的闭包形式（9 MB，作大样本）。
- JSON 与 `。豫` 的读写：用「阶段源码性能」测量程序（`库/编译器核心/编译步骤/总体过程/阶段源码性能。豫`，本提案在其中补上读文件、JSON 解析、树组还原三项计时）。每个样本跑三次，各项取最小值；十二次都精确往返通过。
- 树码的体积：按第五节的规则把文件逐个编成树码，只量字节数；另量“名示拆号”（见 5.3）与“子式共享”（标签 4）两种做法。全缓存按阶段各抽 40 个文件，以抽样所得的比例推算。
- 树码的耗时：还没有实现，按两条保守的假设估计。读取 ≈ 读文件 × 字节比 ＋ 树组还原：解码树码与“由结森值还原树组”要建同样多的结点，还省去按键名逐个比较。写入 ≈ 源码编码 ＋ 写入 × 字节比：两者都是一遍走树、逐段输出。

### 10.2 体积

单位为字节。“树码”是第五节不拆号、不共享的写法。

| 样本 | JSON | `。豫` | 树码 | 树码·拆号 | 树码·拆号加共享 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 签名元数 | 11,803 | 3,904 | 712 | 712 | 712 |
| 词法形式 | 192,064 | 23,092 | 39,042 | 39,042 | 39,042 |
| 表达式解析·闭包形式 | 430,839 | 297,536 | 69,793 | 59,469 | 58,656 |
| 客体执行用例·闭包形式 | 9,238,892 | 5,068,072 | 1,250,549 | 433,517 | 314,492 |

`gzip -9` 之后，单位为字节：

| 样本 | JSON | `。豫` | 树码·拆号 |
| --- | ---: | ---: | ---: |
| 签名元数 | 439 | 436 | 319 |
| 词法形式 | 13,684 | 6,281 | 8,806 |
| 表达式解析·闭包形式 | 17,950 | 18,764 | 12,317 |
| 客体执行用例·闭包形式 | 159,205 | 214,955 | 85,621 |

- 树码的字节大多在串表。大样本的 125 万字节里串表占 84 万，其中 80 万是 31,332 个互不相同的绑定名示（如“常量内联参数值58”），正文只有 41 万；拆号以后降到 43 万，约为 JSON 的二十一分之一。这是议九的由来。
- 词法形式的 `。豫` 最小：它只存源码，令牌在读取时由词法器重算；树码与 JSON 一样存下了「令牌」这一项。
- 压缩以后差距缩小：树码（拆号）比同样压缩后的 JSON 小 1.4 到 1.9 倍，传输时仍值得再套一层 HTTP 压缩。

### 10.3 读取耗时

单位为毫秒。

| 样本 | JSON 读文件 | JSON 解析 | 树组还原 | JSON 合计 | `。豫` 解析 | 树码（估计） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 签名元数 | 0.32 | 2.34 | 18.36 | 21.0 | 25.2 | 18.4 |
| 词法形式 | 0.71 | 8.87 | 22.71 | 32.3 | 3.1 | 22.9 |
| 表达式解析·闭包形式 | 1.23 | 16.03 | 27.40 | 44.7 | 247.0 | 27.6 |
| 客体执行用例·闭包形式 | 20.60 | 358.80 | 104.33 | 483.7 | 14,540.6 | 105.3 |

- 读 JSON 时解析占大头：大样本的 484 毫秒里，解析占 359 毫秒（74%）。
- `。豫` 重解析比读 JSON 慢约三十倍（14.5 秒对 0.48 秒），适合给人看，不适合作缓存的读取路径；词法形式例外，它读的只是源码。
- 树码的读取估计为大样本 JSON 的 1/4.6。小文件受“树组还原”约 18 毫秒的固定开销所限，12 KB 的签名元数也要 18 毫秒；这像是进程内第一次调用时的准备工作，在常驻的编译进程里只付一次，有待核实。
- 按大小折算（以两个闭包形式样本拟合）：读 JSON 约为 23 毫秒加每 MB 50 毫秒，读树码估计约为 24 毫秒加每 MB 9 毫秒。

### 10.4 写入耗时

单位为毫秒。

| 样本 | JSON 编码 | `。豫` 编码 | `。豫` 写入 | 树码（估计） |
| --- | ---: | ---: | ---: | ---: |
| 签名元数 | 5.48 | 4.13 | 0.42 | 4.2 |
| 词法形式 | 19.68 | 0.14 | 0.51 | 未估 |
| 表达式解析·闭包形式 | 35.01 | 14.26 | 0.91 | 14.4 |
| 客体执行用例·闭包形式 | 1,716.31 | 69.20 | 8.20 | 69.9 |

- JSON 编码是写缓存的瓶颈：大样本 1.72 秒，是源码编码的 25 倍，而且文件越大每 MB 越慢（中样本每 MB 81 毫秒，大样本每 MB 186 毫秒）。
- 词法形式的 `。豫` 只写源码，树码还要写令牌，所以没有拿源码编码来估它。

## 十一、测量与验收

样本：本机 `yy4_bs` 编译器构建的缓存目录（22 GB），以及其中 200 个「闭包形式」文件。

| 验收项 | 标准 |
| --- | --- |
| 往返 | 全部阶段的全部文件，经树码往返后与原树结构相等 |
| 体积 | 「闭包形式」压缩前小于 JSON 的十分之一；另报树码与 JSON 各自 gzip 后的大小 |
| 速度 | 一次完整编译器构建里读缓存的总耗时少于 JSON；写入不慢于 JSON |
| 规范 | 同一树组编两次得同样的字节；路径无关的改动完成后，两台机器得同样的字节 |
| 自举 | 用 `--中间格式 树码` 跑完整自举，`yy3_bs.wasm` 与 `yy4_bs.wasm` 逐字节相同 |

## 十二、兼容与迁移

- 缓存目录按编译器的路径与修改时间区分，新旧编译器各用各的缓存，稳定编译器读不到新格式的文件。
- 读取按魔数识别格式，同一目录里新旧格式可以并存。
- 摘要不符按未命中处理，最坏的情形只是多一次重建。
- 云端只收树码；接入的计算机在上传前转换。

## 十三、备选方案

| 方案 | 为何不选 |
| --- | --- |
| 压缩 JSON（gzip、zstd、brotli） | 体积能降约四十倍，但读取仍要解析整个 JSON，字符串也无法共用一份；它适合放在传输层，与树码叠用 |
| 通用二进制格式（CBOR、MessagePack） | 仍要逐个写键名，或另配结构说明；对绑定与 de Bruijn 序数也没有专门的写法 |
| Protocol Buffers 一类 | 需要外部工具与另一种结构描述语言，与“只写豫言、不自造 DSL”的约定不合 |
| 只留 `。豫` 文本 | 人能读，但体积大、解析慢 |

## 十四、未决问题

1. 子式共享：同一定义内重复出现的子树写成回指（标签 4）。按第十节的实测，拆号之后再加共享，全缓存只再省一成多（1,243 MiB 降到 1,100 MiB），但「检查后定义」「检查后对象」能省一半以上；第二版是否只在这两个阶段开启，待定。
2. 源码范围要不要另起一段，让剥掉位置信息的树码在只改注释、空行之后仍然相同，便于跨提交去重。
3. 结构表的规范文本格式与存放位置是否合适，摘要是否也要覆盖编码版本。
4. 小数的负零要不要规范成正零。
5. 格式名「树码」与扩展名 `.树码` 是否合适。

## 十五、实施步骤

1. 结构表与编解码器（含名示拆号与散列串表），加逐构造器的往返测试（编译器核心的单元测试）。
2. `yy树码` 的转换、统计与核对，在 `yy4_bs` 的缓存上跑出体积与往返结果。
3. 接入缓存读写与编译选项，跑完整自举。
4. 测读写耗时，达标后改默认格式，并把「导出中间文本」改为默认关闭。
5. 把模块名改为与路径无关（独立改动），之后验证两台机器得同样的字节。
6. 按测量结果决定子式共享。

## 一、拟定事项

| 编号 | 拟定 |
| --- | --- |
| 议一 | **一种运行机制**：运行豫言代码一律是“在某个封里装入单元，调用入口”。壳里的一句、`豫构 运行` 的脚本、`。豫行` 程序、桌面程序与各工具都经同一个装入器 |
| 议二 | **单元是唯一的代码形式**：库与程序都是装载单元（提案 00003 的格式），程序是“入口单元加依赖闭包”的清单。整程序静态链接改作“合成单元”：把单元闭包连同跨模块优化（提案 00007）预先合成一个大单元，仍由同一个装入器装入 |
| 议三 | **封（隔离域）**：一个封有自己的堆、导入表与身份，可以单独计量处理器与内存，也可以单独削去。壳会话是一个封，每句的单元装进会话的封；`运行` 一个程序就分封一个新封。封之间不共享对象，只经消息传数据 |
| 议四 | **节（能力）**：单元只能调用它导入的东西，导入接到哪里由封决定。程序的清单写明所需之节，由父方在分封时授予；所需之节没有授予，装入时就链接失败，不留到运行时。沙箱由此而来 |
| 议五 | **两种封**：任务封是独立的进程或任务，靠硬件隔离，就是现在的程序；同进程封在同一进程里各用一个堆，靠类型安全隔离，只收普通带 GC 豫言的单元。底层（无 GC）单元只能进任务封 |
| 议六 | **代码共享**：单元按内容缓存、只读映射，同一单元在各封、各任务之间共用物理页。提案 00015 议四“只读段共享”与提案 00003 议十五“系统程序改用动态链接”都由这一条落实 |
| 议七 | **语义不变**：同一程序不论在任务封还是同进程封，不论合成一个单元还是逐单元装入，接受与拒绝的程序相同，输出相同（沿用提案 00003 议一） |
| 议八 | **分三步实施**：先一套装入器（任务封、代码共享），再做节，最后做同进程封；第一步不改用户看得到的行为 |

## 二、动机

### 现在是两套

| | 编译执行（提案 00007、00005） | 脚本运行（提案 00003） |
| --- | --- | --- |
| 代码形式 | 整程序静态链接的豫行或本机程序 | 每个模块一个装载单元 |
| 由谁装入 | 内核、豫行启动器或宿主 | 执行器的单元装载原语，加豫构的名字解析 |
| 何时链接 | 构建时 | 装入时 |
| 隔离 | 独立的进程或任务 | 并进主程序的实例 0，共用一个 GC 堆 |
| 代码共享 | 没有（00015 议四未实施） | 同一进程里同一模块只装一次 |

两套各有一个装入器、一种链接方式与一份代码缓存，而且装入方式和隔离方式捆死了：动态装入就一定同堆，要隔离就一定是整块的静态程序。两套都管不了程序能做什么。

### 由此而来的毛病

- **工具都是整块的**：豫构 91 MB、开发 35 MB、吉特 24 MB，各自静态带一份豫章与运行时；同时开几个，代码也不共享。
- **用分进程换小前导**：为了不让会话的前导变大，正则、差异、解压这些大库只能放进独立程序「开发」，壳的「寻」「易」每次都要起一个进程。不装进会话和分进程本是两件事，现在只能一起要。
- **可靠性随运行方式而变**：同一段代码在壳里跑和作为程序跑不一样。壳里的一句死循环会卡住整个会话，只能按 Ctrl+C；作为程序跑则可以单独杀掉。
- **没有能力控制**：任何程序都能读写全部文件、上网。代理在壳里干活以后（提案 00036、AGENTS.md“本机操作用豫言壳”），这一条更要紧。

### 前例

- **Erlang/BEAM**：整个节点只有一套代码装入，“进程”是各自独立的小堆；启动程序就是在新进程里调某模块的函数。
- **Singularity**：所有进程同在一个地址空间，靠类型安全与验证隔离（软件隔离进程），进程之间只经通道传消息。
- **Wasm 组件模型**：导入即能力，宿主决定给实例接什么，实例各自隔离。豫言的执行边界豫汇与 Wasm 一一对应，执行器本来就按导入导出链接单元。
- **PIE**：位置无关的可执行文件就是“带入口的共享库”，可执行文件与库早已合流。

## 三、目标与范围

目标：

- 一个装入器，宿主、启动器与豫言操作系统共用；
- 单元是唯一的代码形式，程序是清单；
- 隔离（封）与装入分开，成为两件可以分别选择的事；
- 能力（节）经导入表授予，在装入时检查；
- 同一单元的代码在各封、各任务之间共享。

不在范围：

- 林纳兼容程序：提案 00012 有自己的受限模式；
- 宿主本机程序（vim、git 等）：用户 2026-10-16 定壳里不运行；
- 跨机器执行：由提案 00035 的将作负责。

## 四、设计

### 4.1 单元、清单与合成单元

- **单元**：沿用提案 00003 的格式，即豫行段表加豫汇模块、机器码、重定位、符号表四种段，再补一个“模块接口”段（00003 第一版用编译缓存里检查后的定义代替）。单元按内容摘要命名。
- **清单**：写明入口单元、依赖闭包里各单元的摘要、所需之节，以及可选的合成单元摘要。`。豫行` 文件改为“文件头加清单加若干单元”：单元可以全嵌在文件里，单文件发行照旧；也可以只写摘要，从单元仓库取。
- **合成单元**：现在的最终链接流程照旧做跨模块优化，只是产物改为一个合成单元。豫构自己、开机程序这类常驻的大程序用合成单元。旧的静态豫行当作“只有一个合成单元的清单”，照常能跑。
- **单元仓库**：宿主上就是共享构建缓存（提案 00034）。豫言操作系统的盘上放 `/单元/`，按摘要存，造盘时随盘带上；工具与桌面程序只放清单。

### 4.2 封

- 一个封有：堆、导入表（所授之节）、身份（封号、名字）与限额（内存、处理器份额）。
- **会话**：壳会话是一个封，每句编成的单元装进会话的封，这就是今天的行为。
- **运行程序**：分封一个新封，按清单装入单元，调入口。程序退出或被削去时，封的堆整块归还。
- **封之间**：不共享对象，经消息传数据（籍册行或帛），复用现有的子任务消息与壳请求（`库/几席/壳索。豫`）。
- **任务封**：一个封就是一个进程或任务，代码页从单元仓库只读映射，各任务共享。现在的程序都是任务封。
- **同进程封**（第三步）：同一进程里有多个封，各有自己的堆、全局与役，共用代码。只收普通带 GC 豫言的单元，靠类型安全隔离；分封和跑一句话一样便宜。

### 4.3 节与清单

- **节**：一组可以导入的模块。例如案牍节（文件）、驿节（网络）、使者节（起子进程）、显示节（窗口与画面）、全节（今天的程序都相当于全节）。第一版按模块授予，按函数授予以后再说。
- **授予与检查**：清单写明所需之节，父方分封时授予其中一部分。单元导入了未授之节里的模块，装入时报“未授予某节”，程序不运行。
- **节不能伪造**：普通豫言里，函数与对象的引用只能来自导入，或者别人传进来的值，这是对象能力的做法，与 Wasm 相同。底层单元能伪造指针，所以只进任务封，它的节在系统调用边界上由内核或启动器的服务门检查。
- **默认值**：壳会话默认全节。捉刀（提案 00036）这类代理会话可以按节收窄，例如只授案牍节。

### 4.4 一个装入器

- **两层**：装入照提案 00003 分两层。执行器的原语管单元内部：映射机器码、填重定位、规范化类型、追加各表。豫言写的装入库管跨单元的名字解析与节的检查。
- **起程序**：内核与豫行启动器起一个程序，就是建任务、映射装入器，再由装入器按清单映射单元、调入口。原来只认静态豫行的装载路径（提案 00005）收进这一条。
- **宿主后端**：林纳与轩窗宿主上，原生单元装不进本进程，照旧编成网页汇编单元。这是装入器的一个后端，不另成一套。

### 4.5 同进程封（第三步）

- **执行器**：一个进程里有多个 GC 堆，各有根集，各自回收。一个封一个实例，实例之间共用代码与类型表，各有全局。役按封调度；削封就是取消该封的役，整块丢掉它的堆。
- **陷阱**：栈溢出、除零、越界这类陷阱要归到出事的封，只收拾这一封。暂时做不到细分的，就让陷阱所在的封整体失败，不波及会话。
- **收益**：在壳里起一个程序，启动耗时和跑一句话同一量级；程序坏了只丢它自己的封。

### 4.6 拟名

| 通称 | 雅名 | 由来 |
| --- | --- | --- |
| 隔离域 | 封 | 《左传·僖公二十四年》“封建亲戚以蕃屏周”：分土而治，各守其疆，受命于上 |
| 新建隔离域 | 分封 | 同上，分土建国 |
| 销毁隔离域 | 削封 | 《史记·吴王濞列传》“今削之亦反，不削之亦反”：削去封地 |
| 能力 | 节 | 《周礼·地官·掌节》“掌守邦节而辨其用，以辅王命”：持节者凭节行事 |
| 授予、收回能力 | 授节、收节 | 合成词，古书无成例 |

节与将作的虎符、合符同属“以符节喻凭证”一族。仓里目前没有「封」「节」「分封」「削封」「授节」「收节」这几个顶层名或局部名。

## 五、兼容与迁移

- **第一步对用户不可见**：旧的静态豫行当作单一合成单元的清单照常运行；CI 自举里的旧工具链照常能编新源码。
- **ABI 新增**：豫行格式加清单段与单元引用，内核加“映射共享只读单元段”的服务。两项都是豫言内核 ABI 的新增（提案 00021 议八），编号只增不改。
- **造盘**：改为随盘带单元仓库与清单。各工具不再各带一份豫章，盘应当变小。

## 六、备选方案

1. **维持两套**：不取。两个装入器、两种链接，也没有能力控制。
2. **只有同进程封**：不取。底层代码与宿主本机代码需要硬件隔离；所有程序挤在一个进程里，堆与故障都难分开。
3. **只有任务封（壳的每句也起子任务）**：不取。每句一个任务太慢，会话里的定义也没法共享。
4. **用宿主的动态库（dylib、so、dll）作单元**：不取。各宿主格式不同，又绕开了豫汇边界，与提案 00021“豫言内核 ABI 是原生二进制边界”相悖。

## 七、未决问题

1. 节的粒度：先按模块，以后要不要按函数或对象授予。
2. 同进程封里，哪些陷阱能可靠地只收拾出事的那一封。
3. 封之间传值：只传数据，还是也允许移交 GC 对象（转移所有权）。
4. 单元仓库的回收（提案 00034 暂不回收）。
5. 豫构自己是否也拆成单元，按需装入编译器的大部分（提案 00003 议十五“开机程序变小”）。
6. 宿主上的任务封用宿主进程，还是启动器里的轻任务。

## 八、实施步骤

1. **一套装入器**：豫行改为清单加单元，合成单元兼容旧程序；内核、启动器与豫构经同一个装入器装入；单元的只读页在任务之间共享。验收：
   - 造盘的开机程序与工具改用清单；
   - 同时开十个编辑器，物理内存比现在明显下降；
   - 全树测试与 QEMU 冒烟通过，旧豫行照常运行。
2. **节**：清单写明所需之节，分封时授予，越节的导入在装入时失败；壳加「列封」「削封」等命令（照 AGENTS.md“图形程序”一节，先有命令）。验收：
   - 只授案牍节的程序，导入驿节时在装入阶段就失败；
   - 代理会话能按节收窄。
3. **同进程封**：执行器支持多堆、多实例共用代码、按封调度与削封。验收：
   - 在壳里分封运行一个程序，启动耗时和跑一句话同一量级；
   - 削封后内存归还；
   - 程序里的陷阱不波及会话。

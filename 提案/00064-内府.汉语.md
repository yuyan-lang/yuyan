## 拟定事项

- 议一：**接口不变**。内府照豫寓榫卯「对象存储」接口（0.5.0）的语义办事：取元数据、读文字、读字节、写（无条件、唯无、符同三种条件与摘要校验）、删、按前缀列举翻页。应用与九府只改配置里的库类，代码不动。
- 议二：**三层分开**。本机存储引擎用现成的「金匮」（落盘、条件写）；复制层是新的共识库「盟府」；对外是内府台（服务程序）加一个客户端适配。每层能单独测。
- 议三：**先单机、后三副本**。第一步一台内府台，数据只在一台机器上，先让九府多机长跑有共用的存储；第二步三台内府台组成一盟，写入过半数落盘才算成，坏一台不丢数据、不停服务。
- 议四：**一致性**。条件写是九府选领袖的根基，必须线性一致：所有写按同一个序号顺序生效，条件在生效那一刻按当时的状态判；读只由当前盟主答，答前先确认自己仍是盟主。
- 议五：**落盘才回话**。写入在回“成”之前先同步到盘（单机时同步本机；三副本时过半数各自同步了载书）。成组提交（#462）的一秒窗口不能落在已确认的写上。
- 议六：**程序间通信用二进制**。照 AGENTS.md 与提案 00051：TCP 连接上先互投八字节的刺，之后每条消息前写八字节小端长度，消息体是籍册数据值的二进制编码（籍帛），对象正文作为帛原样放在消息里。与九府的置邮同法。
- 议七：**凭证**。客户端与内府台、内府台之间凭虎符（盟内共享密钥，与将作、九府同法）认人，虎符只写文件路径，不进配置与日志。经互联网的连接由封缄（TLS）加密，放第三步。
- 议八：**复制状态机做成确定性的**，在推演（沙盘）里跑：假网、假钟、假盘，随机注入崩溃、重起、断网、分区、丢包与乱序、慢盘，核对不变式；违例凭种子复现。与九府的推演同法。

## 一、动机

九府把全部持久状态放进对象存储，自己不做多副本共识（提案 00054 议五）。持久的担子因此全在对象存储上：现在只有本机落盘的金匮（一台机器，盘坏就丢）与 R2（别家的云）。要“不依赖哪一家云”，就得有自己的、几台机器各存一份的对象存储。九府其余部分不必改：内府照同一接口办事，九府换个库类就接上。

## 二、结构

```
应用、九府 ──(豫寓榫卯「对象存储」)── 客户端适配「豫寓府库内府榫」
                                          │ TCP＋籍帛
                       内府台 ── 内府台 ── 内府台      （第二步：一盟三台）
                         │         │         │
                       盟府      盟府      盟府        （共识：盟主、载书、过半盟成）
                         │         │         │
                       金匮      金匮      金匮        （本机落盘）
```

## 三、第一步：单机内府

1. **内府（库）**：协议与服务的核心。请求是籍册记录：请求号、术（元、读、写、列、删）、桶、键、选项（条件：无凭、唯无、符同加摘要；可选的 sha256；内容类型、缓存控制、自定义元数据；列举的前缀、上限、续标）、正文（帛）。应答带请求号与结果：成（元数据、正文）、无（对象不存在）、冲突（条件不满足，对象原样）、误（缘由）。一条连接上可以连发多条请求，应答按请求号对回。
2. **内府台（程序）**：读配置（`内府台。数据。豫`：数据目录、监听端口、虎符文件路径、桶名单），起服务。存储用金匮，根设在数据目录下。金匮的索引是“读、改、原子写回”，所以写在内府台里排成一列依次办，读可以并发。每批写办完先同步到盘再回话。收到「息」或 SIGTERM 时停收新请求、办完手头的写、同步后退出。
3. **客户端适配「豫寓府库内府榫」**（`豫言操作系统/适配/对象存储内府`）：实现豫寓榫卯「对象存储」接口，把调用转成请求发给内府台；连接复用，断了重连；超时与错误照接口的约定变成返回值或异常。直通出站响应、入站正文写入、分段写物这一步先答“不支持”，第三步补上。
4. **九府接上**：九府的择库多认一个库类「内府」（内府台地址、虎符路径），三台九府指向同一台内府台，就能做多机长跑。
5. **验收**：接口规范里“一致性样例”逐条过（除第 3 条列为不支持的几项）；九府的推演照旧全过；谷歌云上一台内府台、三台九府节点长跑，选主、换手、派单都走内府。

## 四、第二步：三副本（盟府）

「盟府」是通用的共识库（照 Raft 的做法），与存储无关，九府以后也可以用：

1. **状态机**：每员（节点）有任期、本任期所投、载书（日志，每条带任期与序号）；盟主（领袖）收写入，追加成载书，发给各员；过半数各员把这条载书落了盘，就算“盟成”（已提交）；各员按序号依次把盟成的载书交给上层执行。选盟主照 Raft：随机超时、按任期投票、载书不比自己新的不投。
2. **纯状态机、不做输入输出**：输入是收到的消息与钟的滴答，输出是要发的消息、要落盘的载书、要执行的载书。网、盘、钟由上层接；推演就接假网、假盘、假钟。
3. **内府接盟府**：内府台把每个写（含条件）做成一条载书；各员按序执行，条件在执行时按本机状态判，各员结论必然一致；盟主等这条载书执行完才回客户端（成或冲突）。读由盟主答，答前用一轮心跳确认过半数仍认它为盟主。客户端连到不是盟主的员，得到“盟主是谁”的答复，改连过去。
4. **快照与截断**：各员定期把金匮目录连同已执行到的序号存成快照，截掉之前的载书；落后太多的员由盟主发快照追上。
5. **成员**：这一步成员写死在配置里（三或五台）；增减成员放第三步。
6. **推演核的不变式**：同一任期至多一个盟主；两员同一序号的载书相同则此前全同；盟成的载书不会被改写或丢；各员执行的序列互为前缀；在内府这一层，条件写的历史线性一致（同一个键上，成功的“唯无”至多一次，“符同”只在摘要对上时成）。
7. **验收**：推演一万个种子无违例；谷歌云上三台内府台，随手断掉任意一台（含盟主），写入不丢、服务在一个选举超时内恢复；九府照常选主换手。

## 五、第三步及以后（另议）

- 封缄（TLS）加密节点间与客户端连接；
- 直通出站响应、入站正文写入、分段写物；
- 成员增减；数据量大了按键分片成多盟；
- 纠删码代替三份全副本；
- 云仓（yuyan-cloud）各应用的对象存储从 R2 迁到内府。

## 六、名字

照《取名规范》，内府沿用九府诸府的取喻；共识库取《左传》的盟府：诸侯会盟，盟书一式多份，各国与盟府各藏一份，盟主主盟，与“盟主收写、各员各存载书、过半盟成”神似。将作的集群已叫盟、同僚，这里同一套比喻。

| 名字 | 管什么 | 出处 |
| --- | --- | --- |
| 「内府」 | 自己的对象存储：协议与服务核心（库） | 《周礼·天官》“内府掌受九贡九赋九功之货贿、良兵、良器，以待邦之大用” |
| 「内府台」 | 内府的服务程序 | 同九府台 |
| 「豫寓府库内府榫」 | 对象存储接口的内府适配 | 同豫寓府库金匮榫、豫寓府库邸阁榫 |
| 「盟府」 | 共识库（照 Raft） | 《左传·僖公五年》“勋在王室，藏于盟府”；《左传·僖公二十六年》“载在盟府，大师职之”（出处已在殆知阁语料核过） |
| 「盟主」 | 领袖（leader） | 会盟主盟者 |
| 「载书」 | 日志条目（log entry） | 《周礼·秋官·司盟》“掌盟载之法”，盟书称载书 |
| 「盟成」 | 已提交（committed） | 盟约既成 |

模块内部的其余名字在实施时照《取名规范》另拟。

# 提案 00012：兼容林纳克斯程序与驱动

| 项 | 内容 |
| --- | --- |
| 编号 | 00012 |
| 状态 | 草案 |
| 提出 | 2026-10-10 |
| 范围 | 豫言操作系统直接运行未经修改的 Linux（林纳克斯）程序（x86-64 与 ARM64 的 ELF 可执行文件，连同发行版的动态库）；为此新增的内核通用机制及其接口包；豫言桌面的 Wayland 服务；复用 Linux 驱动的驱动客体（现有林客体）。豫言程序的接口、包系统与编译器照旧 |

本文只写现代汉语（AGENTS.md）。下文把运行在豫言上的 Linux 程序简称“林程序”。

## 一、拟定事项

- **议一：一个内核，两个入口。** 林程序的机器码直接在豫言内核上运行，经「林入口」进入兼容层；豫言程序照旧经接口包。豫言的接口包、接口清单与规范里只有豫言自己的概念，Linux 的语义全部留在兼容层。
- **议二：兼容层在用户态，用受限模式。** 林程序的线程在「受限模式」下运行；它执行系统调用或出故障时，内核把控制交给同一任务里的兼容层，兼容层按 Linux 语义办完再回到林程序。兼容层是底层豫言写的普通用户代码；内核只多一个通用的受限模式，不认识任何 Linux 系统调用。
- **议三：先补豫言自己的内核机制。** 兼容层需要的能力，先作为豫言的通用机制做进内核，并以接口包公开：内存对象与逐页权限、写时复制克隆、线程、地址等待、多路等待、句柄随消息传递、故障转交与线程打断。每个机制先有豫言的规范、用例与测试，兼容层是第二个使用者。
- **议四：林根。** 林程序看到的 `/` 是豫言文件树里的一棵子树（如 `/林/<发行版>/`），里面是原样的发行版文件；豫言的文件经 `/豫言` 挂进去。豫言自己的文件树保持豫言的布局。
- **议五：窗口用 Wayland 服务。** 豫言桌面实现 Wayland 服务（豫言写的库），林程序的窗口就是豫言桌面的窗口；X11 程序经发行版自带的 XWayland。
- **议六：驱动客体复用 Linux 驱动。** Linux 驱动在驱动客体里原样运行：驱动客体是豫言内核用硬件虚拟化运行的精简 Linux（即现有林客体），设备经 IOMMU 直通给它，现成驱动（含闭源驱动）照常加载。驱动客体把设备能力以豫言接口（块、网络、显示、计算）交回系统。需要 Linux 内核模块的林程序（如 CUDA 程序）在驱动客体里运行。
- **议七：以真 Linux 为参照验收。** 同一程序在同版本 Linux 上的行为与 strace 记录是参照；系统调用用 Linux 测试项目（LTP）验收；真实程序按清单验收，首个大目标是 Chrome（先无头，后有窗口）。

“完全兼容”由两层合成：常见程序在兼容层里原生运行；用到 Linux 内核模块或兼容层暂缺功能的程序在驱动客体里运行。两层的窗口、文件都接到同一个豫言桌面与文件树。

## 二、动机

- **生态。** 浏览器、Node.js、Python、编译器、编辑器与科研软件都有现成的 Linux 版。豫言自己的应用生态需要时间积累；林程序让这些软件立刻可用。
- **驱动。** 显卡、无线网卡、存储控制器的驱动量大，Linux 已经全有。林客体已经证明 Linux 驱动可以在豫言内核下工作：QEMU/KVM 嵌套里 Linux 6.12 启动到 init，e1000e 网卡直通后六项 TCP 往返通过（`豫言操作系统/裸机/文档/林驱动客体.汉语.md`，2026-10-06）。
- **原生运行。** 林程序的机器码直接在处理器上运行，窗口、文件、剪贴板与豫言桌面一体；虚拟机只承载驱动和少数需要 Linux 内核的程序。
- **业界做法。** 鸿蒙内核兼容 Linux 的 API 与 ABI，并用驱动容器复用 Linux 驱动（OSDI 2024《Microkernel Goes General》）；Fuchsia 的 Starnix 在用户态实现 Linux 系统调用，Zircon 内核保持自己的句柄与通道接口；Windows 的 WSL1 用微进程承载 Linux 程序。本提案取 Starnix 的分层（Linux 语义在用户态）与鸿蒙的驱动复用思路（这里用驱动客体）。

## 三、现状

- **内核。** 豫言内核（`豫言操作系统/裸机/内核/`，底层豫言，AMD64 与 ARM64 共用）：任务、多核、动态任务、消息、自有可执行格式「豫行文件」的装载（提案 00005）。用户内存按 2 MiB 整块按需提交（`豫言操作系统/裸机/文档/内存块管理.汉语.md`）。系统调用：AMD64 `int 0x80`，ARM64 `svc #N`（服务号在立即数里）。
- **用户态。** 用户态 virtio 块驱动与 ext4、USB 键鼠与存储、帧缓冲桌面（无 GPU 驱动）、命令壳、子程序、多实例动态装载、WasmGC 执行器「客体二号」。
- **接口。** `豫言操作系统接口/`（带 GC，应用用）与 `豫言操作系统底层接口/`（不带 GC 的窄腰：句柄、文件、网络、进程、终端、显示；WASI 与 GC 两个 shim 架在上面）。外来接口做成架在窄腰上的 shim，这是已有的做法，林兼容层沿用。
- **虚拟化。** 林客体：Intel VMX/EPT、VT-d 设备隔离、MSI-X；专用镜像、单处理器、客体只有串口，实机未验（`持续改进目标/林设备分配.md`）。
- **相对林程序的缺口。** 4 KiB 粒度与逐页权限、写时复制、共享地址空间的线程、地址等待、故障转交、句柄随消息传递、ELF 装载、Wayland 服务。

## 四、设计

### 4.1 总体结构

```text
豫言程序 ──接口包──────────────────────────────┐
                                               ├─ 豫言内核：任务 线程 内存对象 句柄 消息 等待 受限模式
林程序 ──林入口→ 受限模式 ⇄ 林兼容层（同一任务）─┘
                              └─ 豫言的文件服务、网络、控制台、Wayland 服务
驱动客体（精简 Linux ＋ 现成驱动）──设备环──→ 豫言的块、网络、显示、计算接口
```

### 4.2 守住豫言风格的规则

1. 豫言的接口包、接口清单与规范里只出现豫言的概念。fork、信号、errno 编号、ioctl、`/proc` 文本、uid 与能力位只存在于林兼容层。
2. 内核新增的每个机制，先写豫言规范、豫言用例与测试；兼容层是它的第二个使用者。审查新机制时问一句：没有林兼容层，豫言程序会用它吗？
3. 依赖单向：林兼容层依赖豫言内核与接口包；豫言内核、接口包与标准库不依赖林兼容层。包依赖图可以直接核对。
4. 内核服务号是内部约定，随时可改；对外承诺只在接口包。
5. 林程序的文件、窗口、设备都由豫言的服务提供，兼容层只做翻译。豫言程序看到的始终是豫言的文件树与接口。

### 4.3 林入口与受限模式（议二）

- 任务可以带一个受限区：用户地址空间的下半段给林程序，上半段放兼容层的代码与数据。线程在受限模式下只执行受限区的代码。
- 受限模式下的 `syscall`（x86-64）与 `svc #0`（ARM64）、缺页与其他故障，都由内核保存受限状态（全部寄存器）后转到兼容层入口；兼容层处理完，用「回受限模式」继续。豫言自己的 `int 0x80` 与 `svc #N` 只在普通模式生效，两套调用因此互不冲突。
- 内核可以按兼容层的请求，在下一次进内核时把受限线程拉回兼容层，用来投递信号。
- 切换在同一任务里完成，不经消息往返；内核不解析 Linux 系统调用号。
- 兼容层是普通的底层豫言程序，编成豫行文件随系统发布；翻译逻辑可以在宿主上单独测试。
- 包：`豫言操作系统/裸机/林兼容/`，包名「林兼容」，登记为「豫言裸机」的子包。

### 4.4 内核新增的通用机制（议三）

| 机制 | 豫言用法 | 兼容层用法 |
| --- | --- | --- |
| 内存对象：按 4 KiB 页提交的一段内存，可共享、可映射，映射时给读、写、执行权限，之后可改 | 共享内存、文件映射、将来执行器的即时编译 | mmap、mprotect、mremap、共享映射、memfd、`/dev/shm` |
| 写时复制克隆：复制整个任务，页在写时才真正复制 | 快速建子任务 | fork |
| 线程：同一任务里共享地址空间的多个执行流，各有寄存器与线程局部基址 | 豫言程序多线程、执行器并行回收 | clone、pthread |
| 地址等待：按内存地址等待与唤醒 | 豫言的锁与条件变量 | futex |
| 多路等待：一次等待多个句柄、计时与唤醒 | 豫言的事件循环 | epoll、poll、select、eventfd、timerfd |
| 句柄随消息传递 | 服务之间交付文件、显示面 | Unix 套接字传文件描述符 |
| 故障转交与线程打断：缺页、非法指令、算术故障交给任务里的处理代码；让另一线程的阻塞等待提前返回 | 执行器的守护页与越界检查、取消操作 | 信号、`EINTR` |

这些机制以底层接口包公开（新增 `底层内存`、`底层线程`，扩充 `底层句柄`），macOS、Linux 宿主与裸机各实现一份，与其他底层接口一样“各后端功能一致”。受限模式只在裸机内核里有，供林兼容层使用。

### 4.5 林兼容层（议一）

| 部件 | 内容 |
| --- | --- |
| 装载 | ELF 段映射；按 `PT_INTERP` 装入发行版的动态链接器（ld-linux、ld-musl 原样使用）；初始栈（参数、环境、辅助向量 auxv）；vDSO（读时钟）；线程局部存储（x86-64 FS 基址、ARM64 `TPIDR_EL0`） |
| 进程 | 进程表放在各林任务共享的兼容层公共区（内存对象＋地址等待）；pid、进程组与会话；fork、vfork、clone、execve、wait4、exit_group |
| 内存 | 区段表；mmap、munmap、mprotect、mremap、madvise、brk |
| 信号 | sigaction、信号掩码、按架构的信号帧、sigaltstack、rt_sigreturn、kill、tgkill；故障转成 SIGSEGV、SIGBUS、SIGILL、SIGFPE |
| 文件 | 文件描述符表；open、openat、stat、statx、getdents64、读写、fcntl、flock、rename、link、symlink、chmod、utimensat、inotify；落到豫言的文件服务（ext4），另有管道与内存文件系统 |
| 伪文件 | `/proc`（self/maps、self/exe、cpuinfo、meminfo、stat 等）、`/sys`（处理器拓扑）、`/dev`（null、zero、random、urandom、tty、pts、shm），由兼容层按豫言的系统信息生成 |
| 事件与时间 | epoll、poll、eventfd、timerfd、signalfd、clock_gettime、nanosleep |
| 套接字 | Unix 套接字（含传文件描述符）、TCP 与 UDP（IPv4、IPv6）、最小的 netlink；落到豫言的网络 |
| 终端 | tty、pty、termios；落到豫言的控制台 |

系统调用按 LTP 与真实程序的需要逐个补；没实现的调用返回 `ENOSYS` 并记一行日志，日志就是下一步的清单。

### 4.6 林根（议四）

- `/林/<名>/` 是一棵完整的发行版根，先用 Debian 最小根；造盘时放入，或在系统里解包得到。林程序的 `/` 指向它。
- 豫言的文件经 `/豫言` 挂进林根，林程序可以读写；`/proc`、`/sys`、`/dev`、`/tmp` 由兼容层提供。
- 林程序用发行版自己的包管理器（apt）在林根里安装软件；豫言程序照旧用豫构的包。

### 4.7 窗口与输入（议五）

- 豫言写一个 Wayland 服务库，接在豫言桌面上：wl_compositor、wl_shm（共享内存画面，用内存对象）、xdg_shell、wl_seat（键鼠，带 xkb 键位表）、wl_output、wl_data_device（剪贴板）。
- 先用软件渲染：Mesa 的 llvmpipe、Chrome 的软件合成。
- XWayland 用发行版的包，原样运行。

### 4.8 驱动客体（议六）

- 驱动客体即现有林客体：豫言内核用 VMX/EPT 运行精简 Linux，设备经 VT-d 整个直通，MSI-X 中断转交。现成驱动跟着客体里的 Linux 版本走，闭源驱动也照常加载。
- 交回豫言：客体里的代理程序把设备能力经共享内存环（设备环）交给豫言，分块设备、网络（以太网帧）、显示输出、计算四类；豫言这边表现为普通的豫言设备接口。数据走共享内存，设备的 DMA 直达客体内存。
- Linux 内核内部接口随版本变化；驱动客体让这些变化留在客体内部，豫言内核只面对设备环这一个稳定边界。
- 需要 Linux 内核模块的林程序（CUDA、特殊文件系统等）在驱动客体里运行；窗口经同一个 Wayland 服务显示，文件经共享目录。
- 驱动客体先支持 Intel（VT-x、VT-d），沿用林客体的实现。

### 4.9 架构

- 两种架构都做：x86-64 的豫言跑 x86-64 林程序，ARM64 的豫言跑 ARM64 林程序。Chrome 在 x86-64 上用官方版，在 ARM64 上用发行版的 Chromium。
- 开发验证：ARM64 在本机 HVF 下接近原速；x86-64 用 pit-mbp13 的 KVM；参照用同版本 Linux 运行同一程序。

### 4.10 与提案 00009（网页基础库）的关系

- 分工：00009 用纯豫言写浏览器引擎，给豫言程序当库用，在原生、裸机与诺节上同源运行；本提案让现成的 Linux 程序（含 Chrome）作为用户程序在豫言操作系统上运行。两份提案并行推进。
- 边界：00009 的库只用豫言的库与公共接口（00009 议六），林程序与林根里的库只给用户直接运行，豫言程序与豫言的库一律不调用。本提案规则 5 从这一侧保证同一条边界。
- 共用前置：裸机上的网络、字体与豫言桌面的窗口，两份提案共用同一份实现，谁先用到谁先补。
- 测试：林程序 Chrome 的无头模式（导出 DOM、截屏）可以作 00009 引擎的对照参照，补充 WPT 参照测试。

## 五、兼容与迁移

- 豫言程序、接口包、编译器与包系统照旧；内核机制以新服务、新接口包的形式加入，现有服务号与接口保持原样。
- 林客体从专用镜像并入日常启动盘，原有验收保留。

## 六、备选方案

- **兼容层放进内核**（鸿蒙内核、WSL1、FreeBSD 的 Linuxulator）：每次系统调用少一次切换，代价是 Linux 语义进入内核。本提案用受限模式把 Linux 语义放在用户态，内核保持豫言自己的形状；受限模式的切换在同一任务里完成，开销小。
- **只用虚拟机**（ChromeOS 的 Crostini、WSL2）：兼容性最高、起步最快；林程序与桌面的融合全靠转发，内存与性能开销大。本提案把虚拟机留给驱动与少数程序。
- **在豫言内核里直接加载 Linux 驱动**（FreeBSD 的 LinuxKPI、鸿蒙的驱动容器）：要在豫言里重写大片 Linux 内核内部接口，并随 Linux 版本持续追改。本提案用驱动客体。
- **把源码移植成豫言程序**：适合豫言自己的核心应用；Chrome 这类大程序以年计。

## 七、未决问题

1. 身份与权限：林程序的 uid、gid、文件属主与权限位怎样对到豫言的授权。建议先单用户。
2. 地址宽度：底层接口现在的值是 32 位整数；新增的 `底层内存`、`底层线程` 要 64 位地址，是给底层接口加 64 位版本，还是兼容层直接调内核服务。
3. 首个发行版：Debian（glibc）还是 Alpine（musl）。Chrome 需要 glibc，建议 Debian。
4. Chrome 沙箱：它依赖 seccomp-bpf 与命名空间，放在第 8 步还是更早。
5. 声音：实现 PulseAudio/PipeWire 协议，还是 ALSA 的设备接口。
6. 林程序用 GPU：经驱动客体转发显卡调用，还是只给驱动客体里的程序。
7. 林根的存放：ext4 上的普通目录，还是单独的分区或镜像文件。

## 八、实施步骤

1. **内核机制**：内存对象（4 KiB 页、逐页权限）、写时复制克隆、线程、地址等待、多路等待、句柄随消息传递、故障转交与线程打断、受限模式；各带底层接口包、规范与测试，两架构 QEMU 验收。
2. **静态程序**：ELF 装载与约 40 个系统调用。验收：musl 静态链接的 hello、busybox 的 sh 与常用命令。
3. **动态程序**：glibc 动态链接、文件语义、管道、信号、线程、`/proc` 基本项、林根。验收：Debian 最小根里的 bash、coreutils、python3、git；LTP 系统调用第一批。
4. **网络与事件**：套接字、epoll、eventfd、timerfd、Unix 套接字传文件描述符。验收：curl 取 https 网页、Python 的 http.server、Node.js。
5. **无头 Chrome**：`--headless --no-sandbox --dump-dom` 抓取网页。
6. **窗口**：Wayland 服务。验收：foot 终端、GTK 示例程序、有窗口的 Chrome（软件渲染）。
7. **驱动客体并入系统**：林客体随启动盘启动、受豫言管理；网卡、显卡经设备环交回豫言；CUDA 程序在客体里运行。
8. **隔离**：命名空间、seccomp-bpf。验收：Chrome 开着沙箱运行。

后续版本的事项：AMD（SVM、AMD-Vi）与 ARM64（EL2、SMMU）的硬件虚拟化、跨架构翻译（ARM64 上跑 x86-64 程序）、声音、林程序的 GPU 加速、32 位程序、io_uring、ptrace 与调试器、多个林根并存。

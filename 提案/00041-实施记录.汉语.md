## 一、#152 本机架构不再依赖 PATH 与子进程

### 成因

- 冶铸的「本机架构」在林檎与林纳上执行 `uname -m`，靠 PATH 找 uname。进程环境里没有 PATH（例如 `env -i` 起的壳会话、行在桌面的终端起的子程序）时得空串，判成兼容六十四；在臂六十四上这样编出的单元是 x86 机器码，执行即 SIGILL（macOS 上退出码 132）。
- 执行器只有裸机与轩窗两个实现答只读环境字段「豫言处理器架构」，原生（林檎、林纳）的实现（客体二号的「原生环境变量对象」）还没有这一项，所以不能只靠「问俗」。
- 仓里没有“本程序目标架构”的常量或不新增原语就能取到的编译期值：目标内建导入的「指令集」只在底层代码里可用。

### 修法

- 林檎与林纳改为读本程序文件的头认架构，做法同 `应用/豫构/发行/宿主构建。豫` 的「启动器宿主」：Mach-O 64 位（头两字节 0xCF、0xFA，第 5 字节 0x0C 为臂、0x07 为兼容），ELF（头两字节 0x7F 与 'E'，第 19 字节 0xB7 为臂、0x3E 为兼容）。
- 认不出文头（诺驿宿主、豫行程序）时退回问 `uname -m`；豫言操作系统仍问只读字段，轩窗仍问处理器架构环境变量。
- 结果用「一算」按进程缓存，一次会话只读一次本程序文件。待办事项：现在读整个文件只为取前六十四字节，有了读文件头的原语再换。
- 「本程序径」原在本机架构之后，豫言没有前向引用，整段前移到「本机寓」之后。
- 不新增执行器原语。

### 验证

- pit-mac（臂六十四）：用当前源码编出的一级豫构上，`env -i HOME=/tmp/钩议定点-家 ./豫构新。林檎。豫行 交互 --直读` 执行「问津」退出码 0（改前为 132），执行「加」于「一」于「二」印出 3。

## 二、#157 冷编三级豫构不确定

### 复现

2026-10-20 在 pit-mac 上按任务书的做法，用当前源码先编一级（`构建 豫构 --输出 豫构新 … --执行器 执行器。树码`），再由它跑 `全部`（私有缓存根），自举定点失败：

```
构建任务失败：自举#1
豫构二。林檎。豫行 豫构三。林檎。豫行 differ: char 753, line 1
```

第 753 字节是 Mach-O 的 LC_UUID。`cmp -l` 共 231 字节：UUID 十六字节，代码里十三处指令的立即数，另五字节在文件后部（像代码签名的页哈希）。执行器二、三逐字节相同。

同日在 pit-pc-ubuntu-wired（林纳，兼容六十四）上按共同规矩的做法再复现：先在 `新链/` 编出现源一级，再由它跑 `全部`，自举定点同样失败：

```
豫构二。林纳。豫行 豫构三。林纳。豫行 differ: byte 6994070, line 18922
```

`cmp -l` 只差 6 字节，落在四处：诏令/实现 的 系统槽状态实现_提升函数86（+109）、回退系统实现_提升函数87（+109），小学/拼音 的 直调_作拼音音节_6（+906），中书/智能候选 的 直调_名音段_4（+135）。都是 `mov $0x23e014` 对 `$0x23df14`、`$0x3c8f14` 对 `$0x48f714`——array.new_data 的（类型号 20，数据段号），前者 4576 对 4575，后者 4695 对 9335。数据区的载荷逐字节相同，只有代码里的这些立即数不同。

### 定位

- `nm -n` 两个文件全同（66883 个符号，地址逐个相同）。
- 把差异偏移加上映像起址对到函数，臂六十四上与议题列的函数完全一致：诏令/实现 的 设分辨率、设缩放、设字样、映设、打断役、辍、设登录口令、启远程登录、阖远程登录、远程登录态 各提升函数（都在 +90 上下），几席/役令 的 直调_令打断役_1（+1790）、直调_令辍_4（+2502）。
- 反汇编差异处：`mov w19,#9; mov w20,#0xe314; movk w20,#0x23,lsl #16` 之后 `bl 预编回收指令立`，子码 9 是「新建数据数组」（array.new_data）。立即数十二字节里的两个变长数，一是类型号 20，二是数据段号：臂六十四上二级是 4579、三级是 4580，只差一。

### 已查明

- 同一个驱动（豫构二）在另一个私有缓存根下重编三级，产物与第一次三级逐字节相同（md5 相同）：不是逐次运行的随机性，而是一级（旧工具链编出的现源豫构）与二级（自己编出的豫构）行为不同。
- 排除编译缓存：同一个驱动（豫构新）带缓存编一遍、加 `--do-not-load-cache` 冷编一遍（各用新的私有缓存根），两份产物逐字节相同（md5 相同）。
- 排除执行器：用豫构二配旧执行器编出的豫构，与配现执行器编出的三级逐字节相同（md5 相同）；两级本来用的执行器二、三也逐字节相同。
- 源码、包上下文都相同：构建期间源码树没有变动（`git status` 只有本次改的两个文件）。
- 二级、三级的数据区（__DATA 的载荷）逐字节相同，只有代码与 LC_UUID 不同。可见不是数据段的集合或内容不同，而是指令里的数据段号不同，或指令引用的稳定名不同。
- 剩下唯一的变量是“这个编译器由谁编出”：一级由旧工具链（臂六十四上是 5f73a64df）编，二级由一级编，三级由二级编；二三级行为不同，说明同一份编译器源码换一种编法就生成不同的数据段编号。字面量按首次使用的先后登记成 `$d位`（见 网汇编基 的「字面」），数据段、字面量全局都按这个次序编号；登记次序差一处，后面的号就整体挪位。
- 分片降级的合并次序不是成因：分片输出文件按片号列出并按该次序读入，每个分片工作者的符号表都来自同一份模块，型号、函号、标签、全局量与闭包表序号由「预二预定义符号」预先登记，找不到随完成先后编号的路径。

### 改法

字面量的全局名与数据段名改成由内容决定，模块里的编号随之只取决于内容，与登记的先后无关：

- 内容摘要用六十四位 FNV-1a，末尾与低六十三位的掩相与，写成十进制（没有负号）。全局名是 `$s1` 加摘要（常量上下文）或 `$s2` 加摘要（运行代码），数据段名是 `$d1`、`$d2` 加同一摘要（类号跟着全局名走，冶铸按编号名找同名数据段时才对得上）。名字仍是 `$s`、`$d` 加数字，冶铸按内容改名（预二汇编号名）照旧认得。
- 生成模块前把字面用量按名字排序，同名的并成一项（见 网汇编基 的「字面项正序」）；数据段与字面量全局都按这个次序写出，因此编号只由内容决定。内容与去处都相同的字面量从此共用一个全局、一个数据段。
- 按名合并时核对内容：名字相同而「其文」不同（摘要相撞）就报「字面量摘要相撞：名字 与 内容、内容」，不并成一项。概率极小，但撞了若默默并项就是静默错译。
- 常量类仍写不可变全局（初值 array.new_fixed，超一万字节的仍走 _start 填 `$d` 段的定长数组），运行类仍写可变空全局、第一次用到时从 `$d` 段造出；两类名字不同，模块里各是一个全局，常量初值里的 `global.get` 仍只读不可变全局。
- 引用处不用改写：`字面` 返回的指令里用的就是按内容算出的名字。

### 一级与二级的登记次序为何不同

未查明。两次模块生成只差一处字面量登记（臂六十四上数据段号 4579 对 4580，林纳上 4576 对 4575、4695 对 9335），差在同一个编译器源码由旧工具链编出还是由自举出的编译器编出；插桩比对没跑成（插桩本身先出错），没有找到具体是哪一处登记、为什么只在一种编法里出现。改法不再依赖登记次序，这一处差异对产物已无影响。

## 一、缘起

问簿（SQL，翻译列表的译名）现在是写在 `.豫` 里的字符串。云仓有 39 个源文件写着约 350 条 SQL，表结构是 29 个 `.sql` 迁移文件。例如账户服务里的一句：

```
『SELECT "用户编号" AS id FROM "邮箱账户" WHERE "邮箱"=?』
```

表名、列名拼错，参数个数不对，结果列的类型对不上，都要到运行时才报错；每次执行还要重新做词法分析与解析。自建动态站（C00005）要把这些数据从 D1 搬进芥子，正好一并改写。

本提案不新增语法，不改语法分析器：问簿源用豫言的标准写法（定义、签名、命名元组、构造写法、匿名函数），只多一种文件种类，限制落在翻译那一步（《子语言设计》则一、则三）。

## 二、目标

1. **表结构写成豫言**：一张表是一个行类型（命名元组）加一条表声明（主键、唯一、索引、外键、缺省值）。
2. **查询写成豫言函数**：条件、投影、排序、分组、连接写成以行为参数的匿名函数；查询参数就是函数参数，带标签。
3. **编译期检查**：列名、列的类型、参数个数与类型、结果行的类型由类型检查核对；写法超出问簿能表达的范围，在翻译时报错，带文件、行、列与原因。
4. **构建时编成执行计划**：运行时不再解析 SQL 文字。
5. **SQL 文字照旧可用**：导入 D1 转储、运维时临时查询、迁移期间的旧代码，仍走芥子现有的 SQL 入口。

## 三、文件种类与接缝

- `名。问簿。豫`：问簿源。只写导入、行类型、表声明与查询函数（签名加定义）。能导入别的问簿源与问簿内建声明。
- 问簿内建声明：表、查询、写入等构造写成无体声明，放在芥子包里（如 `问簿内建。问簿。接口。豫`），由翻译器实现，与着色内建同理。
- 高级文件导入问簿源，得到构建时生成的模块（虚拟路径 `名。问簿生成。豫`）。生成模块里：每张表一个表描述；每个查询一个同名的带类型函数，比源里的签名多一个标签参数「库」（芥子的库）。
- 问簿在芥子能跑的地方都能跑：原生、裸机、诺驿（Node.js 后端）、浏览器、云工（Cloudflare Workers 后端）。

## 四、写法（示意，细节以实施为准）

```
寻观「芥子」之「问簿内建」之书。

「邮箱账户行」即「组类」【「用户编号」乃「数」也，「邮箱」乃「文」也，「创建时间」乃「数」也】也。

「邮箱账户」乃（「册」于「邮箱账户行」）者也。
「邮箱账户」者「置册」【「名」者『邮箱账户』也，「主键」者『用户编号』也，「唯一」者「列」【『邮箱』】也】也。

「按邮箱取编号」乃化「邮箱」曰「文」为（「列」于「数」）者也。
「按邮箱取编号」者得「邮箱」曰「址」而
　「检」【「自」者「邮箱账户」也
　，「择」者（得「行」而「文同」于（「行」中「邮箱」）于「址」）也
　，「遍」者（得「行」而「行」中「用户编号」）也
　】
也。

「登记账户」乃化「编号」曰「数」又化「邮箱」曰「文」为「数」者也。
「登记账户」者得「编号」曰「甲」又得「邮箱」曰「乙」而
　「登」【「入」者「邮箱账户」也，「行」者「组值」【「用户编号」者「甲」也，「邮箱」者「乙」也，「创建时间」者「此刻」也】也】
也。
```

高级代码里调用：

```
寻观「账户」之「账户册」之书。
……
　令「编号们」为「按邮箱取编号」于「库」曰「账户库」于「邮箱」曰「来邮箱」而
```

- `「行」中「邮箱」` 是命名元组的按名投影：列名写错，类型检查就报“没有这一项”。
- 「检」是多态的内建：它的类型由「自」的行类型与「遍」的结果类型推出，签名里写的返回类型要与它相等。「择」「遍」「次」（排序）「限」（条数）都是可省的命名项（提案 00019）。
- 两张表连接用「检二」，「择」「遍」的匿名函数各收两行（照“作用于两列的变体加二”）；分组用「聚」，组内可用计、和、最大、最小、平均。
- 改与删：「改」【「册」者…，「择」者…，「为」者（得「行」而 新的组值）】返回改了几行；「删」【「册」者…，「择」者…】返回删了几行。
- 主键、唯一、索引、外键里的列名以文字给出，由翻译器对着行类型核对。

## 五、翻译与执行

1. **条件与投影里能写的**：列（`「行」中「名」`）、参数、字面量、比较（等于、大于、不大于……、文同）、且、或、非、加减乘除，以及一份对上芥子标量函数的白名单（取小写、计字、截取、日期时间、此刻等）。别的函数调用、闭包与递归在翻译时报错，写明“条件里只能写……”。可空列（「可有」）照 SQL 的三值逻辑，另给「是空」「非空」。
2. **第一版的计划**：每个查询编成芥子问簿现有的语法树（`库/群书/藏时部/芥子/问簿/语法树。豫`）。生成模块把它作常量，运行时按位绑定参数，交给现有的执行模块直接执行，省去词法与解析。翻译器同时写出对应的 SQL 文字，供日志与排查。
3. **第二版的计划**：芥子的表与索引搬进页式键值库之后（芥子关系层改造，正在做），翻译器按声明的索引与等值、范围条件选好访问路径，编成带访问路径的计划。
4. **结果**：结果行解成签名里的命名元组或标量的列。
5. **事务**：生成模块给出「同办」（候选名）：把一个以库为参数的函数放进一个芥子事务里执行，出错就整体回滚。

## 六、表结构与库的核对

- 生成模块给出「建册」：库里没有的表与索引就建上，并把表结构的指纹记进库的目录段。
- 打开库时核对指纹：表结构与库里的不同，而变化只是加表、加可空列、加索引的，自动补上；其余变化（删列、改名、改类型）报错，要写显式的迁移步骤（第二期）。
- 云仓迁移时，用一个一次性工具读出 D1 现有的表结构，生成问簿源里的行类型与表声明；SQL 字符串由钩深（DeepSeek）逐条改写成查询函数，改一个应用验一个应用。

## 七、步骤

1. 译场（编译器核心）认 `。问簿。豫` 种类与生成模块；在芥子包里写问簿内建声明（册、置册、检、检二、聚、登、改、删、同办）。
2. 翻译器：表声明编成建表语法树；查询函数编成查询语法树，条件与投影照第五节的白名单；生成带类型的函数与结果解码。
3. 芥子加“执行预建语法树”的入口，参数按位绑定。
4. 「建册」与指纹核对，自动补加表、加可空列、加索引。
5. 先改写账户服务（表少、语句多），再包管理服务、云工作台、项目管理；全部改完，云仓删去 SQL 字符串与 `.sql` 迁移文件。
6. 第二期：访问路径（接芥子关系层）、UPSERT、聚合补全、显式迁移步骤。

## 九、未决（附推荐）

1. **动态查询**：运行时拼条件。推荐第一版只做静态查询；真要动态的，写几个查询，或退回 SQL 文字。
2. **可空列的比较**：推荐照 SQL 三值逻辑，遇空为假，另给「是空」「非空」。
3. **签名里的返回类型**：推荐必须写出；签名就是文档，类型检查拿它核对「检」推出的类型。
4. **迁移的写法**：推荐第一版只自动做加表、加可空列、加索引；删列、改名、改类型的显式迁移步骤放第二期。

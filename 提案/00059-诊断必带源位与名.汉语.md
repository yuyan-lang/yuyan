## 一、拟定事项

- 议一：诊断类型必含源位（文件、起止行列）与所在定义名；构造诊断时不给源位，编译器内部即报错，不生成一条无位置的诊断。
- 议二：语法树节点一律带源码范围；没有范围的节点在建树时即报内部错。诊断子式取所在节点的范围，不取整条语句。
- 议三：所有诊断经统一的定稿出口印出，格式为 `文件:行:列：所在定义：说明`。内部断言与底层降级错误同样带位置（#638 的 135 陷阱印出任务、模块、函数与地址）。
- 议四：标签相关的诊断直接说第几个参数、期望与实际各带不带标签（#559、#787、#805）；签名与定义两处名字不一致时报出两处的名字。
- 议五：校场样例对每条诊断断言带位置；缺位置的样例判失败。格式化与高亮从同一份源位取范围。

## 二、动机

建议表里这条已有 23 个议题。共同点是错在某一行，报错却不指那一行：

1. 签名与定义：同一标签写两遍、形参名两处写反，只报“函数应用缺少显式参数”或“参数标签不匹配”，不带位置与函数名（#646、#805、#787）。
2. 定稿诊断：顶层语句、字面量与构造子式上不带行列，告定讯只认源码范围标注节点（#739）。
3. 入口与长合成表达式：缺显式签名时整段 λ 无定位（#681）。
4. 运行时兜底：模式匹配缺分支只抛一句“缺少分支：鉴表达式”（#650）；内核与执行器的陷阱只印号，不印模块与函数（#638）。
5. 标签写反：报错落在很远的下一条语句（#758）。

## 三、设计

诊断的写法：

```
「诊断」即「组类」
　【「源位」乃「源位」也
　，「定义」乃「文」也
　，「说明」乃「文」也
　】也。
「报定」乃化「源位」又化「文」又化「文」为「诊断」者也。
```

构建语法树时，每个子式在构造处带上起止行列；诊断只从子式取，不从整条语句取。统一出口印出：

```
库/译场门/译场主。豫:317:12：函数「取单元缓」：参数「元」的类型是「单元」，实得「文」
```

内部断言与降级错误走同一个出口，带任务号、模块、函数与地址。校场样例的每条诊断断言位置、定义名与说明的关键词。

## 四、兼容与迁移

诊断的构造器改必填源位；现有调用处在编译时逐个补齐，缺位置的一律编不过。诊断的文字可以不变，行号与文件名增多，测试里按整句比对的样例改为按位置与关键词比对。格式化与高亮的取范围一并改到子式。

## 五、备选方案

只在统一出口补上调用处的语句范围：语句里有多处错时分不清是哪一处，且子式的构造错误仍拿不到范围，故不取。

## 六、未决问题

源位的行列从零数还是一数（现有一数），实施时按译场现状统一。跨文件的导入错误要不要同时印出两处位置，留待样例多了再定。

## 七、实施步骤

1. 诊断类型加必填源位与定义名，改统一出口。
2. 语法树补范围，逐个子式在构造处带。
3. 改现有诊断调用处，编译器自身与校场样例同步。
4. 校场加“诊断必带位置”的断言，缺位置判失败。
5. 格式化、高亮与错误页从同一份源位取范围。

## 八、代价

小到中。改动面广而机械，风险低；主要工作量在把语法树各构造点的范围补齐与改校场样例。

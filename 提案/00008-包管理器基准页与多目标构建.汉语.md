# 提案 00008：包管理器的基准页与多目标构建

| 项 | 内容 |
| --- | --- |
| 编号 | 00008 |
| 状态 | 草案 |
| 提出 | 2026-10-09 |
| 范围 | yuyan-cloud 包管理服务：基准页（基准结果的上报、存储、展示与告警）；可执行包的多目标自动构建与按目标下载。语言仓一侧：基准记录格式与上报工具、CI「性能对比」作业、构建器工作流、工具链包的原生生成套件 |

这是给包管理器补两块能力的提案。两块共用同一条通道：外部作业带身份上报，服务验收并存储，页面展示。

- **基准页**发布包的性能数字。第一批用户是提案 00004 的六十三个基础库与提案 00007 的“原生对比”，任何所有者都可以为自己的包上报。
- **多目标自动构建**让可执行包发布后由平台为每个目标平台构建，并在包页按目标下载。

本文只写现代汉语（AGENTS.md）。

## 一、拟定事项

| 编号 | 拟定 |
| --- | --- |
| 议一 | 包管理服务新增「基准」：接收基准记录，存成时间序列，按包、项目、后端、平台展示趋势、对照与判定 |
| 议二 | 基准记录用统一的结森行格式，由基础库「测试设施」的基准库输出；记录自带对照与目标倍数，服务据此判定「达标／未达标」，并据历史判定「退步／改善」 |
| 议三 | 上报用「基准上报令牌」（账户库新增的令牌种类，只能为本人所有者名下的包上报）；官方记录只来自语言仓 yybs 分支的 CI。GitHub OIDC 免密上报列为后续步骤 |
| 议四 | CI 新增「性能对比」作业（每晚一次，可手动触发）：运行基准入口、上报、读回判定，用一条汇总的 `::warning` 和步骤摘要告知；作业保持成功，达标不作门槛 |
| 议五 | 可执行包的每个修订自动排「目标构建」：目标矩阵为六个原生目标（苹果、林纳克斯、视窗 × 兼容六十四、臂六十四）加网页汇编；缺失的目标自动补构建，历史修订回填 |
| 议六 | 构建由外部构建器完成，协议是“服务派任务，构建器取源码，逐目标回传产物与状态”；第一个构建器是 GitHub Actions 工作流：一台 Linux 交叉生成全部目标，再在各系统真机上冒烟 |
| 议七 | 产物按目标独立存储（不受整档 16 MiB 限制），服务验收后签名；包页显示目标矩阵、状态、摘要与签名，并按访问者的系统高亮对应下载 |
| 议八 | `yy批量发布` 过渡期保持现状，随后只上传源码、文档与构建材料，运行产物全部由构建器生成 |

## 二、动机

### 基准数据散在文档里

2026-10-09 对提案 00004 的六十三个库逐库调查（读各库包说明与记录文档，不运行测试）：

- 22 个库没有任何性能数字，其中邮件格式、列存数据、矢量图、数值格式、统计 5 个库的入口已写好，没跑过。
- 29 个库只有原生对诺节的数字，没有同机 C 对照。
- 12 个库有 C 对照：全部达标的有命令行解析（比值 1.03，对照含进程启动）；部分达标的有可扩展标记（解析 3.04 倍、DTD 校验 4.50 倍）、音频的 WAV（1.77 倍）、压缩的莱齐4 解压（1.8 倍）；其余约 5 倍到数百倍，多数对照含进程启动，口径不一。
- 已有数字写在各库文档里，多为单次测量，机器与负载不统一（记录的负载从 20 到约 150），测于 2026-10-08 前后，早于 2026-10-09 的原生工具链合入。
- 性能入口几乎都在 `测试/全量/` 下或不以「。测试。豫」命名，CI 不运行。趋势、对照与目标只能靠人读文档汇总。

### CI 警告只活一轮

仓库已有先例：`应用/开发工具/原生对比` 在原生慢于 Node 时打印 `::warning`，表写进作业摘要（`.github/workflows/main.yml` 的“原生与 Node 性能对比”步骤）。警告只出现在那一轮的运行页，没有历史，也看不出趋势。性能差距要长期跟踪，需要一个固定的落脚点。

### 可执行下载只有发布者本机那一份

- `yy批量发布` 用 `uname -s`、`uname -m` 取发布者本机的系统与架构（只接受 macOS 与 Linux），生成 `运行/<系统>-<架构>.tar.gz`，内容是编译好的 `.wasm` 程序；`构建/` 同理。
- 服务端把 `运行/` 当作普通材料存取（分类 runtime），没有“目标”的概念。整档 ZIP 与单文件各限 16 MiB，装不下多个原生目标（2026-10-09 在 pit-mac 量得：`yy豫构.exe` 约 10 MB，`yy4_bs.exe` 约 32 MB）。
- 云端构建（云仓《云端构建发布设计》）的第一期已实现，生产开关关闭；构建服务（第二期）尚未建，研究结论是 Worker 的 128 MB 内存装不下工具链；各平台构建机（第四期）尚未动工。
- 结果是访问者在包页拿不到自己系统的可执行文件，除非发布者恰好在同一系统上发布。

### 工具链已能交叉生成

原生生成器 `yy原生生成` 在任意一台主机上都能生成 Mach-O、ELF、PE32+。CI 的“视窗原生样例生成”作业在 ubuntu-latest 上生成 Windows 两个架构与 macOS x86-64 的可执行文件，再由 windows-latest、windows-11-arm、macos-15-intel 运行验证（`.github/workflows/main.yml`）。所以每个平台配一台构建机并无必要：一台 Linux 构建，各系统真机只做冒烟。

## 四、设计

### 4.1 基准记录（语言仓）

一行一条结森对象（JSON Lines），字段如下。

| 字段 | 含义 |
| --- | --- |
| `版本` | 记录格式版本，现为 1 |
| `包` | `<所有者>/<包名>` |
| `项目` | 包内的基准项目路径，用 `/` 分层，如 `泽标/解压/混熵262144` |
| `后端` | `原生`、`诺节`（后续可加 `浏览器`、`豫言系统`） |
| `平台` | 测量所在平台，`<系统>-<架构>`，如 `苹果-臂六十四` |
| `提交`、`工具链` | 语言仓提交；构建所用工具链的提交 |
| `中位纳秒`、`轮数`、`预热`、`噪声` | 计时结果；`噪声` 是各轮相对中位数的绝对偏差的中位数 |
| `规模` | 每次操作处理的字节数或次数，用来换算吞吐 |
| `对照` | 可选：`名称`、`版本`、`中位纳秒`、`口径` |
| `目标` | 可选：`对照倍数`（豫言÷对照）与 `诺节倍数`（原生÷诺节） |
| `机器` | 类别（共享机、自建机、开发机）、处理器、核数、内存 |

示意：

```json
{"版本":1,"包":"豫言/压缩","项目":"泽标/解压/混熵262144","后端":"原生","平台":"苹果-臂六十四","提交":"75f0a5417","工具链":"75f0a5417","中位纳秒":3969000,"轮数":9,"预热":2,"噪声":0.04,"规模":{"字节":262144},"对照":{"名称":"zstd","版本":"1.5.7","中位纳秒":20500,"口径":"同进程内核"},"目标":{"对照倍数":3,"诺节倍数":1.0},"机器":{"类别":"共享机","处理器":"Apple M1","核数":3}}
```

约定：

- 计时：先预热，再重复取中位数，沿用基础库「测试设施」基准库的做法。
- 对照口径有三种：`同进程内核`（对照方只计内核，如 C 循环吞吐）、`端到端`（双方都含启动与读写）、`含启动`（只有一方含启动）。判定只用前两种，第三种展示比值，标“参考”。
- 目标倍数：`对照倍数` 取提案 00004 第五节的 3（第一批）或 5（其余）；`诺节倍数` 取提案 00007 议五的 1.0。两种目标可以同时给出。
- 输出：基准库增加 `记录基准`，在计时后打印以 `基准记录` 开头的一行；现有入口打印的“中位纳秒=”行保留。

### 4.2 上报与身份

- 账户库新增令牌种类「基准上报令牌」，在“凭据与安全”页生成与吊销，权限只含“为本人所有者名下的包写基准记录”。
- 令牌可以标为“官方”。官方令牌只放在语言仓的仓库机密里，作业只在 yybs 与定时触发时取用；拉取请求（含派生仓库）拿不到机密，不会上报。官方运行进入基线与告警；开发机手动上报的运行进入单独的序列，页面上可切换显示。
- 后续：GitHub Actions 的 OIDC 令牌（含 repository、ref、workflow 声明）免去长期机密，服务用基础库「密码」的 RSA 验签校验。

### 4.3 存储

D1 新增四张表（迁移编号取实施时的下一个，当前最新为 0024），列名用中文，沿用 `云端构建任务` 的风格。

| 表 | 用途 | 主要列 |
| --- | --- | --- |
| `基准机器` | 机器登记 | 编号、名称、类别、系统、架构、处理器、核数、内存、首次出现 |
| `基准运行` | 一次上报 | 编号、所有者、来源（工作流运行网址）、官方、提交、工具链提交、机器、上报者、起止时间 |
| `基准样本` | 一个项目的一次测量 | 运行、包、项目、后端、平台、中位纳秒、轮数、噪声、规模、对照名称与口径与耗时、目标倍数、判定 |
| `基准基线` | 被接受的参照运行 | 所有者、包、项目、后端、平台、运行、接受者、时间、说明 |

- 序列的键是（所有者、包、项目、后端、平台、官方）。
- 幂等键是（来源运行编号、作业、尝试号），重传同一份不重复入库。
- 原始上传（JSON 行）存 R2 的 `基准/<运行编号>.jsonl`，供审计与导出。
- 限额往大里定：单次上传 16 MiB、20 万条样本；每个所有者每天 200 次上报；样本保留 800 天，之后折叠为每日中位数；原始上传保留 800 天。

### 4.4 判定

每条样本得到两个判定。

| 维度 | 判定 | 条件 |
| --- | --- | --- |
| 目标 | 达标 | 有目标，实测倍数不超过目标 |
| 目标 | 未达标 | 有目标，实测倍数超过目标；显示实际倍数 |
| 目标 | 参考 | 对照口径为“含启动”：显示比值，不判定 |
| 目标 | 无对照 | 没有对照也没有可比的诺节记录 |
| 趋势 | 退步／改善 | 比基线变差／变好超过阈值 |
| 趋势 | 持平 | 其余 |
| 趋势 | 不稳 | 噪声超过 30%，或序列历史离散度过大；不触发告警 |
| 趋势 | 新增 | 序列的第一个官方点 |

- 基线取序列最近 5 个官方运行的中位数；维护者可以把某次运行“接受为基线”，固定下来。
- 阈值是 `max(20%, 3 × 序列历史相对离散度)`（历史离散度取最近 10 个官方运行的相对中位绝对偏差；不足 3 个运行时取 50%）。初始规则，实施时用头几周的真实数据校准。
- 告警优先用同一运行内的比值（原生÷诺节、豫言÷对照），其次用绝对耗时，以抵消共享机的速度差。

### 4.5 页面

路由：`/基准`、`/基准/<所有者>/<包名>`、`/基准/<所有者>/<包名>/<项目>`、对应的 `….svg` 徽章。官网路由的包服务前缀表（`应用/网站/入口/路由。豫` 的 `包府路径`）加入 `/基准`；包页概览加“基准”入口。

- **总览**：顶部统计（达标、未达标、参考、无对照的项数，按包组汇总，包组取“包含在”层级）；「差距总表」按差距倍数降序，列有包、项目、后端、平台、耗时、对照（名称与口径）、倍数、目标、判定、趋势小图；筛选项有包组、后端、平台、判定、官方／开发机；另有“最近退步”和“机器”两节。
- **包页**：该包全部项目的最新值与趋势小图。
- **项目详情**：折线图两张（耗时、倍数），按后端×平台出线，横轴是提交时间，悬停显示提交与机器；运行表；对照说明；原始记录下载（JSON 行、CSV）；所有者可见“接受为基线”按钮。
- **徽章**：显示“达标”或“N 倍”，可贴进包说明。
- **渲染**：服务端用豫言生成 HTML 与内联 SVG。SVG 里的文字由浏览器用页面字体绘制，服务端不需要字体。图（折线、小图、徽章）由包服务私有库实现，约二三百行；基础库「图表」暂不接入，免得把二维绘图与字体带进 Worker。
- **无脚本可用**：表与图都是静态内容；筛选沿用包列表的纯 CSS（`:has`）做法。样式沿用包服务页面的外壳。

### 4.6 CI 作业（语言仓）

- 作业名「性能对比」，运行平台同“Wasm 包起步”：ubuntu-latest、ubuntu-24.04-arm、macos-latest。每晚一次（schedule）加手动触发。推送 yybs 时照旧只跑“原生对比”的构建场景。
- 驱动：把 `应用/开发工具/原生对比` 扩展为「性能对比」（保留原有功能），或新建应用复用其计时与摘要代码，实施时定。驱动读 `性能目标.tsv`：每个基准入口一行，写明包、入口、参数、对照命令与口径、目标倍数。原生与诺节交替运行取中位数；对照命令在 runner 上有对应系统工具时运行（gzip、xz、zstd、lz4、bzip2、openssl、xmllint、flac、sqlite3 等），没有时记“无对照”。
- 上报：新工具 `yy基准上报`（`应用/发布/基准上报`）把 JSON 行 POST 到服务并读回判定，批量发布的令牌读取方式可复用。
- 告警：整个作业只发一条 `::warning title=基准::未达标 N 项、退步 M 项，详见 https://yuyan-lang.org/基准`，前 30 个差距写进步骤摘要，作业保持成功。上报失败也只发警告。
- 时限：每平台 20 分钟；入口可用 `--快` 缩小迭代数。

### 4.7 目标矩阵与自动构建

| 目标 | 常用名 | 产物 | 原生生成参数 | 冒烟运行器 | 成熟度 |
| --- | --- | --- | --- | --- | --- |
| 苹果-臂六十四 | macOS（Apple 芯片） | Mach-O，tar.gz | `苹果 臂六十四` | macos-latest | 稳定 |
| 苹果-兼容六十四 | macOS（Intel） | Mach-O，tar.gz | `苹果 兼容六十四` | macos-15-intel | 稳定 |
| 林纳克斯-兼容六十四 | Linux x86-64 | ELF，tar.gz | `Linux 兼容六十四` | ubuntu-latest | 稳定 |
| 林纳克斯-臂六十四 | Linux ARM64 | ELF，tar.gz | `Linux 臂六十四` | ubuntu-24.04-arm | 稳定 |
| 视窗-兼容六十四 | Windows x64 | PE32+，zip | `视窗 兼容六十四` | windows-latest | 预览 |
| 视窗-臂六十四 | Windows ARM64 | PE32+，zip | `视窗 臂六十四` | windows-11-arm | 预览 |
| 网页汇编 | 跨平台（Node／浏览器） | `.wasm` 加 Node 宿主，tar.gz | `豫构 构建 … --输出 x.wasm`（提案 00007 落地后写作 `--目标 网页汇编`） | ubuntu-latest | 稳定 |

- 矩阵放在云仓 `应用/包管理服务/库/构建任务/目标表。豫`，构建器每次领任务时核对自己支持的目标。
- 触发点：修订登记成功（整档上传或云端构建发布）且包类型是可执行文件，就为矩阵里每个目标写一行 `发布目标构建`（状态“排队”）并派发构建器作业。
- 补构建：定时清扫扫描“缺目标或失败可重试”的修订；发布者与所有者可手动重试；矩阵新增目标时对已发布的可执行包修订全量回填。
- 能力检查：构建器按包的接口依赖闭包对照各目标的“宿主提供”清单（`豫言操作系统/适配/` 下各适配的 `宿主提供.json`），缺接口的目标记「不支持：缺接口 X」，不算失败。
- 完整性：所有“稳定”目标都是“成功”或“不支持”时，修订标「运行材料完整」；包页显示“已完成 n／m”。“预览”目标（视窗）的状态照常显示，不影响完整性；待 Windows 的宿主接口覆盖补齐后转为“稳定”（与提案 00007 第 6 步的 Windows 原生工具链一并考虑）。

状态表 `发布目标构建`（每修订每目标一行）：修订、目标、状态（排队、构建中、成功、失败、不支持）、原因、产物键、字节、SHA-256、签名键、冒烟（未测、通过、失败）、冒烟运行器、构建器与工具链提交、日志键、时间。（修订，目标）唯一；状态迁移用触发器约束，沿用 `云端构建任务` 的做法。

### 4.8 构建器协议与第一个构建器

服务到构建器：

- 经 GitHub API 派发（`repository_dispatch`，事件 `package-build`，载荷只含修订编号），令牌是只限构建器仓库的细粒度令牌，存为 Worker 机密。
- 派发失败按 30、60、120 秒退避重投，沿用云端构建的定时清扫。

构建器到服务（身份是构建器令牌，存在构建器仓库机密里，只有回传作业持有）：

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/builder/jobs/<修订>/start` | 领取任务：返回源码短期签名地址、包身份、要构建的目标；任务置“构建中” |
| `PUT /api/builder/jobs/<修订>/targets/<目标>` | 回传目标产物（字节流，头带 SHA-256） |
| `POST /api/builder/jobs/<修订>/targets/<目标>/status` | 回传目标状态、冒烟结果、日志（至多 64 KiB） |

第一个构建器是构建器仓库（建议单独的公开仓库 `yuyan-lang/yuyan-package-builder`）里的 GitHub Actions 工作流，三段：

1. **构建**（ubuntu-latest，不持有机密）：取固定版本的工具链包（`historical-binaries` 里的 Wasm 包，按 SHA-256 核对）；取源码；`豫构 构建 … --输出 x.wasm` 得 `.wasm`；对每个原生目标运行 `yy原生生成`；打包（Unix 目标 tar.gz 保留 755 权限，视窗 zip），算 SHA-256。
2. **冒烟**（矩阵，各系统真机，不持有机密）：下载对应产物，限时运行（默认无参数、标准输入关闭、5 秒），记录退出码与装载错误。包声明可以带冒烟参数与期望退出码，字段名实施时定。
3. **回传**（持构建器令牌，只上传文件，不运行任何包代码）：逐目标 PUT 产物，POST 状态、冒烟结果与日志。

安全：

- 包名、版本先按字符集校验，只以环境变量或参数传递，不拼进 shell 命令。
- 构建与冒烟作业不持有机密；回传作业不运行包代码。
- 原生生成不执行包代码；冒烟会运行产物，所以只在无机密的一次性 runner 上进行。
- 云端构建发布设计里的服务绑定契约（`BUILDER`）保留，外部构建器是同一调度下的另一种实现；设计里第四期“各平台构建机”由“交叉生成加真机冒烟”取代。

工具链包需要加入原生生成套件：`yy原生生成.wasm`、`yy客体二号.wasm`、`yy执行器.wasm`。当前 `yuyan-wasm` 包只含编译器、豫构与 Node 宿主（`.github/workflows/main.yml` 的“发布工具链包”作业）。

### 4.9 产物存储、签名与下载

- 存储：主桶 `releases/<修订>/运行/<目标>/<文件名>`，分类仍是 runtime，下载沿用 `files/runtime/…`。单个产物至多 100 MiB（取当前套餐的请求体上限，更大的用分段上传，见未决问题）；每个修订至多 8 个目标产物。
- 验收：字节数与 SHA-256 同声明；文件头魔数与架构字段同目标（Mach-O、ELF、PE）；源码摘要同修订；构建器与工具链提交在白名单里。
- 签名：服务验收后用平台 Ed25519 密钥生成旁签，格式沿用《产物签名规范》（DER 旁签）；私钥种子存 Worker 机密，公钥公开在文档里。
- 下载：包页「可执行下载」区块列目标矩阵（目标、状态、大小、SHA-256、签名、冒烟、下载）；页面脚本按访问者的系统与架构高亮对应行；永久链接 `/packages/<所有者>/<包名>/<版本>/下载/<目标>`，版本写 `latest` 取最新；`GET /api/releases/<编号>/targets` 返回同样的 JSON。
- 兼容：已有修订的 `运行/<系统>-<架构>.tar.gz` 原样保留，包页标“发布者本机构建（网页汇编）”。可执行包的整档上传不再强制 `运行/`。
- 限额：每目标构建 30 分钟，每个修订整体 2 小时。

## 五、兼容与迁移

- 新接口都是新增，旧整档上传与旧接口不变。
- `yy批量发布` 过渡期（建议两个月）照旧生成 `运行/`；之后只传源码、文档与构建材料。
- 回填：对已发布的可执行包修订批量排目标构建；回填的预算按包数估算，一次排一批。
- 文档同步：包服务使用说明、云端构建发布设计（第二期与第四期状态）、批量发布包说明、产物签名规范、提案 00004 的性能验收条款（以基准页为准）。

## 六、备选方案

- **github-action-benchmark、Bencher、CodSpeed 等现成服务**：数据在站外，页面风格与账户体系各立一套；仓库的工具都用豫言写，所以自建。
- **只放 GitHub Pages 静态页**：缺账户与所有者体系，与包页割裂，难做按包的页签与徽章。
- **平台内构建器（Cloudflare 容器）**：留作将来的构建器实现；它缺各系统真机冒烟，也没有现成的运行器矩阵。
- **每个平台一台自建构建机**（云端构建发布设计第四期原案）：运维成本高；交叉生成使它没有必要。
- **发布者本机交叉生成全部目标**：实现最快（`yy批量发布` 加 `--全部目标`，再按目标上传），可作过渡；产物与源码的对应关系无法由平台核对，历史修订也无法补构建，所以主路径选平台构建。
- **每次推送都跑性能作业**：共享机噪声大，一天几十次推送会生成大量样本；每晚一次足以定位到“哪一天”，手动触发补足。

## 七、未决问题

1. **构建器放哪**：GitHub Actions 起步（本文的选择），还是直接做平台内容器构建器；公开仓库的构建日志公开，而包本来就是公开的。
2. **需要用户创建的东西**：构建器仓库、只限该仓库的细粒度令牌（Worker 机密）、构建器令牌（构建器仓库机密）、平台签名密钥种子（Worker 机密）。
3. **产物上限与分段上传**：Worker 请求体上限随套餐；单个产物超过 100 MiB 时改用 R2 分段上传。
4. **冒烟约定**：默认“无参数启动不报装载错误”够不够；包声明里的冒烟字段名与语义。
5. **Windows 目标成熟度**：PE32+ 写出器已在 CI 的 Windows 两架构上实跑，宿主接口的覆盖仍少于 macOS 与 Linux（提案 00007 把 Windows 原生工具链列为后续），所以先标“预览”。
6. **macOS 隔离属性与公证、Windows SmartScreen**：浏览器下载的未公证可执行文件会被系统拦一道，页面需要给出放行步骤。
7. **图在 Worker 里的成本**：趋势图的 CPU 与内存是否需要预聚合（每日中位数表）。
8. **基准机的稳定性**：GitHub 共享机波动大。自建运行器（pit-mac）可作“基准机”，但它同时服务云仓部署，且是开发机；是否划独占时段待定。
9. **目标倍数与对照命令的归属**：集中在 `性能目标.tsv`（本文的选择），还是由各包在包内声明。

## 八、实施步骤

基准页（1 至 5）与多目标构建（6 至 9）可以并行，两条线共用的令牌种类与词表（机器、目标）先做。

1. **记录格式**：`记录基准`、字段校验与解析、诺节与原生各一个入口输出合法记录。验收：测试设施的测试通过。
2. **服务端**：迁移、基准上报令牌、上报与查询接口、判定、限额。验收：豫言验收覆盖达标、未达标、参考、退步、不稳、幂等、越权。
3. **页面**：总览、包页、项目详情、徽章，官网路由前缀。验收：浏览器检查（桌面与窄屏），筛选与图可用。
4. **CI 作业**：性能对比驱动、`性能目标.tsv`、汇总警告与摘要、上报；先接已有 C 对照的 12 个库和原生对比的构建场景。验收：一次手动运行后页面有数据，运行页有警告。
5. **其余库的入口**：按提案 00004 补空白入口，登记到 `性能目标.tsv`（属 00004 的工作，接入驱动即可）。
6. **产物模型**：迁移 `发布目标构建`、目标表、构建器接口、验收与签名、包页目标矩阵与下载、永久链接。验收：假构建器驱动全部状态转移，旧修订页面不变。
7. **构建器**：工具链包加入原生生成套件；构建器仓库与工作流（构建、冒烟、回传）。验收：三个真实可执行包（如 `豫言/云设备代理`）端到端，六个原生目标在真机冒烟通过。
8. **回填与切换**：历史修订回填；`yy批量发布` 切换；文档同步。
9. **后续**：OIDC、平台内构建器、豫行目标、Windows 转正、公证与代码签名。

## 一、拟定事项

- **议一：豫行是统一的原生程序格式。** 同一个豫行文件既在豫言操作系统上运行，也经启动器在 macOS、Linux、Windows 上运行。每次发布按架构各出一份豫行（ARM64、AMD64），以后再合成一份两架构合装的豫行。
- **议二：服务门。** 豫行里的内核服务调用一律经一张固定位置的服务门：代码段开头 64 KiB，第 N 项对应服务 N，每项 16 字节。编译器写出的门项在裸机上执行 `svc #N`（ARM64）或 `int 0x80`（AMD64）；启动器装载时把门项换成转进自己的跳板。用户陷阱（服务 7）同样走门。
- **议三：启动器。** 每个宿主一个启动器 `yy豫行`，由豫言编译器直接编成本机程序，只用操作系统自带的接口（macOS 的 libSystem、Linux 的系统调用、Windows 的 kernel32）。它在自己的进程里装入豫行、换门、起跑，兼任内核与初始任务：每次服务调用就是一次函数调用，文件请求直接落到宿主文件系统。设计原则（用户 2026-10-13 定）：Docker 提供隔离，豫言提供集成。
- **议四：只用普通进程的能力。** 启动器在用户态翻译服务调用，凡能运行普通程序的机器都能运行豫行（用户 2026-10-13 定）。Hypervisor.framework、KVM、WHPX 这类硬件虚拟化接口列在第六节备选方案里。
- **议五：豫行位置无关，段按 64 KiB 对齐。** macOS 的 arm64 进程必须留出 4 GiB 的 __PAGEZERO（实测见第二节），而两架构豫行现在的各段都在 4 GiB 以下。豫言系统目标改用 macOS 已在用的相对址式：入口按 PC 相对求出锚（ARM64 的 x25、AMD64 的 r10），名义地址一律写成“锚加偏移”；映像里没有绝对代码地址，各段整体平移同一偏移即可运行。裸机内核照旧按名义地址装载（平移量为零），启动器把映像放在宿主地址空间的任意空处。64 KiB 对齐同时合乎 macOS 的 16 KiB 页与 Windows 的 64 KiB 分配粒度。（2026-10-13 第 0 步盘点后由“整体上移到 4 GiB 以上”改定，理由见实施记录。）
- **议六：工具链按“豫行加启动器”发布与自举。** 发布物改为豫行工具链包（两架构）与各宿主的启动器；Windows 由此得到原生工具链，自举起点改用豫行工具链包。网页汇编留给浏览器与云工两个网页后端。
- **议七：单文件发行。** 启动器可以自带豫行：豫行作为尾块附进启动器的可执行文件，沿用现有的 `YUYANMOD` 尾块（Linux、Windows 附在文件末尾，macOS 放进 __LINKEDIT、代码签名之前）。启动器起跑时先读自己文件的尾块，带着豫行就直接运行它，命令行参数原样交给程序。用户每个宿主下载一个文件即可运行；单独发布的启动器照旧运行命令行上给出的豫行。
- **议八：豫言内核 ABI 是原生程序的二进制边界。** 豫行格式、服务门、启动块、代办协议、退出码与寄存器约定合称豫言内核 ABI，统一写进平台接口规范，编号只增不改。源码一侧照旧有两层接口：应用用豫言操作系统接口，执行器内部用豫言操作系统底层接口。依赖宿主库的能力经接口代办进 ABI（议十一）。
- **议九：直出改为合成。** 普通程序只编一次，编成豫行；要某个宿主的本机可执行文件时，把该宿主预编好的启动器与豫行合成单文件（议七）。编译器直出 Mach-O、ELF、PE 只留给启动器自身。构建时输出名以 `。豫行` 结尾就出豫行，是本机可执行文件名（如 `yy名.exe`）就出合成的单文件。切换条件有三项，满足之前现行直出照常使用：① 速度：macOS arm64 与 Linux x86-64 上，合成的豫构冷缓存构建编译器，耗时不超过直出工具链的 1.1 倍；② 一致：三个宿主上的一致性验证与全树测试用合成的工具链全部通过；③ 能力：窗口、键鼠、声音，以及经接口代办的图形处理器与张量计算，在启动器下可用（议十一）。
- **议十：ARM64 豫行用硬件浮点。** 裸机执行器最初按纯整数设计，浮点全用软件实现。2026-10-09 起 AMD64 改用硬件浮点：预编二把客体的浮点运算写成宽浮点内在，降级成 SSE2 指令；ARM64 的宽浮点内在列为待做（`浮点降级。豫`）。豫言内核已为每个任务保存浮点状态（`内核/任务。底层。豫` 的浮点即时切换，ARM64 浮点区 528 字节），所以补上 ARM64 的宽浮点内在即可。在那之前，裸机执行器的浮点原语先照原生执行器的做法改用硬件浮点（`客体二号/说明.汉语.md`）。
- **议十一：宿主能力经两条路进 ABI。** ① 窗口、键鼠与声音：豫行照裸机的做法调内核的显示、按键、鼠标与声音服务，启动器用宿主的窗口与声音接口实现这些服务，复用原生执行器现有的窗口代码。② 图形处理器与张量计算（Metal、CUDA）：应用本来就经接口调用，宿主库只在原生适配（`豫言操作系统/适配/图形处理器原生`、`张量计算原生`）里经「系统库调用」打开。这些适配连同「系统库调用」编进启动器；豫行里的执行器遇到本机没有实现的接口函数，把调用编成“接口代办”请求发给初始任务，启动器交对应的适配办理，资源句柄留在启动器的授权表里。裸机的初始任务对这类请求按“本机无此设备”应答。
- **议十二：统一门后端与六十四位底层接口。**（用户 2026-10-14 定）豫行里只编豫言操作系统底层接口的门后端：五十个函数各对应服务门上的一项服务（110–159），参数原样放进寄存器，地址、长度、偏移都是六十四位。启动器直接用宿主后端办理这些服务，不再仿真初始任务；裸机内核把子任务的调用转交初始任务，初始任务用它的裸机后端（ext4、网络栈）办理，缓冲由内核在两个任务之间拷贝。底层接口随之改成六十四位。整块代办里的文件、网络与进程请求、节点原语 210–219 与零拷贝 202、203 一次删去，不留旧协议。

## 二、动机

### 每次发布四份原生工具链

CI 现在为 ubuntu-latest、ubuntu-24.04-arm、macos-latest 各出一份原生工具链（`yuyan-native-<平台>.tar.gz`），Windows 与自举起点用 Wasm 工具链包加诺节（`.github/workflows/main.yml`）。为此编译器维护 Mach-O、ELF、PE 三种写出器（`豫言操作系统/裸机/库/裸机后端` 的 马赫格式写出、链接格式写出、视窗格式写出），执行器维护苹果、林纳克斯、视窗三套平台层（`豫言操作系统/裸机/客体二号/平台接口/`），再加上裸机的豫行与平台层。同一个程序编出四五份，各份的行为差异分别排查。

### 豫行本身已经与宿主无关

- 豫行程序与外界的接触全部经执行器的「平台」导入：裸机后端只绑定这一个模块，把它映成 75 个内核服务，编号 0–84（`整数降级。豫` 的「裸机服务号」）。
- 子任务的文件与网络请求本来就交给初始任务代办（`客体二号/远程文件。底层。豫`）：可代办的原语是 28–37、39、61–64、72、73、180、200、210–217、220–229；整块代办把请求编码进子任务自己的内存，只发一条消息（高字节 0x61），由初始任务读写对方内存办理。
- ARM64 后端本来就把 x18 留给宿主（苹果与视窗的 ARM64 保留它，见 `臂降级原语。豫` 开头的寄存器约定），生成的代码合乎这两个宿主的寄存器约定。

所以只要有一方替豫行实现这些内核服务、替它办理代办请求，豫行就能在那里运行。

### 硬件虚拟化取决于宿主条件

用 Hypervisor.framework、KVM、WHPX 运行豫行，要求程序带 hypervisor 权益签名、宿主给出 `/dev/kvm` 权限、Windows 开着“虚拟机监控程序平台”；虚拟机、容器与 CI 运行器里常常缺这些条件。直接编成的本机程序在任何能运行普通程序的机器上都能运行。启动器沿用后者：它自己就是一个本机程序。

### 实测：macOS 的地址空间

2026-10-13，本机 macOS 27（Darwin 27.0.0）arm64。测法：复制原生程序 `yy终端尺寸查询.exe`，用 lldb 在 `write` 处停下，在进程里调用 `mmap`、`getpagesize`。

| 试验 | 结果 |
| --- | --- |
| 把它的 __PAGEZERO 改成 4 KiB 并重新签名 | 内核在执行时杀掉进程（退出码 137）；只重新签名的对照照常运行（退出码 0） |
| `mmap` 固定地址 0x40200000（ARM64 豫行的用户区） | 失败 |
| `mmap` 固定地址 0x20000010000（2 TiB），读写 | 成功 |
| `MAP_JIT` 加 `MAP_FIXED` | 失败，EINVAL |
| `MAP_JIT` 以 0x20000100000 为提示地址 | 正好映在提示地址 |
| 页大小 | 16 KiB |
| 在原生程序的代码签名之后追加 48 MiB | 照常运行；`codesign -v --strict` 报“main executable failed strict validation” |
| 尾块放在签名之内的原生工具（`yy豫构.exe`、`yy4_bs.exe`，含 `YUYANMOD` 尾标） | `codesign -v --strict` 通过 |

原生映像自身另有一条限制：映像须整个落在 0x180000000 之下（`苹果可执行。豫` 的「苹果零页」说明）；这条只管映像本身，`mmap` 现映的区域可以放在 4 GiB 以上的空处（上表 2 TiB 处即是）。

## 三、目标与范围

目标：

1. 同一个豫行文件在豫言操作系统、macOS arm64、Linux x86-64 与 arm64、Windows x86-64 上运行，输出相同。
2. 工具链（豫构、编译器、格式化等）以豫行发布，各宿主只装一个启动器。
3. macOS arm64 上，启动器下的豫构冷缓存构建编译器，耗时不超过同机原生 Mach-O 工具链的 1.1 倍。
4. 用户每个宿主只下载一个文件：自带豫行的启动器，双击或在终端里直接运行。

范围：豫行格式与裸机后端、两架构内核的装载、ARM64 硬件浮点、启动器、宿主能力与接口代办、单文件发行、直出改为合成、CI 的发布与自举。

后续版本的事项：两架构合装豫行；macOS 的 arm64 与 x86_64 两片合成一个通用单文件；Windows ARM64 与 Intel macOS 的启动器；裸机的图形处理器驱动；接口代办的大块数据在进程内零拷贝。

## 四、设计

### 1. 架构总览

```text
                        豫言程序
                           │  豫言操作系统接口（应用 API：源码边界，各后端共用）
            ┌──────────────┴───────────────┐
   网页后端（浏览器、云工）              原生：编成豫行（每个架构编一次）
   网页汇编加宿主胶水                      │  执行器（客体二号）：原语、回收、装载、GC 与 WASI 垫片
                                           │  豫言操作系统底层接口（执行器内部的窄腰）
                                           │  底层接口的门后端：五十个函数各是一项服务（议十二）
                      ════════ 豫言内核 ABI（二进制边界）════════
                      豫行格式、服务门、启动块、代办协议、退出码
                           ┌───────────────┴────────────────┐
                   豫言内核（裸机）                    启动器 yy豫行（每个宿主一个）
                   门项是 svc 或 int 0x80              门项转进跳板与服务分派
                   驱动、ext4、网络栈、初始任务          任务是宿主进程，内存用 mmap
                                                       底层服务直接交宿主后端（议十二）
                                                         → 底层接口的宿主后端
                                                         → libSystem、Linux 系统调用、kernel32
```

三层边界：

- **豫言操作系统接口**：应用写程序用的 API，照旧。网页后端照旧把它直接绑到宿主胶水上。
- **豫言操作系统底层接口**：执行器内部的窄腰，GC 垫片与 WASI 垫片架在它上面（`豫言操作系统底层接口/总纲.汉语.md`）。它照旧有裸机、macOS、Linux、Windows 四个后端：豫行里固定编进门后端（议十二），三个宿主后端编进启动器，直接办理底层服务；裸机的后端留在初始任务里。同一份执行器代码在两边各编一次，两边的行为由此一致。
- **豫言内核 ABI**：原生程序的二进制边界，见第 2 小节。

挪了位置的部分：

| 部分 | 现在 | 提案之后 |
| --- | --- | --- |
| 苹果、林纳克斯、视窗平台层与底层接口的宿主后端 | 编译时选一套，链进每个原生程序 | 只编进启动器 |
| 编译器的原生目标 | Mach-O、ELF、PE、豫行 | 程序只编豫行；三种宿主格式只用来编启动器 |
| 文件与网络 | 执行器直接调宿主 | 执行器经门后端调底层服务；启动器交宿主后端办理，裸机内核转交初始任务（议十二） |
| 程序里的执行器 | 每个宿主一个变体 | 只有一个变体，底层接口走门后端（议十二） |

### 2. 豫言内核 ABI

组成：

1. **豫行格式**：版本 3、段布局与 64 KiB 对齐、入口与栈顶（第 4 小节）。
2. **服务门**：位置、门项大小、服务号、参数寄存器、返回值；指针参数是线性内存里的偏移（第 3 小节）。
3. **启动块**：命令行参数、程序名与环境的编码（服务 38）。
4. **代办协议**：请求是原语号加按执行器引用编码序列化的参数，应答是错误码加编码后的结果；整块请求只发一条消息（高字节 0x61），大文件按 16 MiB 分段（`客体二号/远程文件。底层。豫`）。接口代办是其中一类请求，带接口包名、函数名与签名摘要（第 12 小节）。
5. **退出与故障**：退出码约定（打断为 130，陷阱与故障各有其码）与故障诊断的格式。
6. **寄存器约定**：线性基址（ARM64 x28、AMD64 r9）、全局基址与线性长度由入口设置；ARM64 把 x18 留给宿主。

规范：`客体二号/平台接口/规范.汉语.md` 与 `平台。底层接口。豫` 是 ABI 的唯一出处；代办协议与可代办的原语号一并写进这篇规范。

扩展规则：

- 新能力加新的服务号或新的可代办原语号，同时写进规范；裸机内核与启动器各自实现，或按“本机无此设备”应答。
- 编号只增不改：已有编号的参数与语义保持原样，要改就另加新号。
- 程序收到 −1（未知服务）就走“没有这项能力”的路径；规范里“旧内核按未知服务返回 −1”是现成的先例。
- 依赖宿主库的能力这样进 ABI（议十一）：窗口、键鼠与声音走内核的显示、按键与声音服务，由启动器用宿主接口实现；图形处理器与张量计算走接口代办，由编进启动器的原生适配经「系统库调用」打开 Metal、CUDA 办理。裸机上由初始任务调驱动办理，暂缺驱动时按“本机无此设备”应答。
- 豫行文件头的版本号管格式；服务与原语的集合由规范列出，启动器的新版本只增不减。

### 3. 服务门

- 位置：代码段开头 64 KiB。第 N 项在“代码段起址 + N × 16”，共 4096 项；现有服务号 0–84 都在前面，最后 4 KiB 留给启动器写公共跳板与地址表。
- 裸机门项由编译器写出：ARM64 是 `svc #N; ret`，AMD64 是 `mov eax, N; int 0x80; ret`，余下补零。
- 平台导入的桩改为调用门项（ARM64 `bl`，AMD64 `call`）。参数照旧：寄存器与现行服务约定相同，指针参数仍是线性内存里的偏移。
- 用户陷阱（服务 7，含函数序言的栈溢出检查触发的陷阱）也调用门项。
- 内核照旧把代码段映进任务，门项就是普通代码，内核的服务入口照旧。

### 4. 地址布局与对齐

- **相对址式**：豫言系统目标与 macOS、ARM64 Windows 一样用相对址式（`降级目标。豫` 的「目标相对」「目标址式」）。入口用 `adr`（ARM64）或 `lea rip`（AMD64）求出锚，全局量、数据段描述、传参暂存、页数格、栈界都按锚访问；代码之间本来只有相对跳转，跳表项是相对跳转，栈图表只存代码偏移。
- **布局**：照 macOS 的排法，代码在下，数据段与栈在上、靠近锚，所有按锚访问的地址都在锚之上 4 GiB 以内（AMD64 在 2 GiB 以内）。各段落在两架构内核「按段建任务」现有的窗口里。
- **动态区**：线性内存迁入的动态区离锚太远，相对偏移放不下，改为间接：入口向平台要动态区基址（新增内核服务“动态区基址”：裸机内核返回 1 TiB，启动器返回自己映射的地址），存进数据段里的一个格，增长助手从格里读，与 macOS ARM64 现有的做法相同。
- **对齐与版本**：段的虚址、内存长度、文件内偏移按 64 KiB 对齐。豫行的版本号改为 3，编译器只写版本 3，两架构内核只认版本 3，一次切换。
- **内核**：只需认版本 3、接受新布局的段与新服务；内核据此判断线性内存是否还在静态区的那条比较随静态区的新位置改。

### 5. 启动器

用法：`yy豫行 程序。豫行 参数…`。

- **装载**：读文件头与段表，按段映到原虚址。Linux 用 `MAP_FIXED_NOREPLACE`，Windows 用 `VirtualAlloc` 指定地址；macOS 的代码段用 `MAP_JIT` 加提示地址并核对落点，与执行器装单元的做法相同（`客体二号/单元装载。底层。豫`）。落点与段表不符时报错退出。
- **换门**：门项写成 `movz x16, #N; b 门公共`（ARM64）或 `mov eax, N; jmp 门公共`（AMD64）。「门公共」保存豫行的现场（ARM64 的 x25 全局基址、x28 线性基址、x15 线性长度与被调用者保存寄存器，AMD64 的对应寄存器，以及栈指针与返回地址），换上启动器自己的基址与栈，调用启动器的服务分派，再换回原现场返回。
- **起跑**：照文件头的入口与栈顶起跑。豫行在启动器里看到的平台就是豫言操作系统（平台号 1），身份是动态子任务；启动块（服务 38）里的命令行参数、程序名与环境取自宿主。
- **故障**：宿主的 SIGSEGV、SIGBUS、SIGILL（Windows 的向量化异常）按裸机“故障”的退出码与诊断格式结束进程。
- **写法**：启动器是在宿主平台上编出的执行器（客体二号）加一个新模块「豫行客体」。代办请求的服务端复用 `远程文件。底层。豫` 里初始任务一侧的办理代码，经宿主平台层落到 libSystem、Linux 系统调用或 kernel32。

### 7. 文件与网络

（议十二起由第 13 小节取代：文件与网络改走统一门后端。下面是此前的做法。）

- **文件**：豫行在子任务里把文件原语编成整块请求发给初始任务；启动器收到后直接在宿主上办理，把结果写回豫行的应答缓冲。路径就是宿主路径。要模拟豫言操作系统的目录（如 `/工具`、`/源`）时，沿用原生执行器的环境变量「豫言根目录」挂一个虚根。
- **网络**：网络原语 220–229 已在代办之列，启动器同样就地用宿主套接字办理。标准库的传输控制原语 77–90 加进代办之列，裸机的子任务也随之能联网。
- 两架构的子任务都走整块代办；逐条消息每条三字节的旧协议留作后备。

### 8. 发布与自举

- CI 每次提交生成豫行工具链包：ARM64、AMD64 各一份 `yy豫构`、`yy4_bs`、`yy格式化` 等。启动器在各平台的作业里构建，按版本发布，版本相同就复用。
- 新检出的仓库下载豫行工具链包与本机的启动器，经启动器运行豫构做原生自举；Windows 走同一条路。Wasm 工具链包留给浏览器与云工后端的构建。
- 启动器自己由编译器直出 Mach-O、ELF、PE。

### 9. 单文件发行

- **格式**：沿用三种宿主格式现有的尾块（`马赫格式写出。豫`、`林纳克斯可执行。豫`、`视窗可执行。豫`）：块后紧跟 16 字节尾标，“YUYANMOD”加 8 字节长度。块的内容就是整个豫行文件，以豫行魔数开头，启动器据魔数认出自带的豫行，与执行器自带的预编模块区分开。
- **运行**：启动器起跑时照执行器现有的读法读自己文件的尾标（`客体二号/原生装载。底层。豫`「读取可执行文件自带的模块」）。带着豫行就从文件里映出各段运行，程序名是这个可执行文件的路径，命令行参数原样交给程序；文件里只有启动器时，照 `yy豫行 程序。豫行 参数…` 运行。
- **合成**：豫构的「发行」加一种单文件产物，输入是豫行与目标宿主的启动器。Linux 与 Windows 拷一份启动器、附上豫行与尾标即成，直接拼接。macOS 把豫行放进 __LINKEDIT、代码签名之前，再重算签名的页散列，与马赫格式写出现有的尾块做法相同；第二节实测表明，附在签名之后的文件虽能运行，过不了严格签名校验。
- **一个文件对应一个宿主**（操作系统 × 架构）。程序只编一次，各宿主的单文件由同一个豫行机械合成。

### 10. 直出与合成

- **构建产物**：输出名以 `。豫行` 结尾时出豫行，各系统通用；输出名是本机可执行文件名时，取本机的启动器与新编的豫行合成单文件；网页后端照旧出 `.wasm`。
- **启动器**：编译器照旧直出 Mach-O、ELF、PE，只用于启动器；启动器按版本发布，合成时按目标宿主取用。
- **切换**：议九的三项条件满足之前，现行的直出照常使用，CI 同时构建两种产物并比较；三项都满足后，默认构建与工具链发布改为合成。

### 11. ARM64 硬件浮点

- **第一步**：裸机执行器在 ARM64 上的浮点原语改用硬件浮点，照原生执行器的做法复用底层库的硬件浮点内在。客体的浮点运算照旧调用执行器，每次调用里改用硬件指令计算。
- **第二步**：补上 ARM64 的宽浮点内在，照 `兼浮点降级。豫` 的做法由降级器把客体浮点运算展开成 ARM64 的浮点指令，省去调用。
- **核对**：硬浮探针（`普通探针/硬浮探针。脚本。豫`）在诺节、AMD64 与 ARM64 上的位形逐字相同。

### 12. 宿主能力与接口代办

| 能力 | 豫行里的路径 | 启动器的做法 |
| --- | --- | --- |
| 窗口与画面 | 显示服务：提交帧 32、帧缓冲信息 33、显示模式 57–59 | 宿主窗口：macOS 用原生执行器现有的窗口代码，Linux 与 Windows 用各自的窗口接口 |
| 键鼠 | 按键服务 53、54，鼠标服务 36、47 | 宿主窗口的输入事件 |
| 声音 | 声音服务 80–84 | 宿主的声音接口 |
| 图形处理器、张量计算 | 接口代办 | 编进启动器的原生适配（`适配/图形处理器原生`、`适配/张量计算原生`），经「系统库调用」打开 Metal、CUDA |

- **接口代办**：执行器为每个本机没有实现的接口导入生成代办桩。请求带接口包名、函数名与签名摘要，参数沿用代办协议的引用编码；字节数组拷贝一次，资源句柄留在启动器的授权表里，豫行只拿句柄号。启动器按自己的宿主支持清单核对接口与签名，不支持的按“本机无此设备”应答。
- **线程**：macOS 的窗口操作要在主线程上做。启动器把主线程留给宿主的事件循环，豫行在另一个线程上运行，显示服务转交主线程办理。
- **裸机**：同一类请求交初始任务，按“本机无此设备”应答；裸机的图形处理器驱动留待后续版本。

### 13. 统一门后端与六十四位底层接口

议十二的起因：按第 7 小节的做法，豫行在启动器下仍是子任务，每个文件请求编码成代办消息，启动器解码、办理、再编码回去，启动器本身又是一整个执行器。实测（实施记录“第 10 步前测”）合成工具链真冷构建编译器为原生的 1.7 至 1.8 倍，不派工作者的单进程类型检查也慢 1.5 倍，零拷贝代办没有可测改善。差别不在系统调用本身，而在这层仿真。

- **底层接口改成六十四位**：句柄、标志、模式与状态码仍是 32 位整数；地址、长度、偏移、大小与纳秒改为六十四位，一个参数传一个量，不再拆成低、高两半；结果照旧写进出址（六十四位地址）。GC 垫层直接把堆里的缓冲地址交给底层接口，去掉低址中转缓冲；WASI 垫层把三十二位的值零扩展。四个后端（裸机、macOS、Linux、Windows）随之改签名，《调用约定》同步改写。
- **服务号**：底层基础 110–120，底层句柄 121–133，底层文件 134–142，底层网络 143–149，底层终端 150–151，底层进程 152–154，底层显示 155–159，各组内按该包规范里函数的次序排。
- **寄存器**：参数扩到六个，ARM64 为 x0–x5，AMD64 为 rdi、rsi、rdx、rcx、r8、r9（前四个与现有服务相同）；返回值是状态码。指针参数是调用者线性内存里的六十四位地址。
- **豫行一侧**：执行器在豫行里走原生那套代码（原生文件原语、原生子进程、原生网络原语等），它们架在底层接口上；豫行里的底层接口只有门后端，每个函数就是一次过门。裸机子任务的代办客户端（远程文件里的文件、网络与进程请求）删去。
- **启动器一侧**：每项服务交给启动器自己的宿主后端（libSystem、Linux 系统调用、kernel32）。客体缓冲的绝对地址减去启动器的线性内存基址，就是启动器线性内存里的六十四位地址，宿主后端直接使用。运行程序起一个新的启动器进程跑同一个豫行，常驻工作者照旧。启动器只剩门的分派与这层映射，不再仿真初始任务。
- **裸机一侧**：初始任务照旧直接调用裸机后端，它是文件与网络的服务方。子任务过门时，内核把（服务号，六个参数，子任务号）排进初始任务的请求队列并挂起子任务；初始任务的服务循环用裸机后端办理，每个子任务一张句柄表（子任务的句柄号对到初始任务里打开的句柄）；缓冲经内核在两个任务之间拷贝（读他任务、写他任务扩到六十四位地址）；办完由内核写回状态码与出址并唤醒子任务。子任务的句柄 0、1、2 照旧接到父任务的捕获与输入。运行程序由初始任务装载并建任务。
- **删去的部分**：整块代办里的文件、网络与进程请求（原语 28–39、72、73、117–128、173、180、200–203、210–229 的远程转发），节点原语 210–219（林兼容层改用底层接口），零拷贝 202、203，远程分段上限与分段读写，启动器里「豫行代办文件」等仿真初始任务的部分。显示代办、系统库代办与接口代办另行保留。
- **切换与验收**：一次切换，不留旧协议。验收：macOS 与 Linux 上合成工具链真冷构建编译器并比较原生、全树测试分片；两架构 QEMU 起机、命令壳、桌面终端起子程序并读写文件、系统内造盘。
- **实施（2026-10-14，第一部分：文件）**：过门的落法改为“底层请求消息”：子任务把服务号与六个参数（各 8 字节）写进自己的底层请求块，向句柄 0 发一条消息（标 0x64），等应答（标 0x74，低 24 位为状态码）。裸机上由初始任务的消息循环办理（经服务 41、42 读写子任务内存），启动器在客体发消息的那次服务里当场交宿主后端办理；两边都不改内核、不加门寄存器，豫行里只有这一种落法。子任务的文件原语改按原生的做法在本任务里执行，底层调用经转送；传输控制随后也改经转送（实施记录“网络部分”）；进程随后在启动器下切换（实施记录“进程部分”）：客体探到服务方能办进程（宿主门）时，句柄 0–2 也转送，子程序与常驻工作者按原生的做法起，运行程序、建管道、取进程退出码与终止进程经转送，启动器删去任务仿真，合成真冷构建编译器在 Linux x86-64 上由原生的 2.0 倍降到约 1.2 倍；裸机初始任务随后也办底层进程（实施记录“裸机进程部分”），子任务一律按原生的做法起子程序。显示（显示代办）暂走原路；数据报交换 176 与林兼容层的节点原语 210–219、网络原语 220–229 随后也改经底层转送（底层文件 0.2.0 加建链与改模式，底层网络 0.2.0 加数据报与套接字地址，服务号 163–169；林兼容层自带一个小的转送客户端），整块代办只剩系统库原语；执行器内部仍是三十二位地址经中转缓冲。详见实施记录“第 11 步”。

## 五、兼容与迁移

- 豫行版本 3 一次切换：编译器只写版本 3，两架构内核只认版本 3，启动盘与系统内造盘随之重造。
- 现行的 Mach-O、ELF、PE 直出照常使用；议九的三项切换条件满足后，普通程序改为合成，直出只留给启动器，发布与自举随之改为“豫行加启动器”。
- 执行器的苹果、林纳克斯、视窗平台层继续用在启动器里。

## 六、备选方案

- **硬件虚拟化**：用 Hypervisor.framework、KVM、WHPX 为每个豫行开一个轻虚拟机，原样运行带 `svc` 的豫行。它要求宿主具备第二节所列的虚拟化条件；用户 2026-10-13 定采用启动器。
- **各宿主各出原生程序（现状）**：每次发布四份以上，行为差异分别排查。
- **发布豫汇，在目标机上编译**：与架构无关；启动器要带上整个后端，首次运行要编译。可作为合装豫行之外的另一条路，后续版本再议。
- **装载时改写 `svc` 指令**：要靠反汇编找出每一处；服务门把调用点集中在一处，更直接。
- **布局整体上移到 4 GiB 以上**：初稿的做法。AMD64 绝对址式里的 `[disp32]`、`cmp rsp, imm32`、`mov r32, imm32` 在 2 GiB 以上全部失效，最后仍得改成相对址式；还要改两架构内核的窗口、页表与开机介质；1 TiB 的动态区在 39 位虚址的 ARM64 Linux 上也放不下。第 0 步盘点后改用相对址式。
- **一个文件通吃所有操作系统**（如 Cosmopolitan 的 APE 多格式文件）：macOS arm64 只执行签了名的 Mach-O，这类文件要靠外壳脚本或另装的装载器起步。按宿主各出一个单文件，每个都是该宿主的正规可执行文件，下载即可运行。

## 七、未决问题

1. 段对齐：64 KiB（推荐）或 16 KiB。
2. macOS 的代码段：`MAP_JIT` 加提示地址（推荐，执行器装单元已用此法），或先读写再改成可执行（lldb 下可行；调试状态会放宽签名检查，要在无调试器时实测）。
3. 标准错误：裸机控制台只有一条流，启动器先全部写到标准输出；分开两条流留待后续版本。
4. 单文件的尾标：沿用“YUYANMOD”、按豫行魔数区分（推荐），或另立一个尾标。

## 八、实施步骤

0. **盘点**：两架构豫行里写死的地址与对宿主的假设（入口设的寄存器、栈下界、大段与动态区、各服务的参数约定、直接读写内核内存的地方）；核对 ARM64 子任务的整块代办；在三个宿主上试映初拟基址。
1. **位置无关布局**：豫言系统目标改用相对址式、照 macOS 排布、动态区基址改间接、64 KiB 对齐、豫行版本 3，编译器与两架构内核一起改；QEMU 冒烟验收（两架构开机壳、构建你好）。
2. **服务门**：平台导入的桩、用户陷阱与栈溢出检查改经门；裸机行为照旧，同样以 QEMU 冒烟验收。
3. **ARM64 硬件浮点**：照第四节第 11 小节两步走；硬浮探针在诺节与两架构上逐字相同。
4. **macOS arm64 启动器**：装载、换门、第四节第 6 小节的服务、文件代办。验收：`yy豫行 yy豫构 构建 你好` 正常运行；用它把编译器编成豫行，产物与原生工具链加 `--目标系统 豫言 --目标架构 臂` 编出的逐字节相同；耗时对照第三节目标 3。
5. **Linux 与 Windows 启动器**：Linux x86-64、arm64 与 Windows x86-64，验收同第 4 步。
6. **单文件发行**：启动器读自身尾块；豫构的「发行」加单文件产物。验收：单文件的豫构在三个宿主上直接运行，macOS 上 `codesign -v --strict` 通过。
7. **网络代办**：220–229 在启动器里办理，77–90 加进代办之列。
8. **宿主能力**：窗口、键鼠与声音的内核服务在启动器里实现；接口代办，以及编进启动器的图形处理器、张量计算原生适配。验收：平铺桌面在 macOS 的启动器下开窗运行；张量计算的现有测试经接口代办通过。
9. **发布与自举**：照第四节第 8、9 小节改 CI 与新检出的起步流程，Windows 作业改用启动器。
10. **直出改为合成**：议九的三项条件满足后，默认构建与工具链发布改为合成，直出只留给启动器。
11. **统一门后端**：照第四节第 13 小节把底层接口改成六十四位、豫行改用门后端、启动器与裸机内核实现底层服务，删去旧协议，一次切换。验收同该小节。
12. **后续版本**：两架构合装豫行；macOS 通用单文件；裸机的图形处理器驱动。

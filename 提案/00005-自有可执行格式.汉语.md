# 提案 00005：自有可执行格式

| 项 | 内容 |
| --- | --- |
| 编号 | 00005 |
| 状态 | 讨论中 |
| 提出 | 2026-10-08 |
| 范围 | 豫言操作系统的原生可执行格式；裸机后端的写出；开机程序与子程序的装载（内核起第一个任务、用户态装载器、内核的通用调用）；工具与系统里生成的程序；造盘 |

这是给豫言操作系统定一种自己的可执行格式的提案。按总体架构的“各后端并列”，执行边界是中文 Wasm IR，`.wasm` 只是它的一个目标；原生后端在 Linux 上写 ELF，在 macOS 上写 Mach-O。豫言操作系统也是一个目标，它的原生程序应当是自己格式的可执行文件，由用户态装载，而不是把 `.wasm` 当可执行文件带进系统、开机再解析。用户 2026-10-08 定下这个方向（“native 需要有 yuyan-os 的自有可执行格式”），并定为写成提案。

本文只写现代汉语（AGENTS.md）。

## 一、拟定事项

- **议一：格式。** 豫言操作系统的原生程序用一种自己的可执行格式（暂名「豫言可执行格式」）：文件头加段表，每段写明种类、在文件中的位置与长度、虚拟地址、内存长度与权限。不做动态链接与重定位。
- **议二：生成。** 裸机后端从中文 Wasm IR 的整数层生成机器码，连同数据写成这种文件，与 ELF、Mach-O 的写出并列。
- **议三：装载。** 子程序由用户态装载：父任务读文件、拆段表，用内核的通用调用建任务。内核只在起第一个任务时读段表。
- **议四：开机程序与工具。** 壳与工具都改成这种文件。内核镜像不再嵌入壳.wasm；去掉开机程序写死的大段区与 3 GiB 映射，去掉工具映像引导模块、内核映像表与“长度加三处样本”的匹配。
- **议五：系统里生成。** 系统里新编的程序也能写成这种文件并原生运行；系统内造盘照旧与宿主逐字节相同。

## 二、动机

### 大段区溢出

2026-10-08，yybs 4e9d88cea 上「豫言系统 启动盘 --预编二」报“裸机大段区超过 0x3D0000 字节：大段字节 14512444”，最新 yybs 造不出启动盘。原因：

- 开机程序把整份壳.wasm 嵌在内核镜像的用户载荷里：末尾 448 KiB 放模块窗口，前段作被动数据段放进 0x400000 起的大段区。开机时执行器把两段拼进线性内存，再解析、实例化、运行。
- 大段区夹在用户载荷与外置内核代码（0x7D0000 起）之间，造盘上限 3.8 MiB，开机程序只映 2 MiB。
- 867e8aac6 让壳核心静态接入「中文处理」的完整数据（拼音三份约 11.3 MB，另有 Unicode 属性表），壳.wasm 从约 1.7 MB 涨到约 15 MB。

壳以后还会变大，只放大这块窗口治不了根。

### 内核替具体程序做装载

- 开机程序的预编机器码是第三个引导模块，内核写死映到用户虚址 3 GiB；大段区也由内核写死映在 0x400000。
- 工具映像（128 字节头、2 MiB 用户载荷、至多 4 MiB 大段区、机器码）作第四个起的引导模块。内核开机登记映像表（0x1F0000）；服务 37「装载任务」按映像号把载荷拷进子任务，机器码映到 3 GiB，大段区只读映到 0x400000。
- 执行器从数据盘读到 `.wasm` 后，按长度与三处样本认出对应的工具映像。

这些都是写在内核里、针对具体程序布局的装载逻辑，与微内核“装载器在用户态”的边界（系统编程语法方案「已澄清方向与微内核边界」一节）相反。工具映像本身已是可执行格式的雏形，只是只能作引导模块。

### 系统里新编的程序只能解释执行

原生映像只能在造盘时作为引导模块登记，所以系统里新编出来的程序只能由执行器解释执行（见持续改进目标「系统内工具链」的待办）。

### `.wasm` 在系统里是多余的中间形态

预编二已把每个客体函数编成机器码（yy4_bs.exe 含 13,696 个客体函数），但运行时仍依赖模块字节：未内联的指令调后备处理函数时，传入的是立即数在模块字节里的地址（`豫言操作系统/裸机/库/裸机后端/预编二转译。豫`，yy4_bs.exe 里约 6.9 万处）；执行器开机还要从模块解析类型表、初始化全局与数据段（yy4_bs.exe `--version` 每次约 4600 万条指令，不到 10 毫秒）。这三项数据由另一个会话 2026-10-08 在 macOS 上测得。

## 三、目标与范围

做：

- 格式规范、裸机后端的写出、豫言写的查看工具。
- 开机程序：引导器装入壳的可执行文件，内核按段表建初始任务。
- 子程序：用户态装载器与内核的通用调用；豫构、编译器、豫言系统改为数据盘上的可执行文件。
- 系统里的生成器写可执行文件；系统内造盘照旧逐字节相同。

留待后续：

- 动态链接与共享运行时（第一版每个文件各带一份执行器运行时，与 yy4_bs.exe 相同）。
- 去掉文件里的模块字节段（第十一节第 5 步）。
- 能力清单的检查与签名。
- ARM64（先做 AMD64）。

## 四、设计：格式

### 4.1 文件头

| 字段 | 说明 |
| --- | --- |
| 魔数 | 暂定「豫行」两字的 UTF-8 六字节，补两字节零 |
| 版本 | 从 1 起 |
| 指令集 | 1 为 AMD64，2 为 ARM64 |
| 入口 | 入口的虚拟地址 |
| 栈顶 | 初始栈指针 |
| 段表 | 段表在文件中的偏移与项数 |
| 附录 | 附录在文件中的偏移与长度（可为零） |

整数一律小端。字节布局在实施第 1 步定下，写进规范。

### 4.2 段表

每项记：种类（代码、只读数据、可写数据、全零）、权限（读、写、执行）、虚拟地址、内存长度、文件内偏移、文件内长度。内存长度超出文件内长度的部分补零，全零段的文件内长度为零。地址与长度按 4 KiB 对齐；段不得落进内核保留的地址范围（AMD64 现有 0x7D0000 起的外置内核代码等，以内核规范为准）。

段表项的布局同时就是内核通用调用的参数格式（第五节），装载器把段表项交给内核时，只需把文件内偏移换成自己缓冲里的地址。

### 4.3 附录

给人看的信息：符号表（函数名与地址，供调用栈、剖析与崩溃报告用）、包名与版本；以后加能力清单与回收用的栈映射。文字一律 UTF-8。

### 4.4 第一版的段

按现在开机程序与工具映像的布局排段，生成器改动最少：

- 代码段：预编机器码（执行器与程序编在一起），映在 3 GiB。
- 用户载荷段：0x200000 起的跳板、元数据与初始线性内存，可写。
- 模块字节段：程序的 `.wasm` 字节，只读，放在长度不受限的高地址（取代大段区与模块窗口，具体地址实施时定）。
- 栈：全零段。

## 五、设计：装载

### 5.1 第一个任务

引导器把壳的可执行文件作为引导模块装入，取代现在的第三个模块（预编机器码）；内核镜像不再带用户载荷里的嵌入壳。内核开机核对魔数、版本与指令集，按段表给初始任务分配物理块，拷入或映射各段，设好权限，跳到入口。这是内核唯一读这个格式的地方。

### 5.2 子程序

父任务的执行器在用户态读可执行文件，核对文件头，把各段读进自己的缓冲，再用一个内核通用调用建任务。参数是段描述表（格式同段表项，文件内偏移换成父任务缓冲里的地址）、入口与栈顶。内核为新任务建地址空间、分配块、拷入各段、设权限、启动；它不解析文件，也不知道这是哪个程序。这取代服务 37 的映像号参数、映像表与样本匹配。

### 5.3 内核调用

新增服务「按段建任务」（编号实施时定），参数与错误码写进内核规范。工具迁完后，删去服务 37、38、40 里与映像有关的部分。

## 六、设计：生成与工具

- 裸机后端（`豫言操作系统/裸机/库/裸机后端`）加「可执行文件写出」，与 Mach-O、ELF 的写出并列。预编二的裸机路径改出一个可执行文件，不再出“引导模块映像加用户载荷”。
- 查看工具：列出文件头、段表与附录。
- 造盘：壳的可执行文件作引导模块；工具（yy豫构、yy4_bs、yy豫言系统）的可执行文件放数据盘 `/工具`，不再作引导模块。ISO 只带内核、控制台字模、桌面字体与壳。
- 系统里：系统内的生成器（现在用来造工具映像的那一套）改写可执行文件；「运行」遇到可执行文件就原生装载，遇到 `.wasm` 照旧交给执行器解释执行。

## 七、与中文编程的关系

格式是后端与装载器之间的约定，内容是机器码，以及地址、长度、权限这些数字，与源程序用什么语言写无关。按“各后端并列”，其他语言的程序经中文 Wasm IR 也能生成同样的文件。中文出现在两处：规范、生成器、装载器与查看工具的命名和文档；文件里给人看的文字（符号表的函数名、包名与版本、以后的能力清单），按 UTF-8 存。

要有自有格式，理由在操作系统一侧：装载约定由我们自己定，文件还要带能力清单、运行时元数据、回收用的栈映射这些豫言操作系统自己的信息。

## 八、兼容与迁移

- `yy裸机验证` 的验证镜像照旧用用户载荷方式，内核保留这条路；以后另行迁移。
- `.wasm` 程序在系统里照旧可以运行，由执行器解释执行。
- 浏览器、诺节、云工等后端不受影响，它们的目标是 `.wasm`。
- ARM64 先保留现有做法。
- 桌面字体模块与服务 34、35 不变。
- 系统内造盘：ISO 的内容会变，宿主与系统里造的仍须逐字节相同。

## 九、备选方案

1. **大段区挪到 3 GiB 以上，作单独模块由内核映射**：内核里针对具体程序的装载逻辑更多，与微内核边界相反。
2. **拼音数据改成数据盘上的文件**：要拆「中文处理」的「输入」「拼音」两个模块，网页版另留用内嵌数据的入口；拼音挪走后壳的前段仍剩约 3.2 MB，内核还得给开机程序映到 3.8 MiB。只能解决这一次溢出。
3. **整份壳.wasm 做成引导模块，服务 34、35 推广为按序号读引导模块**：`.wasm` 仍是运行形态。
4. **用 ELF**：可行，我们已有 ELF 写出。装载只用得到段表这一小部分，以后还要带豫言操作系统自己的信息；自定一种更简单，也合“全部是豫言自己的代码”。
5. **裸机用旧的小字库**：裸机的输入法与其他后端不一致。

## 十、未决问题

1. 格式与文件的名称、扩展名（或不要扩展名、只认魔数）、魔数的取法。
2. 用户态装载器放在执行器里，还是另作一个装载服务。
3. 每个文件各带一份执行器运行时，还是以后共享。
4. 第一个任务由内核读段表，还是内核只起一个最小装载器，再由它装载壳。
5. 用户段可用的地址范围与内核保留区（外置内核代码、内核任务窗口等）的划分。

## 十一、实施步骤

1. **格式、写出与查看工具**：定字节布局与规范；裸机后端写出可执行文件（第一版带模块字节段）；查看工具。
2. **开机程序**：内核按段表起第一个任务；去掉用户载荷里嵌入的壳与开机程序的写死映射。验收：最新 yybs 能造启动盘，壳与桌面在 QEMU（SeaBIOS 与 OVMF，光盘与 U 盘）上可用。这一步完成后大段区溢出即解决。
3. **子程序与工具**：内核加「按段建任务」；执行器在用户态装载；工具改为数据盘上的可执行文件；去掉映像表、工具映像模块与样本匹配。验收：系统里构建并运行你好、构建编译器本身。
4. **系统里生成与造盘**：系统里写可执行文件并原生运行；系统内造盘复验与宿主逐字节相同、能启动。
5. **去掉模块字节段**：转译器把立即数与类型信息放进生成时的侧表，类型表、全局与数据在生成时算好；文件里不再带 `.wasm` 字节，开机不再解析。

在第 2 步完成之前，造启动盘先用旧版本：867e8aac6 之前的能造；要桌面可用，用 9f33a4d8b 之前的。

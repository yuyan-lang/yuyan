## 拟定事项

- 议一：**只依赖机器与一个对象存储**。机器在哪都行：谷歌云、局域网、别家云；宿主上的林纳、林檎也可以，照 AGENTS.md「各宿主行为一致」。平台的一切持久状态都存进一个支持条件写的对象存储，节点本机只放缓存。
- 议二：**对象存储经接口隔开**。九府只经豫寓榫卯「对象存储」接口读写，第一套实现走 R2 的 S3 接口；以后有了自己的对象存储（内府），换一套实现即可，平台其余部分不动。
- 议三：**自组织**。节点开机后在对象存储的名册前缀下写自己的心跳（节点号、地址、能力、时刻），读别人的心跳认识全盟。领袖用条件写抢一份带期限的领袖租约，同一时刻只有一个领袖；领袖定期续约，过期了别的节点接手。对外的域名由领袖把健康节点写进解析记录。
- 议四：**领袖是唯一派活的**。持久对象分片、队列、定时事件、役（任务）由领袖分给各节点，派单写进对象存储；节点照派单干活。节点心跳过期，领袖就改派。
- 议五：**容错只求够用**。一台节点坏了，别的接上；已确认的写入都先进了对象存储，所以不丢；换手时有几十秒空档可以接受。不做多副本共识。
- 议六：**各接口的做法**：
  - 对象存储：直通后端；
  - 持久对象：片主串行执行，状态快照与提交日志存进对象存储；
  - 消息队列：消息按段存进对象存储；
  - 定时事件：由领袖触发；
  - 役：按派单执行；
  - 网页服务：每台都接请求，按派单转发。
- 议七：**节点之间**用 00051 的二进制帧（长度前缀，消息体是籍册即数据文件的二进制编码），走 TCP，由封缄（TLS 库）加密。入盟凭虎符（盟内共享密钥，与将作同法）。对象存储的凭据放在本机只读的 `。数据。豫` 配置里。
- 议八：**领袖选举、派单、换手做成确定性状态机**，在沙盘（模拟宿主）里推演：假对象存储、假网、假钟，随机注入崩溃、断网、延迟、条件写冲突，按种子复现。
- 议九：**单机先稳**。开机自启的服务有看护，崩了、卡死了就重起；收到关机信号走「息」（关机）；硬重启后文件系统靠日志重放恢复。这些在谷歌云测试台上长跑验证。
- 议十：分步上线，每一步都能单独用。

## 一、动机

1. 云仓 C00005 把动态站缓办了，原因是豫言系统之间的通信链路还不成熟。用户要先打地基，做一套通用服务平台，网页平台、构建、AI 市场等都跑在它上面。
2. 豫寓榫卯的平台服务接口是照 Cloudflare 定的（R2、持久对象、队列、定时触发），现在只有两种实现：一是云工，转给 Cloudflare 的绑定，要跑在 Workers 上；二是沙盘，状态放在内存里。我们自己的机器上还没有能落盘、能多机的实现。
3. 将作已经有一套小集群：盟、同僚、虎符、邻籍（局域网多播发现）、候簿。但它只为构建服务，不存状态，也只认得局域网。九府把成员、选主、派活做成通用的，状态放进对象存储，机器在哪都能入盟。
4. R2 本身持久、强一致，支持条件写，而且免出站流量费。把持久性交给它，节点就可以几乎无状态：一台没了，别的照派单接上。复杂的多副本共识因此省掉。

## 二、目标与范围

目标：

1. 任一台节点被收回、崩溃、硬重启或断网，几十秒内由别的节点接上，已确认的写入不丢。
2. 豫寓榫卯的对象存储、持久事务、持久独占、持久告警、持久频道、命名持久服务、消息队列、定时事件、网页服务，在九府上各有一套实现。云仓的应用（账户、包仓库、试写间、项目管理等）不改业务代码就能跑。
3. 加机器就加吞吐；机器来自哪家都行，混着用也行。
4. 运维动作都是壳命令（照 AGENTS.md「图形程序」一节）：「九府态」看全局，「入府」「出府」加减节点，「改派」挪分片；各有查询命令打印状态。

范围外，留待后续版本：

- 自己的对象存储（内府），用来代替 R2；
- 多副本共识，以及更强的可用性（毫秒级换手）；
- 拜占庭容错；
- 按用户计量与配额。

## 三、设计

### 3.1 总体

```
  对外：解析记录（领袖维护）或 Cloudflare 代理
                     │
   ┌─────────────────┼─────────────────┐
 节点甲（领袖）      节点乙              节点丙            …… 每台跑服务程序「九府」
 外府：收请求、按派单转发
 片主：执行分到本机的持久对象分片
 泉府、大府：消费分到本机的队列，执行领到的役
 本机缓存
   └─────────────────┼─────────────────┘
                     │
        对象存储（第一套实现是 R2）：名册、领袖租约、派单、各府数据
```

### 3.2 对象存储后端

九府需要后端提供：读写对象、列举前缀、条件写（只在对象的摘要等于给定值时写，或只在对象不存在时写）、删除。R2 的 S3 接口都有，而且读写、列举都是强一致的。

- 九府只经豫寓榫卯「对象存储」接口办事。第一步补上它的「R2 经 S3 接口」实现：HTTPS，签名用 SigV4（HMAC 沙二五六）。节点在任何宿主上都能用它，不必跑在 Workers 里。
- 键都放在一个桶的 `九府/` 前缀下，按用途分子前缀：名册、领袖、派单、对象、分片、队列、役。
- 写入量要省着用（R2 每月一百万次写免费）：心跳十五秒一次；持久对象的提交按批合并（见 3.5）。

### 3.3 名册与领袖（天府）

- **名册**：节点每十五秒写一次 `九府/名册/<节点号>`，内容有地址、可用区或机房、能力（核数、内存）、版本、时刻。超过四十五秒没更新，就算它掉线。节点号取本机公钥摘要的前八字节，钥存在 /系统/九府/。
- **领袖租约**：对象 `九府/领袖` 里记着领袖的节点号、任期号与到期时刻。
  - 抢：读出它与它的摘要；若已过期，就用条件写（摘要须相同）写进自己、任期加一。条件写成了才算当上领袖，于是同一时刻只有一个。
  - 续：领袖每十秒以同样的条件写续约，租期三十秒。
  - 丢：续约失败（别人已抢走或后端不通），就立即停止一切领袖的动作。
- **防旧领袖**：领袖写派单时带上任期号；节点只认任期号不小于它见过的最大值的派单。
- **对外解析**：领袖每分钟把健康节点的地址写进对外域名的解析记录（Cloudflare 的 DNS 接口），这也是唯一用到解析的地方。节点之间互相找，只靠名册。

### 3.4 派单（大府的核心）

- 领袖维护 `九府/派单`：持久对象分片 → 节点，队列 → 消费节点，定时表 → 领袖本身，役 → 执行节点。领袖按名册里的能力与负载分派，节点掉线就改派给别的节点。
- 节点每次心跳读一遍派单（带任期号），照着接手或交出。交出时先存盘再放手，接手时先从对象存储载入再开工。

### 3.5 持久对象（事务、独占、告警、频道、命名服务）

- **分片**：对象名散列到 1024 个分片，派单把每片分给一台节点作片主。发给对象的事件都转到片主，片主按对象串行执行，满足持久事务、持久独占的语义。
- **存**：片主本机用芥子（嵌入数据库）作缓存与工作库。每批事务（至多五十毫秒或一百条）的写集追加成一个日志段 `九府/分片/<号>/日志/<序号>`，写成后才回应用。每隔一阵（日志满一千段或十分钟）写一份快照，并删去快照之前的日志段。
- **换手**：新片主载入最新快照，按序重放快照之后的日志段，然后开工。旧片主若只是断了网，它的派单任期一过就停止执行；日志段序号用条件写（只在不存在时写）占位，两个片主不会写进同一个序号。
- **告警**：随状态存。换手后，新片主从日志恢复告警表。
- **频道**：只在片主内存里。规范本来就写明频道随实例而丢。

### 3.6 消息队列（泉府）与定时事件

- **队列**：每条队列分给一个消费节点。生产者把消息追加成段，条件写占位序号；消费节点按段领一批，确认后在对象存储里记确认位。过了领期没确认的重投，重投次数超限转进死信段。
- **定时事件**：时刻表存在对象存储，领袖每分钟算出该触发的项，作为役派出。

### 3.7 役（任务）

- 役是跑一个豫行程序（带参数、所需核数与内存、期限、重试次数），或调某个应用的一个入口。
- 役记录写进 `九府/役/<号>`。领袖派给有空的节点，节点定时续领期；节点掉线或过了领期就重派，保证至少执行一次，应用用幂等键去重。结果写回役记录。
- 将作的候簿（00053）以后可以作为一类役跑在九府上，另议。

### 3.8 外府（对外服务）

- 每台节点都跑网页服务前端：宾主（TCP 服务端）监听，封缄做 TLS 1.3。请求按派单交给本机的应用，或转给持有对象的节点。长响应（SSE、事件流）照样转发。
- 对外入口：领袖维护的解析记录，或 Cloudflare 代理。哪种都不绑在某一家云上。
- 应用部署：云仓各服务编成豫行，上传到对象存储。命令「布府」记下新版本，各节点在心跳里看到后滚动换上。

### 3.9 单机层面的前提

1. 开机自启的服务受看护：崩溃、退出、卡死（不回心跳）都重起；起不来就写进起居注（内核日志）。
2. 收到关机信号（ACPI，如谷歌云收回 Spot 实例）就走「息」：九府先交出分片、存盘，再关机。
3. 硬重启后文件系统靠日志重放恢复（环形日志加成组提交，#462）。本机只放缓存，坏了也能从对象存储重建。
4. 时钟：租约、领期一律按本机单调钟计，并留出余量；跨机器只比任期号与序号，不比墙钟。

这几条在谷歌云测试台上长跑验证。谷歌云只是“出机器的一家”，测试台用到的托管设施不进九府本身。

### 3.10 沙盘推演

- 名册、领袖租约、派单、换手、日志段占位这几段状态机，只经三个抽象接口办事：对象存储（读、条件写、列举）、网、钟。真实现走系统调用与 R2，推演实现在沙盘里。
- 推演器在一个进程里跑 N 台节点与一个假对象存储，按种子随机调度，注入：节点崩溃与重起、断网与分区、后端变慢或报错、条件写冲突、时钟快慢。
- 核对不变式：同一任期至多一个领袖；一个分片同一时刻至多一个片主在执行；已确认的写不丢；队列消息至少投一次。违反了就凭种子与事件序列复现。

### 3.12 与现有部件

- 复用这些现成部件：00051 的帧与籍册二进制编码，封缄，宾主，芥子，虎符，豫寓榫卯的接口与沙盘的模拟验收。
- 云工（Workers）那套实现照旧保留，九府是另一套实现，应用按部署选用。
- 将作暂不动（见 3.7 末条）。

## 四、实施步骤

1. **单机先稳**（3.9 节）：看护、关机信号、对时；在谷歌云测试台上长跑（硬重启、停机再开、断网、盘满），把查出的毛病修掉。
2. **对象存储的 R2 实现**：S3 接口、SigV4 签名、条件写、列举；在林纳、林檎、豫言系统上都能用。
3. **九府骨架**：服务程序、节点身份、名册心跳、领袖租约、派单读写、节点间二进制通信；壳命令「九府态」；沙盘推演。
4. **外府与「布府」**：网页服务前端、按派单转发、滚动部署；对外解析记录。
5. **持久对象分片**：日志段、快照、换手；持久事务、独占、告警、频道、命名服务的九府实现。
6. **泉府、定时事件与役**。
7. **云仓应用上九府**：接 C00005 的动态站，等用户恢复动态站时再做。

每一步合入前先过沙盘推演，再上真机：谷歌云两台 Spot 加局域网一台，混着跑。

## 五、验收

- **推演**：每段状态机跑一万个种子，没有违例。
- **真机长跑**：三台节点，至少来自两处（如谷歌云与局域网）；持续跑这几样负载：
  - 写读对象；
  - 跑持久对象计数器，每次加一，最后核总数；
  - 队列投收，核每条至少收到一次；
  - 定时役。

  每十分钟随机杀掉、重启或断网一台（领袖也在其内）。连跑二十四小时，要求已确认的数据零丢失，换手在一分钟内完成，服务可用率不低于 99%（外部探针每秒探一次）。

## 六、待定事项（附推荐）

1. 心跳与租期：推荐心跳十五秒、领袖租期三十秒、续约十秒。写入量每台每月约十七万次，三台在 R2 免费额度以内。
2. 对外入口：推荐先用 Cloudflare 代理指向各节点（免费）；领袖维护的解析记录同时写着，便于以后换别家解析服务。
3. 分片数：推荐 1024，以后可以再细分。
4. 自己的对象存储（内府）：推荐等九府跑稳、应用迁上来以后另立提案；接口已隔开，换实现不动别处。
5. 将作是否作为一类役跑在九府上：推荐等九府稳了以后另议。

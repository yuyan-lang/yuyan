## 一、拟定事项

- **议一：`鉴` 的每个分支都写 `或有 模式 则 体`，删去首支专用的 `有 模式 则 体`。**
- **议二：只换首支的关键词。** 首支操作符「模式匹配分支符」的关键词由 `有` 改为 `或有`，成为前缀 `或有〇则〇`；后续分支的中缀 `〇或有〇则〇`（提案 00022）照旧。语法树节点、规约关系表、类型检查、覆盖分析、代码生成与树码都不变，没有 ABI 与性能影响。
- **议三：分三步合入。** 编译器先两种都认 → CI 发布新原生工具链包后改钉 → 两仓迁移并删去 `有〇则〇`。云仓在第一步合入之后、第三步合入之前迁移。
- **议四：迁移只做词法替换。** 在名称、字符串、注释与 `《《…》》` 之外单独出现的 `有` 前插入 `或`，不整篇重排。

## 二、动机

1. **分支同形。** 现在首支写 `有`、其余写 `或有`：增删、调换分支时首支要单独改字，生成豫言代码的程序与测试也要区分首支。统一后每个分支写法相同，改一支只动那一行。
2. **规则更少。** 关键词 `有` 只有首支这一个用处。删去后 `鉴` 只剩 `鉴…而` 与 `或有…则` 两种组件；格式化器里为 `有`、`而有` 单写的十余处判断、语言服务找分支范围时的两种长度、《编译警告》里“指向 `有` 或 `或有`”的说法都可以合并。

## 三、设计

### 写法

```
「内建常量表示」者会「量」而
　鉴「量」而
　　或有「内建类型字符串」则『《《内建类型：字符串》》』
　　或有「内建类型整数」则『《《内建类型：整数》》』
　　或有「其他」则『……』
也。
```

《词法与语法》语一的语法改为：

```text
   | "鉴" 式 "而" 分支 { 分支 }
分支 = "或有" 式 "则" 式 ;
```

### 解析

- 前缀 `或有〇则〇` 与中缀 `〇或有〇则〇` 共用关键词 `或有`。`而` 之后没有左操作数，只能按前缀认；分支体之后按“同一处中缀关键词留最长”的规则认作中缀，`或有` 照旧按一个词认。
- 规约关系表不改：前缀 `或有〇则〇` 落在现有的“任意左 与 `〇或有〇则〇`：左规约”一条，前一分支体照旧先收束；内层 `鉴` 照旧收下其后的分支（第七节候选一）。
- 两个操作符得到的节点与现在相同：前缀得「模式匹配分支」，中缀把分支依次接成「模式匹配」，交给 `鉴〇而〇`。

### 格式化器与其他工具

- 格式化器（`库/源码排版`）：拆词时把 `而有` 作一片，使 `鉴…而` 的 `而` 留在行末、首支另起一行；改为把 `而或有` 作一片。其余判断已把 `或有` 当分支开头，删去 `有` 的那一半即可。
- 语言服务「寻找源码分支范围」与《编译警告》的分支关键字范围只认 `或有`。
- 抽象语法友好表示（调试输出）打印 `或有`。
- VS Code 语法与网页高亮按字着色，`或`、`有` 原本都是关键词字，照旧可用。

## 四、兼容与迁移

### 规模（2026-10-14）

| 仓 | 提交 | 首支 | 文件 |

| 语言仓 | yybs ab82e8594 | 19,895 处 | 2,893 个 |
| 云仓 | main 1b8aad9 | 1,441 处 | 233 个 |

另有：约二三十篇文档（双语成对）的示例；会生成或检验首支写法的字符串：`库/基础库/系统工具/文件类型/数据生成/入口。豫`、`库/源码排版/测试/排版。测试。豫`（8 处）、`库/编译器核心/测试/覆盖匹配范围。测试。豫`、`库/编译器核心/测试/编译警告。测试。豫`、`库/网页客户端/源码高亮测试数据。豫`，云仓首页示例与包管理服务阅读逻辑的测试；云仓 `应用/包管理服务/库/阅读处理/限定链接。豫` 的「限绑定词们」要加 `或有`，否则首支的模式变量收不进绑定名。

### 词法替换

- 名称、字符串、注释与 `《《…》》` 之外单独出现的 `有` 只作首支关键词：语言仓这样的 `有` 与 `鉴` 数目相等，只差四个拿裸字测报错的旧测试（`应用/豫言编译器/测试/语法/类型检查/类型检查其一。豫` 至 `其三`、`表达式构造/表达式构造无法解析其一。豫`），迁移时跳过。
- 所以迁移就是在这些 `有` 前插入 `或`，用不着语法分析。原型里逐字核对过，改动全是插入 `或`。
- 不整篇重排：仓里多数文件与当前格式化器的输出不一致（见第七节候选四），整篇重排会带来几十万行无关改动。只做替换时，语言仓只有 3 行超过 160 列（格式检查只发警告）。
- 迁移工具按 AGENTS.md 用豫言写，一次性使用，不入库。

### 自举与换钉

CI 自举的一级是 `main.yml` 钉住的原生工具链包里的豫构，由它用旧编译器编当前源码。工具链源码先用了前缀 `或有`、包还不认，自举就失败。所以先合入“两种都认”，等 CI 发布新包，改钉 `YY_NATIVE_TOOLCHAIN_URL`、`YY_NATIVE_TOOLCHAIN_SHA256` 并更新本机稳定工具，再迁移工具链源码。Wasm 工具链包（Windows 与抽样作业用）每轮由当前源码现编，照常可用。云仓发布每轮取 yybs 最新提交现编工具，第一步合入后即可迁移；第三步合入时云仓须已迁完。

### 并行会话

第三步合入后，其他分支里新写的 `有` 首支报“无法解析”，变基时改过的行也会冲突。各会话变基后在自己的改动上重跑同一替换即可。`LOCALAGENTS.md` 与本地模型指南同步改写。

### 原型验证（2026-10-14，原型已删）

- 基于 yybs ab82e8594，用钉点原生工具链 5c517a9c8（macOS arm64 包）。
- 解析器加前缀 `或有〇则〇`：新操作符「模式匹配首支符」（编号负一四四），登记进文言符集与控制操作符表，共 17 行；用稳定豫构编出一级原生豫构。
- 全仓词法迁移后跑 `豫构 目标 类型检查 -j 24`：原生二级 106 秒、原生三级 53 秒，二、三级逐字节相同，类型检查通过，共 168 秒。
- 用一级豫构从迁移后的源码编出格式化器，逐个解析 2,893 个迁移过的文件：13 个失败，全是迁移前就解析不了的旧式测试（见候选五）。云仓 507 个源文件迁移后全部能解析。
- 抽样 305 个文件，比较“先迁移后排版”与“先排版后迁移”：4 个不同。3 个是首支行宽了两列后正常折行；1 个是 `鉴…而` 一行超长时 `而` 落到下一行，即上文格式化器 `而或有` 一条要处理的情形。

## 五、备选方案

- **保留 `有` 作首支的另一写法**：两种写法长期并存，分支仍不同形，格式化器、语言服务、文档都要一直讲两种。不采用。
- **去掉 `鉴…而` 的 `而`**：分支都以 `或有` 开头后，`而` 只起分隔作用。去掉要把首支做成 `鉴〇或有〇则〇` 一个操作符，首支与后续又不同形，每处只省一字。不采用。

## 七、扩大范围的候选（待定）

第三步要改动每一个 `鉴`。若还要对 `鉴` 或分支写法作别的改动，并在同一次迁移里做，只需一次换钉、一次大改动、一次各会话变基。下面是这次检查中看到的候选。数据为 2026-10-14 语言仓 yybs，剥去名称、字符串、注释与空白后统计。

### 候选一：`鉴` 的结束标记（嵌套 `鉴` 吞分支）

- 现状：`鉴` 没有结束标记，分支体里的内层 `鉴` 收下其后全部 `或有`。内层不在最后一支时必须加括号或拆成函数；漏了就静默改变语义，运行时报“模式匹配错误，缺少分支”。`LOCALAGENTS.md` 专列一条。
- 数据：`鉴` 19,906 个，其中 5,139 个（26%）写在全角括号里，分支体以括起的 `鉴` 开头的（`则（鉴`）3,523 处；分支体直接以不带括号的 `鉴` 开头的（`则鉴`）1,358 处，这些须在最后一支才对。
- 做法甲（可选结束词）：`鉴` 可以带一个结束词（字待定），有结束词时内层到此收束，后面的 `或有` 归外层。旧写法照常可用，不必迁移；格式化器可以把括起的内层 `鉴` 改写成带结束词。
- 做法乙（必写结束词）：每个 `鉴` 都写结束词，全部括号可以去掉。迁移要知道每个 `鉴` 在哪里结束，须按语法树的源码范围改写，词法替换不够用。

### 候选二：模式里名称的认法

- 现状：模式里的名称只要能看到同名的顶层定义（函数、类型、类型别名、模块、命名空间等）或外层局部绑定，就按那个名称检查，成不了新变量，常报看不出原因的“不相等！”“不支持的模式匹配项”“命名空间不是一等值”，或运行时“缺少分支”；单独的「点」被读成小数；反过来，没导入的无参构造器被当成新变量，静默变成兜底。
- 数据：`LOCALAGENTS.md` 里这类条目约 19 条（第 5–13、135、139 行，速查表第 356、373、374、391、406、419、420 行，及第 461、481、490、504、516 行），是其中最大的一类坑；相关修补提交如 2d841c173、b2c8751a8、35a97d6c5。
- 做法：模式位置只把构造器（`立` 声明的与内建的）和字面量当匹配对象，其余名称一律新绑定；模式变量与某个构造器同名时发警告（含没导入的）。这是语义改动，要逐处核对有意引用顶层常量的现有模式。

### 候选三：`若` 链

- `否则若` 23,502 处，单独的 `若` 53,349 处。`若…则…否则若…则…否则…` 的首支与后续支也不同形，但 `否则若` 已是格式化器认的一个词，各支对齐成行，可保持现状。若要与 `鉴` 合流，可考虑分支守卫 `或有 模式 若 条件 则 体`，属新功能。

### 候选四：整仓按格式化器重排，CI 强制

- 现状：抽样 305 个文件（约 5%），按当前格式化器重排有 228 个会变，差异 29,632 行，推算整仓约 60 万行；格式检查只查行宽。所以本提案只能做词法替换。
- 做法：整仓重排一次，格式检查改为“重排后不变”才通过。此后的语法迁移都可以写进格式化器、靠重排完成。代价是一次很大的改动与各并行分支的冲突。

### 候选五：清理解析不了的旧式测试

- 13 个文件在迁移前就解析不了：`库/标准库/测试/字符串/模式其一。豫` 至 `模式其一零`、`库/标准库/测试/异常/错误其四。豫` 至 `错误其六`，用的是旧符集（如 `衔`）。可删去或改写，与本提案相互独立。

## 八、实施步骤

1. **编译器两种都认**：加前缀 `或有〇则〇`，与 `有〇则〇` 得到同样的节点；格式化器把 `而或有` 作一片；《词法与语法》注明两种写法。推送 yybs。等 CI 发布新原生工具链包，改钉 `main.yml` 两项，更新本机稳定工具。
2. **云仓迁移**：词法替换 233 个文件；改首页示例、阅读逻辑测试，「限绑定词们」加 `或有`。推送云仓 main。
3. **语言仓迁移并删去 `有`**：全仓词法替换（跳过四个裸字测试）；首支操作符只留 `或有`；格式化器、语言服务、抽象语法友好表示、编译警告的分支范围去掉 `有`；改生成或检验首支写法的字符串与测试；改文档（《词法与语法》《规约关系表》《编译警告》《语言规范》《豫言赋》、各包说明的示例、`LOCALAGENTS.md`、本地模型指南）与 VS Code 测试样例。已有提案与历史指南保持原文。冒烟：`豫构 目标 类型检查 -j 24`、格式化器测试。合入推送。

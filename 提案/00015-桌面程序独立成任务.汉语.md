## 一、拟定事项

- **议一：画面直接映射。** 子程序的显示面放在共享物理块里，复用内核服务 55「区段物块」与 56「映物块」，子任务与初始任务各映一份：子任务画，初始任务读。子程序提交画面时只给初始任务发一条“哪块区域变了”的短消息，像素不再经服务 41 拷贝，也不进消息。
- **议二：初始任务直接合成。** 外壳把每个外部程序格在屏幕上的矩形登记给执行器；初始任务收到变化区域，就从映射的显示面把这块直接写进帧缓冲（裁到格子以内），外壳界面不用重画。外壳自己的标签栏、边框与弹出层照常提交；弹出层盖住某一格时，那一格暂停直贴，弹出层关掉后整格重贴一次。
- **议三：桌面程序独立成任务。** 终端、文件浏览、任务管理器、设置各成一个可执行包，随启动盘带上。活动栏启动它们，每个程序是一个子任务，显示在外部程序格里。程序文件缺失或宿主不支持直贴（浏览器、诺节、原生）时，外壳照旧在自己里面开同一个格子程序。编辑、搜索、构建输出、差异与会话这些工作台格子留在外壳里，同 VS Code 的编辑器。
- **议四：外壳请求。** 接口「豫言操作系统子程序显示」升到 0.2.0，子程序可以请外壳办四件事：在编辑格里打开文件、新开外部程序格运行程序、重读桌面设置、结束外壳起的某个程序。文件浏览、终端与任务管理器经它与外壳配合。
- **议五：一个程序出错只影响它那一格。** 子任务陷阱、缺页或退出时，内核收回它的块，初始任务停止贴它的画面，外壳把那一格换成“程序已结束”（原因与退出码）和“重新运行”“关闭”两个按钮，其余格子与外壳照常运行。任务管理器里每个程序有自己的处理器与内存读数，可以结束。

## 二、动机

1. 用户 2026-10-11 在 AMD64 实机上看到：开了终端、文件浏览与任务管理器，任务管理器里没有它们，因为这些格子程序和桌面同在初始任务里。用户定：画面直接映射，程序分开，一个程序崩了不带崩整个图形界面。
2. Windows 与 macOS 都由系统组件合成窗口（DWM、WindowServer），程序把画面画在与合成器共享的内存里。资源管理器、访达、终端、任务管理器（活动监视器）都是普通进程，出错不影响合成。
3. 现在的子程序显示代办（00014 议四）每次取画面都经初始任务整块拷画布（1280×800 约 4 MB，00014 第九节），再让外壳重画像素图；外部程序的画面越大越慢。

## 三、目标与范围

做：

- 裸机，AMD64 先验收。内核与执行器是两种架构共用的底层豫言，ARM64 等 ARM 工作恢复后验收。
- 议一至议五。

留待后续：

- 工作台格子（编辑、搜索、构建输出等）拆成独立程序：需要一个程序开多个显示面。
- 原生 macOS 的共享内存代办（现走管道，功能相同）。原生上外壳仍在自己里面开这四个格子程序，共享内存代办做好再切。
- 几个程序共用同一份执行器与库的机器码（豫行只读段按内容共享，见《动态任务》后续事项）。
- 孙任务（程序再起的程序）取显示面：先经「请外壳办」由外壳新开格子。

## 四、设计

### 4.1 共享显示面（议一）

- 子任务的执行器取得转授的显示面时（代办开关见 00014 §4.6），在自己动态区顶端留出整块（2 MiB）放画布：宽×高×4 字节，向上取整到块。用服务 55 逐块取物理块号，随“已取得显示面”的代办消息交给初始任务。尺寸变了就另留一批块，再交一次。
- 初始任务用服务 56 把这些块映进自己动态区里预留的一段，每个子程序一段，按句柄记录，只读使用。
- 子程序提交画面时，执行器把变化区域的行从客体的画面字节串拷进共享块（本任务内拷贝），再发一条短消息（区域矩形）。初始任务贴完回确认，子程序收到确认才写下一帧，画面不会撕裂。
- 子任务结束时按服务 55、56 的规则归还块：初始任务先撤下自己的映射（数据块项写零），两边都不再映着时块才归还。

### 4.2 初始任务直接合成（议二）

- 新函数「设子程序画面位置」（句柄、屏幕矩形、可见）：外壳每次排版后对每个外部程序格调一次；格子被弹出层盖住、切到后台标签或缩成零时设为不可见。
- 初始任务在显示轮办里收到变化区域：可见时把区域与格子矩形取交，从映射块按行写进帧缓冲（同提交帧的区域写入，服务 32），随后补画鼠标光标；不可见时只记下脏区，重新可见时整格重贴。
- 外壳一侧：外部程序格在支持直贴的宿主上画成占位，不画像素图；其余宿主照旧取画面贴像素图。

### 4.3 程序拆分（议三）

- 新可执行包放在 `豫言操作系统/应用/`：终端、文件浏览、任务管理器、系统设置（包名实施时定）。每个包只有一个小入口：打开转授的显示面，用显示控件主循环跑原来的格子程序。格子程序的代码仍在 `库/平铺桌面`、`库/用户态桌面`、`库/工作台`，外壳与独立程序共用。
- 启动盘把它们编成豫行文件放进 `/程序/`（依赖 00007 续：编译器直出豫行）。
- 活动栏：找得到程序文件且宿主支持直贴时，启动程序、新开外部程序格；否则照旧开外壳里的格子程序。

### 4.4 外壳请求（议四）

接口「豫言操作系统子程序显示」0.2.0 加三个函数：子程序一侧的「请外壳办」，外壳一侧的「取外壳请求」与 4.2 的「设子程序画面位置」。

```
「外壳请求」立「元类型」也。
  「外壳打开文件」立化「字符串」而「外壳请求」也。
  「外壳运行程序」立化「字符串」而化（「列」于「字符串」）而「外壳请求」也。
  「外壳重读设置」立「外壳请求」也。
  「外壳结束程序」立化「整数」而「外壳请求」也。
```

- 裸机：子任务把请求编码后发给初始任务（同代办消息），执行器记进该子程序的待办请求；外壳每轮用「取外壳请求」（句柄）逐条取出办理。
- 原生 macOS 经事件管的反向通道传递；诺节、浏览器返回五十八（暂不支持）。

### 4.5 出错与结束（议五）

- 外壳每轮查子程序状态（现有子程序接口）。子程序结束（正常退出、陷阱、缺页、被结束）时，格子显示原因与退出码，下面是“重新运行”“关闭”两个按钮。
- 结束程序：任务管理器经「请外壳办」请外壳结束；外壳只结束自己起的程序及其子孙。

### 4.6 任务管理器

独立程序出现在系统任务里，处理器与内存读数来自内核服务 46。“桌面里的程序”一节（2026-10-11 加，16b952be1）只列外壳里的格子。

## 五、兼容与迁移

- 「豫言操作系统子程序显示」0.1.0 → 0.2.0：新增函数，旧函数行为不变；接口清单与各适配的 `宿主提供.json` 重生成。
- 没带这四个程序的旧启动盘、浏览器、诺节与原生照旧在外壳里开格子程序。

## 六、备选方案

| 方案 | 结论 |
| --- | --- |
| 内核替初始任务把子任务画面合成进帧缓冲 | 不取。裁剪、弹出层与光标的规则写在执行器的底层豫言里更好改，内核只管块与映射 |
| 子程序直接写帧缓冲里自己那一格 | 不取。子程序会写坏外壳的边框与弹出层，出错时也收不回来 |
| 另设一套内核共享内存服务 | 不取。服务 55、56 已能把同一批物理块映给两个任务，林兼容的内存文件在用 |
| 外壳整个拆成独立程序 | 留待后续。显示与块设备只许初始任务用（00014 第九节），先拆外壳里的程序 |

## 七、未决问题

1. 程序放 `/程序/` 还是 `/工具/`，默认 `/程序/`。
2. 双缓冲（子程序不等确认）值不值得：先用确认，量过再定。
3. 每个独立程序各带一份执行器与库，常驻内存多大：实施时量，超出预期再做只读段共享。

## 八、实施步骤

1. 内核：核实服务 55、56 对初始任务可用（槽 0 的动态区、映物块的目序范围），缺的补上；裸机验证。
2. 执行器：共享显示面（子任务留块、取物理块号、提交只发区域）；初始任务映射与直接合成（设子程序画面位置、脏区、光标补画）；子任务结束时撤映射。QEMU 探针：两个子程序并排画动画，量帧延迟与初始任务的处理器占用，与 0.1.0 对比。
3. 接口 0.2.0：「请外壳办」「取外壳请求」「设子程序画面位置」，裸机与 macOS 实现，诺节、浏览器返回五十八；接口清单重生成。
4. 外壳：外部程序格占位与登记位置、出错显示与重新运行、外壳请求的办理。
5. 拆程序：四个可执行包；活动栏改为启动程序，缺程序时退回外壳里的格子程序；文件浏览的打开与运行、设置的重读、任务管理器的结束都改经外壳请求。
6. 启动盘带上四个程序；QEMU 与实机验收：四个程序并排使用，结束或弄崩其中一个时其余照常，任务管理器显示各程序的处理器与内存。
7. 文档：子程序显示规范、客体二号说明、《动态任务》、平铺桌面与用户态桌面的包说明、提案 00014 的相关小节。

依赖：读盘缓存（2026-10-11 造盘时桌面卡死的修复；程序启动要从 U 盘读）；00007 续（启动盘由编译器直出豫行）。

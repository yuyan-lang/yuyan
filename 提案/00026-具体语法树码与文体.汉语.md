# 提案 00026：具体语法树码与文体

| 项 | 内容 |
| --- | --- |
| 编号 | 00026 |
| 状态 | 草案 |
| 提出 | 2026-10-14 |
| 范围 | 编译器前端：以具体语法树为规范层，存为 `。树码`（含注释与源码位置）；源码的文本写法抽成可替换的“文体”，解析与打印都由文体驱动；转写工具；格式化器改由树打印 |
| 相关 | 提案 00024（首支或有可作为一种文体的差别）、00025（文学性研究的结果以新文体落地）；语言技术规范《词法与语法》《规约关系表》 |

本文只写现代汉语（AGENTS.md）。

## 一、拟定事项

- **议一：规范层是具体语法树。** 源码先解析成具体语法树：保留全部写法信息，即构造（含语法糖）、名字、字面量、注释（方向与双语内容）、源码位置；不含任何关键词的拼写。它可以存为 `。树码`，树码文件头的“种类”标明是具体语法树。
- **议二：文体是数据。** 一种文体规定源码的全部文本写法：名字、字符串、注释、数字怎么写；每个构造由哪些组件组成、槽位什么次序；构造之间的规约关系；排版规则。现在的写法是第一种文体，称“今制”。
- **议三：解析与打印都由文体驱动。** 解析：现有的操作符表解析器读文体的构造表与规约关系，产出具体语法树。打印：按文体把具体语法树写回源码，自行补必要的括号、放回注释、排版。
- **议四：往返不变。** 对任一文体，“打印再解析”得到同一棵树（不计位置）。语法糖的展开（列字面、`且`/`或`、`附` 等）移到具体语法树之后，展开后的抽象语法树与今天的解析结果相同，此后各阶段不变。
- **议五：切换文体即整仓转写。** 新命令 `豫构 转写 --文体 名 路径…` 把源码改写成另一种文体。仓库同一时刻只用一种文体；换文体就是加入新文体、整仓转写一次，不再为每次语法改动单写迁移工具。
- **议六（后续）：** 编辑器与语言服务按读者所选文体显示与编辑。

## 二、动机

1. **语法可以低成本地换。** 00024 为改一个关键词，要写专门的迁移脚本、核对两万处；00025 的文学性研究若定出新写法，改动遍及每一行。有了文体，任何只涉及文本写法的改动都变成“写一份文体，转写一次”。
2. **文学性的方案可以并存与比较。** 研究给出的甲稿、乙稿各写成一种文体，同一份代码可以两种写法并排对照，定稿前就能整仓试读。
3. **格式统一。** 打印器按文体排版，取代现在逐字处理的格式化器，从此格式只由文体决定。

## 三、现状

可以直接利用的：

- **解析器由操作符表驱动。** `文言符集` 列出全部操作符，每个操作符是组件串（固定字与槽位）加一个构造函数；规约关系另有一张表（`文言优先级关系`）。文体的构造表就是把这张表数据化。
- **语法树已保留注释。** `带注释节点`（前置、后置注释）、`顶层注释节点`、`带注释编译单元`（含文件尾注释），由 `注释操作` 把词法注释挂到最近的节点上；格式化器、源码文档、文档站、接口检查都在用。
- **树码已能序列化这些节点。** 抽象语法树的树码编码、解码表已含注释节点；树码文件头有“种类”字段。
- **已有一种通用的树形写法。** 各中间阶段可把任一节点写成 `「《《节点名》》」【……】`，相当于一种只为机器读的文体。

缺口：

- **解析时就展开语法糖。** 操作符的构造函数直接产出展开后的节点：`「列」【甲，乙】` 成为 `缀`、`罄` 的调用，`且`/`或` 成为 `若`，`附` 成为拼接调用。打印器拿到的是展开后的树，写不回原来的写法。
- **节点没有源码位置。** 词法记号不带位置，语言服务另行回扫源码重建范围；`源码范围标注节点` 只在名称解析到类型检查之间存在。
- **规约关系按模式串查表。** 表里写的是 `〇于〇` 这样的串，换了组件就对不上；要改为按构造查。
- **格式化器逐字处理。** 它只用解析器确认能否解析，排版本身按字面片段进行，打印不经过树。

## 四、设计

### 具体语法树

- 节点按“构造”区分，与写法无关：如“模式匹配分支”“列字面”“短路且”“带标签实参”“局部名”。语法糖各有自己的构造，不在这一层展开。
- 叶子：名字（原样）、字符串（原样）、数（存数值，由文体决定拼法）、真假与单位值。
- 注释：沿用现有的前置、后置与顶层注释，双语注释存为汉语、文言两段。
- 位置：每个节点记源码范围（文件、起止行列），供诊断与语言服务；打印成另一文体后由打印器重新给出位置。
- 括号：源码里的括号不进树；打印器按文体的规约关系补上必需的括号。

### 文体

一份文体包含四部分：

1. **词法**：名字、字符串、注释、数的写法，标点。
2. **构造表**：每个构造的组件串（固定字与槽位，槽位次序可与今制不同，如“以「零」为「起」”与“于「起」为「零」”）。
3. **规约关系**：按构造查表，含后备规则。
4. **排版规则**：换行、缩进、对齐，即每种文体自己的格式化规则。

文体的约束：能写出全部构造；读法唯一（解析无歧义）；往返不变。

### 流程

```
源码（文体甲） ─解析─▶ 具体语法树（。树码） ─展开─▶ 抽象语法树 ─▶ 现有各阶段
                         │
                         └─打印─▶ 源码（文体乙）
```

### 文体如何标明

建议先只用“仓库统一”：仓库里的源码一律是当前文体（今制），编译器默认用它；换文体时整仓转写。需要混用时再定标明方式（文件头、后缀或包描述字段，见第六节）。

### 换钉

工具链源码也要转写，所以钉住的稳定编译器必须认得新文体：先把新文体加进编译器、等 CI 发布新工具链并改钉，再整仓转写（同 00024 第四节）。若文体描述做成编译器运行时读入的数据文件，稳定编译器读得懂新文体的描述就能编新写法，可免去这次换钉，前提是描述格式本身不变。

## 五、验收

- **展开等价**：全仓每个源文件，“解析成具体语法树再展开”与今天的解析结果逐文件相同（比较抽象语法树的树码）。
- **往返不变**：全仓每个源文件，“解析、按今制打印、再解析”得到同一棵具体语法树（不计位置）。
- **转写等价**：做第二种文体（先只换少量关键词，如首支 `或有`），整仓转写后编出的抽象语法树树码与转写前逐字节相同。

## 六、未决问题

1. 具体语法树是复用现有的 `表达式` 类型（加语法糖节点与位置标注），还是另立类型？
2. 文体怎样标明：仓库统一（建议先这样）、文件头、文件后缀，还是包描述字段？
3. 数的拼法：只存数值、由文体统一拼法，还是保留原拼法？
4. 冗余括号：一律去掉，还是记下来照原样打印？
5. 排版：完全由文体的排版规则决定，还是保留源码里的换行？前者改动一次全仓格式（现有文件与格式化器的输出差距很大），后者转写时排版更贴近原文。
6. 文体的表达力：操作符表能否表达叙事体的写法，如“以「甲」自乘，名之曰「甲方」”这种先算后命名、以“其”指上一结果的句式？
7. 文体描述放进编译器（换文体要换钉），还是做成运行时读入的数据文件？

## 七、实施步骤

1. **具体语法树与树码**：定义具体语法树节点（语法糖与位置），解析器产出它，展开另成一步；验收“展开等价”。
2. **今制数据化**：把文言符集、规约关系与词法规则合成“今制”文体；规约关系改按构造查表。
3. **打印器**：按今制从具体语法树打印源码；验收“往返不变”。之后可用它替换格式化器的排版内核（一次性重排全仓格式）。
4. **第二种文体与转写命令**：做一种只换少量关键词的文体与 `豫构 转写`；验收“转写等价”。00024 可就此落地。
5. **文学性文体**：00025 的研究定稿后，按方案写成新文体；必要时扩充构造表的表达力，再整仓转写。
